# 척추 요구 사항 (Spine Requirements) — v0.4 초안

이 문서는 **엔진 코어(척추)가 무엇을 만족해야 하는가**만 적는다. 근거, 옛 프로젝트 조사, 실험 결과, 진행 상태는 여기에 없다. 결정이 나온 구체 상황은 `use-cases.md`에 있고, 여기서는 사례 ID(`U1` …)로만 인용한다.

**상태 표기.** ✅ 확정(사용자가 명시적으로 선택) · 🟡 잠정(반론 없으나 합의 전) · ❓ 미정.

---

## 1. 명제와 판별 기준

- 핵심 명제: **모드 지원. 텍스트 에디터(VS Code)로 수정하기 쉬울 것.**
- 어떤 기능이 척추인지는 *"이게 없으면 모더가 C# 없이 할 수 없는 일이 생기는가?"*로 가른다.
- 코어는 특정 게임을 위해 만들지 않는다. 장르가 다른 여러 게임이 코어 수정 없이 모드로 구현될 수 있어야 한다. 최소한 다음 축을 모두 지원한다.
  - **시간:** 턴제(시간이 멈춘 채 질문에 답하는 구조), 실시간(시간이 흐르는 동안 입력과 기한 있는 질문이 섞임), 둘이 섞인 형태(일시정지가 있는 실시간 등).
  - **참가자:** 한 명, 여러 명, 사람과 AI가 섞인 경우, 동시에 입력하는 경우.
  - **정보:** 모두에게 공개되는 경우와 참가자마다 다르게 보이는 경우 (후자의 구체 형태는 미정, 9절).
  
  한 기본 요소가 이 축 중 하나에만 맞는 모양이면 커널에 둘 수 없다. 이름만 중립으로 바꾸는 것으로는 충분하지 않다.

## 2. 원칙

| # | 원칙 | 상태 |
|---|---|---|
| P1 | 구현 언어는 C#. 엔진을 모르는 **순수 .NET 코어**(UnityEngine/Godot 참조 없음), 호스트 엔진은 얇은 어댑터. 호스트 엔진 선택은 뒤로 미룬다. | ✅ (호스트 엔진 ❓) |
| P1a | 🟡 **호스트 경계는 언어 중립 모양.** 호스트 함수(S7)·확장(`ext.*`)·UI 구독(S10)이 커널과 주고받는 것은 닫힌 값 타입, 핸들(엔티티·접근기·리스트·맵), 일괄 칼럼 API뿐이다. 관리 객체 참조나 C# 전용 타입(델리게이트 캡처, `object`, LINQ 등)은 경계를 넘지 않는다. .NET 밖 호스트(C ABI)는 비목표지만 이 규칙으로 길을 남긴다. 코어는 `netstandard2.1` + C# 9(Unity가 소스 패키지로 컴파일할 수 있게). | 🟡 |
| P2 | **결정론을 구조로 강제.** 로직에서 `float`, 비시드 난수, 비결정 순회, 프로세스 의존 해시를 쓸 수 없다. 수치는 `int`(64비트, 오버플로=오류)와 `fixed`(십진 스케일 정확히 10⁶, 곱셈·나눗셈은 128비트 중간값, 반올림은 0에서 먼 쪽, `//`=floor, `%`=floor 부호, 소수 리터럴은 `fixed`, `float` 혼합과 0 나눗셈은 오류, 상한은 명시적 `clamp()`) 둘뿐이다. 저장 폭(32/64비트)은 스키마의 범위 선언이 정하는 구현 세부. 파이썬 `round()`(은행가 반올림)와 다름을 문서화. | ✅ |
| P3 | **전역 상태 금지.** 정적 서비스 로케이터 없이 컨텍스트를 명시적으로 넘긴다. | 🟡 |
| P4 | Unity ECS/Burst 의존 제외. 대규모 연산은 코어 안의 데이터 지향 서브시스템으로 푼다. | ✅ |
| P5 | **시뮬레이션과 표현 분리.** 코어에 UI/그래픽 타입이 없다. 뷰는 변경을 구독한다. | 🟡 |
| P6 | **규모 정책.** 목표는 소~중규모, 대규모는 비목표(탈출구: 독립 서브시스템). 상태 저장소는 인터페이스 뒤에 격리하고, 스크립트 경로는 로드 시점에 슬롯 핸들로 바인딩한다. 객체+ECS 혼합은 피한다. | 🟡 |

결정론의 수단: 정수 틱, 시드 기반 RNG(상태 저장 가능), 순서가 보장된 순회, 프로세스 무관 해시. 모드가 추가하는 C# 코드가 결정론을 깨는 것은 규칙으로 못 막으므로 틱별 상태 해시 비교 도구가 필요하다(S9).

## 3. 커널 편입 기준

커널에 들어가는 조건은 X3의 경계 규칙(결정성·저장·진단을 위해 엔진 지원이 꼭 필요하거나, 제한된 언어로 쓸 수 없는 것)과, 1절의 축에서 특정 한쪽을 전제하지 않는 것이다. 시험은 "서로 다른 장르의 게임 둘이 코어 수정 없이 이 기본 요소를 쓸 수 있는가"이다.

## 4. 척추

### S1. 콘텐츠 로딩 파이프라인 ✅
- **요구.** 텍스트 정의(S2의 단일 형식), ID 기반 참조, 상속(`parent`, `abstract`), 패치(남의 정의를 파일 수정 없이 변경), 모드 매니페스트(`id`, `dependencies`, `loadAfter`, `optional`, `extensions`).
- **6단계:** ① 모드 발견·정렬(사이클·누락은 오류) ② 스키마·정의 단계: 먼저 모든 모드의 **스키마 파일**만 모드 순서대로 실행해 타입을 완성하고(②a), 그다음 Def 파일을 실행해 Def를 *등록만* 한다(②b) ③ 패치 단계(단일; 기록된 `patch.*` 호출의 대상·경로·연산·값 모양·충돌 검사, 변경 이력 만들기) ④ 상속 펼치기와 패치 적용(Def마다 부모 → 자식: 부모의 최종 값 물려받기, `inherit` 식 평가, 그 Def의 패치를 로드 순서로 적용) ⑤ 링크(Def를 가리키는 id 문자열이 있는 Def인지 검사: 존재·타입·보이는 범위·`abstract` 금지, 값은 바꾸지 않음, 실패는 `파일:줄` + "혹시 …?") ⑥ 검증·동결(최종 값을 스키마와 대조, Def 동결, `.pyi` 스텁 생성).
- **⑥ 검증·동결·스텁**(spec-gaps G67~G72)
  - **필수 값:** 기본값이 없는 `const`(숫자·문자열·bool·`DefId`·함수 자리)는 구체 Def가 최종 값을 못 가지면 오류. 리스트·맵은 비어 있으면 빈 컬렉션, `abstract` Def는 면제, `field`는 해당 없음.
  - **타입·범위:** 최종 값의 타입이 스키마와 맞아야 한다(`int` → `fixed`만 암묵 허용). `min`/`max`는 양끝 포함이고 리스트 원소·맵 값에 각각 적용한다(맵 키 제외). 오류는 값을 처음 적은 모드의 것이다(물려받은 값은 부모 쪽, 패치가 쓴 값은 패치 모드).
  - **키 컴포넌트 줄:** `keys="all"` 컴포넌트의 `const` 멤버는 기본값이 있어야 하고(없으면 스키마 오류), 동결본은 적힌 줄만 저장하며 `TryGetRow`가 적히지 않은 줄(키 타입의 구체 Def)을 기본값으로 채워 돌려준다(G77). `extend`가 더한 `const`도 기본값이 있어야 한다(G74). 스키마 `default`도 같은 규칙으로 검사한다(G73).
  - **동결:** 검증을 통과한 `abstract`가 아닌 Def만 읽기 전용 `DefSet`으로 확정한다. 모든 `const`(컴포넌트 안의 것 포함)는 스키마 기본값까지 채우고(출처 `Default`), 런타임 칼럼 `field`는 적힌 값만 둔다. 값의 출처(직접/상속/패치/기본값)는 덤프(S9)용으로 남는다.
  - **`.pyi` 스텁(작성용):** 모드마다 그 모드가 보는 범위의 Def 타입·컴포넌트 클래스, `Literal` Def id(`abstract` 제외), `patch`, `mod_loaded`, `inherit`를 생성한다. 값 인자는 모두 선택(필수 여부는 엔진이 검사), `fixed`는 `int | float` 별칭이다. 로직용으로 엔진 이름(데코레이터, 사전 조건, 쓰는 내장, `ask`, `random`, `Ref`)과 엔티티 읽기 속성, Def 타입별 `query`·`spawn`을 더했다(spec-gaps G207). 스키마 파일용 스텁도 모드마다 그 모드가 보는 클래스를 담는다(G209). `pyrightconfig.json`은 "None일 수 있음"을 경고로 둔다(G208).
- ✅ **스키마 단계를 따로 둔다**(schema-design 4.1). 한 번에 실행하면 남의 타입 확장(`extend`)이 로드 순서보다 늦게 실행된 Def에만 반영되기 때문이다. 스키마 파일(예: 모드 폴더의 `schema/`)에는 스키마 선언과 스키마가 가리키는 순수 함수(`derived` 식 등)만 두고, Def 생성은 로드 오류. `.pyi`의 타입 부분은 ②a만 실행해 만들 수 있다(Def id 목록 `Literal[...]`은 ②b까지 필요).
- **패치.** 남의 정의를 바꾸는 방법은 기록되는 `patch.*` API뿐: `patch.set/add/append(Def id, "경로", 값)`, `patch.remove(Def id, "경로"[, 원소나 키])`. 로드 후 직접 대입 금지. 필드별 변경 이력(모드, 연산, 값, 호출 위치, 적용 여부)을 덤프(S9)에 표시. (결정: spec-gaps G34~G62)
  - **경로**는 이름을 점으로 잇고 맵 키는 `['키']`나 `[3]`으로 쓴다(`Health.base_max`, `cost.Wood`, `cost['core.Wood']`, `Skill.Medicine.level`). 정규형으로 비교하므로 `cost.Wood`와 `cost['Wood']`는 같고, 한 경로가 다른 경로의 앞부분이면 "같은 필드"로 겹친다(G47·G50). 대상 Def나 경로가 없으면 오류(“혹시 …?” 안내).
  - **로드 순서는 항상 하나로 정해진다.** ①의 정렬에서 의존 관계(`dependencies`/`loadAfter`)가 없는 모드끼리는 모드 id 순. **모든 연산은 이 로드 순서(같은 모드 안에서는 호출 순서)대로 하나씩 적용한다**(G41). 연산 종류별 단계는 없다.
  - **충돌:** 순서가 선언되지 않은 두 모드의 겹치는 패치는, 결과가 순서에 달리면 둘 다 오류(`loadAfter` 안내): `set`끼리·`set`과 `add`/`append`/`remove`·`remove`끼리. 같은 경로의 `add`끼리, `append`끼리는 순서와 무관하니 충돌이 아니다. 순서가 선언된 모드끼리는 나중이 이기고, 뒤 모드의 `set`이 앞 모드의 `set`/`add`/`append`를 덮을 때만 경고한다. 같은 모드가 같은 필드를 두 번 `set`하면 경고(G37·G41).
  - **연산:** `int`/`fixed`는 `set`·`add`(정확한 덧셈, `add`의 기준값은 상속과 `default`까지 합친 현재 값, G53). 리스트·맵은 `set`·`append`(같은 종류의 컬렉션, 맵은 이미 있는 키가 오류)·`remove`(지울 원소·키를 세 번째 인자로, 없으면 오류). 맵의 키 하나는 경로 `set`(없는 키는 새로 만듦, G54). 컴포넌트는 `set` + 컴포넌트 값으로 붙이고(이미 있으면 오류) `remove` 두 인자로 뗀다(없으면 오류). 타입에 붙은 컴포넌트는 떼지 못하고 값만 패치한다(G36·G44·G51).
  - **실패한 패치:** 호출 줄에 오류를 내고 건너뛰며 같은 Def의 나머지 패치는 계속 적용한다(G60). 패치 값 안에 `inherit`는 쓸 수 없다(G62).
  - **선택 의존(`optional`) 모드:** 설치되었을 때만 적용할 패치는 `if mod_loaded("m"):` 가드 안에 `patch.*`만 둔다. 가드 안에서만 그 모드의 Def와 이름을 쓸 수 있고, 건너뛴 패치는 정보로 알린다(G38·G46).
  - 비율 변경(`mul`)은 v1에 없다. 게임 중 % 보정은 기여 행과 `derived`(S4)가 맡는다. 필요해지면 `set` → `add` → `mul` 단계로 추가를 검토.
- **`inherit.필드`:** 자식 필드 식에서 부모의 해석된 값을 읽는 특수 이름(`tags = inherit.tags + ["fast"]`). `inherit`가 든 식은 4단계에서 부모 먼저 순서로 평가. 다른 Def의 값을 읽는 것은 정의 단계에서 금지, 단계 함수에서 `defs["Name"].field`.
  - `inherit.move`, `inherit.Health.base_max`는 부모의 최종 값(패치까지 반영)을 읽고, 부모에 값이 없으면 스키마 `default`를, 둘 다 없으면 오류(G56·G58). 식에서 쓸 수 있는 것은 리터럴, 리스트·맵 리터럴, `int`/`fixed`의 `+ - *`과 단항 `-`, 리스트·문자열의 `+`, 같은 파일의 이름, 컴포넌트 값 생성자(`Health(...)`)다. 그 밖의 연산은 로드 시점에 아직 지원하지 않는다(`EVL002`).
  - Def 하나는 (1) 부모의 최종 값 확정 (2) 자식이 적은 값과 `inherit` 식 평가 (3) 그 Def의 패치 적용 순서로 처리한다(G55). `merge="append"` 필드에 `inherit` 식을 쓰면 그 결과가 전체 값이고 부모를 다시 붙이지 않는다(G59).
  - `parent` 오류(없음, 보이지 않음, Def 타입이 다름, 순환)는 자식 Def를 쓴 모드의 오류이고 자식은 연쇄 오류 없이 건너뛴다. `abstract` Def도 부모 역할을 하며 엔티티를 만들 수 없다는 표시만 단다(G57).
- **매니페스트는 `mod.py`**: `Mod(id=..., dependencies=[...], loadAfter=[...], optional=[...], extensions=[...])` 호출의 인자만 리터럴이어야 하며 엔진은 이 호출을 **파일 실행 없이 AST로** 읽는다. 조건부 의존성은 없음. 파일 실행 순서는 `use("a.py")` 목록으로 명시, 편의로 `use_all("dir/")`는 정렬된 순서. `extensions`는 그 모드가 쓰는 커널 확장(`ext.*`, X3) 목록이며, 게임에 없는 확장이면 Def 줄마다가 아니라 모드 단위 오류 하나로 알린다.
- ✅ **보이는 범위 = 필수 의존의 닫힘**(schema-design 4.3). 모드는 자기와 `dependencies`(전이적)로 닿는 모드의 타입·필드·컴포넌트·Def만 이름으로 쓸 수 있다. 그 밖을 쓰면 로드 오류 + "의존을 선언하세요". `.pyi`는 모드마다 그 범위로 생성한다. `optional` 대상의 Def와 이름은 `if mod_loaded("m"):` 가드 안의 `patch.*`에서만 쓸 수 있다(위 "선택 의존" 항목, G38).
- **리스트 병합은 필드별로 스키마에서 선언**(기본 `merge="replace"`, 필요한 필드만 `"append"`). 컴포넌트 목록은 이름을 키로 하는 맵이라 키 단위 병합이고, 컴포넌트 안의 값은 값 단위로 합친다(자식이 적은 값만 덮어쓰고 안 적은 값은 물려받음, 키 컴포넌트는 줄 키 단위 → 같은 줄은 값 단위, G58).
- **중복 Def ID는 오류.** 의도적 교체는 `Unit("Scout", override=True, ...)`로 명시.
- **에셋**(텍스처/사운드/UI/맵)은 가상 경로 덮어쓰기: 같은 경로면 나중 모드가 대체.
- **오류 정책:** 오류를 모아 `파일:줄`과 함께 한 번에 보고하고, 실패한 모드는 부분 로드하지 않고 통째로 비활성화(또는 시작 거부). 패치 단계(③) 이후에 모드가 비활성화되면 그 모드와 필수로 의존하는 모드를 빼고 ②a부터 다시 실행한다(`extend`와 `mod_loaded` 가드가 낡은 채 남지 않게, G49). 모드가 자기 오류와 다른 모드와의 충돌 오류를 함께 가지면 자기 오류가 있는 모드를 먼저 빼고 충돌은 그 뒤에 다시 판정한다(G28).

### S2. 선언적 로직 언어 ✅(형식) / 세부 문법은 실험으로
- **콘텐츠 형식은 하나: 제한된 유효 파이썬 부분집합(Starlark 계열).** 이 "하나"는 Def와 로직에 적용된다. 에셋, 번역 파일, UI 정의의 형식은 별도로 정한다(X4, S10). 파일이 항상 유효한 파이썬이어야 해서 VS Code가 구문 강조·들여쓰기·린트를 제공한다. 자동완성은 엔진이 생성하는 `.pyi` 스텁(검증 필요).
- 데이터 정의는 키워드 인자 호출: `Unit("Scout", move=3, ...)`. 로직은 `@command def ...`, `require(...)`, 문장 수준 `ask(...)`/`match`.
- **허용:** 대입·복합 대입, `if/elif/else`(로드 시점에는 `mod_loaded("m")`를 조건으로 한 가드와 그 안의 `patch.*`만, 스키마 파일에서는 불가, G46), `for`(유한 컬렉션), `match/case`(가드 포함), 컴프리헨션, 제한된 람다, 함수 정의(재귀 금지), 매개변수 타입 어노테이션. **금지:** `import`(→ `use`), `class`, `try/except`, `global`, 제너레이터, `eval/exec`, 스키마에 없는 속성 대입. `while`은 파이썬 그대로 허용하고 따로 `limit`은 없다: 상한은 단계 예산(구간마다 새로 셈, 넘으면 오류)이 맡는다(spec-gaps G195). 로드 시점 단계 예산과 실행 단계 상한 가드. 로드 후 정의는 동결. 커맨드 본문 안의 필드 대입은 그 커맨드가 기록하는 쓰기로 허용, 커맨드 밖 직접 대입은 금지.
- **`ask`는 값을 돌려주는 문장**: `pick = ask(party, "Title_Key", ["a", "b"])`(질문받는 쪽은 엔티티, X1·G125). 중단점(`ask`/`await`/`wait`)은 **문장 수준에서만** 가능하고 식 중간에는 쓸 수 없다. 분기는 `if`/`match`, 지역 변수는 그대로 이어진다.
- **Def 참조는 문자열 + `.pyi` 스텁**(`Literal["Scout", ...]`로 오타 표시와 자동완성). pyright로 확인함(schema-design 3.1).
- ✅ **스키마 선언은 함수 호출**(schema-design 3, 클래스 선언 방식과 pyright로 비교): `component(...)`, `deftype(...)`, `extend(...)`, 값 종류 `const(타입)`/`derived(타입, 함수)`/`field(타입)`, 엔티티 Ref 칼럼 `ref("X", inverse=, optional=, order_by=)`. 타입은 파이썬 표기 그대로(`int`, `fixed`, `list[str]`, `dict[DefId["X"], fixed]`), 스키마 안의 다른 타입 이름은 문자열. 참조 타입은 `Ref["X"]`(엔티티)와 `DefId["X"]`(Def id) 둘이며 자리와 무관하게 뜻이 같다(spec-gaps G32). 생성 스텁은 Def 타입마다 클래스 하나(타입이자 생성자), `const`·`derived`는 읽기 전용 프로퍼티. 스텁은 `type` 문을 쓰므로 `pythonVersion` 3.12 이상.
- **텍스트 키 타입.** 화면에 나가는 곳(`log`, `label`, 툴팁)은 `str`이 아니라 **텍스트 키 타입**만 받는다: `log("msg.lost_units", name=..., n=...)`. 키는 로컬라이제이션 파일에서 스텁으로 생성되어 오타와 `log("그냥 문자열")`을 표시한다. f-string·문자열 연산은 ID 조합 등에 어디서나 허용.
- **커맨드 머리부는 명시적 `with preconditions:` 영역.** 영역 안에는 `require`/`cost`/`choose`만 허용(부작용 문장은 로드 오류), 커맨드당 최대 하나. 엔진은 이 영역만 본문 실행 없이 따로 평가해 UI 비활성 사유와 AI 합법 수 나열에 쓴다.
  ```python
  @command(free=True, acts_for=lambda party: party)  # 람다는 커맨드 매개변수를 이름으로 골라 받는다 (G130)
  def Move(party: Ref[Party], unit: Ref[Unit], dest: Ref[City]):
      with preconditions:
          choose(unit, where=lambda u: u.owner == party)
          choose(dest, from_=neighbors(unit.Location.city))
          cost(party.Treasury.points, 1)  # 첫 자리는 칸 자체: 확인하고 본문 시작 때 뺀다 (G185·G186)
          require(unit.Moves > 0, "msg.no_moves")
      ...
  ```
  ✅ **`me`는 없다**(spec-gaps G119~G127). 이전 엔진의 `^Self` 하나가 맡던 역할을 나눴다: 커맨드를 보낸 연결은 issuer(S6, 스크립트에서는 입구 정책 함수만 읽음) · 행동하는 진영과 비용 지불자는 인자나 인자에서 끌어낸 값(`party`, `unit.owner`; 어느 쪽인지는 모더가 정함, G120) · 질문받는 쪽은 엔티티(X1, G125) · 소유 검사("자기 유닛만", U1)는 전제 조건. 커맨드의 결과는 인자와 상태만으로 정해진다. UI의 "나"는 클라이언트가 보고 있는 엔티티로 시뮬레이션 상태가 아니다(S10, G127).

  본문 중간의 동적 비용은 bool을 돌려주는 `pay(...)` 문장(사전 검사에는 쓰이지 않음). ✅ `ok = pay(party.Treasury.op, 2)`: 첫 자리는 `cost`처럼 칸 자체, 있으면 빼고 `True`, 모자라면 그대로 두고 `False`. 쓰기라 한 줄 전체나 이름 대입의 오른쪽에만 온다(`if pay(...)`는 로드 오류). 취소 때 돌려주기는 게임 상태로 한다(G187).
- **함수는 한 종류, 효과는 엔진이 자동 판정.** 정적 분석으로 분류하고 잘못된 곳에서 호출하면 이유와 `파일:줄`로 로드 오류.

  | 함수가 하는 일 | 호출 가능한 곳 |
  |---|---|
  | 순수(읽기만) | 로드 시점·런타임 모두 |
  | Def 생성 | 로드 시점만 |
  | 엔티티 쓰기 | 런타임 Flow 본문(커맨드·반응)의 문장 수준만 |
  | `ask`/`await`/`wait` 포함 | 런타임 Flow 본문(커맨드·반응)의 문장 수준만 |
  | 난수(`random.*`) 포함 | 런타임 Flow 본문(커맨드·반응)과 그 본문이 부른 함수, 식 안도 가능 (G178) |

  ✅ "문장 수준"은 한 줄 전체의 호출이나 이름 대입의 오른쪽 전체(`u = make_scout(c)`)다. 조건·인자·리스트 안·`x += f()`는 식 안이라 로드 오류(spec-gaps G117·G135). 쓰는 내장(`spawn` 등, S4)을 부르는 함수도 엔티티 쓰기 함수다.

- ✅ **함수는 Def 값이 될 수 있다**(schema-design 3.3.3). Def가 규칙을 가질 때(성공 조건, 성공 효과) 함수를 Def 필드에 넣는다. 스키마는 자리의 종류를 선언한다: 확인용(`Cond`·`Fn`, 위 표의 "순수"만) / 바꾸는 함수(`Action`, Flow 본문으로 실행). 함수 자체는 여전히 한 종류이고, 자동 판정된 효과가 자리와 맞지 않으면 로드 오류. 다른 모드가 덧붙이는 확장 지점은 `list[Action]` + `merge="append"`. 언제 부를지는 그 Def 타입을 선언한 모드가 정한다. 함수 값은 Def(`const`)에만 둔다. 타입 이름은 ❓(`.pyi` 구현 때).

- **평가 모델:** 명시적 프레임 스택, 단일 스레드, "막힐 때까지 실행". 식은 재귀 평가이며 중단 불가. 저장 = 프레임 전체 + RNG 상태.
- ✅ **난수: 카운터 기반, Flow마다 난수열 하나.**
  - 값 = `H(월드 시드, 난수열 키, n)`. H는 ChaCha20(RFC 8439, 20라운드)이고 키 = SHA-256(시드, 실행 횟수, 정의 id), nonce = n, 블록 카운터 = 한 호출 안의 블록 번호다. RFC 테스트 값과 엔진 출력의 골든 값 테스트로 고정한다(C6, spec-gaps G181).
  - 월드 시드는 호스트가 월드를 만들 때 준다(주지 않으면 0). 저장에 남고 스크립트는 읽거나 바꿀 수 없다(G180).
  - 난수열 키는 Flow의 출처로 정한다: 커맨드(자유·응답)가 만든 Flow는 (커맨드 정의 id, 그 커맨드의 실행 횟수), 핸들러·`when` 반응이 만든 Flow는 (그 정의 id, 발동 횟수). 횟수는 사전 조건을 통과해 본문이 시작될 때 1 늘고 본문이 난수를 쓰는지와 무관하다. 횟수 카운터는 시뮬레이션 상태다. Flow id는 키로 쓰지 않는다(다른 모드의 Flow 생성에 밀리지 않도록, G182).
  - 스크립트는 `import` 없이 `random` 이름 공간을 쓴다. 파이썬과 이름·뜻이 같은 것만 있다: `randint`, `randrange`, `choice`, `choices`(가중치는 정수), `sample`, `random()`(파이썬과 달리 `fixed`). `shuffle`·`seed`는 없다(섞기는 `sample(seq, len(seq))`). `chance` 같은 편의는 표준 모드가 준다(G179).
  - 난수 함수를 부를 때마다 그 Flow의 n이 1 증가하고(한 호출에서 여러 번 뽑아도 1), `ask`·`wait`로 멈췄다 재개해도 같은 난수열을 잇는다. Flow의 RNG 상태 = (키, n).
  - 부를 수 있는 곳은 Flow 본문(커맨드·핸들러·반응)과 그 본문이 부른 함수이고 식 안에서도 된다. `random`을 쓰는 함수는 전이적으로 난수 함수가 되어 순수 자리(`derived`, 조건, 사전 조건, 입구, `Cond`)에서 로드 오류이고, 이름으로 알 수 없는 길은 실행 중 안전망이 막는다(G178).
  - 카운터가 상태 안에 있으므로 롤백되면 함께 돌아가고, 실패한 입력은 난수를 소비하지 않는다(C10).
  - 알려진 성질: 실시간에서 같은 커맨드를 두 참가자가 내면 먼저 들어온 쪽이 앞 번호를 받는다(결정적이지만 순서 의존). 키에 issuer를 넣지 않는 것은 의도.
- **값 타입:** `int`, `fixed`, `bool`, `str`, 텍스트 키, Ref, 리스트, **맵(딕셔너리)**, **외부 값**, **함수**(Def 값만, 위)의 닫힌 집합. 변환은 명시적이고 실패는 로드 시 오류.
- 🟡 **외부 값:** `ext.*`가 등록한 칼럼 타입(X3)의 값. 스크립트에는 이름 있는 불투명 값으로 보이고(`.pyi`에도 그 이름의 타입), 다루는 방법은 그 확장이 등록한 호스트 함수뿐이다(`spatial.distance(a, b)`). `==`/`!=`만 허용되고(확장이 제공한 동등 비교), 그 외 연산자·필드 접근·다른 타입으로의 암묵 변환은 없다.
  - ✅ 표기(schema-design 3.3.4): 타입은 확장 이름을 붙여 `field(spatial.Point)`. Def 리터럴은 확장이 등록한 "로드 중에 불러도 되는 순수 생성 함수"로(`spatial.point(3, 4)`). 기본값은 확장이 주거나 필드에 `default=`/`optional=True`가 있어야 하며, 둘 다 없으면 로드 오류. 키 컴포넌트의 키로는 쓸 수 없다.
- **리스트·맵이 놓일 수 있는 곳:**

  | 위치 | 리스트 | 맵 | 상태 |
  |---|---|---|---|
  | Def 필드(리터럴) | 허용 | 허용 | ✅ |
  | 지역 변수 · Flow 프레임 · 커맨드 매개변수 · Request `options` | 허용 | 허용 | 🟡 (저장되므로 정규형 대상) |
  | 엔티티 칼럼 | 불가(`tags`만 내장 sugar) → 원소 엔티티 + `inverse` | 불가 → 키 컴포넌트 | ✅ (S4) |
  | 키 컴포넌트 줄의 칼럼 | 불가 | 불가 | ✅ (G129. 스택 노드의 인자 묶음은 런타임 컴포넌트, 이름 없는 값 목록은 `int` 키 컴포넌트 + `replace_rows`/`append_row`) |

- ✅ **순수 함수의 실행 규칙**(spec-gaps G95~G108). 실행되는 코드는 파이썬과 같은 결과를 내고, 파이썬과 다르게 될 쪽은 오류로 막는다(부분집합).
  - 참/거짓, `and`·`or`, 지역 변수 규칙(함수 안 어디서든 대입하면 지역, 대입 전에 읽으면 오류)은 파이썬과 같다(G104).
  - **순수 함수 안의 값은 불변이다.** 그 자리에서 고치는 연산(항목·속성 대입, 리스트 `+=` 등)은 모두 오류다(G104).
  - 키 컴포넌트의 줄 묶음(`h.Skill`)은 `dict`처럼 `len`·`in`·비면 거짓이고, 부착 여부는 `is not None`이다(G104).
  - 함수 본문의 이름 오타는 `check`가 로드 시점에 잡는다(G108).
  - 실행 단계 상한은 최상위 읽기 하나에 예산 하나이고, 그 안의 중첩 `derived`가 나눠 쓴다(G101).
- 구현: 이 부분집합을 읽는 **파서를 직접 만든다**(중단 가능한 실행과 `파일:줄` 오류에 AST 직접 제어가 필요).
- **열린 점:** 식의 반응성 의존 수집과 자동 설명의 구체형 · 목록 연산 중 순환 다음 원소(길이·행 개수·합은 G97·G104로 정함). ✅ 컴프리헨션과 제너레이터 식: 리스트·딕트 컴프리헨션, 제너레이터 식은 호출 인자로만(값으로 존재하지 않음, `any`·`all`은 일찍 멈춤). 금지된 "제너레이터"는 `yield` 함수와 제너레이터 객체를 값으로 들고 다니는 것으로 읽는다(G189).

### S3. 데이터 경로 해석 🟡
- 문자열 경로로 상태 읽기(`unit.Location.city`). 조건·스탯·UI·로그가 전부 이걸로 참조한다. **로드 시점에 스키마로 검증**한다(존재하지 않는 경로에 `파일:줄` + "혹시 …?"). 반응형 구독은 척추 밖(뷰/트리거 모듈).
- `a.b.c`의 각 세그먼트는 컴포넌트 / 필드 / Ref 필드 / 키 컴포넌트의 키(`Stats.Security`, `Stats[s]`) / 관계 컬렉션 중 하나. 로드 시 스키마에 대해 컴파일해 접근자 체인으로 만든다. 컴포넌트 이름은 명시적으로 쓴다.
- ✅ **optional Ref:** 선언 시 optional인 Ref만 `None`을 낼 수 있고, 그 외 비어 있으면 오류. 죽은 엔티티를 가리키는 오래된 Ref는 세대(generation) 카운터로 감지.
- 🟡 쓰기: path는 기본적으로 읽기용. 쓰기는 커맨드/`patch.*` 같은 기록되는 경로로만.
- ✅ **관계와 역방향:** 정방향 Ref만 저장하고 역방향은 스키마가 파생한다(`city = ref("City", inverse="units")` → `city.units`). 계층과 다대다도 같은 방식, 엔진이 인덱스를 유지. 역방향 컬렉션의 순서는 엔티티 id 순이고, `ref("Pile", inverse="cards", order_by="pos")`면 원소의 그 칼럼 순(동률은 엔티티 id). 섞기·"맨 앞에 넣기" 같은 규칙은 그 칼럼을 쓰는 표준 모드 함수(schema-design 3.3.2).
- ✅ **쿼리 = 파이썬 컴프리헨션**, 로드 시 컬럼 루프로 컴파일. 전역 순회는 **명시적 호출** `query(...)`만 허용(G190·G192): 출처는 Def 타입 하나 그리고/또는 컴포넌트들(`query("Unit", "Wounded")`)이고 값 조건은 컴프리헨션. 어디서나 쓸 수 있고 읽으면 그 목록을 읽은 것으로 기록해 `when`이 엔티티 생성·삭제와 컴포넌트 부착·분리를 안다(G193). 결과는 리스트가 아니라 엔티티 묶음이다(G194: 인덱스 없음, 사본은 컴프리헨션). 순서는 엔티티 id 순, 재귀 없음.
- ✅ **Def 상속은 로드 시 완전히 펼친다.** 런타임 읽기는 Entity 오버라이드 → 최종 Def 두 단계뿐. 병합 규칙: 스칼라 덮어쓰기, 키 맵은 키 단위 병합, 리스트는 기본 교체. `patch.*`는 펼치기 전에 적용되어 부모 패치가 자식에 반영된다.

### S4. 구성 모델 ✅
- ✅ **ECS형 데이터 모델.** 공개 API는 "엔티티 ID + 컴포넌트 스키마 + 쿼리"까지만 약속하고 내부 저장 방식은 약속하지 않는다. 엔티티 = ID(+세대). 컴포넌트 = **스키마로 정의된 컬럼**(모드가 정의, C# struct 아님). 구조 변경(생성/삭제/부착)은 즉시 보이고, 순회는 시작 시점의 목록을 돌며 그사이 죽은 것은 건너뛴다(spec-gaps G88). 스크립트에서 이 규칙은 엔진이 준 묶음(역방향 컬렉션, `query()`, 키 줄)에 적용되고 그 묶음의 `len`·`in`은 살아 있는 것만 본다. 컴프리헨션으로 만든 사본은 파이썬 리스트다(G194, 파이썬 `weakref.WeakSet`과 같은 구분). 순회 순서는 엔티티 id로 고정하고, id는 재사용하지 않아 생성 순과 같다(G87). 스크립트가 임의 객체 그래프를 들고 다니지 않고 Ref와 쿼리로만 간다.
- ✅ **Def와 Entity 분리(Flyweight).** Def는 로드 후 동결되는 공유 정의. Entity는 `def` 참조 + 자기가 바꾼 값만 저장하고 읽을 때 없으면 Def 기본값. Def 패치가 기존 Entity에 반영되는 것은 의도.
- ✅ **값은 세 종류**(schema-design 2.6, B′): `const`(불변 설정, Def에서 읽음) · `derived`(계산 값, 쓰기 불가, 저장 안 함) · `field`(칼럼, 커맨드가 쓰고 저장됨). `const`는 Def 타입 바로 아래나 컴포넌트 안, `derived`·`field`는 컴포넌트 안. 고르는 순서: 커맨드가 직접 써야 하면 `field` → 다른 값으로 계산되면 `derived` → 그 밖은 `const`. `const`·`derived` 대입은 로드 오류. 읽기 순서: 엔티티 값 → Def 값 → 스키마 기본값. 스키마 기본값은 ⑥ 동결 때 Def에 채워지므로 Def가 가진 컴포넌트는 런타임에 두 단계(S3)이고, Def에 없던 런타임 부착 컴포넌트만 스키마 기본값을 직접 읽는다. 컴포넌트가 없는 Def 타입은 데이터 전용(엔티티가 되지 않음), Def 없는 엔티티는 없다. `field`의 기본값은 같은 컴포넌트의 값에서 가져올 수 있다(`default_from="max"`, `default=lambda h: ...`; 생성 시 초기값일 뿐).
- ✅ **컴포넌트 유무:** Def가 가진 컴포넌트는 항상 있고 뗄 수 없다. 런타임에만 붙는 컴포넌트는 있을 수도 없을 수도 있다(스텁에서 `X | None`).
- ✅ **남의 타입 확장**(schema-design 4.2): `extend("Unit", components=[...])`로 남의 Def 타입 전체에 내 컴포넌트를, `extend("Resource", x=const(...))`로 `const`를 추가할 수 있다. 특정 Def에 컴포넌트를 붙이는 것은 Def 패치(S1). 남의 컴포넌트에 칼럼 추가, 남의 필드의 타입·범위 변경은 불가. 같은 이름을 두 모드가 추가하면 로드 오류.
- ✅ **런타임 필드에 리스트 없음.** Def에서만 리터럴 리스트. `tags`(문자열 집합)는 내장 sugar. 가변 길이 데이터는 둘로 가른다(schema-design 3.3.2): 원소가 정체성을 가지면(따로 존재하고, 옮겨 다니고, 남이 참조한다) 원소 엔티티 + Ref, 컬렉션은 `inverse`로 얻고 저장하지 않는다(S3). 정체성이 없고 "이 엔티티의 키 K 값"이면 키 컴포넌트.
- ✅ **키 컴포넌트:** 엔티티 하나에 키마다 한 줄인 컴포넌트(`component("Skill", key="SkillDef", level=field(int), ...)`). 줄 안에서 `const`·`derived`·`field`가 그대로 동작하고, 줄마다 위의 읽기 순서(엔티티 값 → Def 값)를 따른다. Def 값은 키별 리터럴(`Colonist("Doc", Skill={"Medicine": Skill(level=8)})`). 키는 Def 타입, 엔티티 Ref, `int`(G129: 항상 `listed`, 이름 없는 값의 순서 있는 목록용. 커널 헬퍼 `replace_rows`·`append_row`로 리스트처럼 쓰며 번호를 다시 매기면 줄을 지우고 새로 만든다)만. 런타임 `str` 키는 금지. 접근은 정적 키(`pawn.Skill.Medicine.level`), 동적 키(`pawn.Skill[s]`), 순회(키 id 순). ECS로는 쌍(pair)이다.
  - 저장은 있는 줄만. 없는 키를 읽을 때의 의미는 선언이 정한다: `keys="all"`(기본; 기본값으로 채운 줄, 새 모드의 키가 기존 엔티티에 자동으로 생김) / `keys="listed"`(`None`, 스텁 `X | None`; 처음 줄은 엔티티 Def 리터럴에 적힌 키, 런타임에 붙이고 뗄 수 있고 Def에서 온 줄은 못 뗌; 유무가 쿼리 필터로 성립). 엔티티 키는 항상 `listed`처럼 동작하고, 키 엔티티가 죽으면 그 줄을 엔진이 지운다.
  - ✅ 줄 부착과 분리도 즉시 보인다(G88).
- ✅ **스크립트의 구조 변경은 이름 붙은 커널 내장 함수**(spec-gaps G134): `u = spawn("core.Warrior", Health=Health(current=3))`(Ref를 돌려줌), `destroy(u)`, `attach(u, Wounded(turns=3))`, `detach(u.Wounded)`, `add_row(u.Skill, "core.Medicine", Skill(level=3))`, `remove_row(u.Skill, "core.Medicine")`. 처음 값은 Def 리터럴과 같은 컴포넌트 값이고 생성자는 로직에서도 쓰는 이름이다(그 모드에 보이는 컴포넌트만). `spawn`에 리터럴로 적은 Def id는 ⑤가 검사한다. 키 줄은 `spawn` 뒤에 `add_row`로 붙인다. 쓰는 함수라 커맨드 본문(과 그 본문이 문장으로 부른 쓰기 함수)의 문장, 또는 `u = spawn(...)`처럼 이름 대입의 오른쪽 전체에서만 부른다(G117).
- ✅ **스탯/모디파이어는 엔진 내장이 아니라 세 부품:** (1) `derived` 필드(식으로 계산, 저장 안 됨. 지금은 읽을 때마다 새로 계산하고 캐시하지 않는다. 읽은 값의 기록은 `Explain`을 부를 때만 켜지고 근거 트리로 나온다, G105. 캐시는 벤치로 필요가 확인되면 이 기록기 위에 더한다) (2) 기여 행 `(대상, 연산, 값, 출처)` — 커널 전용 저장, 값은 `fixed`, 대상은 `derived`뿐(G98). 합성 규칙은 엔진이 아니라 `derived` 식이 정한다 (3) 수명 — 커널이 책임지는 것은 출처·대상 엔티티 제거뿐이고, N틱·이벤트 만료는 표준 모드가 만료 칼럼과 반응으로 행을 지운다(G98). 태그 부여에도 쓴다. `stat(...)` 같은 템플릿은 표준 모드가 제공.
  - ✅ **`derived`의 식**(schema-design 3.3.1): `derived(타입, 함수)`, 이름 붙은 함수나 람다. 인자는 계산할 자리 하나(그 컴포넌트 또는 키 컴포넌트 줄)이고, 영향 요소는 함수 안에서 찾아 읽는다(같은 컴포넌트, 같은 엔티티의 형제 컴포넌트와 Ref(`h.Location.city`, 엔티티 자신은 `h.entity`, G103; 엔티티의 Def 타입 바로 아래 `const`는 타입 이름으로 `h.entity.Unit.cost`, G107), `contribs(컴포넌트, "값 이름")`이 주는 기여 행 `op`/`value`/`source`). `op` 이름은 커널에 불투명하고 의미는 식이 정한다. 순수 함수(위 S2 표의 "순수"). 반환 타입은 선언과 맞아야 하며 `fixed` → `int`는 `floor()` 등으로 명시. 순환은 로드 시 타입 정보로 속성 경로를 보수적으로 추적해 막고, 빠져나간 경우는 실행 중 재진입 감지로 오류.
  - ✅ `field`가 `derived` 상한을 넘는 경우(버프 해제로 max가 current 아래로)는 게임이 고른다(G99): 커널은 자동 규칙이 없고 `field`의 `min`/`max`는 숫자 리터럴만 받는다. 표준 패턴은 (D) 피해량을 `field`로 두고 `current`를 `derived`로(버프가 다시 붙으면 복원), (B) `@when(lambda u: u.Health.current > u.Health.max)` 반응이 정착에서 저장값을 자른다(S5). B에서 커맨드 밖(호스트)의 변경은 다음 정착 지점까지 넘은 채로 읽힌다.

### S5. 반응 규칙 ✅
- 소스 두 가지: (a) `when <식>`: 읽은 칸이 바뀔 때만 재평가하고 false→true 전환(edge)에서 1회 발동, 참인 동안 반복하려면 `repeat=True`. (b) `on("Name")` + `emit("Name", ...)`: 상태에 흔적이 남지 않는 사건 신호.
- 본문은 Flow(`ask`가 있으면 Request가 열린다). 슈거: `cooldown=N`, `once=True`(상태는 칼럼이라 저장).
- 커널 기본 요소에서 제외: 확률(`rand()`는 본문에서), MTTH(= `repeat=True` + `chance(1/N)`; 표준 모드 슈거).
- ✅ **순서 = 이름 있는 단계(stage)의 위상 정렬.** 정수 `order=`는 두지 않는다(다른 모드의 숫자를 알아야 끼어들 수 있으므로). U3, U8.
  ```python
  stage("core.economy", after=["core.admin"])
  stage("smuggling.black_market", after=["core.economy"], before=["core.politics"])

  @on("tick", stage="core.economy")
  def pay_wages(): ...
  ```
  - 단계 id는 모드 id 접두사 네임스페이스(S7 호스트 함수와 같은 규칙). 어느 모드든 단계를 선언하고 남의 단계 사이에 끼워 넣을 수 있다. 단계는 신호와 무관한 하나의 전역 그래프이고, 신호마다 그 신호에 핸들러가 붙은 단계만 쓴다.
  - 로드 시 정렬한다(S1 ⑤ 링크 단계). 사이클은 사이클 경로 + `파일:줄`로 로드 오류. 없는 단계를 가리키면 오류이며 `optional_after=`/`optional_before=`로 선언한 것만 무시.
  - 동률 규칙(결정론): 서로 순서 관계가 없는 단계끼리는 단계 id 순. 같은 단계 안의 핸들러는 모드 로드 순서 → 정의 순서.
  - 🟡 `stage=`가 없는 핸들러는 그 신호의 모든 단계 핸들러가 끝난 뒤, 모드 로드 순서 → 정의 순서로 실행한다.
  - `when` 반응도 `stage=`를 가질 수 있고, 정착(settle)의 한 회차 안에서 같은 규칙으로 정렬한다.
  - 턴 흐름의 확장도 같은 장치로 한다: 턴 루프 Flow(표준 모드)가 `emit("turn_start")` 같은 신호를 내고, 다른 모드는 그 신호의 단계에 핸들러를 붙인다.
- **난수열은 Flow별**(S2 "난수"). 반응이 만든 Flow의 난수열은 (반응 정의 id, 발동 횟수)로 정해져, 다른 반응이 추가·제거되어도 밀리지 않는다.
- 🟡 **`when`은 정착 지점에서만 평가한다.** 정착 지점 = 커맨드 하나(그 Flow 실행)가 끝난 뒤, 그리고 틱 처리의 마지막 단계(X2). 쓰기마다 평가하지 않으므로 한 커맨드 안에서 0→5→0으로 바뀐 값은 edge로 보지 않는다. 발동한 반응이 값을 바꾸면 더 바뀌는 것이 없을 때까지 반복하고, 반복 상한을 넘으면 오류.
- 🟡 **`emit`의 처리 시점:** `on(...)` 핸들러는 각각 새 Flow로 만들어지고, 현재 Flow가 막히거나 끝난 뒤 발생 순서대로(같은 신호의 핸들러끼리는 위의 단계 순서 규칙) 실행된다.
- 🟡 **트랜잭션 단위 = Flow 한 번의 실행**(재개부터 다음 막힘·종료까지). 커맨드가 일으킨 반응·핸들러는 각자 별도 트랜잭션이다. 반응에서 오류가 나면 그 반응의 효과만 되돌리고 진단을 남기며, 원인이 된 커맨드는 유지된다. `advance` 중의 오류도 같은 규칙.
- **Event는 커널에 두지 않는다**(표시 방식·severity·문구는 UI·장르 요소; 표준 모드의 `event(...)` 템플릿).
- **지연/만료 = 자는 Flow.** `wait(ticks=n)`은 스크립트 안에서만 허용되고 Flow가 (프레임 스택 + 지역 변수 + 깨울 틱)으로 저장된다. "임의의 명령을 나중에 실행하는 예약 API"는 열지 않는다. 기여 행의 `expires_at`은 틱 경계에서 엔진이 일괄 스윕.
- 참조 대상 소멸: generation으로 감지하고 Flow는 `on_stale=`(기본 취소)로 처리.
- 닫힌 질문: 취소/대체 가능한 훅(`prevent_default`)은 두지 않는다(G176). `wait` 중 Flow를 취소하는 전용 기능은 두지 않고 상태로 표현한다(G177). `when`(과 `repeat`) 조건의 평가 비용은 읽은 엔티티에 쓰기가 있었거나 `now()`를 읽었고 틱이 바뀐 조건만 다시 평가해 줄인다(결과는 매번 모두 평가한 것과 같다).

### S6. 커맨드 ✅(방향) / 세부 진행 중
- 커맨드는 **타입 있는 매개변수(기본값 포함) + 비용(1급) + `require`(각각 개별 평가, 실패 사유 개별 반환) + 본문**을 가진다. 상태 변경의 단일 입구이며 직렬화 가능(저장·리플레이·네트워크·AI·테스트의 기준점). 평가 결과는 구조화 데이터(`message_key` + 인자).
- **동작 종류:** 시뮬레이션 커맨드(`@command`, 로그에 남음) · 프롬프트 응답(열린 Request에 대한 응답, 커맨드와 같은 길) · UI 동작(`@ui_action`, **클라이언트 로컬**: 시뮬레이션 상태를 읽을 수 있고 쓸 수 없으며 커맨드를 제출할 수 있음, 저장/네트워크 대상 아님) · 디버그(개발 모드에서만).
- **권한 3층:** ① 호스트가 연결에 제출자(`issuer`) 꼬리표를 붙인다(연결 ↔ 꼬리표는 호스트 몫, 엔진은 검증하지 않고 받은 그대로 쓴다) ② **입구**: 커맨드가 "누구로서" 행동하는지(자유 커맨드는 `acts_for`, 응답 커맨드는 명시한 응답 엔티티)를 정하고, 모드가 선언한 정책 함수 `may_act(issuer, 엔티티)`가 그 issuer가 그 엔티티로 행동해도 되는지 본다 ③ 규칙은 `preconditions`(소유 검사 `unit.owner == party`, 차례 검사 포함). 커맨드 본문에 권한 검사를 반복하지 않는다. 입구 검사는 순수하고 거부는 상태·난수를 건드리지 않는다(C10). (spec-gaps G119~G126)
- **issuer는 "어느 연결에서 왔나"이고 행동하는 진영이 아니다**(G119). 불투명한 문자열이며 커맨드 로그·거부 사유·입구에만 쓰이고, 스크립트에서 읽는 곳은 정책 함수뿐이다. 행동하는 진영과 비용 지불자는 인자에서 나온다(G120).
- **담당 정보("연결 A가 진영 P를 맡는다")는 모드 데이터다**(G121). 담당 칼럼, 상속·합병 때 옮기는 규칙, 정책 함수는 표준 모드나 게임 모드(본편 포함)가 만든다. 로비 배정·접속 끊김은 호스트가 아래의 직접 쓰기 경로로 쓴다. 정책 함수는 활성 모드 전체에서 최대 하나(교체는 `override=True`), 없으면 모두 허용하되 호스트가 "정책 필수"를 켜면 시작을 거부한다(G124).
- 호스트가 시뮬레이션 상태에 직접 쓰는 경로는 하나뿐이며, 그것도 기록·롤백·권한의 대상이다.
- **두 종류의 제출:** 응답 커맨드(Request id와 응답 엔티티를 가짐; 엔티티가 그 응답의 목록에 없거나 정책이 거부하면 이유와 함께 즉시 거부, 본문은 대기하던 Flow의 스택 위에서 실행, G126) · **자유 커맨드**(Request id 없음; 정의에 `free=True`가 있을 때만 허용, 기본 거부; 제출마다 새 Flow). 자유 커맨드는 `acts_for`를 반드시 적고 누구로서도 아니면 `acts_for=None`(이때도 정책 함수는 `None`으로 불린다), 빠지면 로드 오류(G123). 응답 커맨드도 `acts_for`로 답하는 엔티티를 인자에서 고른다(`None` 불가, G139).
- **예약 실행 큐 없음(엔진 수준).** 지연 실행은 게임이 `Order` 같은 **상태 데이터**로 만들고 처리 시점은 턴 흐름/틱 처리가 정한다. 호스트(전송 계층)의 입력 큐/커맨드 로그는 존재하며 엔진은 받은 순서대로 즉시 원자적으로 실행하고 그 순서가 저장·리플레이의 로그가 된다. 머리부·후보 범위는 실행 시점에 재평가하며 실패는 기록되는 거부.
- **draft = 제출 전의 매개변수 값**(`payload: dict[DefId[Resource], int]`처럼 값 전체를 하나의 매개변수로). UI 편집 화면은 그 값을 만드는 위젯일 뿐 제출 전에는 엔진 상태가 아니다. 같은 `preconditions`로 편집 중 실시간 사유를 보여 준다.
- **네트워크 방식은 정하지 않는다.** 인터페이스는 "커맨드 로그를 순서대로 받는다". 락스텝과 서버 권위 스냅샷 중 선택은 호스트/게임의 몫. 연결마다 보낼 상태는 거른 읽기 `World.ViewAs(issuer)`로 만든다(모드의 보기 정책 `@view_policy`를 따름, spec-gaps G196~G206). 서버 권위면 이것이 숨김을 지키고, 락스텝이면 모든 컴퓨터가 전체 상태를 가지므로 화면 표시에만 쓴다.
- ✅ **`choose`·`cost`(G183~G188):** `choose`는 매개변수의 후보를 정하고 엔진은 그것을 제출 검사(후보가 아니면 `require` 실패와 같은 구조로 거절)와 나열 양쪽에 쓴다. 호스트 API `Candidates(커맨드, 정한 인자들, 매개변수)`는 후보나 "먼저 정할 매개변수"를, `LegalMoves(커맨드, 정한 인자들, 최대 개수)`는 사전 검사를 통과한 조합을 `choose` 순서 → 후보 순서로 준다. 큰 후보 집합은 최대 개수에서 멈추고 잘렸음을 알린다. 블록에 적힌 순서가 고르는 순서라 후보 식이 아래쪽 `choose`의 매개변수를 읽으면 로드 오류다. `cost`는 사전 검사에서 확인하고(같은 칸은 합산) 본문이 시작될 때 뺀다.
- **열린 질문:** `@ui_action`의 로컬 저장소 모양 · 매개변수 타입의 표현 범위.

### S7. 코드 탈출구 (호스트 함수) ✅
- *호스트 함수* = 호스트(게임/서버/테스트)가 C#으로 짜서 이름으로 등록하고 스크립트가 일반 함수처럼 부르는 함수.
- **등록 주체는 호스트(게임 개발자)만.** 공개 모더는 텍스트만 쓴다.
- **명시 등록.** 리플렉션 스캔과 조용한 이름 충돌 무시 금지. 이름은 모드 id 접두사 네임스페이스(`core.find_path`), 충돌은 로드 오류. 서명(입력/출력 타입)과 효과 등급(순수 / 엔티티 쓰기)을 등록 시 선언하고 `.pyi` 스텁이 자동 생성된다.
- **동기 함수만.** 중단 가능한 구성은 언어 쪽에만.
- **엔티티 접근은 엔진이 건네는 제한된 접근기로만**(읽기 집합 추적 유지). 시스템 시계, 비시드 난수, 부동소수점 금지.
- **세이브에 C# 클래스 이름 금지.** 상태는 칼럼과 Flow뿐, 함수는 이름 문자열로만 참조.
- **모드 DLL은 막지 않되 지원하지 않는다.** 결정성·안전성·로드 진단을 보장하지 않는다. 막지 않기 위한 규칙: 코어를 과하게 `internal`로 숨기지 않고 레지스트리를 공개 API로 둔다. 나중에 필요하면 "신뢰된 DLL 등급"(기본 꺼짐)으로 별도 검토.
- **열린 질문:** 서명/타입 선언 문법 · 결정론 위반 방어(→ S9).

### S8. 저장 호환성 ✅
- **요구.** 참조는 문자열 ID, 없는 Def는 우아하게 처리, 모드 목록 기록, 마이그레이션 훅. 모드가 추가/제거/수정돼도 세이브가 깨지지 않아야 한다.
- **호환성을 3단계로 나눈다.**
  - Def 값 변경(밸런스, 문구): **항상 허용**.
  - 스키마 변경: 칼럼 추가는 기본값으로 채움. 삭제는 **고아 데이터** 영역에 보존하고 경고(조용히 버리지 않음). 타입/이름 변경은 모드가 `migrate(from=..)` 함수를 텍스트로 제공(같은 제한 언어라 결정적).
  - 멈춘 Flow의 함수 본문 변경: Flow는 (함수 이름, 위치)와 **함수별 본문 해시**를 저장한다. 해시가 같으면 정확히 재개, 다르면 위치를 옮기려 시도하지 **않고** 기본은 로드 거부 + 바뀐 함수 목록, `migrate` 또는 "해당 Flow 취소 후 로드"로 해결.
- **세이브 메타:** 엔진 형식 버전(순서 있는 마이그레이션 단계, 골든 세이브 파일 테스트), 모드 목록(id, 버전, 내용 해시), 틱, 난수 상태, 카운터. 모드 목록이 다르면 로드 전에 추가/제거/변경된 모드를 보여 준다.
- **참조는 id+generation.** 선택적 Ref는 None 복원 + 보고서, 필수 Ref는 로드 오류(엔티티/칼럼 목록 제공).
- **로드는 원자적.** 새 월드를 따로 만들어 전부 성공하면 교체, 실패하면 현재 게임 유지.
- **불일치 시 기본은 "상세 목록과 함께 거부"**, 사용자가 선택하면 격리 로드(제거된 모드의 Def를 참조하는 엔티티는 격리 영역에 보존되고 모드를 다시 설치하면 복구).
- **저장 형식은 정규형**: 같은 상태는 같은 바이트로 저장되고 Save→Load→Save가 동일하다.
- **열린 질문:** 고아/격리 영역의 저장 모양과 복구 규칙 · `migrate` 문법과 허용 연산 · 큰 세이브의 증분/압축 · 멀티플레이 세이브 공유.

### S9. 모더용 진단 ✅
- **진단은 데이터:** `Diagnostic { code, severity, message, mod, file, line, col, hint, related[] }`. 외부 `check` 명령(`engine check mods/`)을 1급 기능으로 두어 게임을 켜지 않고 터미널/CI에서 모든 오류를 한 번에 본다(JSON 출력 포함). 언어 서버는 만들지 않고 `check` JSON과 `.pyi` 스텁까지만 약속.
- **조용히 잘못 동작할 수 있으면 오류.** 알 수 없는 필드/Def 참조, 타입 불일치, 패치 대상 없음, 존재하지 않는 상태 경로 읽기는 전부 오류이며 did-you-mean 후보를 붙인다. 경고는 동작은 하지만 의심스러운 경우만.
- **런타임 스크립트 오류도 위치와 맥락:** 모드 `파일:줄` 스택 + 실행 중이던 커맨드/반응 + 관련 엔티티 id. **커맨드는 원자적이다**(단위는 Flow 한 번의 실행, S5): 실행 중 오류가 나면 그 커맨드의 모든 효과(상태, 행, 로그, Flow, 난수, 틱, 질의 번호)가 없던 일이 된다. 개발 모드에서는 롤백 대신 그 자리에서 멈추고 상태를 보존.
- **"왜?" 도구 5가지:** (1) 최종 Def 덤프 + 필드별 출처 (2) 파생값 추적(기여 행 목록) (3) 커맨드 전제 조건 보고서(`require`/`cost`마다 통과/실패 + 키 + 인자) (4) 반응 추적(마지막 평가의 읽은 값과 쿨다운 상태) (5) 단계 순서 덤프(신호별 최종 단계 순서, 각 단계의 핸들러와 선언 모드, 순서를 정한 `after`/`before`와 동률 규칙).
- **결정론 검사는 개발 전용:** 틱마다 테이블별 롤링 해시를 남기고, 같은 커맨드 로그를 두 번 재생해 처음 갈라지는 틱과 테이블을 알려 준다.
- 핫리로드는 후순위(새 정의를 현재 월드에 S8 호환성 검사로 적용하는 방식으로 길을 열어 둔다).
- ✅ **`check` JSON**(spec-gaps G75): `version`·`ok`·`counts`·`mods`·`diagnostics`(코드, 심각도, 메시지, 모드, 위치, 힌트, 관련 위치), 키 순서와 들여쓰기 고정. **최종 Def 덤프**(G76): `abstract` 포함 모든 Def를 등록 순서로, 값마다 최종 값·출처(직접/상속/패치/기본값)·처음 적은 위치·영향을 준 패치(적용 순서, 부모 쪽 먼저). 실패한 패치는 덤프에 없고 `check` 진단으로 본다.
- ✅ **CLI**(G78~G85): `engine check <mods> [--json] [--warnings-as-errors]`(기본은 `파일:줄:열: 심각도 코드: 메시지` 텍스트, `--json`이면 stdout에 JSON만), `engine dump <mods>`(덤프 JSON은 stdout, 진단은 stderr), `engine stubs <mods>`(모드마다 `__builtins__.pyi`, `schema/` 안에 스키마 스텁, 없을 때만 `pyrightconfig.json`; 비활성화된 모드도 첫 회차 결과로 스텁을 받는다). 종료 코드: 0 오류 없음, 1 콘텐츠 오류, 2 사용법·환경, 3 엔진 내부 예외. 종료 코드 0 ⇔ `ok`. 경고 승격은 정보를 올리지 않는다. `check`는 폴더에 있는 모드 집합만 검사한다(선택 모드는 폴더에 두면 검사됨).
- **열린 질문:** 진단 코드 체계 · 나머지 “왜?” 도구 4가지.

### S10. UI 연동: path와 delegate의 분리 🟡
1. path는 **읽기 전용 데이터**(값/Ref/컬렉션)이고 항상 직렬화 가능하다. delegate/Action 값이 path로 흐르지 않는다.
2. UI의 동작은 **커맨드 참조 + 인자**(예: `<Button command="X" args="{...}" />` — 이전 엔진의 표기일 뿐, UI 정의 형식은 ❓이며 UI 모듈이 정한다). 로드 시 커맨드의 파라미터 스키마와 대조해 `파일:줄` 오류. 같은 정의가 AI의 합법 수 열거에도 쓰인다.
3. 규칙에 영향을 주거나 저장돼야 하는 상태는 UI 로컬에 두지 않는다. 순수 UI 상태(펼침, 하이라이트, 렌즈, 창)는 `@ui_action`과 UI 로컬 저장소. `command=`는 시뮬레이션 커맨드를, `ui_action=`은 로컬 동작을 가리킨다.
4. 반응성은 delegate가 아니라 **읽기 집합**: 바인딩된 path를 로드 시 컴파일해 (엔티티, 컬럼) 읽기 집합을 얻고, 컬럼 버전 카운터가 바뀐 바인딩만 다시 읽는다. 구독 API는 UI 어댑터가 쓴다.
5. **UI의 "나"는 그 클라이언트가 보고 있는 엔티티**이고 UI 로컬 값이다(시뮬레이션 상태 아님, G127). 호스트나 UI가 설정하고(핫시트 전환, 관전자는 `None`), 후보는 입구 정책 함수(S6)로 구하며, 커맨드를 낼 때 `party`·응답 엔티티의 기본값이 될 뿐 기록에는 명시된 값이 남는다.
6. 호스트 기능(소리, 화면 이동)은 이름이 등록된 호스트 함수(`host.play_sound("x")`)로만. 시뮬레이션 결과에 영향을 주지 않는다.
- 대가: UI에 쓸 동작마다 커맨드 정의가 필요하다. 그 정의가 곧 문서이자 AI/네트워크 인터페이스.

## 5. 척추 밖이지만 결정된 것

### X1. 질의/응답 (Request) ✅
- **Request** = 흐름을 멈추고 응답을 기다리는 일반 구조. 필드: `id`, `hint`(UI/AI용 불투명 문자열), `accepts`, `options`, 제목 키, `blocks_time`, `deadline`(선택), `on_timeout`(마감 시 엔진이 결정론적으로 주입하는 기본 응답), 가시성(미정, 9절).
- **`accepts`:** 받는 응답 이름별 **답할 수 있는 엔티티 목록**(G125). 목록은 질의가 열릴 때 평가되어 굳고(저장됨) Request에 데이터로 노출된다. 응답은 어느 엔티티로서 답하는지 명시하고, 제출 시 엔진은 그 엔티티가 목록에 있는지와 정책 함수 `may_act(issuer, 엔티티)`를 본다(S6 입구, G126). 담당 확인은 응답이 올 때 하므로 기다리는 중에 담당이 바뀌면(접속 끊김 → AI) 새 담당이 답한다. 거부 사유는 구조화(예: `엔티티 X는 응답 R을 낼 수 없음, 허용: [..]`). 요청 단위 모드(`Any/All/순서대로`)나 "차례"라는 특별 개념은 없다.
- **응답은 Request id에 묶인 커맨드.** id로 매칭해 늦거나 중복된 응답이 다음 질문에 답하는 일을 막는다. 소비된 id는 거부한다. 응답이 접수되면 그 Request를 기다리던 Flow가 즉시 이어서 실행된다(run-until-blocked). 응답 커맨드의 본문은 대기하던 Flow의 스택 위에서 실행되고, 끝나면 `ask`/`await`가 응답 이름·답한 엔티티·(선택지면 번호)를 값으로 돌려준다(issuer는 돌려주지 않는다, G125).
- **다중 보류 흐름(Flow).** 질문을 기다리는 스크립트마다 자기 프레임 스택을 가진다. 한 Flow는 최대 하나의 대기(스택 맨 위)를 가지며, 열린 Request 집합 = 모든 Flow의 대기의 합집합. Flow id와 Request id는 **시뮬레이션 상태 안의 카운터**(무작위 UUID 금지). 실행 순서는 결정론적(입력을 받은 Flow가 먼저, 나머지는 Flow id 오름차순).
- 호출은 이름 문자열로 저장·호출되고(리터럴은 링크 단계에서 존재 검사), 인자는 접두사 규약이 아니라 데이터(맵)로 넘긴다.
- `ask`와 "한 주체가 여러 행동을 하다 종료 커맨드로 끝내는 페이즈" 같은 관용구는 커널이 아니라 표준 모드의 편의 문법이다.

### X2. 시간 ✅
- 엔진의 시간 단위는 **틱 하나**. 단일 `advance(n)`을 두고 누가 호출할지(게임 C# 루프 또는 스크립트 흐름)는 게임이 정한다. 틱은 저장 상태다.
- **`blocks_time`인 Request가 하나라도 열려 있으면 `advance`는 진행하지 않고 거부한다.** `blocks_time=False`인 Request는 시간을 멈추지 않고 마감 틱을 가질 수 있다. 시간을 막는 Request에 마감을 두는 것은 오류(도달 불가). 턴제 질문은 `blocks_time=True`, 실시간 이벤트는 `False`+마감.
- 🟡 **`advance(1)` 한 번의 순서:**
  1. 틱 카운터 +1.
  2. 만료 스윕: `expires_at`이 지난 기여 행 제거. (커널은 만료 칼럼을 모른다: 표준 모드가 이 단계에서 `RemoveContribution`으로 지운다, G98.)
  3. Flow 깨우기: 수면이 끝난 Flow를 깨우고, 마감이 지난 Request에는 `on_timeout` 응답을 주입한다(답한 엔티티는 `None`, G126). 같은 틱에 여럿이면 Flow id 순, 각각 막힐 때까지 실행.
  4. `emit("tick")`: `on("tick")` 핸들러를 단계 순서(S5)대로 실행. 매 틱 도는 게임 로직(이전 엔진의 tickable 목록)과, 호스트 함수(S7)를 부르는 C# 대량 연산은 여기에 둔다.
  5. 정착: `when` 반응 재평가(S5).
  
  `advance(n)`은 위를 n번 반복하며, 매 반복 전에 `blocks_time` 검사를 다시 한다.
- 적용 틱은 호스트가 정한다(전송 계층). 턴 관리는 게임 쪽 코드이며 엔진 소유가 아니다.
- `wait(ticks=n)`의 n은 1 이상이다.

### X3. 층 구조 ✅
- **경계 규칙.** 커널에는 (1) 결정성·저장·진단을 위해 엔진 지원이 꼭 필요하거나 (2) 제한된 언어로는 쓸 수 없는 것만 둔다. 나머지는 전부 모드다.

| 층 | 구현 | 성격 |
|---|---|---|
| 커널 | C# | 필수. 데이터 모델, 로더, 언어, Flow·Request·커맨드·반응, 저장, 진단 |
| 커널 확장 `ext.*` | C# | 선택. 호스트가 빌드 시 골라 포함. 호스트 함수 레지스트리에 더해 **칼럼 타입과 인덱스를 등록**할 수 있다. 예: `ext.spatial` |
| 표준 모드 `std.*` | 스크립트 | 선택. 일반 모드와 같은 방식으로 로드. v1: `std.stats`, `std.events`, `std.stack`(해결 스택·우선권), `std.mtth` |
| 게임 모드 | 스크립트 | 콘텐츠와 규칙 |

- **특권 없음.** 표준 모드는 공개 스크립트 API만 쓴다. 확장은 커널 내부(저장소 구조, Flow 테이블, 틱 루프)에 접근하지 않고 공개 확장 API(칼럼 직접/일괄 읽기, 변경 통지, 인덱스 등록)만 쓴다. 표준 모드를 만들다가 커널이 부족하면 그것이 커널의 결함이다(범용성 시험). 모더는 표준 모드를 통째로 교체하거나 일부만 쓸 수 있다.
- 🟡 확장이 칼럼 타입을 등록할 때는 **정규형 직렬화/역직렬화**(같은 값 → 같은 바이트, C4), 동등 비교, 결정론적 해시(C6)를 함께 제공해야 한다. 스크립트에는 외부 값(S2)으로 노출된다. 기본값과 로드 시점 생성 함수도 함께 등록할 수 있다(S2 외부 값 표기). 모드는 쓰는 확장을 `mod.py`의 `extensions`에 선언한다(S1). 확장의 인덱스를 필드에 연결하는 표기는 ❓(확장 API 모양과 함께).
- 확장이 만든 인덱스는 칼럼에서 다시 만들 수 있어야 하며 세이브에 저장하지 않는다. 확장 목록과 버전은 세이브에 기록한다.
- 모드는 새 **문법**을 추가할 수 없다(함수 호출과 키워드 인자까지).
- `std.stack`의 정책(우선권이 어디서 시작하는지, 몇 번 연속 통과하면 해소하는지, 반응 후 재시작 여부)은 하나의 정책이다. 설치 인자나 문서에 드러나야 한다.

### X4. 로컬라이제이션 ✅(원칙) / 🟡(방식)
- **P1.** 상태·세이브·커맨드 로그에는 번역문이 아니라 **키와 인자**만 저장한다.
- **P2.** 시뮬레이션은 번역된 텍스트를 읽지 않는다 (비교·정렬은 id).
- **P3.** 폴백: 요청 언어 → 모드의 기본 언어(`mod.py`에 선언) → 키 자체. `check`가 번역 안 된 키, 존재하지 않는 키의 번역, 자리표시자 불일치를 보고한다.
- **P4.** 언어 선택은 호스트의 몫. 엔진은 `text(key, args, lang)`만 제공한다. 엔진 진단 메시지의 현지화는 v1 범위 밖(영어 + 코드 번호).
- 방식(🟡, v1 구현 직전 재확인): 규칙으로 도출한 키(`Scout.label`) + 인라인 기본 텍스트 · 템플릿은 호출 쪽이 넘긴 이름 있는 인자만 보고 월드 경로는 평가하지 않음 · ICU MessageFormat 부분집합(`plural`, `select`, `number`; 조사 등은 언어 팩의 확장 포매터) · 번역 파일 형식 미정.

**검증 시나리오 (도메인 중립)** — 구현은 코어 수정 없이 아래를 모두 표현할 수 있어야 한다. 시나리오의 도메인 용어(참가자 이름, 자원 이름)는 구현이 정한다.
- **① 끼어들기 스택:** 한 참가자가 낸 효과가 대기열에 올라가고, 참가자들이 순서를 돌며 통과하거나 반응(새 효과를 올림)할 수 있다. 모두 연속으로 통과하면 위에서부터 해소되며 효과가 다른 대기 효과를 취소할 수 있다. 해소 중에도 질문(선택)이 열릴 수 있고 그 시점에 저장해도 이어서 진행된다. ✅ 코어 수정 없이 표현됨(대기 효과는 엔티티, 해소는 Def의 `Action`, 우선권 고리는 `while` + 응답 커맨드, 해소 중 질문에서 저장 뒤 이어 하기까지 같은 결과). 표현하다 `while`이 없어 우선권 고리가 조용히 멈출 수 있는 것을 찾아 열었다(G195). 스택 정책은 테스트가 박아 둔 것이고 `std.stack`의 몫이다.
- **② 동시 비공개 선택:** 모든 참가자가 서로의 선택을 보지 못한 채 동시에 선택하고, 모두 끝나면 공개된다. ✅ 코어 수정 없이 표현됨(참가자마다 핸들러가 질문을 열어 동시에 답함, 선택은 숨긴 컴포넌트와 공개 "골랐음", 모두 고르면 `@when`이 공개). 숨김을 위해 보기 정책과 거른 읽기를 더했다(G196~G206). 공개 전에는 다른 참가자가 무엇을 냈든 거른 읽기가 글자 하나까지 같다. 거른 읽기는 결과(`Show`)·합법 수·근거(`Explain`)까지 다 있고(G196~G206), 시간 진행 결과는 G206.
- **③ 단일 플레이어 + AI + 틱 이벤트:** 엔진이 합법 수를 나열하고 AI가 고르며, 틱마다 반응 규칙이 발동한다. ✅ 코어 수정 없이 표현됨(`LegalMoves`, `@when(repeat=True)`, 난수, 저장 뒤 이어 하기까지 같은 결과).
- **④ 실시간:** 한 참가자에게 기한이 있는 선택이 뜨고(시간은 멈추지 않음) 그 사이 다른 참가자가 자유 커맨드를 여러 개 동시에 진행시키며, 선택 뒤 같은 스크립트가 이어진다. 기한이 되면 기본 응답으로 진행한다. ✅ 코어 수정 없이 표현됨(`ask(..., deadline=3, on_timeout="retreat")`는 시간을 막지 않음(G159), 그 사이 틱 수입과 다른 참가자의 `wait` 행군 둘·`cost` 건설이 진행, 답하면 그 틱에, 안 하면 마감 틱에 같은 스크립트가 이어짐, 어느 단계 사이에서 저장해도 같은 결과).

## 8. 구현 과정 요구

1. **이 문서만 보고 만든다.** 이전 구현이 있었더라도 참조하지 않는다. 애매하거나 빠진 곳은 추측해서 채우지 말고 **"spec 빈틈" 목록**에 기록한다(무엇이 비어 있었나, 어떻게 정했나, 이유).
2. 모든 커널 변경에 3절의 편입 기준을 적용한다. 검증 시나리오는 7절의 서로 다른 둘 이상으로 시작한다.
3. 구현이 끝나면 빈틈 목록을 이 문서의 결정으로 반영한다. 이 목록이 곧 이 문서가 부족했던 곳의 평가다.

## 9. 열린 결정과 검증 대상

**미결 결정**
1. **호스트 엔진** (Godot / Unity / 둘 다): 뷰/UI 어댑터를 만들기 시작할 때 정한다. 영향: 모드 DLL 가능 여부, 뷰 어댑터.
2. ~~**공개/비공개 정보 표현**~~ → 정함(spec-gaps G196~G206): 모드의 보기 정책 `@view_policy def may_see(issuer, entity, component)`와 호스트의 거른 읽기 `World.ViewAs(issuer)`. 스크립트와 전체 저장은 전부 본다. 거른 읽기를 보안에 쓸지 화면에만 쓸지는 호스트의 네트워크 방식이 정한다.

**실험으로 닫는 항목**
- 로딩 파이프라인 수직 슬라이스: 정의 → 상속 → 패치 → 링크 → 검증, 오류에 `파일:줄`, `check` JSON 출력, 최종 Def 출처 덤프.
- 식 언어 + 경로 스키마 검증: 오타에 "혹시 …?", 자동 설명과 의존 경로 수집, 호스트 함수 서명 선언과 `.pyi` 자동 생성, Pylance가 `fixed`/`Literal`을 처리하는 방식.
- 저장 호환 3단계: 함수 본문 해시, 스키마 변경(기본값/고아/`migrate`), 골든 세이브 파일, 원자적 로드.
- 컬럼 저장소 + 스키마 기반 path 컴파일 + 쿼리 + 순회 벤치(1k/10k/100k 엔티티): 규모 직관, `derived` 의존성 추적·trace 성능, 확장 API가 공개 API만으로 충분한지, 명령 단위 롤백의 비용(전체 스냅샷 vs 쓰기 로그).
- 목록·맵 연산 세트와 행 값 타입.
- X4 방식(키 부여, 템플릿 인자 범위, 번역 파일 형식)은 v1 구현 직전에 재확인.

**설계 세부 열린 질문:** `@ui_action` 로컬 저장소 · 매개변수 타입 표현 범위 · `prevent_default` 훅 · 고아/격리 영역과 `migrate` 문법 · 진단 코드 체계 · `ext.*` 확장 API 모양.
