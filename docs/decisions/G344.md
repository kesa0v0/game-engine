**위치:** G332에서 이어서: 사전을 돌려주는 함수의 필드를 UXML에서 읽는 법

**무엇이 비어 있었나:** G332의 식은 "호출 하나나 변수 하나"라서 `for="row in mymod.unit_rows()"`처럼 사전의 목록을 돌려받아도 항목의 필드(`row.name`)를 읽을 수 없었다. 칸마다 함수가 필요했다(`mymod.row_name(row)`). 이전 게임의 `binding-path` 105개는 거의 전부 `Self.Label`·`Item.Icon`처럼 점으로 이은 필드 경로였다.

**어떻게 정했나:** **변수에서 사전 키를 점으로 읽는다.**

- 변수 뒤에 `.키`를 써서 사전의 문자열 키 값을 읽는다. 중첩도 된다(`row.stats.hp`). 값 자리(`bind-text="row.name"`)와 호출의 인자 자리(`on-click="mymod.select(row.unit)"`) 모두에 쓴다.
- 변수가 사전이 아니거나 키가 없으면 그 바인딩의 오류다(G341).
- 필드를 읽는 것은 화면 안의 순수 읽기다. 사전은 함수가 만든 값이라 그 호출의 영수증(G246)이 이미 변화를 알리므로 새 영수증이 필요 없다.
- **엔티티에는 점을 쓰지 않는다.** 컴포넌트를 UXML에서 바로 읽으면 보기 규칙과 영수증을 해석기가 직접 다뤄야 하고 값이 모드 함수를 거친다는 원칙(G244)이 깨진다. 호출 결과에도 점을 쓰지 않는다(같은 호출이 칸마다 반복됨).
- 정하지 않았다: 리스트의 번호 읽기(`row.items[0]`), 호출 결과 공유 규칙.

**이유:** 셋 중 고른 것: 변수에만 점(이것), 필드 접근 없음(칸마다 함수가 필요해 사전을 돌려주는 방식이 쓸모없어지고 이전 게임 화면을 옮기면 함수가 폭증함), 호출 결과에도 점(편하지만 칸마다 같은 함수를 다시 부르는 비용과 결과 공유 규칙이 따로 필요함).
