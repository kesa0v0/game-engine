**위치:** S1·S3 추상 Def·`override`된 Def의 패치

**무엇이 비어 있었나:** 추상 Def를 패치 대상으로 쓸 수 있는지, `override`로 교체된 Def를 패치하면 교체본인지 원본인지가 없었다.

**어떻게 정했나:** 둘 다 허용하고 별도 규칙을 두지 않는다. 패치 대상은 항상 id로 레지스트리에서 찾은 현재 Def(교체본)다. 추상 Def는 일반 Def처럼 패치하고 자식 반영은 ④의 상속이 한다. 교체되기 전 Def(`Replaced`)는 패치 대상이 아니다. `override`는 ②b에서 풀리므로 패치는 로드 순서와 무관하게 항상 **교체본** 위에 쌓인다(G41의 로드 순서 원칙의 예외이며, G21은 교체끼리의 순서만 다룸). 결과가 로드 순서에 달리지 않으므로 충돌 오류로 막지 않고, 순서가 선언되지 않은 `override`와 패치의 조합에는 정보 진단 하나를 남긴다("`Scout`는 모드 `a`가 교체했으며 이 패치는 교체본에 적용됩니다"). 변경 이력에는 교체본의 출처 모드가 나오고, 상속으로 반영된 값의 출처는 "부모 `Base`의 패치 ← 모드 `m`"으로 남긴다(이력 연결은 ④에서 구현, 여기서는 요구만).

**이유:** "Unit 전부에 +1"은 가장 흔한 요구라 추상 Def 패치를 막으면 안 된다. Factorio의 정의 단계 → 수정 단계(교체는 앞 단계에서 풀리고 수정은 항상 교체본 위)와 같은 구조이고, 순서 미선언 조합을 오류로 막는 쪽은 G37·G41이 막으려는 "결과가 순서에 달리는" 경우가 아니라서 과하다. 새 규칙을 늘리지 않고 S3을 그대로 쓰는 쪽이 일관되고, 영향 범위는 S9의 최종 Def 덤프가 출처와 함께 보여 준다(경고는 정상 사용에서도 떠서 노이즈).
