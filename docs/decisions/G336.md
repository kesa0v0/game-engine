**위치:** G330에서 이어서: UXML 요소의 클릭 반응

**무엇이 비어 있었나:** 버튼은 커맨드(상태를 바꿈)나 `@ui_action`(화면만 바꿈)을 가리킨다(G276·G280). 이전 게임은 `command-def`(12곳)·`bind-click`(11곳)·`ui-action`(51곳)으로 갈라 적었고 UXML이 인자를 조립했다(`cmd-ctx-*`, `bind-args`). 인자 조립은 G330에서 스크립트의 일이 됐다.

**어떻게 정했나:** **속성 하나로, 이름으로 구분한다.**

- `on-<이벤트 이름>="모드.이름(인자, …)"`(`on-click`). `bind-<속성>`(G331)과 대칭이다. 인자는 G332의 문법(변수나 고정값)이다.
- 해석기가 이름을 `Commands()`와 `UiActions()`에서 찾는다. 커맨드면 `Submit`, 화면 동작이면 `Act`(적힌 `submit`을 이어서 냄, G283)를 부른다. 어느 쪽에도 없으면 로드 때 오류다(G249의 `CheckCall`처럼 미리 확인).
- 함수 이름은 모드 안에서 하나라 커맨드와 화면 동작의 이름이 겹치지 않는다고 본다(구현 때 확인).
- 정하지 않았다: 눌러도 되는지(회색 버튼과 이유)를 보이는 법(경계에 `CheckPreconditions`에 해당하는 호출이 없음), 클릭 말고 다른 이벤트, 호스트 전용 동작(창 조작).

**이유:** 셋 중 고른 것: 속성 하나(이것), 속성 둘로 나눔(`on-click-action`·`on-click-command`: 무엇을 부르는지 파일에서 바로 보이나 같은 일에 말이 둘), 이전 엔진의 어휘(`command-def`·`bind-click`·`ui-action`: 이름은 익숙하나 UXML이 인자를 조립하던 전제가 G330에서 바뀌어 의미가 어긋남).
