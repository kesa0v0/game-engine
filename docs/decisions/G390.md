**위치:** G389에서 이어서: 호스트의 그래픽 파일 표기

**무엇이 비어 있었나:** 그림 값(`look(이름, 키=값…)`)을 받아 정의를 고르고 변형을 고르며 값을 속성에 잇고, 모더가 코드 없이 부품·가변 목록·애니메이션까지 조립할 파일이 없었다. 사용자는 조립을 모더에게 열고 넓힐 수 있게 하자고 했다.

**어떻게 정했나 (사용자가 고름):**

- 정의는 그냥 XML이다(Unity UXML이 아니고 Unity는 모른다). 폴더·확장자를 화면 UXML과 나눈다.
- 읽기와 해석은 UXML 장치를 다시 쓴다: 중첩, `for`, `bind-<속성>`, `bind-display`, `Include`(인자). 식의 이름은 모드 함수가 아니라 그림 값의 키다(`team`, `gear.items`). 비교식이 필요하면 `Look` 함수가 참거짓 값으로 넘긴다(G332).
- 요소 종류는 호스트가 등록한다. Unity 패키지가 기본 종류를 주고 게임은 C#으로 새 종류를 더한다(G389의 프리팹 탈출구가 이 자리). 다른 호스트는 제 종류를 둔다. 모르는 요소·속성은 로드 때 진단한다.
- 커널은 이 파일을 모른다(G240·G387). 파일 경로는 G335의 가상 경로.
- 같은 이름의 정의는 로드 순서가 뒤인 모드가 통째로 이긴다. 칸 하나만 고치는 경로 패치(RimWorld의 XML 경로 패치 꼴)는 사례가 생기면 더한다.

고른 것: USS 꼴(이름 + 키=값이 선택자와 맞으나 중첩·가변 목록을 못 함), 우리 데이터 Def(덮어쓰기·패치·검사가 다 있으나 펼치기·조건을 데이터에 적을 표기가 없음), XML 정의(이것: 템플릿 장치가 다 있고 패치가 약함).

**이유:** 모더에게 여는 조립(중첩·펼치기·조건·재사용)이 이미 시험된 장치로 되고, 넓히는 축이 "호스트가 요소 종류를 등록"이라 G387(뜻은 호스트가 정함)과 맞는다. 약한 패치는 RimWorld가 XML Def에 경로 패치를 둔 검증된 모양으로 나중에 메울 수 있다(일반 지식). Look 정의가 결국 Def와 같은 것(이름 붙은 정적 데이터)이라는 점은 사용자가 짚었고, 차이는 어느 Def 장치를 쓰나다.

**상태:** 확인
