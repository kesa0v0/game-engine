**위치:** G325에서 이어서: 호스트 경계의 호출은 동기냐 비동기냐

**무엇이 비어 있었나:** 같은 프로세스에서는 `Submit`·`Call`이 곧바로 끝나지만, 원격(서버 권위)이면 메시지 왕복으로 수십~수백 ms가 걸려 동기로 기다리면 Unity 메인 스레드가 멈춘다. 같은 프로세스에서도 틱 여러 번이나 큰 합법 수 나열은 한 프레임을 넘길 수 있어 커널을 작업 스레드로 옮기고 싶어질 수 있다. 커널은 단일 스레드이고 "막힐 때까지 실행"한다(spine-spec 평가 모델).

**어떻게 정했나:** **경계는 비동기로 정의한다.**

- 세션과 운영의 호출은 `ValueTask`(결과가 있으면 `ValueTask<T>`)를 돌려준다. 같은 프로세스 구현은 이미 끝난 결과를 준다(기다림·할당이 거의 없음).
- 원격 구현(메시지 왕복)과, 같은 프로세스에서 커널을 작업 스레드에 둔 구현도 같은 경계다. 해석기 코드는 셋 모두 같다.
- 커널은 계속 한 스레드에서만 돈다. 한 세션의 요청은 낸 순서대로 처리되므로 `Submit` 뒤에 낸 `Call`은 바뀐 뒤의 상태를 본다.

**이유:** 셋 중 고른 것: 비동기 경계(이것), 동기 경계(지금 가장 단순하나 원격에서 메인 스레드가 멈추거나 클라이언트 거울 상태가 따로 필요하고 해석기를 다시 고치게 됨), 보내고 매 프레임 꺼내는 메시지 방식(`await`는 없으나 요청·응답 짝짓기를 해석기가 상태 기계로 다룸). 근거: 이전 엔진은 커맨드 처리와 틱 진행을 비동기(UniTask)로 했다(`SessionCommandRouter.RouteCommandAsync`, `AdvanceTickAsync`, use-cases). LSP의 요청·응답도 비동기 메시지다(일반 지식). `netstandard2.1`의 `ValueTask`와 Unity 6의 `Awaitable`로 같은 프로세스일 때의 비용은 작다.
