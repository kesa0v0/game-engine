**위치:** X1 `ask`의 호출 모양과 돌려주는 값 (G126이 미룬 필드 이름)

**무엇이 비어 있었나:** 실제 질문은 세 모양이었다(TR): 문구 N개 중 하나(`Effect_Choice`), 후보 중 하나(`Effect_SelectTarget`), 인자가 있는 여러 행동 중 하나(우선권의 통과·대응). 앞의 둘은 원소 종류만 다르고 어떻게 보일지는 G137에 따라 UI가 정한다. 셋째는 조합(카드·대상·추가 지불)이 많아 목록으로 펼칠 수 없다.

**어떻게 정했나:** **`ask(who, title, choices=[...], responses=[...], hint=, data=)`.** `who`는 엔티티 하나 또는 목록(그중 누구든), `title`은 텍스트 키나 `text(...)`. `choices`는 고를 값의 목록(문구 키·`text(...)`·엔티티·Def id)이고 `responses`는 받을 응답 커맨드(자유 커맨드가 아닌 `@command`) 이름의 목록이며 하나만 써도 둘 다 써도 된다. 돌려받는 값 `r`은 한 모양이다: `r.response`(커맨드 이름, 고르기면 `None`), `r.index`·`r.choice`(고른 번호와 값, 응답 커맨드면 `None`), `r.by`(답한 엔티티, 시간 초과면 `None`). 고를 수 없는 선택지의 표시, 시간 관련 인자, 응답 커맨드 본문이 답한 엔티티를 읽는 법, 응답 커맨드 인자를 `r`로 받을지, 동시 고르기(시나리오 ②)는 이 항목이 정하지 않는다.

**이유:** 종류별 내장(`choose_option`·`choose_target`·`ask_response`)은 문구와 대상이 섞인 목록을 표현하기 어렵고 종류마다 커널 내장이 는다. 응답 커맨드만 두면 선택지 하나 묻는 데도 커맨드 선언이 필요하다.

**상태:** 확인

**바뀜:** 선택지는 맨 값이나 `option(값, label=, desc=, style=, data=)`이고, 엔진이 맨 값을 감싸 호스트는 늘 option 목록을 받는다(`r.choice`는 여전히 안의 값) → G271.
