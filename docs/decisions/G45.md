**위치:** S1·S9 패치 변경 이력의 구현 모양

**무엇이 비어 있었나:** 필드별 변경 이력(S1)을 담을 자료구조와, ③이 어디까지 채워야 하는지가 없었다.

**어떻게 정했나:** ③이 `PatchLog`를 만든다. `DefRecord`는 건드리지 않는 별도 객체이고, 필드마다 항목 목록을 가진다. 항목은 (대상 Def id, 필드 경로, 연산, 값, 모드, 호출 위치, 적용 결과). ③은 로그와 함께 패치가 반영된 필드 값(`DefRecord`와 별도의 반영본)을 ④로 넘기고, ④·⑥과 덤프는 로그를 읽기만 한다. G28의 모드 비활성화는 로그에서 그 모드의 항목을 빼고 다시 계산한다. 이번 슬라이스는 로그를 채우는 것까지이며 덤프 출력 형식과 `check` JSON은 만들지 않는다(spec 9절 열린 결정). 테스트는 로그를 직접 읽어 확인한다.

**이유:** ②의 불변 구조를 고치지 않고 ③의 결과만 얹는다. 실패한 모드의 처리가 "항목 빼고 다시 계산"으로 단순하다. 필드를 가변으로 바꾸는 쪽(B)은 롤백이 복잡하고, ⑥에서 재구성하는 쪽(C)은 보류 연산(G42)과 출처 연결 정보를 잃기 쉽다.

**상태:** 확인
