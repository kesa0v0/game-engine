**위치:** G359에서 이어서: 모드 USS의 잘못을 어디서 알려 주나

**무엇이 비어 있었나:** Unity는 모르는 속성(`colr: red;`)을 조용히 무시한다. 이전 엔진도 오타를 알려 주지 않았다. 속성 이름을 검사하려면 올바른 이름 목록이 필요하고, 그 목록을 누가 드는지 정해야 했다.

**어떻게 정했나:** **엔진이 진단하고 목록도 엔진이 든다.**

- 문법 오류(닫히지 않은 괄호, 모르는 선택자 모양)와 모르는 속성 이름은 `Kesa.Engine.Ui`가 USS를 읽을 때 `UiProblem`(`파일:줄`, 메시지)으로 낸다. UXML 오류와 같은 길이다.
- `--`로 시작하는 사용자 변수는 이름 검사를 하지 않는다.
- 속성 이름 목록은 엔진에 둔다. Unity 패키지의 창 없는 확인이 이 목록과 Unity 내부의 속성 표를 비교해, Unity 판을 올려 어긋나면 실패한다.
- 값의 형식 오류(`color: 10px`)는 값을 Unity 값으로 바꾸는 호스트가 알게 되므로 호스트가 같은 `UiProblem`으로 돌려준다.

**이유:** 고른 것: 엔진이 목록을 든다(이것), Unity 호스트가 Unity 내부 속성 표로 검사한다(늘 판에 맞으나 진단이 Unity 안에서만 나오고 리플렉션 의존이 는다, OneJS의 방식), 검사하지 않는다(이전 엔진의 "왜 안 먹지" 문제가 남음). 진단이 한곳에 모여 `dotnet test`로 시험되고, 목록이 낡는 것은 Unity 확인이 잡는다.

**상태:** 확인
