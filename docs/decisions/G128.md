**위치:** X3 `std.stack`: 대기 중인 행동(“나중에 해소할 것”)의 표현과 커널의 몫

**무엇이 비어 있었나:** 이전 TR 스택 노드는 효과 객체와 컨텍스트 바구니를 들고 저장했고(U5), 새 spec은 세이브에 함수 객체를 넣지 못한다(S7). 노드를 데이터(행동 Def id + 인자)로 둘지, 행동의 Flow가 멈춰 기다리게 할지가 비어 있었다.

**어떻게 정했나:** **표현은 `std.stack`(모드)의 몫이고 커널 결정이 아니다.** 방향은 데이터 방식(노드 엔티티에 행동 Def id와 인자를 두고, 해소할 때 그 Def의 `Action` 함수를 부름)이며 `std.stack`을 만들 때 확정한다. **커널의 몫은 이 방식을 커널 기능만으로 만들 수 있게 하는 것**이고, 막히는 곳은 상태에 담을 수 있는 값의 모양(행동마다 다른 인자, 주사위 눈 같은 목록)이다(이어서 정함). Flow가 다른 Flow의 신호를 기다리는 기능은 지금 추가하지 않는다(데이터 방식이면 필요 없음, 다른 사례가 요구할 때 다시 본다).

**이유:** X3 경계 규칙과 “표준 모드를 만들다가 커널이 부족하면 커널의 결함”. MTG 스택(카드 + 대상), RimWorld `Job`(JobDef + 대상 칸), CK3 지연 이벤트(`trigger_event` + `save_scope_as`)가 모두 데이터 방식이다(일반 지식). 데이터면 UI·AI가 스택 내용을 읽을 수 있고 모드 업데이트 뒤에도 새 본문으로 해소된다(멈춘 Flow는 본문 해시가 바뀌면 로드 거부, S8).

**상태:** 확인
