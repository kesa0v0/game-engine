**위치:** S2 `match`/`case` (G13·G102가 미룸, 모더 안내서를 쓰며 드러난 spec과 구현의 어긋남)

**무엇이 비어 있었나:** spec S2는 `match/case`(가드 포함)를 허용 목록에 두고 `ask`의 답을 `if`/`match`로 가른다고 적었지만, G13과 G102는 `match`를 미뤄 파서가 `PAR002`로 거부했다. 모더 안내서(G252)는 구현을 따라 "`match`는 로드 오류"라 적어 spec과 안내서가 반대로 말했다. 파이썬 `match`의 패턴 중 무엇을 받을지도 정한 적이 없다.

**어떻게 정했나:** **함수(커맨드·핸들러·순수 함수) 안의 `match` 문을 연다.** 받는 패턴은 다음뿐이다.

- 리터럴: 문자열(이어 붙인 문자열 포함), 정수, `fixed`, 앞에 `-`를 붙인 수, `True`, `False`, `None`. Def id도 문자열이므로 `case "Scout":`로 쓴다.
- 리터럴을 세로줄로 이은 것(`case "a" | "b":`).
- `_`(나머지 전부). 파이썬처럼 가드 없는 `_` 뒤에는 `case`를 더 쓸 수 없다(구문 오류). 세로줄 안에서는 마지막 자리에만.
- 가드(`case "a" if 조건:`).

그 밖의 패턴은 `PAR002`다: 이름 캡처(`case x:`, 파이썬에서는 비교가 아니라 아무 값이나 받아 담는 것이라 함정이다. 안내는 "가드를 쓰세요: `case _ if pick == x:`"), 점 이름(`case Kind.Fast:`), 괄호·`as`·시퀀스·매핑·클래스 패턴, `match a, b:`. 받는 패턴을 나중에 넓혀도 기존 모드가 깨지지 않으므로 좁게 시작한다.

**뜻:** 파서가 `match`를 `$m0 = 대상` 대입과 `if`/`elif`/`else`로 바꿔 넣는다. 대상은 한 번만 평가하고, 패턴 비교는 `==`(타입이 다르면 같지 않음, 그래서 `True`와 `1`은 서로 맞지 않는다), 세로줄은 `or`, 가드는 `and`, 가드 없는 `_`는 `else`다. 숨은 변수 이름은 모더가 쓸 수 없는 `$`로 시작하고 번호는 함수마다 0부터(다른 함수를 고쳐도 이 함수의 본문 해시가 그대로이게). 그래서 검사기·실행기·저장은 `if`의 것을 그대로 쓰고, `case` 안에서 `ask`·`wait`로 멈춘 흐름도 `if`처럼 저장·재개된다. 맞는 `case`가 없으면 아무것도 하지 않는다(파이썬과 같음). 콘텐츠 파일 최상위에서는 `for`·`while`처럼 로드 오류(`EVL002`)다.

**이유:** `ask`의 답 가르기가 가장 흔한 자리이고 `if`/`elif`보다 읽기 쉽다. 패러독스 스크립트의 `switch = { trigger = … }`도 같은 쓸모다(일반 지식). 파이썬 `match`의 나머지 힘(클래스·시퀀스 풀기)은 이 언어가 금지한 `class`·튜플에 기대므로 받을 것이 없다. `if`로 바꿔 넣으면 새 실행 경로가 없어 저장 형식과 검사기 여섯 곳을 건드리지 않는다.

**상태:** 확인
