**위치:** S1 Def id의 이름 공간 ④ 구분자와 실행 중의 정규형 (G258에서 이어짐, 사용자 제안: Minecraft식)

**무엇이 비어 있었나:** G258~G260의 점 하나 구분자로는 `rigs.Brig`가 "rigs 모드의 Brig"인지 "내 모드의 rigs.Brig"인지 글만으로 알 수 없어 G260에 까다로운 풀이 규칙이 필요했다. 실행 중에 Def id는 그냥 문자열(`StrValue`)이고 명령 인자·필드 쓰기·`spawn`에서만 확인하므로(`World.Commands.cs`, `World.Values.cs`), 명령 인자로 `"harbor.Sloop"`이 들어오고 스크립트가 `kind == "Sloop"`이나 `PRICES[kind]`(키 `"Sloop"`)로 쓰면 조용히 거짓이 되거나 키 없음이 났다.

**어떻게 정했나:** **Def id는 `모드id:경로`이고 경로의 하위 이름 공간은 `/`로 나눈다**(`harbor:rigs/Brig`). `:`는 한 번만, 조각의 글자는 G259 그대로(ASCII 식별자, 대소문자 구분)라 id 안에 `.`는 없다. 정의 자리는 `:` 없이 내 모드 기준이고(`Ship("rigs/Brig")` → `harbor:rigs/Brig`), `override=True`는 전체 이름을 쓴다. 참조 자리에서 `:`가 있으면 전체 이름, 없으면 그 코드가 속한 모드 기준이다. **실행 중의 Def id 값은 언제나 전체 이름이다.** 경계(명령 인자, `spawn`, `DefId` 필드, 저장, 호스트)로 들어오는 짧은 이름은 그 자리에서 전체 이름으로 바꾸고, 스크립트에서 타입을 아는 자리(`spawn("Sloop")`, `DefId` 필드 값, `DefId` 목록의 `choose(from_=...)`, `parent=`, `patch.*` 대상)의 리터럴은 불러올 때 푼다. 타입을 모르는 자리(`==` 비교, 사전 키)는 전체 이름을 쓰거나 불러올 때 내 모드 기준으로 풀리는 `defid("Sloop")`을 쓰고(이름은 임시), `check`는 `DefId` 값을 맨 문자열 리터럴과 비교하거나 사전 키로 찾을 때 경고한다. 사람이 읽는 표기(오류 메시지·`check`·콘솔·DefDump)에서 데이터 경로를 붙일 때는 `harbor:rigs/Brig.Health.base_max`처럼 `.`로 잇는다. 고르지 않은 것: Minecraft의 소문자 제한(id가 파일 경로에서 나오기 때문이라 우리에겐 이유 없음), 이름 공간을 빼면 기본 게임(우리는 `core`도 한 모드), 종류별 등록부(G19 그대로 전역 하나).

**이유:** `:`가 모드를 글로 드러내 풀이 규칙이 "있으면 전체, 없으면 내 모드" 한 줄이 되고, `.`는 데이터 경로(G34의 `Health.base_max`)에만 남아 섞이지 않는다. 실행 중의 모양이 하나여야 저장·호스트·비교가 맞고, 조용히 거짓이 되는 비교는 `check`가 잡는다. 사례(일반 지식): Minecraft는 `namespace:path`에 경로 안을 `/`로 나누고, 명령에서 짧게 쓴 `stone`도 읽는 순간 `minecraft:stone`이 되어 실행 중·저장(NBT)에는 전체 이름만 있다. RimWorld는 문자열 defName을 XML을 읽을 때 한 번 풀고 C#에서는 Def 객체를 비교한다. Def 전용 값이 문자열과 비교할 때 모드 기준으로 푸는 안은 같은 `"Sloop"`이 어느 모드 코드냐에 따라 달라지고 사전·`in`·정렬마다 특례가 들어서 고르지 않았다.

**상태:** 확인

**바뀜:** 엔진 바깥에서 들어오는 이름(명령 인자, 호스트 C# API, 저장 파일)은 짧은 이름을 풀지 않고 전체 이름만 받는다 → G264. 스크립트 안의 풀이는 그대로다.
