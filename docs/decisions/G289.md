**위치:** S9 "왜?" 도구 (5) 단계 순서 덤프의 CLI 진입점 (G80에서 이어서, handoff "남은 일" 3번)

**무엇이 비어 있었나:** spec S9는 단계 순서 덤프에 담을 것(신호별 최종 단계 순서, 각 단계의 핸들러와 선언 모드, 순서를 정한 `after`/`before`와 동률 규칙)만 적었다. 어떻게 부르고 어떤 모양으로 내는지, `@when` 반응도 담는지가 없었다.

**어떻게 정했나:**
- 새 명령 `engine stages <mods-dir> [--host <file>]`. G80의 "왜? 도구는 각자 명령"을 따른다.
- stdout에 사람이 읽는 텍스트를 낸다.
  - 단계 순서와 동률 규칙(앞에 올 수 있는 단계가 여럿이면 id 서수순).
  - 각 단계 앞에 오게 한 `after`·`before`와 그것을 적은 위치.
  - 신호별로 단계마다의 핸들러와 그 위치. 순서 규칙(단계 → 로드 순서 → 정의 순서, `stage=` 없는 것은 맨 뒤)을 머리에 적는다.
  - `@when` 반응을 같은 모양의 한 절로.
- 진단은 stderr에 G79 텍스트로, 종료 코드는 G78. 오류가 있어도 살아남은 모드로 낸다(G80과 같다).
- JSON(`--json`)은 필요한 사례가 생기면 더한다.

**이유:** 순서 문제를 찾을 때 사람이 눈으로 보는 도구라 텍스트가 먼저다. `dump`의 JSON에 넣으면 한 명령의 출력이 여러 목적을 갖게 되고 읽기 어렵다(G80의 이유와 같다). `@when`도 같은 단계 규칙을 따르므로(S5) 빼면 순서가 궁금한 반응 하나가 도구 밖에 남는다.

**상태:** 확인
