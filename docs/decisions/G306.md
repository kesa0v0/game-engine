**위치:** S2 이름 쓰는 원칙: 로직 안에서 스키마 이름(Def 타입·컴포넌트·신호)을 맨 이름으로 (spec S2 "Def 참조는 문자열", G108·G134·G192·G230·G305 보강)

**무엇이 비어 있었나:** spec S2와 schema-design 3절은 언어를 Starlark 계열로 정하고 "Def 참조는 문자열 + 스텁"이라고 했다. 그 결과 로직 안에서 타입·컴포넌트를 가리키는 자리가 문자열이 되었다(`query("City")`, `defs("City")`). 그런데 스텁에서는 Def 타입이 클래스이고(`Ref[City]`, G72·G207), 신호는 이미 맨 이름이며(`@on(Sunk)`), 컴포넌트 이름은 로직 안에서 생성자 값이다(G134·G230). 에디터가 보는 세계(클래스)와 실행이 어긋나 "어디는 이름, 어디는 문자열"로 보였고, 문자열에는 정의로 가기·이름 바꾸기가 되지 않았다. Def 타입 이름만 로직 안에서 로드 시점 이름이라 쓸 수 없었다(G108, `EVL001`). 후보는 (A) 지금 그대로 모두 문자열, (B) 스키마 이름은 맨 이름이고 Def id는 문자열, (C) 클래스 선언으로 바꿈(schema-design 3.1에서 버린 길)이었다.

**어떻게 정했나:** **(B).** 원칙은 셋이다.

1. **이름을 지을 때(선언)는 문자열:** `component("At", ...)`, `deftype("City", components=["Research"])`, `ref("City")`, `City("Atlanta", ...)`의 id. 스키마 파일 안의 다른 타입 이름도 뒤에서 정의될 수 있어 문자열로 남는다(파이썬 타입 힌트의 forward reference와 같은 이유).
2. **이미 있는 스키마 이름을 로직에서 쓸 때는 맨 이름:** `defs(City)`, `query(Unit, Wounded)`, `@on(Sunk)`. 로직 안에서 Def 타입 이름은 **부를 수 없는 타입 값**이 된다(부르면 `spawn`을 쓰라는 오류, Def 선언 `City(...)`는 Def 파일 맨 위에서만). 이름 찾기는 G230과 같다(지역 → 모드 이름 → 보이는 스키마 이름 → 내장).
3. **Def id는 언제나 문자열:** `spawn("brink:Santiago")`, `defid("Atlanta")`, `defdata(k)`. 수가 많고 `:`·`/`가 들어가 파이썬 이름이 될 수 없으며 모드 이름 공간이 있다(G258~G261). 데이터의 키다.

스텁은 `query`·`defs`를 클래스로 받게 적어(`type[City]`) pyright가 결과 타입을 클래스에서 안다. **남은 것:** 문자열 표기를 계속 받을지, 보기 정책 `may_see`의 `component` 인자의 모양, 멈춘 Flow가 든 타입 값의 저장.

**이유:** 파이썬은 클래스를 값으로 넘긴다(`isinstance(x, City)`, SQLAlchemy `session.query(City)`, 일반 지식). 신호는 이미 이렇게 쓰고 있었고, 스텁이 보여 주는 세계와 실행이 맞는다. 기준이 "식별자인 스키마 이름인가, 데이터 키인 Def id인가"로 설명하기 쉽다. 패러독스 스크립트는 모두 따옴표 없는 이름이고, RimWorld는 C#에서 타입은 클래스·Def는 `defName` 문자열(자주 쓰는 것은 `ThingDefOf`)이다(일반 지식). (C)는 2026-10-13 실험에서 `Health: Health` 충돌로 버렸고 Def id 문제도 남는다.
