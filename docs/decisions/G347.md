**위치:** G328·G343에서 이어서: 로컬 UPM 패키지를 놓을 곳과 빌드한 DLL을 넣는 법

**무엇이 비어 있었나:** G328이 "저장소 안의 로컬 UPM 패키지, `dotnet build`가 DLL을 `Plugins/`로 복사, Unity 연결부는 패키지 안의 소스와 asmdef"를 정했고 자리는 구현 때 정하기로 했다. G343은 복사할 DLL이 하나 늘고 G345가 경계만 참조하는 `Kesa.Engine.Ui`를 정했다.

**어떻게 정했나:** **저장소 안 `hosts/unity/`에 패키지와 복사용 프로젝트를 둔다.**

- 패키지 폴더는 `hosts/unity/uk.kesa.engine.unity/`다(`package.json`, `Runtime/`의 asmdef와 C# 소스). 다른 호스트가 생기면 `hosts/` 아래에 형제로 둔다. `src/`는 .NET 프로젝트만 두기로 한다.
- `hosts/unity/Kesa.Engine.Unity.Plugins.csproj`는 코드가 없는 프로젝트로 커널·경계(`Bridge`)·같은 프로세스 구현(`Bridge.Local`)·번역(`Text`)·`Ui`를 참조하고, `dotnet build`가 끝나면 빌드 출력의 DLL(Linguini 포함)을 패키지의 `Plugins/`로 복사한다. 솔루션에 넣어 루트 `dotnet build`가 복사까지 한다.
- `Bridge.Local`은 같은 프로세스 구현이라 커널이 Unity에 들어가는 한 함께 둔다. 원격 호스트가 생기면 그때 뺀다.
- `Plugins/`의 복사본은 git에 올리지 않는다(`.gitignore`). 결정론 분석기를 거친 빌드만 Unity에 들어간다는 G328의 약속을 지키고, 바이너리가 저장소에 쌓이지 않게 한다. Unity가 만드는 `.meta`도 올리지 않는다.
- 게임은 이전처럼 `manifest.json`에 `file:` 경로로 쓴다.
- 정하지 않았다: 런타임에 USS 글을 `StyleSheet`로 읽는 법(Unity에 공개 API가 없고 이전 엔진은 직접 파서 `RuntimeStyleSheet`를 만들었다), 이미지 파일 읽기 방식의 세부, 데모 씬.

**이유:** 사용자가 고른 대로다. 복사본을 올리는 대안은 Unity 팀원이 빌드 없이 쓸 수 있으나 바이너리가 쌓이고 분석기를 거치지 않은 DLL이 섞일 수 있다.
