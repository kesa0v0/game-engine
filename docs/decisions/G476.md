**위치:** G475의 2단계. 값을 배열에 어떻게 놓을지가 비어 있었다.

**어떻게 정했나 (사용자가 고름):** Def 표와 곁표(A). 컴포넌트마다 표(B, EnTT 방식)와 조합마다 표(C, 아키타입, Unity DOTS·Flecs 방식)를 비교했다. DB로 말하면 A는 Def별 테이블에 선택 항목만 별도 테이블로 뺀 것, B는 끝까지 나누고 늘 JOIN하는 것, C는 상태가 바뀌면 행이 다른 테이블로 옮겨 가는 것이다. 모드가 보는 모습은 셋 다 같고 물리 배치만 다르다.

**이유:**

- 한 엔티티의 값이 같은 줄 번호라 묶음 API와 Burst에 배열을 그대로 넘길 수 있다(engine-improvements 15번).
- 줄이 옮겨 가지 않아 Def 표의 순서가 이력을 따르지 않고, 훑는 중에 컴포넌트를 붙여도 줄이 사라지지 않는다. C는 이 두 가지가 주요 칼럼에도 생겨 계약에 비용을 남긴다.
- 빈도를 짐작하지 않는다. 동적 부착은 실제 사례가 있고(Quarantined의 상태 태그) 앞으로의 빈도는 모른다. 거의 모든 컴포넌트를 나중에 붙이는 게임이면 모든 값이 곁표로 가 B와 비슷한 구조가 되는 것으로 보고, 그것이 A의 나쁜 쪽 한계라고 본다. 실제 구현에서 재 보지 않은 판단이다.

**시제품 값 (엔티티 1만 개, 칸은 `long`, 검사·도장·되감기 없음, .NET 9):** 함께 훑기 A 0.4ns, B 약 1ns, 지금 구조 약 10ns. 사전으로 id 읽기 A 4~5ns, B 4ns, 지금 구조 14ns. 곁표 붙이고 떼기 약 20ns인데 지금 엔진의 한 쌍은 324ns다.

**남는 약점:** Def 칸과 곁표 칸을 함께 훑으면 약 4ns로 같은 표일 때의 10배다. 묶음 API는 표 하나가 아니라 배열 묶음을 여러 번 내주는 모양으로 정해 나중에 곁표를 표 안으로 합칠 길을 남긴다(3단계에서 묻는다).
