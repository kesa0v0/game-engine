**위치:** G343에서 이어서: 해석기와 렌더러 사이의 인터페이스

**무엇이 비어 있었나:** G343은 해석 어셈블리와 렌더러 인터페이스를 두기로 했을 뿐 모양을 정하지 않았다. 후보는 요소 핸들을 쓰는 작은 명령형과 해석기가 완성된 트리를 만들고 렌더러가 차이를 받는 방식이었다.

**어떻게 정했나:** **요소 핸들을 쓰는 작은 명령형이다.**

- 어셈블리는 `src/Kesa.Engine.Ui`(`netstandard2.1`, C# 9, 결정론 분석기 적용)이고 경계(`Bridge`)만 참조한다. G343이 적은 번역(`Text`) 참조는 하지 않는다: 값을 글자로 바꾸는 일은 호스트가 주입한다(번역기는 커널을 끌고 오기 때문). 호스트가 `Translator.Value`를 꽂는다.
- 렌더러는 요소를 핸들로 가리키며 만들고, 속성을 넣고, 클래스를 붙이고 떼고, 옮기고, 없애고, 클릭을 받는다. 판단은 모두 해석기가 하고 렌더러는 변환이 끝난 값만 받는다: 글자, 참거짓, 숫자(고정소수점의 원래 정수값, 실수로 바꾸는 것은 Unity 렌더러가 화면에 쓸 때, G326), 이미지 경로(G341·G335).
- 만들 때 UXML에 직접 적은 고정 속성(`name`, `class`, `text`, `style`, `<Style src>`)도 렌더러에 전달한다.
- 해석기는 비동기 순환(G327)을 가진다: 한 파일을 한 자리에 올리고, 갱신 때 `Changed()`가 알린 키만 다시 부르고, `Version()`이 움직였으면 버튼을 다시 `Check`한다. 이 어셈블리가 낸 화면 동작은 UI 기록을 바꾸지만 `Version()`은 움직이지 않으므로 낸 뒤에도 버튼을 다시 확인한다.
- 영수증 키는 패널·요소 경로·항목 키·속성으로 만들어, 반복이 항목을 없앨 때(G339) `Unbind`할 수 있게 한다.
- 정하지 않았다: 렌더러 메서드의 정확한 이름과 시그니처(구현하며 정한다), 여러 값을 가진 이벤트, 키보드 입력.

**이유:** 해석기가 이미 정한 갱신 방식(`Changed()`가 알린 키만 다시 부름, 키로 짝짓기)을 그대로 쓰고 작게 시작해 시험하기 쉽다. 가상 트리를 따로 만들면 키 짝짓기와 영수증 갱신이 그 안에서 한 번 더 돌아야 한다.

**상태:** 확인
