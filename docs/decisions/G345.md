**위치:** G343에서 이어서: 해석기와 렌더러 사이의 인터페이스

**무엇이 비어 있었나:** G343은 해석 어셈블리와 렌더러 인터페이스를 두기로 했을 뿐 모양을 정하지 않았다. 후보는 요소 핸들을 쓰는 작은 명령형과 해석기가 완성된 트리를 만들고 렌더러가 차이를 받는 방식이었다.

**사용자가 고른 것:** **요소 핸들을 쓰는 작은 명령형이다.**

- 렌더러는 요소를 핸들로 가리키며 만들고, 속성을 넣고, 클래스를 붙이고 떼고, 옮기고, 없애고, 클릭을 받는다. 판단은 모두 해석기가 하고 렌더러는 변환이 끝난 값만 받아 시키는 대로 한다.

**구현하며 제가 정한 것(사용자 확인 전):**

- 어셈블리 이름은 `Kesa.Engine.Ui`(`src/Kesa.Engine.Ui`, `netstandard2.1`, C# 9, 결정론 분석기 적용)다.
- (사용자가 확인함) 어셈블리는 경계(`Bridge`)만 참조한다. G343이 적은 번역(`Text`) 참조는 하지 않고 값을 글자로 바꾸는 일은 호스트가 주입한다(번역기가 커널을 끌고 오기 때문). 호스트가 `Translator.Value`를 꽂는다. 원격 호스트가 생기면 꽂는 함수가 경계 너머에 묻게 바꾼다.
- (사용자가 확인함) 숫자 속성은 고정소수점의 원래 정수값(`BridgeFixed.Raw`, `long`)으로 렌더러에 가고 렌더러가 `BridgeFixed.Scale`로 나눈다. 실수로 바꾸는 것은 Unity 렌더러가 화면에 쓸 때다(G326).
- 만들 때 UXML에 직접 적은 고정 속성(`name`·`class`·`text`·`style`)과 `<Style src>`를 렌더러에 전달한다.
- 해석기는 비동기 순환(G327)을 가진다: 한 파일을 올리고, 갱신 때 `Changed()`가 알린 키만 다시 부르고, `Version()`이나 `UiVersion()`이 움직였거나 영수증 키가 하나라도 바뀌었거나 이 해석기가 동작을 냈으면 버튼을 다시 `Check`한다. (사용자가 확인함) 화면 동작은 UI 기록만 바꾸고 `Version()`은 움직이지 않으므로 경계가 연결마다 UI 기록 도장 `UiVersion()`을 준다. 호스트가 세션에 직접 동작을 내도 알릴 것이 없다. `ActAsync`는 내고 바로 화면을 맞추는 편의다.
- 영수증 키는 패널 번호·요소 경로·항목 키·속성으로 만든다. (사용자가 확인함) 한 세션에 해석기를 여럿 둘 수 있고 호스트는 따로 할 일이 없다: 해석기마다 세션 안의 번호를 키 앞머리로 받아 영수증이 겹치지 않는다.
- 만들 수 없는 문서(없는 함수·이름, 모르는 `params`, 없는 `Include`)는 올리기 전에 모두 모아 알리고 아무것도 만들지 않는다.
- 정하지 않았다: 렌더러 메서드 이름의 최종형(구현에 있는 것이 현재 안), 여러 값을 가진 이벤트, 키보드 입력.

**이유:** 해석기가 이미 정한 갱신 방식(`Changed()`가 알린 키만 다시 부름, 키로 짝짓기)을 그대로 쓰고 작게 시작해 시험하기 쉽다. 가상 트리를 따로 만들면 키 짝짓기와 영수증 갱신이 그 안에서 한 번 더 돌아야 한다.

**상태:** 잠정
