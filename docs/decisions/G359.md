**위치:** 모드가 UI 모양을 바꾸는 법(이미지는 G335)

**무엇이 비어 있었나:** UXML의 `<Style src>`는 게임의 읽기(`Resources.Load` 등)로만 찾아서 모드 폴더의 USS는 쓰이지 않았다. Unity는 USS 글을 `StyleSheet`으로 바꾸는 파서를 에디터에만 두어 실행 중에는 공개 API가 없다. 이전 게임(Quarantined·TurbulentRepublic)은 USS 35개를 모드 폴더에 두었고(`:hover` 32곳, 자손 선택자 27곳, `var()` 68곳, `transition` 13곳), 이전 엔진은 정규식으로 읽어 요소마다 인라인 스타일로 박고 마우스 이벤트마다 다시 계산했다. 자손 선택자는 적용되지 않았다.

**어떻게 정했나:** **모드도 USS를 주고, 진짜 StyleSheet으로 만든다.**

- 모드 폴더의 USS는 이미지와 같은 공유 가상 경로로 찾는다. 같은 경로는 로드 순서가 나중인 모드가 이긴다(G335). 게임이 에셋으로 주는 스타일시트도 그대로 쓴다.
- 문법 읽기(규칙, 선택자, 선언, 주석, `var()`), 지원 범위, 진단은 `Kesa.Engine.Ui`에 둔다. 호스트와 무관하고 `dotnet test`로 시험한다. 범위 밖 문법은 버리지 않고 진단으로 알린다.
- Unity 호스트는 읽은 결과를 Unity의 공개되지 않은 `UnityEngine.UIElements.StyleSheets.StyleSheetBuilder`(런타임 DLL에 있음)에 리플렉션으로 넘겨 `StyleSheet`을 만들고 `styleSheets`에 붙인다. 캐스케이드, 우선순위 적용, 상태(`:hover` 등), 자손·자식 선택자, `var()`, `transition`은 Unity가 처리한다.
- 빌더 연결과 값 변환(치수, 색, 키워드, 함수)은 OneJS(`Singtaa/OneJS`, MIT)의 `StyleSheetBuilderWrapper.cs`·`UssCompiler.cs`를 참고해 옮기고, 옮긴 파일 머리와 고지 파일에 MIT 고지를 남긴다. OneJS의 JS·React 부분과 ExCSS DLL은 들이지 않는다.
- Unity 6000.3.8f1에서 시제품으로 확인했다: 빌더로 만든 시트가 런타임 패널에서 클래스, 자식(`>`)과 손자 구분, `:root`의 `var()`, `.card:hover .name`을 맞게 적용했다.
- 정하지 않았다: 약속하는 문법 범위와 속성 목록, 진단 코드, 모드 시트와 게임 시트의 순서, `url()`·`resource()`의 경로, IL2CPP의 `link.xml`.

**이유:** 고른 것: 엔진이 읽고 Unity가 만든다(이것, A2), OneJS의 파일과 ExCSS DLL을 그대로 넣는다(A1: 빠르나 파서와 진단이 Unity 쪽에만 있고 외부 DLL이 는다), 모더가 Unity로 에셋번들을 구워 온다(텍스트만 고치는 다른 모드 파일과 결이 맞지 않음), 우리 캐스케이드를 만들어 인라인으로 박는다(Unity가 가진 것을 다시 만들고 `transition` 등이 남음). 공개되지 않은 API라 Unity를 올리면 깨질 수 있다(OneJS도 Unity 6.5에서 `resource()` 경로를 고쳤다). 리플렉션은 한곳에 모으고 Unity 판을 고정하며 창 없는 확인으로 잡는다. React를 들이는 OneJS 전체는 모드 UI 언어(G330)를 바꾸고 모드에 임의 코드 실행을 주므로 맞지 않다.
