---

**위치:** S2 "함수 정의(재귀 금지)"와 G102 "재귀는 금지한다"

**무엇이 비어 있었나:** 체스 같은 탐색 봇(minimax), 트리 훑기, 나눠 풀기는 재귀가 자연스러운데 S2가 막았다. 막은 이유는 끝없는 재귀가 C# 스택을 넘쳐 프로세스를 죽이는 것이었다. 끝없는 반복은 이미 단계 예산(G101)이 끊으므로, 재귀도 깊이만 따로 막으면 된다.

**어떻게 정했나 (사용자가 재귀를 열고 상한은 모드가 정하기로 고름):**

```python
patch.set("engine:Rules", "max_call_depth", 250)
```

- 직접 재귀의 로드 오류와 실행 중 "같은 함수가 호출 사슬에 있음" 오류를 없앤다. 입구(즉시 핸들러 등, `@wrap`은 빼고)가 자기 안에서 다시 도는 것은 G310대로 `RUN014`.
- 깊이는 한 `PureEvaluator` 안에서 지금 도는 실행들의 프레임 수 합이다. 식 안의 호출과 문장 호출을 똑같이 센다(어디서 걸리는지가 쓴 모양에 달리지 않게). 고정된 수라서 결정론적이다(스택 남은 양을 보지 않는다).
- 넘으면 `RUN024`: `calls went deeper than 200: … -> f -> f`(사슬은 끝 6개). 흔적(G105)은 안쪽 10단, `... N more calls`, 바깥 5단.
- 값은 1 이상 300 이하(넘으면 `VAL003`). 천장은 엔진 상수다.

**잰 값 (벤치 `--stack`, 호출 한 단의 C# 스택):**

| 경로 | Release | Debug |
|---|---:|---:|
| 식 안의 호출 | 615 B | 2119 B |
| 문장 호출(대입 오른쪽) | 0 | 0 |
| 커맨드에서 시작한 식 재귀 | 624 B | 2128 B |
| `@wrap` 안에서 대상을 이름으로 | 720 B | 2320 B |

Unity로 복사되는 DLL은 기본 Debug 빌드이고, 스레드 스택은 흔히 1MB다. 천장 300은 Debug로 약 700KB, 기본 200은 약 460KB다. IL2CPP와 Unity 메인 스레드의 실제 스택은 재지 않았다.

**숫자 (사용자가 고름):** 기본 200, 천장 300. 탐색(minimax 4~20), 트리·봉신 사슬(5~30), 나눠 풀기(약 30)는 들어가고, 깊이가 데이터 길이를 따라가는 재귀(격자 DFS, 리스트를 하나씩)는 반복문으로 써야 한다. 천장을 크게 올리는 길은 식 안의 호출도 문장 호출처럼 C# 스택 없이 프레임만 쌓게 실행기를 고치는 것이고, 뒤의 슬라이스로 미뤘다. 큰 스택의 전용 스레드에서 돌리는 길은 커맨드마다 스레드를 넘나드는 비용과 Unity 메인 스레드 문제로 버렸다.

**고친 결함:** 문장·식 노드가 오류에 위치를 붙이려고 `catch { Attach; throw; }`로 다시 던지면, 깊은 재귀에서 되돌아오며 단마다 예외 처리 틀이 스택에 쌓여 100단에서도 넘쳤다. 예외 필터(`when`)로 붙이고 잡지 않게 바꿨다. 필터는 안쪽 `finally`보다 먼저 돌므로, 중첩 `derived` 경계 줄은 목록 길이 대신 들어올 때 정한 값으로 판단한다.

**이유:** 엔진은 모드가 게임 로직이므로 깊이 상한도 게임의 성질로 모드가 정한다(G451). 천장은 프로세스가 잡을 수 없이 죽는 것을 막는 엔진의 몫이다. 더 깊은 탐색은 반복과 리스트(명시적 스택)로 쓰면 깊이 제한이 없다.
