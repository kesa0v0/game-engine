**위치:** G362에서 이어서: UI Builder가 저장하는 경로

**무엇이 비어 있었나:** 모더가 Unity 프로젝트의 `Assets/` 안에서 UI Builder로 화면을 만들면 `<Style src>`가 `project://database/Assets/…/screen.uss?fileID=…&guid=…&type=3#screen` 같은 경로로 저장된다. G362·G363의 공유 가상 경로와 맞지 않아 그냥 "찾을 수 없음"이 됐다. 이전 세 게임의 UXML 81개, `src` 107곳은 모두 모드 안의 경로였다(UXML이 Unity가 가져오지 않는 `StreamingAssets/…/Mods` 아래에 있어 손으로 썼다).

**어떻게 정했나:** **모드 경로만 받고, 다른 모양이면 무엇이 틀렸는지 알린다.**

- `project://`처럼 `://`가 든 것, `/`·`\`나 드라이브(`C:`)로 시작하는 절대 경로, `..` 조각, `?`·`#`이 붙은 것은 모드 경로가 아니다.
- 이런 경로는 바꾸어 찾지 않는다. 진단이 "Unity 프로젝트 경로(UI Builder가 쓰는 모양)다, 모드 안의 경로(`ui/screen.uss`)로 쓰라"고 알린다.
- 무게는 그 자리의 원래 규칙을 따른다: `<Style src>`와 `url()`은 화면을 막지 않고(G364) 그 시트나 선언만 빠지며, `Include`는 다른 UXML 문제처럼 화면을 막는다.

**이유:** 고른 것: 모드 경로만 받고 진단(이것), `project://` 경로의 앞부분을 떼어 가며 모드 공간에서 맞는 파일을 찾기(UI Builder 파일이 그대로 돌지만 추측이라 다른 모드의 같은 이름 파일에 잘못 맞을 수 있고 모드를 둔 폴더에 따라 결과가 달라짐), UXML 기준 상대 경로도 받기(G362·G363의 "시트 기준 상대 경로가 아니다"를 뒤집고 경로 규칙이 둘이 됨). 이전 게임이 모드 경로로만 일했고, 잘못 맞을 위험이 없고, 진단 한 줄로 고칠 수 있다. UI Builder로 일하는 모더가 많아지면 UI Builder 경로를 모드 경로로 바꾸는 도구를 따로 둘 수 있다.
