**위치:** G328·G330에서 이어서: UXML 해석 코드를 어디에 두는가 (G332가 열어 둔 식 파서의 자리를 넓힘)

**무엇이 비어 있었나:** G330~G342로 UXML의 규칙(`bind-*`·`on-*`·`for`·`params`·`Include`·`seat`, 식 문법, 이름 범위, 키 짝짓기, 타입 변환, `Check`)이 쌓였다. 이전 엔진의 `UIInterpreter`(958줄)·`UIBinder`(1117줄)·`UIRepeater`(274줄)는 XML 읽기·바인딩 규칙·반복 짝짓기와 `VisualElement`를 만들어 값을 넣는 일이 Unity 타입과 섞여 있어, 시험하려면 Unity가 필요했다(`UIRepeaterTester`).

**어떻게 정했나:** **그리지 않는 부분을 엔진 무관한 어셈블리로 뺀다.**

- `netstandard2.1`의 작은 어셈블리가 UXML 텍스트 읽기, 속성 분류, 식 파서, 변수 이름 범위 검사, 로드 때 오류 잡기, 리스트 항목 짝짓기 계산, 타입 변환의 값 판정을 맡는다. 경계(`Bridge`)만 알고 Unity를 모른다 (번역은 G345에서 주입으로 바뀜).
- 이 어셈블리는 "이 요소를 만들어라, 이 속성에 이 값을 넣어라, 이것을 없애라"를 **렌더러 인터페이스**로 알린다. Unity 패키지는 이 인터페이스의 구현(`VisualElement`를 만들고 값을 넣고 이벤트를 잇는 일)만 가진다.
- **시험용 렌더러**가 메모리에 요소 트리를 만든다. 규칙은 이것으로 `dotnet test`에서 시험한다. 렌더러가 둘이라 인터페이스가 Unity에만 맞게 굳는 것을 막는다.
- 콘솔 호스트가 UXML을 읽어 글자로 그리는 것(`ui/console.txt` 대체)은 하지 않는다. 필요해지면 그 위에 렌더러를 더한다.
- 이 어셈블리가 Unity 패키지의 `Plugins/`로 복사되는 DLL과 asmdef 참조에 더해진다(G328은 경계와 번역만 참조한다고 했다).
- 정하지 않았다: 어셈블리 이름, 렌더러 인터페이스의 모양, 시험용 렌더러가 보일 트리의 형식.

**이유:** 셋 중 고른 것: 어셈블리 + 시험용 렌더러(이것), 어셈블리만(시험을 어셈블리 단위로만 하나 렌더러가 하나라 인터페이스가 Unity에 맞게 굳기 쉬움), 어셈블리 + 콘솔이 UXML을 읽음(UI 규칙 전체를 실제로 돌려 보나 콘솔의 버튼을 메뉴로 바꾸는 설계가 새로 생기고 콘솔 테스트가 기대하는 출력과 어긋나 일이 큼). 이 엔진은 호스트와 무관한 규칙을 `dotnet test`로 시험하는 것이 기본이다. 규칙이 열한 개 넘게 쌓인 UI를 Unity 테스트 러너 없이는 못 시험하는 구조는 피한다.

**상태:** 확인

**바뀜:** 어셈블리는 번역(`Text`)을 참조하지 않고 경계만 안다. 값을 글자로 바꾸는 일은 호스트가 주입한다 → G345.
