**위치:** S1 패치 대상의 보이는 범위

**무엇이 비어 있었나:** 패치 대상 Def가 보이는 범위(필수 의존의 닫힘, 4.3) 밖에 있을 때, 그리고 `optional` 모드의 Def를 패치할 수 있는지가 비어 있었다.

**어떻게 정했나:** 패치 대상이 될 수 있는 범위는 보이는 범위(자기 모드 포함)에 `optional`로 직접 선언한 모드를 더한 것이다. `loadAfter`만 걸린 모드는 범위 밖. 이름을 여는 곳은 패치 호출의 대상 id와 필드 경로 문자열뿐이고, Def 리터럴·스키마·`.pyi`의 보이는 범위는 그대로 닫혀 있다. 없는 id는 "대상 없음 + 혹시 …?", 있지만 범위 밖이면 별도 오류 + "`dependencies`에 선언하세요"(그 Def가 있는 모드 id를 `related`로). `optional` 모드의 Def를 가리키는 패치는 **`if mod_loaded("그 모드"):`의 참 가지 안에서만** 쓸 수 있다(G46). 가드 밖이면 오류("`if mod_loaded("m"):`로 감싸세요")이고, 모드가 없어 id가 미등록이면 가드 밖의 미등록 id는 원래 오류라서, 호출의 유효성이 설치 상태에 따라 달라지지 않는다. 가드가 거짓이면(설치 안 됨, 또는 로드 실패 G8) 그 가지는 실행·검사하지 않고(모양 검사도 못 함, 문법 검사만), 가지 안의 `patch.*` 호출 수를 구문에서 세어 모드당 한 건의 정보 진단 "`other_mod`가 없어 패치 N건 적용 안 함"을 남긴다. 가드가 참이면 G36·G39를 그대로 전부 검사한다. 선택 모드와의 `set` 충돌은 `optional`이 순서 관계에 들어가므로 G37대로 경고 + 나중이 이김. **열린 점:** `check`가 선택 모드를 모두 설치한 것으로 놓고 검사하는 실행 방식은 `check` 출력 스키마 때 정한다(기본은 설치된 모드 집합). → G85에서 닫음: 옵션 없이 설치된 모드 집합만 검사한다. 가드가 거짓이면 그 안의 대상 id 오타는 못 잡는다(`mod_loaded`의 모드 id 오타는 선언 검사가 잡음).

**이유:** 실제 모딩에서 호환 패치를 같은 모드 안에 조건 블록으로 두는 것이 보통이고(RimWorld `PatchOperationFindMod` 등), 별도 호환 모드를 요구하면 모더 부담이 크다. 대상 모드를 `mod=` 키워드로 표시하는 방식(문제 2의 A)보다 가드가 여러 패치를 한 번에 묶고 같은 `if`를 나중에 패치 밖에도 쓸 수 있어 채택했다. 패치 문자열 한 자리만 여는 좁은 결정이라 spec이 ❓로 남긴 "optional 대상의 이름을 쓰는 방법"을 앞지르지 않고, 나중에 넓혀도 기존 모드가 깨지지 않는다. 건너뜀을 조용히 두지 않으려고 정보 진단을 남긴다(경고로 하면 호환 패치를 가진 모드마다 노이즈).
