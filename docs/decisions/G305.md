**위치:** S2·S4 스크립트가 한 Def 타입의 Def를 모두 도는 길 (판데믹 확장 모드 `brink`에서 드러남)

**무엇이 비어 있었나:** 확장 모드가 `City` Def를 더하고 기존 도시의 이웃을 패치로 이어도, 코어의 판 깔기는 스크립트에 박은 도시 이름 목록만 돌아 새 도시의 엔티티가 생기지 않았다(임시 시험으로 재현: 도시 12개 그대로, 보고타가 엔티티 없는 도시와 이웃). `query`는 이미 있는 엔티티만 돈다. G70은 "런타임이 타입의 모든 Def를 순회할 때 abstract를 뺀다"를 전제했지만 스크립트에서 부를 길이 없었다. 후보는 (A) 내장 함수로 타입의 Def id 목록, (B) 엔진은 그대로 두고 코어가 목록 `const`를 두어 확장이 `patch.append`로 더함(지금도 됨, 잊으면 조용히 빠짐), (C) 둘 다였다.

**어떻게 정했나:** **(A).** 내장 **`defs("City")`**가 그 타입의 Def들의 전체 id 목록(`list[str]`)을 준다.

```python
for name in defs("City"):
    spawn(name)
```

- 순서는 모드 로드 순서, 그 안에서 등록 순서(결정론).
- `abstract` Def는 빠진다(G70과 같음).
- 부른 모드가 의존하지 않는 모드의 Def도 나온다(`query`가 어느 모드의 엔티티든 주는 것과 같다). 코어가 확장의 도시를 받아야 하기 때문이다.
- 타입 이름이 리터럴이면 로드 때 검사해 없는 타입은 오류("혹시 …?").
- (B)는 엔진이 막지 않으므로 모드가 고른 일부를 다룰 때 그대로 쓸 수 있다.

**이유:** RimWorld의 `DefDatabase<T>.AllDefs`가 이것이고, 모드들이 "모든 무기 Def"를 늘 돈다(일반 지식). 타입의 전부를 따로 적은 목록으로 관리하면 확장이 빠뜨려도 아무도 모른다.

**상태:** 확인

**바뀜:** 타입 이름은 문자열이 아니라 맨 이름으로 준다(`defs(City)`) → G306.
