**위치:** G330에서 이어서: 창을 열고 닫는 일의 소속과 모양

**무엇이 비어 있었나:** 이전 게임의 `ui-action` 51곳은 대부분 `OpenWindow`·`CloseWindow`·`ToggleWindow`(창 이름 `Window_Settings` 등)였고, 이전 엔진의 `WindowManager`(레이어 5단, 열린 창 목록, ESC 닫기 스택, 드래그)가 호스트에서 처리했다. 새 엔진은 창의 열림이 시뮬레이션 밖의 화면 상태라는 점만 정해져 있었다. 다른 사례는 UI 쪽 상태라는 데 모이고 소유자만 갈린다(일반 지식, 세부 미확인): RimWorld `Find.WindowStack`과 WoW `Frame:Show()`는 UI 프레임워크가, CK3 UI 로컬 변수와 웹 앱의 `isOpen` 상태는 스크립트나 앱이 쥔다.

**어떻게 정했나:** **창은 별도 개념이 아니라 UI 기록에 묶은 패널이다.**

- 창의 열림 여부는 모드가 선언하는 UI 기록(G277)에 두고, 창 패널의 보임을 `bind-display`(G331)로 묶는다. 열고 닫는 일은 `@ui_action`이 UI 기록을 바꾼다(G276·G278). 클릭은 `on-click`(G336)이다. 호스트에는 `OpenWindow`류 전용 동작이 없다.
- **하나만 열 때:** 값 하나(예: 정보창이 보이는 유닛, 없으면 닫힘)에 묶고 패널은 UXML에 하나만 둔다. 다른 유닛을 클릭하면 값이 바뀐다. 서로 닫히는 묶음도 스크립트가 값 하나로 만든다.
- **하나만 열지 여럿을 열지는 모드가 정한다.**
- **창이 여럿일 때:** 각 창은 평범한 창이다(위치는 그 창 요소가 가진다). 창의 수가 UXML을 쓸 때 정해지지 않으면(엔티티 N개를 골랐으면 창 N개) 템플릿에서 만들어야 하고, 그 "템플릿에서 N개 만들기"는 repeater(G330)의 일이다. 끌기와 맨 위로 올리기는 repeater가 아니라 각 창 요소의 동작이다(이전 엔진은 71줄짜리 `PointerManipulator`로 제목줄에 붙임).
- 정하지 않았다: 끌기와 맨 위로 올리기를 UXML에서 적는 속성, 창을 닫았다 다시 열 때 위치를 기억할지, ESC로 맨 위 창 닫기와 모달·레이어(창 전체를 아는 쪽이 필요한 기능이다).

**이유:** 하나만 여는 창은 UI 기록과 `bind-display`만으로 되므로 호스트에 창 전용 동작이 필요 없다. 호스트가 창을 내장하는 방식(RimWorld·이전 엔진)은 호스트에 창 관리자와 창 요청이라는 새 경계 결과가 필요하고 스크립트가 열림 여부를 알 수 없어 택하지 않았다. UI 동작을 모드로 고칠 수 있게 한다는 기존 요구(G276)와도 맞는다.

**상태:** 확인
