**위치:** G330에서 이어서: 창을 열고 닫는 일의 소속과 모양

**무엇이 비어 있었나:** 이전 게임의 `ui-action` 51곳은 대부분 `OpenWindow`·`CloseWindow`·`ToggleWindow`(창 이름 `Window_Settings` 등)였고, 이전 엔진의 `WindowManager`(레이어 5단, 열린 창 목록, ESC 닫기 스택, 드래그)가 호스트에서 처리했다. 새 엔진은 창의 열림이 시뮬레이션 밖의 화면 상태라는 점만 정해져 있었다. 다른 사례는 UI 쪽 상태라는 데 모이고 소유자만 갈린다(일반 지식, 세부 미확인): RimWorld `Find.WindowStack`과 WoW `Frame:Show()`는 UI 프레임워크가, CK3 UI 로컬 변수와 웹 앱의 `isOpen` 상태는 스크립트나 앱이 쥔다.

**어떻게 정했나:** **창은 별도 개념이 아니라 UI 기록에 묶은 패널이다.**

- 창의 열림 여부는 모드가 선언하는 UI 기록(G277)에 두고, 창 패널의 보임을 `bind-display`(G331)로 묶는다. 열고 닫는 일은 `@ui_action`이 UI 기록을 바꾼다(G276·G278). 클릭은 `on-click`(G336)이다. 호스트에는 `OpenWindow`류 전용 동작이 없다.
- **하나만 열 때:** 값 하나(예: 정보창이 보이는 유닛, 없으면 닫힘)에 묶고 패널은 UXML에 하나만 둔다. 다른 유닛을 클릭하면 값이 바뀐다. 서로 닫히는 묶음도 스크립트가 값 하나로 만든다.
- **여럿을 열 때:** UI 기록의 목록에 항목을 더하고 repeater(G330)로 그린다. 목록의 마지막이 맨 위 창이라 "맨 위 닫기"와 겹침 순서가 목록 순서다. 죽은 엔티티는 목록을 읽을 때 빠지므로(G284) 그 유닛의 창이 사라진다.
- 어느 쪽을 쓸지는 모드가 정한다. 서브창은 부모 창 안에 중첩하면 함께 닫히고, 따로 끌려면 별도 최상위 창으로 둔다.
- 정하지 않았다: ESC로 맨 위 창 닫기와 모달·겹침 같은 창 시스템 기능을 호스트가 줄지(키 입력을 `on-<이벤트>`로 받아 스크립트가 처리하는 길도 있음), 끌어 옮긴 창의 위치와 크기를 호스트가 창 키별로 기억하는 법, 레이어. 첫 화면을 만들며 필요가 확인되면 정한다. 여럿을 열 때의 repeater 항목 대응 키는 repeater의 결정에 달려 있다.

**이유:** 셋 중 고른 것: UI 기록에 묶는 패턴(이것), 호스트가 창을 내장하고 모드가 열기를 요청(RimWorld·이전 엔진 방식: 호스트에 창 관리자와 창 요청이라는 새 경계 결과가 필요하고, 스크립트가 열림 여부를 알 수 없고, 모더가 창 규칙을 바꾸려면 C#을 만져야 함), 둘 다(단순한 열고 닫기는 이것, 창 시스템 기능은 호스트에 나중에 더함: 이 결정이 이후에 그렇게 넓힐 수 있게 열어 둠). 하나만 열기와 여럿 열기가 모드마다 다르므로 둘 다 새 장치 없이 표현되는 쪽이 맞다. 사용자의 기존 요구도 UI 동작을 모드로 고칠 수 있게 하는 것이었다(G276).
