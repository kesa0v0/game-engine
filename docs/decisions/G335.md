**위치:** G331에서 이어서: 모드 데이터가 이미지를 가리키는 법과 호스트가 파일을 찾는 법

**무엇이 비어 있었나:** 새 엔진에는 이미지나 자산에 관한 결정이 없었다. 이전 게임의 UXML은 이미지 바인딩이 20곳(`binding-image-vpath="Self.Icon"` 등)이었고, 값은 데이터가 가진 가상 경로(`vpath`)였다. 이전 엔진의 `AssetProvider`가 물리 경로와 가상 경로를 매핑해 모더가 자원을 교체하게 했다.

**어떻게 정했나:** **모드 전체가 공유하는 가상 경로, 나중에 로드된 모드가 이긴다.**

- 모드 데이터(Def의 칸, 모드 함수의 값)는 이미지를 문자열 경로로 말한다(`art/harbor/sloop.png`). 경로는 각 모드 폴더 안의 상대 경로다.
- Unity 호스트가 모든 모드 폴더(`BridgeContent`가 로드 순서대로 준다, G325)를 하나의 가상 경로 공간으로 겹친다. 같은 경로가 여러 모드에 있으면 로드 순서가 나중인 모드의 파일을 쓴다(패치의 규칙과 같은 원칙, G41).
- UXML은 `bind-image="모드.함수(…)"`로 `Image` 요소의 그림을 그 경로로 채운다(G331의 `bind-<요소 속성>`).
- 커널은 경로를 문자열로만 알고 파일이 있는지 보지 않는다. 파일을 찾고 읽는 일은 호스트 몫이다. 이 규칙은 Unity 호스트의 관례다.
- 모드는 자기 id를 딴 폴더 아래에 파일을 두라고 권한다(우연한 이름 충돌을 피함). 같은 경로를 일부러 쓰면 그것이 교체다.
- 정하지 않았다: 파일이 없을 때의 보임, `Image`가 아닌 요소의 배경 그림, 스프라이트 시트와 같이 한 파일 안의 일부를 가리키는 법, 그림 파일 종류와 읽기 방식.

**이유:** 셋 중 고른 것: 공유 가상 경로(이것), 모드 id를 앞에 붙인 경로(`harbor:art/sloop.png`: 어느 파일인지 분명하나 그림 교체 모드가 Def를 패치해 경로를 바꿔야 함), Def 이름 규칙으로 찾기(경로를 적지 않아도 되나 한 Def에 그림이 여럿이면 이름 규칙이 더 필요). 이전 엔진이 모더가 자원을 교체하게 하려고 고른 방식이고, 스킨만 만지는 사람이 데이터를 건드리지 않고 그림을 바꿀 수 있다. 패러독스 게임의 파일 겹치기도 같은 방식이다(일반 지식).

**상태:** 확인
