**위치:** G296에서 이어서: 선언 보너스가 키 컴포넌트 줄을 겨냥하는 표기

**무엇이 비어 있었나:** 키 컴포넌트 줄 안의 `derived`(`Skill[Medicine].eff`)도 기여 대상이지만, `contrib("Skill.eff", ...)`만으로는 어느 줄인지 적을 수 없었다. 호스트 API는 키를 따로 받는다(`AddContribution(대상, 멤버, 키, op, 값)`, 키는 Def id·엔티티·int). 후보는 키워드 인자 `key=`와 대상 문자열 안의 표기(`"Skill[Medicine].eff"`, 새 작은 파서와 그 안까지의 링크 검사·이름 풀이·스텁 자동완성이 따로 필요)였다.

**어떻게 정했나:** **키워드 인자 `key=`로 적는다.**

```python
Trait("SteadyHands", grants=[contrib("Skill.eff", "add", 2, key="Medicine")])
```

- 키는 Def id 문자열이고 다른 Def 참조와 똑같이 풀고 검사한다(짧은 이름은 쓴 모드 기준 G260, 로드 때 링크 검사와 "혹시 …?"). 대상 컴포넌트가 키 컴포넌트면 `key=`가 있어야 하고, 아니면 없어야 한다(로드 오류).
- 선언의 키는 Def id만 된다. 엔티티 키는 Def에 적을 수 없고, int 키(G129)는 번호를 다시 매기면 줄이 지워지고 새로 생기는 목록이라 선언으로 겨냥할 뜻이 없다. 둘이 필요하면 저장된 기여 행(스크립트 입구)을 쓴다.
- 겨냥한 줄이 엔티티에 없으면 그 선언은 조용히 적용될 곳이 없다(오류 아님). 저장된 기여 행은 넣는 순간 줄이 없으면 `RunNoRow`로 그대로 둔다: 넣는 쪽은 지금 이 줄을 겨냥하지만, 선언은 붙을 수 있는 모든 엔티티를 위한 것이다.

**이유:** 키를 Def 참조로 다루면 이미 있는 이름 풀이·링크 검사·스텁을 그대로 쓰고 새 문법이 없으며, 호스트 API의 모양(키를 따로)과 같다.

**상태:** 확인
