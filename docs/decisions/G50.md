**위치:** S1 패치 "같은 필드"의 판정과 Def별 적용 순서

**무엇이 비어 있었나:** G37·G41은 충돌을 "같은 필드"로, G42는 연산을 (Def, 경로)별로 다뤘다. 경로를 문자열로 비교하면 (1) `set "Cost"`와 `set "Cost.Wood"`처럼 결과가 순서에 달리는 겹침을 못 잡고, (2) G47 이후 `"Cost.Wood"`와 `"Cost['Wood']"`가 같은 경로인데 다르게 보이고, (3) A가 `Morale`을 붙이고(G44) 그에 의존하는 B가 `Morale.base`를 `set`할 때 경로별로 묶어 적용하면 B가 먼저 실행되어 "컴포넌트가 없음" 오류가 난다. 부모·자식 Def의 패치 사이 순서도 없었다.

**어떻게 정했나:** 경로는 **정규형**(이름 또는 키 값의 조각 목록)으로 바꿔 비교한다(`Cost.Wood` = `Cost['Wood']`). 한 경로가 다른 경로의 **접두사이면 겹친다**고 본다(`"Health"`/`"Health.base_max"`, `"Skill.Medicine"`/`"Skill.Medicine.level"`). 겹치는 두 연산에 G37·G41의 충돌 규칙을 적용한다("같은 필드" = 겹치는 경로). ④는 Def마다 연산을 **기록된 전역 순서 하나**(모드 로드 순서, 같은 모드 안에서는 호출 순서)로 적용하며 경로별로 묶지 않는다. 부모 Def의 패치는 부모의 최종 값을 먼저 만들고, 자식의 패치는 그 위에 쌓인다(자식 모드가 로드 순서상 앞서도 상속 순서가 우선).

**이유:** 판정은 정규형 접두사 비교 하나, 적용은 순서 하나라 규칙이 단순하고 G41의 로드 순서 원칙과 일관된다. 정확히 같은 경로만 충돌로 보면(B) 순서에 달리는 조합을 조용히 허용하고(S9), 경로별로 묶어 적용하면(C) 붙이기 → 필드 `set`의 의존 순서가 깨진다.

**상태:** 확인
