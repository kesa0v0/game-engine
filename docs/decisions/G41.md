**위치:** S1 패치 적용 순서 (spec의 "단계 고정"을 바꿈)

**무엇이 비어 있었나:** spec은 같은 필드의 적용 단계를 `set` → `add` → `append` → `remove`로 고정했다. 그러면 모드 X의 `add +5`와, X에 의존하는 모드 Y의 `set 10`이 15가 되어 Y가 자기 의존 모드의 `add`를 이길 수 없다.

**어떻게 정했나:** `set`·`add`·`append`는 **로드 순서대로**(같은 모드 안에서는 호출 순서) 적용한다. `set`은 그때까지 쌓인 값을 대체하고, 뒤에 오는 `add`·`append`는 그 위에 쌓인다. `remove`도 같은 로드 순서로 적용하고(예외 없음, 대상이 없으면 오류. 앞 모드의 `remove` 대상이 뒤 모드의 `append`로 생기는 경우는 "`remove`하는 모드가 `loadAfter`로 대상을 추가하는 모드 뒤에 오게 하세요"라고 안내) 순서가 선언되지 않은 두 모드가 같은 필드에 `remove`와 `set`/`add`/`append`/`remove`를 겹쳐도 오류. **충돌:** 순서가 선언되지 않은 두 모드(G37 기준)가 같은 필드(겹치는 경로, G50)에 `set`과 `set`/`add`/`append`를 겹치면 오류(`loadAfter` 안내, 결과가 모드 id 순에 달리므로). `add`끼리, `append`끼리는 충돌이 아니다(결과가 로드 순서와 무관하거나 spec대로 로드 순서). 순서가 선언된 모드끼리는, 뒤 모드의 `set`이 앞 모드의 `add`/`append` 기여를 덮어쓰면 경고(`set`끼리 경고하는 것과 같은 원리). `set` 뒤에 `add`/`append`가 쌓이는 것은 경고하지 않는다. 변경 이력(S9)은 필드마다 (연산, 값, 모드, 호출 위치)를 적용 순서대로 남긴다. G37은 이 규칙의 `set`-`set` 부분이다.

**이유:** 의존하는 모드가 마지막에 이긴다는 직관과 맞고, 서로 모르는 모드는 결과가 우연에 달리지 않게 오류로 막는다. `remove`도 로드 순서로 한다(처음에는 spec 원문대로 마지막에 두었다가 바꿈): 마지막에 두면 모드 A가 맵 키·컴포넌트를 `remove`하고 A에 의존하는 B가 다시 `append`/붙일 때 B가 "이미 있음" 오류로 막히거나, `set`을 쓰면 A의 `remove`가 B의 값을 지워 의존하는 모드가 이기지 못한다. 대가: 순서가 선언되지 않은 모드끼리 `set`과 `add`를 겹치면 이제 오류. **spec 반영 때 고칠 곳:** S1 패치 문단의 "같은 필드의 적용 단계는 고정"·`add`·`append`·"`remove`는 모든 `append` 뒤에" 항목, `use-cases.md` U16의 "적용 단계 고정".

**상태:** 확인
