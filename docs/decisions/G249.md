**위치:** S10 2·4항 UI 정의 파일은 누구의 것인가 (G244에서 이어서)

**무엇이 비어 있었나:** G244는 "호스트가 UI 정의가 가리키는 함수를 부른다"고 했고 S10 2항은 UI 정의 형식을 ❓로 두었다. 그 파일을 엔진이 정하고 읽는지(모든 호스트 공통), 호스트마다 다른지가 없었다. 콘솔 호스트에서 스커미시 판을 보이려다(구멍 3의 4단계) 드러났다.

**어떻게 정했나:** UI 정의 파일은 호스트의 것이다. Unity는 UXML/USS, Godot은 장면과 Theme, 웹은 HTML/CSS, 콘솔은 콘솔 호스트가 정하는 형식이고, 그 안에 무엇을 보여 줄지(값 함수 이름)와 어떻게 생겼는지가 함께 있다. 엔진은 UI 파일을 읽지 않고 G247·G248의 `Call`·`CheckCall`·`ViewAs(…).Call`·`Changed`만 준다. 함수 이름이 틀렸는지는 호스트가 UI 파일을 읽을 때 `CheckCall`로 확인한다("혹시 …?"까지 엔진이 준다). 엔진이 검사하는 공통 패널 목록(무엇을 보여 줄지만 적은 층)은 두지 않는다. 범용 호스트가 여럿 생기면 그때 덧붙인다. 호스트 파일이 이미 함수 이름을 가리키므로 길은 막히지 않는다. S10 2항의 "같은 정의가 AI의 합법 수 열거에도 쓰인다"는 커맨드 정의가 맡는다(G184 `LegalMoves`, G232 `LegalResponses`). 그래서 UI 파일이 호스트 것이어도 AI는 그대로다.

**이유:** 모더는 대개 게임 하나와 그 게임이 고른 호스트 하나를 목표로 한다. RimWorld와 패러독스는 클라이언트가 하나다(일반 지식). 호스트가 몇 개(Godot·Unity·콘솔)뿐이면 공통 마크업과 호스트별 번역기를 만드는 값이 따로 쓰는 값보다 크다. Godot에는 마크업이 없어(노드 트리·컨테이너·Theme, 일반 지식) 번역기가 특히 크다. 이전 엔진은 UXML 안에 `binding-path`와 인라인 스타일을 두고 USS를 런타임에 직접 파싱했다(`Scripts/Test/Core/UIRepeaterTester.cs`, `Scripts/Core/Data/Base/UI/RuntimeStyleSheet.cs`). 그 바인딩이 문자열 경로라 Unity와 스키마에 묶였는데, 이제는 값이 모드의 순수 함수(G244)이므로 호스트 파일은 함수 이름만 가리킨다. 범용 콘솔 호스트도 호스트 하나라서 게임 모드가 콘솔용 UI 파일을 가지면 된다.

**상태:** 확인
