**위치:** G323·G249에서 이어서: Unity 호스트의 UXML 해석기가 식에 쓰는 이름과 리스트 반복

**무엇이 비어 있었나:** UXML 요소가 모드 함수의 값을 보이려면 호출식에 인자를 써야 하는데, 그 인자(이를테면 반복되는 카드의 유닛)가 어디서 오는지 정해지지 않았다. 이전 엔진(`uk.kesa.engine`의 `UIInterpreter`·`UIBinder`·`UIRepeater`)은 이름 붙은 객체 꾸러미(`ScopeContext`: `Self`·항목 키)를 상속시키고, 데이터 경로를 반응형으로 구독했고, 버튼의 커맨드를 UXML에서 인자까지 풀어 조립했다. 새 엔진은 경로가 없고(G244), 커맨드는 스크립트가 조립한다(G276·G283).

**어떻게 정했나:**

- **변수는 이름 범위(lexical)다.** 윗 요소가 변수 이름을 정의하고 아래 요소가 그 이름을 모드 함수 호출식의 인자로 쓴다. 바깥 변수는 안쪽에서도 보인다. 이름은 UXML을 쓰는 모더가 짓고 엔진이 정한 이름(`me` 등)은 없다.
- **변수를 정의하는 곳은 둘이다:** 패널의 루트(화면을 여는 쪽이 값을 줌)와 반복 요소(항목마다 변수 하나).
- **반복은 UXML 안의 선언형 반복이다.** 모드 함수가 리스트를 주고 호스트가 항목마다 조각을 만든다. 모드가 UI 구조를 데이터로 내는 길(엔진 중립 UI 노드 언어)은 가지 않는다(G249대로 모양은 호스트 파일의 몫).
- **커맨드 조립은 UXML이 하지 않는다.** 버튼은 `@ui_action` 이름과 인자(변수)를 가리키기만 하고, 어느 커맨드를 낼지는 스크립트가 정한다.
- 속성 이름, 호출식의 문법, 패널 루트 변수를 선언하는 모양, 리스트가 바뀔 때 항목을 대응시키는 키는 정하지 않았다.

**이유:** 셋 중 고른 것: 이름 범위(이것), 역할별 고정 이름(`item`: 반복이 중첩되면 안쪽이 바깥을 가림, 패러독스 GUI도 `DataModelRoot` 같은 별도 장치를 둠), 해석기가 암묵적으로 붙이는 변수(함수가 무엇을 받는지 숨고 인자가 곧 입력이라는 순수 함수 원칙과 어긋남). 반복의 대안은 스크립트가 트리를 만드는 방식(React의 `map`, Factorio의 GUI 스크립트)과 템플릿에 코드 반복(WoW 애드온)이고(일반 지식), 엔진 중립 UI 언어가 있어야 해서 G249가 미룬 일을 앞당기게 되므로 택하지 않았다. 반복 요소에서 어려운 부분은 반복이 아니라 리스트가 바뀔 때의 갱신이고, 엔티티는 id가 키가 되어 유리하다.
