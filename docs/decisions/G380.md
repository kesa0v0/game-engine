**위치:** G137·G271이 미룬 "UI가 질문을 어떻게 보이고 답받나", Unity 데모에서 드러남

**무엇이 비어 있었나:** skirmish의 맞음 질문(`ask(..., choices=[...])`)이 사람 자리에 열리면 Unity 데모가 멈췄다. UXML 화면도 모드 스크립트도 열린 질문을 읽을 길이 없었다. 콘솔 호스트만 호스트 코드로 질문을 그렸다. 질문은 창만이 아니라 판 위 엔티티 클릭, 칸 강조, 이미 있는 버튼으로도 답받아야 한다.

**사례:** BGA는 서버 상태의 `args`(후보)를 클라이언트 게임 코드가 상태 이름마다 읽어 강조하고 버튼을 단다. 상태 표시줄의 안내 문구는 플랫폼 기본이다. Forge(MTG)는 활성 입력이 후보를 갖고 카드 그림이 그 입력에 묻는다. CK3·Stellaris·이전 엔진(QU·WG)은 이벤트 종류 이름으로 모드 파일의 창을 고른다. React·Vue는 판단을 공유 함수(selector)에, 모양을 컴포넌트에 두고 재사용한다(일반 지식).

**어떻게 정했나 (사용자가 고름):**

1. 게임 규칙: `ask`가 누구에게, 어떤 후보, 덤 데이터(`data`), 뜻(`hint`·선택지의 `style`)을 상태로 내놓는다. 보이는 모양은 정하지 않는다.
2. 판단: 화면 쪽 모드 스크립트와 봇이 열린 질문을 읽어 "이 유닛이 후보인가" 같은 것을 계산한다. 어디서든 부르는 공유 함수다. 답은 `submit("engine.pick", ...)`(G379)과 응답 커맨드로 낸다.
3. 그림: UXML과 나중의 월드 표시는 판단 함수에 묶이기만 한다(G331). 같은 그림의 재사용은 컴포넌트 쪽 문제다.
4. 엔진 기본: 아무도 그리지 않은 질문 때문에 판이 멈추지 않게 하는 몫만 진다. 모드가 그린 요소에 클래스를 끼우거나(전역 강조 공급자) 클릭을 가로채 답하지(엔티티 자동 답) 않는다.

읽는 내장의 모양, 기본 몫의 모양, 컴포넌트 재사용, 월드 표시는 따로 정한다.

**이유:** 엔진이 남의 그림을 바꾸면 그 화면을 만든 모드가 모르는 사이 모양과 클릭의 뜻이 바뀐다(영역 침범). 판단을 스크립트에 두면 UXML 문법을 늘리지 않고, 봇이 질문을 읽는 길(이전에는 거절에 기댐)과 같은 것으로 풀린다.

**상태:** 확인

**바뀜:** G448이 선택지의 `style`과 질문의 `hint`를 뺐다(이름표·제안은 `data`에).
