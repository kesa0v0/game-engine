**위치:** G336에서 이어서: 눌러도 되는지(회색 버튼과 그 이유)를 경계로 보이는 법

**무엇이 비어 있었나:** 커널에는 누르지 않고 사전 조건만 평가하는 호출이 이미 있다(커맨드 `World.CheckPreconditions`, 화면 동작 `WorldView.CheckPreconditions`, G110·G280). 경계 세션에는 합법 수를 나열하는 `LegalMoves`뿐이었다. 또 `Call`은 영수증으로 `Changed()`가 알리지만(G246) 사전 조건 검사에는 읽은 곳 기록이 없어 돈이 생기는 것 같은 변화를 호스트가 알 길이 없었다.

**어떻게 정했나:** **경계에 `Check`와 `Version`을 더하고 보수적으로 다시 확인한다.**

- `Check(이름, 인자)`: 이름을 커맨드 목록과 화면 동작 목록에서 찾아(G336) 알맞은 검사를 한다. 통과 여부와 이유 목록(번역할 글 포함)을 `BridgeResult`와 같은 모양으로 준다. 눌러 보지 않으므로 상태를 바꾸지 않는다.
- `Version()`: 세계 변경 도장(`World.Version()`, G235)을 세션에 노출한다. 호스트는 도장이 바뀌면 보이는 `on-click` 버튼을 모두 다시 `Check`한다. 바뀌지 않은 버튼도 확인하는 보수적 방식이고 비용은 보이는 버튼 수만큼이다.
- 영수증 방식(검사가 읽은 곳을 기록)은 하지 않는다. 성능이 실제로 문제가 되면 그때 올린다.
- 정하지 않았다: 회색 버튼을 USS 클래스로 어떻게 표시할지, 이유를 어떻게 보일지(툴팁과 함께 정할 일), 화면 동작이 읽는 UI 기록의 변화로도 다시 확인할지.

**이유:** 셋 중 고른 것: `Check`와 도장(이것: 커널의 사전 조건 실행기를 그대로 쓰고 필요한 화면이 됨), 검사에도 영수증(가장 정확하나 사전 조건 실행기에 읽은 곳 기록을 넣는 커널 작업이 큼), 회색 처리를 안 함(가장 단순하나 회색 버튼이 안 됨).

**상태:** 확인

**바뀜:** `Check`는 사전 조건만이 아니라 입구(`acts_for`, 응답 커맨드는 낼 수 있는 열린 질문)도 본다 → G346.
