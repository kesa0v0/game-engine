**위치:** 큰 판 읽기에서 이어서: 긴 봇 생각이 호스트 화면을 막는가

**무엇이 비어 있었나:** Unity 데모는 `Update()`에서 `BotSeat.Run()`을 부르고 `LocalScriptBot.Act`는 `Think`를 동기로 끝까지 돌린다. 커널은 한 스레드다(G327). G467로 생각 한 번은 시간이 막혔지만 기본 예산을 다 쓰면 데스크톱 Release에서 약 40~240ms라 프레임이 끊긴다. 보통 봇(다 훑고 수 하나)은 1만 유닛 판에서 3.6ms다.

**어떻게 정했나:**

- 엔진과 경계는 그대로다. 호스트 문서(Unity 패키지 README "봇이 생각하는 시간")에 최악 시간과 호스트가 고를 것을 적는다: 봇마다 예산 낮추기(`Bot`·`LoadBot`의 `stepBudget`), 차례제면 "생각 중"을 먼저 그리고 멈춤을 받아들이기, `maxActs`와 부르는 간격.
- 커널을 작업 스레드에 두는 호스트는 실제 호스트가 필요로 할 때 만든다. 그때 정할 것: Unity에서 다른 스레드가 끝낸 `await`의 이어 하기가 다음 프레임으로 밀려 화면 갱신(경계 호출 여러 번)이 늘어지므로 묶은 읽기나 밀어 주는 화면 사본이 필요하고, 게임의 호스트 함수가 커널 스레드에서 돌아 Unity API를 부를 수 없다.

**이유:** 고른 것: 호스트가 다룸과 문서(이것), 커널 전용 스레드 호스트(화면이 안 멈추고 틱·`advance`·저장에도 듣지만 위 두 비용을 실제 Unity 화면에서 재 봐야 모양을 고를 수 있다), 생각을 여러 프레임에 잘라 돌리기(식 안의 호출이 C# 스택으로 돌아 아무 걸음에서나 멈출 수 없어 실행기를 고쳐야 하고(G452), 자른 사이에 판이 바뀌면 섞인 판을 보고 잘린 자리가 프레임 속도를 따라 결정론이 깨지므로 생각 중 판 잠금이 필요하다. 미뤄 둔 실행 모델 결정과 함께 볼 일이다). 일반 지식: RimWorld는 모든 일을 메인 스레드에서 하고 긴 일은 로딩 화면(`LongEventHandler`)으로 가린다. 패러독스 게임은 AI를 여러 스레드로 돌린다. 차례제 전략 게임은 AI 차례에 대기 표시를 흔히 띄운다.
