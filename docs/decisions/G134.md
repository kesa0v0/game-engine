**위치:** S4·S6 스크립트에서 엔티티 생성·삭제, 런타임 컴포넌트 부착·분리, 키 줄 붙이기·떼기의 표기

**무엇이 비어 있었나:** spec은 구조 변경이 즉시 보인다는 것(G88)만 정하고 스크립트 표기가 없었다. 호스트 C# API(`Create`·`Destroy`·`Add`·`Remove`·`AddRow`·`RemoveRow`)만 있었다. 타입 이름 호출 `Unit("x", ...)`은 S2 표에서 로드 시점의 Def 생성이고, `add`·`remove`는 `patch.add`·`patch.remove`와 겹친다. 컴포넌트 값 생성자 `Health(...)`는 로드 시점 이름이었다.

**어떻게 정했나:** **이름 붙은 커널 내장 함수 여섯과, 처음 값은 Def 리터럴과 같은 컴포넌트 값 모양.** `u = spawn("core.Warrior", Health=Health(current=3))`(Ref를 돌려줌), `destroy(u)`, `attach(u, Wounded(turns=3))`, `detach(u.Wounded)`, `add_row(u.Skill, "core.Medicine", Skill(level=3))`, `remove_row(u.Skill, "core.Medicine")`. 줄 함수는 G129의 `append_row(node.Die, ...)`처럼 첫 인자가 줄 묶음이다. 컴포넌트 값 생성자는 런타임 이름으로도 연다(그 모드에 보이는 컴포넌트만, G112의 덮어쓸 수 있는 내장). `spawn`의 Def id가 리터럴이면 로드 때 존재·타입·보이는 범위를 검사하고(G116 기본값과 같은 방식), 값이면 실행 때 검사한다. 키 컴포넌트의 줄은 `spawn`에 넣지 않고 `add_row`로 붙인다. Def에서 온 컴포넌트·줄은 뗄 수 없다(S4). 검사는 호스트 API와 같다(G89·G91~G93).

**이유:** 처음 값의 모양이 Def 리터럴과 같아 새로 배울 것이 없다. `=`의 뜻이 값 쓰기(G132) 하나로 남는다(`u.Wounded = ...`·`del` 문을 쓰면 같은 `=`가 구조 변경도 되고, 이미 있는 줄에 대입할 때 덮어쓰기인지 애매하다). 평평한 키워드(`spawn("x", current=3)`)는 `extend`로 같은 멤버 이름이 두 컴포넌트에 생기면 모호하다. 사례: 이전 엔진 `InstanceFactory.CreateInstance(def)`(C# 쪽만), RimWorld `GenSpawn.Spawn`·`Thing.Destroy`·`AddHediff`/`RemoveHediff`, 패러독스 `create_character`·`add_modifier`/`remove_modifier`(동작 이름이 곧 효과, 일반 지식).

**상태:** 확인

**바뀜:** Def 타입 이름도 로직 안에서 열되 부를 수 없는 타입 값으로(부르면 `spawn` 안내) → G306.
