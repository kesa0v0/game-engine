**위치:** G278·G279에서 이어서: `ui.…`와 `submit`을 쓸 수 있는 함수 (구현하며 드러남)

**무엇이 비어 있었나:** G278은 `@ui_action` 본문이 UI 기록에 쓰고 `submit`한다고만 했다. 여러 동작이 함께 쓰는 보통 함수(`remember(u)`처럼 기록을 고치는 도우미)가 `ui`를 써도 되는지, 게임 쪽 코드(커맨드·핸들러·반응·정책·`derived`)가 그런 함수를 부르면 어떻게 되는지 정하지 않았다.

**어떻게 정했나:**
- 보통 함수도 `ui.기록.칸`에 대입하거나 `submit`할 수 있다. 그런 함수는 "UI를 쓰는 함수"이고 `@ui_action`이나 다른 UI를 쓰는 함수 안에서 문장으로만 부른다(쓰기 함수의 G117과 같은 규칙). `submit` 자체도 문장으로만 부른다.
- "UI를 건드린다"(읽기든 쓰기든 `submit`이든)는 표시는 문장 호출·식 호출 모두를 따라 퍼진다. 게임 쪽 입구(`@command`·`@on`·`@when`과 그 조건·`acts_for`·정책 함수)와 순수 자리(`derived` 등)는 그런 함수를 쓸 수 없다(`CMD007`, 증거는 처음 건드린 곳).
- 거꾸로 `@ui_action`은 게임을 바꾸거나 난수를 쓸 수 없다(`CMD007`). `ui.기록.칸.x = …`처럼 기록이 가리키는 엔티티에 쓰는 것도 게임 쓰기다.
- `ui`는 늘 `ui.기록.칸` 꼴로 적는다. `s = ui.Selection`처럼 기록을 값으로 들 수 없다. 그러면 뒤의 `s.unit = …`가 UI 쓰기인지 엔티티 쓰기인지 알 수 없다. 기록·칸 이름이 틀리면 `EVL001`("혹시 …?"), 의존하지 않는 모드의 기록이면 `SCH003`이다.
- `submit("이름", 인자=…)`에 리터럴로 적은 커맨드는 링크 단계에서 본다(`CMD008`): 있는지, `@ui_action`이 아닌지, 보이는지(`LNK003`), 넘긴 이름이 매개변수인지, 기본값 없는 매개변수를 넘겼는지. 인자는 이름으로만 넘긴다. 이름을 계산한 `submit`은 실행 때 본다.
- 호스트의 `Call`은 UI를 쓰는 함수를 거절한다. UI를 읽는 화면 함수는 G280의 `Call(이름, ui, …)`가 들어올 때까지 거절한다.
- Def 값이나 패치로 `Cond[...]`·`Action[...]` 자리에 넣은 함수도 같다(2026-10-21 구현). UI를 건드리는 함수는 로드 오류이고, 패치로 넣었으면 그 패치 모드의 오류다(G64). 처음에는 쓰기·난수 함수만 이 자리에서 막아 `ui`를 읽는 함수가 로드를 통과하고 실행 때 터졌다.

**이유:** UI 기록은 연결마다 다르고 저장되지 않으므로, 게임 쪽 코드가 한 번이라도 읽으면 컴퓨터마다 판이 갈라진다(spec P2). 도우미를 막으면 동작마다 같은 줄을 복사해야 한다. 커맨드 쪽 쓰기 규칙(G117)을 그대로 따르면 엔진 일이 적고 모더가 익힐 규칙도 하나다. RimWorld의 `Find.Selector`는 게임 코드가 선택을 읽을 수 있어서, 선택에 기댄 동작이 멀티플레이 모드에서 어긋나는 원인이 된다(일반 지식).
