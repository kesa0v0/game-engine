# spec 빈틈 상세: S6 커맨드 (C8 롤백, S10 UI의 나 포함)

색인과 상태 규칙은 `docs/spec-gaps.md`. 이 파일은 G 번호마다 무엇이 비어 있었고 어떻게, 왜 정했는지의 전문이다.

## G109

**위치:** S6 커맨드의 이름(id)

**무엇이 비어 있었나:** 난수열 키(S2), UI의 `command="X"`(S10), 커맨드 로그·저장(S6·S7)이 모두 커맨드를 이름으로 가리키는데 그 이름이 무엇인지 없었다. 최상위 이름 공간은 모드마다 하나라(G20) 두 모드가 같은 함수 이름을 쓸 수 있다.

**어떻게 정했나:** **커맨드 id는 자동으로 `모드id.함수이름`이다**(`core` 모드의 `def Move`는 `core.Move`). 데코레이터는 `@command`와 `@command(free=True)` 두 모양을 받는다(S6: Request 없이 낸 커맨드는 `free=True`일 때만 받는다).

**이유:** 단계(S5)·호스트 함수(S7)와 같은 접두사 규칙이고(모드 id에 점이 없는 이유, G2), 다른 모드가 추가돼도 이름이 겹치지 않아 난수열 키가 밀리지 않는다. 함수 이름을 바꾸면 id가 바뀌는 문제는 멈춘 Flow의 함수 이름(S8)과 같은 문제라 S8 마이그레이션에서 함께 다룬다. 명시 `id=`(B)는 손이 많이 들고, 접두사 없는 이름(C)은 서로 모르는 두 모드를 함께 설치할 수 없게 만든다.

**상태:** 확인

## G110

**위치:** S6·C7 여러 `require`의 평가와 서로 기대는 조건

**무엇이 비어 있었나:** S6은 `require`를 각각 평가해 실패 사유를 하나씩 돌려준다고 하지만, `with preconditions:` 안에는 `if`가 없어(S2) 앞 조건이 실패하면 뒤 조건이 평가 중 오류가 나는 경우(`require(c is not None)` 뒤의 `require(c.walls > 0)`)를 어떻게 다룰지 없었다.

**어떻게 정했나:** **`require`는 모두 위에서부터 평가한다. 앞에 이미 실패한 `require`가 있고 뒤 `require`의 평가가 실행 오류(None 접근, 죽은 Ref 등)를 내면, 그 `require`는 “평가 안 됨”으로 표시하고 사유 목록에 넣지 않는다.** 앞에 실패가 없는데 오류가 나면 스크립트 오류다. 결과는 `require`마다 통과 / 실패(메시지 키와 인자) / 평가 안 됨이고(S9 “왜?” 도구 3이 그대로 쓴다), 실패가 하나라도 있으면 커맨드는 거부되고 본문은 실행하지 않는다. **보강:** 단계 예산 초과(`RUN013`)와 순환(`RUN014`)은 앞에 실패가 있어도 언제나 스크립트 오류다(앞 조건에 기대서 생기는 오류가 아님). **알려진 한계:** 속성 이름은 로드 시점에 보지 않으므로(G108) 앞에 실패가 있으면 뒤 `require`의 속성 오타(`unit.Moves.nope`)도 평가 안 됨에 묻힌다. 앞이 모두 통과할 때는 오류로 드러난다. 로직용 `.pyi`가 생기면 편집기가 잡는다.

**이유:** 실패 사유를 모두 보여 주면서(Paradox 결정 툴팁) 서로 기대는 조건을 `if` 없이 쓸 수 있고, 진짜 버그는 그대로 오류로 남는다. 첫 실패에서 멈추기(B, 이전 엔진·RimWorld)는 S6의 “개별 반환”과 어긋나고 UI에 사유가 하나만 보인다. 오류를 늘 스크립트 오류로 보기(C)는 기대는 조건을 하나로 합치게 만들어 사유를 나눌 수 없다.

**상태:** 확인

## G114

**위치:** S6 커맨드 매개변수의 타입 (S6 열린 질문 “매개변수 타입의 표현 범위”)

**무엇이 비어 있었나:** S6은 “타입 있는 매개변수”라고만 했고, 어노테이션이 필수인지, 어떤 타입을 쓸 수 있는지 없었다. 제출 검사·직렬화·UI 대조(S10)·AI 후보 나열·스텁이 모두 이 타입에 기댄다.

**어떻게 정했나:** **커맨드의 모든 매개변수는 어노테이션이 필수다**(없으면 로드 오류). 일반 로직 함수의 어노테이션은 지금처럼 보지 않는다. 허용 타입: `int`·`fixed`·`bool`·`str`, `Ref[X]`(그 타입의 살아 있는 엔티티), `DefId[X]`(그 타입의 Def id), `list[T]`, `dict[K, V]`(키는 `str`·`int`·`DefId`·`Ref`), 그리고 None을 허용하는 “T 또는 None”(파이썬의 세로줄 표기 `T`·`None`). 표기는 스키마 타입 표기와 같고 타입 이름은 따옴표 없이(`Ref[Unit]`, spec 예제)도 문자열(`Ref["Unit"]`)로도 쓸 수 있다. 함수, `TextKey`, 외부 값, 대상 미지정 `Ref`는 아직 없다.

**이유:** 커맨드는 밖에서 값이 들어오는 유일한 입구라 타입이 곧 검사·직렬화·UI·AI의 기준이다. CK3 interaction(정해진 scope)·Civ VI UnitOperation(정해진 매개변수 표)·Unreal 서버 RPC(복제 가능한 타입만)도 매개변수 종류를 정해 둔다. 이전 엔진은 타입 없는 컨텍스트 맵이라 잘못된 값이 실행 중에야 드러났다.

**상태:** 확인

## G115

**위치:** S6·C7 제출된 인자가 매개변수 타입에 맞지 않을 때

**무엇이 비어 있었나:** spec은 사전 조건 실패와 허용 목록 위반의 거절을 구조화한다고 했지만 인자 자체가 틀린 경우(빠짐, 남는 인자, 타입 불일치, 죽은 엔티티, 없는 Def id)는 없었다.

**어떻게 정했나:** **인자 문제는 예외가 아니라 구조화된 거절이다.** 사전 검사 결과(`PreconditionReport`)에 인자 거절 목록이 따로 있고, 하나마다 매개변수 이름·컬렉션 안의 위치(`path[1]`, `goods["Iron"]`)·사유 종류(빠짐, 남는 인자, 타입 불일치, 죽은 엔티티, 엔티티 타입 다름, 없는 Def, Def 타입 다름)·기대 타입을 담는다. 인자 거절이 하나라도 있으면 사전 조건은 평가하지 않는다. 문제는 모두 모아 한 번에 돌려준다. 숫자는 G95를 따른다: `fixed` 자리의 `int`는 올려 받고 `int` 자리의 `fixed`는 거절한다. `bool`은 `int`가 아니다. 커맨드 id가 없는 것은 여전히 호출자 오류(예외)다.

**이유:** 인자는 클라이언트·네트워크에서 오는 믿을 수 없는 입력이고, 죽은 엔티티는 클릭과 제출 사이에 유닛이 죽는 정상 상황이다. 호스트가 예외 처리 없이 결과만 보면 된다. 숫자 규칙이 칼럼 쓰기·derived와 하나로 유지된다.

**상태:** 확인

## G116

**위치:** S6 커맨드 매개변수의 기본값 (spec “타입 있는 매개변수(기본값 포함)”)

**무엇이 비어 있었나:** spec은 기본값이 있다고만 했고 무엇을 쓸 수 있는지, 언제 평가하는지, 로그에 무엇이 남는지 없었다. 파서는 모든 기본값을 거부했다.

**어떻게 정했나:** **기본값은 `@command` 함수에만, 리터럴만 쓸 수 있다**: 수(앞의 `-` 포함)·문자열·bool·None과 이것들로만 된 리스트·맵 리터럴. 로드 시점에 매개변수 타입과 대조한다(G95대로 `fixed` 자리의 int는 올림). `Ref`는 리터럴로 못 적으므로 기본값은 None뿐이고 타입이 “T 또는 None”이어야 한다. `DefId` 기본값은 ⑤ 링크에서 Def 값과 같은 규칙(존재·타입·보이는 범위·abstract 금지)으로 검사한다. 기본값 있는 매개변수 뒤에 기본값 없는 매개변수가 오면 구문 오류다(파이썬과 같음). 제출 시 빠진 인자를 기본값으로 채우고, 커맨드 로그에는 채운 뒤의 전체 인자를 남긴다(모드 업데이트로 기본값이 바뀌어도 리플레이가 같다). UI draft의 초기값도 이 기본값이다. 일반 함수와 람다의 기본값은 아직 거부한다.

**이유:** 값이 고정이라 결정론·리플레이가 단순하고 파이썬의 가변 기본값 함정이 없다. 모드 상수나 상태를 읽는 기본값은 사전 조건과 역할이 겹치고 평가 순서 규칙이 더 필요하다.

**상태:** 확인

## G118

**위치:** S6 커맨드를 로직에서 일반 함수처럼 쓰기

**무엇이 비어 있었나:** `@command` 함수도 평범한 이름으로 묶여 다른 함수와 커맨드가 `Heal(u)`로 부를 수 있었다(재현함, 로드 통과). 그러면 사전 조건과 권한 3층(S6)을 건너뛰고, 로그에는 바깥 커맨드만 남는다.

**어떻게 정했나:** **로직에서 커맨드 이름을 쓰는 것은 로드 오류다(`CMD004`)**: 함수 본문에서 부르기와 값으로 쓰기(대입, 인자로 넘기기) 모두. 스키마의 함수 자리(`derived`, 함수 기본값)와 Def·패치의 함수 값(`Cond[...]`·`Action[...]`)에도 커맨드를 둘 수 없다. 같이 쓰는 효과는 일반 쓰기 함수로 빼서 각 커맨드가 부른다. 커맨드는 제출(호스트·UI·AI)로만 실행된다. 최상위 대입(`x = Heal`)처럼 이름으로 알 수 없는 경로는 G117의 런타임 안전망이 막는다.

**이유:** 규칙이 한 줄이고 잃는 표현력이 거의 없다(공용 효과 함수가 있음). 하위 커맨드로 허용하면 실패의 뜻(거절인가 오류인가)·롤백·로그 표현을 따로 정해야 한다.

**상태:** 확인

## G119

**위치:** S6 제출자(issuer)와 S2 `me`의 관계 (S2 `me` ❓의 일부)

**무엇이 비어 있었나:** S6은 issuer를 호스트가 넘기는 불투명한 문자열로 정했는데, S2 예제는 `me.Points`·`cost(me.Points, 1)`·`u.owner == me`처럼 issuer를 게임 안의 행동하는 진영(엔티티)처럼 썼다. 이전 엔진의 `^Self` 하나가 연결·행동하는 진영·비용 내는 쪽·질문받는 쪽·UI의 나를 모두 맡던 것을 옮겨 온 표기다(U1).

**어떻게 정했나:** **issuer는 “어느 연결에서 왔나”이고 행동하는 진영이 아니다.** issuer를 진영·비용 지불자처럼 쓰는 표기(`me.Points`, `cost(me.Points, 1)`)는 틀렸다. 규칙이 issuer를 어떤 형태로든 읽을 수 있는지(입구 ②의 검사 자료가 어디 있는지 포함), 행동하는 진영·질문받는 쪽·UI의 나를 어디에 둘지는 이 항목이 정하지 않는다(이어서 정함). S2·S6·X1 문구는 그 결정과 함께 고친다.

**이유:** 연결과 진영은 핫시트(연결 하나가 진영 여럿), AI(호스트 안에서 여러 진영을 대신함, U13), 관전자(진영 없음)에서 갈라진다. TR 라우터도 연결의 playerId를 정당 엔티티로 변환해 넘겼다(`SessionCommandRouter.cs` 34~39행).

**상태:** 확인

## G121

**위치:** S6 입구(②): “연결 A가 진영 P를 조종해도 되는가”의 자료와 검사는 어디에 있는가

**무엇이 비어 있었나:** G120으로 행위자는 인자에서 나오므로 남의 유닛을 움직이는 제출을 막을 검사가 필요한데, S6의 자유 커맨드 입구는 `free` 선언만 보고 소유 체인(U2)은 자리가 없었다.

**어떻게 정했나:** **담당 정보는 게임 상태 안에 두되 커널 개념이 아니라 모드 데이터다.** 담당 칼럼(정당·캐릭터·진영 중 무엇에 둘지), 상속·합병 때 옮기는 규칙, “이 issuer가 이 진영의 담당인가” 검사는 표준 모드나 게임 모드가 만든다. 로비 배정·접속 끊김 같은 변경은 호스트가 S6의 “호스트가 상태에 직접 쓰는 하나뿐인 경로”로 쓴다. **커널은 issuer를 불투명한 꼬리표로 받고, 입구에서 모드가 정한 검사를 부를 자리만 연다**(거부된 제출은 상태·난수를 건드리지 않는다, C10). 그 자리의 모양은 이 항목이 정하지 않는다(이어서 정함).

**이유:** 담당이 게임 규칙으로 바뀌는 일(CK3 상속, 일반 지식)을 시뮬레이션 안에서 처리하고 저장·리플레이에 함께 남는다. X3 경계 규칙상 칼럼과 규칙은 제한 언어로 쓸 수 있어 모드 몫이고, 제출 길목에 끼어드는 것만 언어로 쓸 수 없다. 이전 엔진도 이 검사는 게임 쪽(TR·WG의 `SessionCommandRouter`)에 있었다. 턴 관리가 게임 몫인 것(X2)과 같다.

**상태:** 바뀜(G236)

**바뀜:** 담당 정보는 모드 데이터가 아니라 커널이 게임 상태로 드는 "엔티티 → 앉은 연결" 배정 표이고, 입구 검사도 커널이 한다. 근거로 든 "이전 엔진도 게임 쪽에 있었다"는 이전 엔진에 빈자리가 있어 게임이 메운 것이었다 → G236·G237.

## G122

**위치:** S6 입구(②)에서 모드가 정한 검사를 부르는 자리의 모양 (G121)

**무엇이 비어 있었나:** 입구가 알아야 할 것은 둘이다: 이 커맨드가 누구로서 행동하나(커맨드마다 다르고 그 커맨드를 쓴 모더가 앎), 이 issuer가 그 대상으로 행동해도 되나(게임에 하나이고 담당 정보를 만든 모드가 앎).

**어떻게 정했나:** **둘로 나눈다.** 커맨드는 “누구로서”를 인자에서 고르는 순수 함수로 선언한다(`@command(free=True, acts_for=lambda party, unit, dest: party)`). 담당 정보를 가진 모드가 정책 함수 하나를 선언한다(`@submit_policy def may_act(issuer, target)`, 순수). 입구는 `may_act(issuer, acts_for(인자))`가 거짓이면 이유와 함께 거부하고, 이 검사는 전제 조건(③)보다 먼저 돈다. 스크립트에서 issuer를 읽는 곳은 정책 함수뿐이다. **소유 검사(“이 유닛이 그 진영 것인가”)는 입구가 아니라 커맨드의 전제 조건이다**(`require(unit.owner == party, ...)`). 표기(`acts_for`·`submit_policy` 이름, 인자 받는 방식), `acts_for` 없는 자유 커맨드, 정책 함수가 없거나 둘 이상일 때는 이 항목이 정하지 않는다.

**이유:** OpenTTD 서버는 연결마다 플레이 중인 회사(`client_playas`)를 들고 커맨드 패킷의 회사와 다르면 끊고, 대상 소유는 각 커맨드가 `CheckOwnership(v->owner)`로 본다(소스 확인). Factorio 권한 그룹도 동작 종류만 보고 인자별 권한은 넣지 않기로 했다(공식 문서·개발진 답변). 게임 전체 검사 하나(B)는 모드가 커맨드를 추가할 때마다 고쳐야 하고, 커맨드마다 검사(C)는 issuer와 담당 칼럼을 모든 커맨드가 알아야 한다. 소유 검사를 전제 조건에 두면 UI 비활성 사유에 그대로 쓰이고 WG처럼 두 곳에 중복되지 않는다(U2).

**상태:** 일부 바뀜(G237)

**바뀜:** 모드가 선언하는 정책 함수 `may_act`는 없어지고 입구는 커널의 배정 표로 `acts_for`가 고른 엔티티를 본다. `acts_for`와 "소유 검사는 전제 조건"은 그대로 → G236·G237.

## G123

**위치:** G122의 `acts_for`가 없는 자유 커맨드

**무엇이 비어 있었나:** 채팅·일시정지 요청처럼 누구로서도 행동하지 않는 커맨드가 있다(TR `IsSystemCommand`). 그런데 `acts_for`를 빠뜨린 것을 “누구나”로 읽으면 모더가 깜빡한 `Move`가 조용히 모두에게 열린다.

**어떻게 정했나:** **자유 커맨드(`free=True`)는 `acts_for`를 반드시 적는다.** 누구로서도 아니면 `acts_for=None`이라고 명시한다. 빠지면 로드 오류. `None`이어도 정책 함수는 불린다(`may_act(issuer, None)`) — 관전자 채팅 금지 같은 결정은 게임 정책이 한다. 응답 커맨드는 이 항목 밖이다(Request `accepts`와 함께 정함).

**이유:** S9 “조용히 잘못 동작할 수 있으면 오류”. OpenTTD도 기본은 회사가 있어야 하고 회사 없이 낼 수 있는 커맨드만 `Spectator` 표시로 명시한다(소스 확인).

**상태:** 일부 바뀜(G237)

**바뀜:** "`None`이어도 정책 함수는 불린다"는 없어지고 `acts_for=None`은 어느 연결이든 통과한다. `acts_for`를 반드시 적는 규칙은 그대로 → G237.

## G124

**위치:** G122의 정책 함수가 없거나 둘 이상일 때

**무엇이 비어 있었나:** 싱글 플레이와 테스트는 연결이 하나라 정책이 필요 없지만, 멀티 게임에서 빠뜨리면 모두에게 열린다. 커널은 게임이 멀티인지 모른다(S6 네트워크 방식은 호스트 몫). 표준 모드의 정책을 본편이 바꾸고 싶을 수 있다.

**어떻게 정했나:** **정책 함수가 없으면 모든 issuer를 허용한다.** 호스트는 시작할 때 “정책 필수”를 켤 수 있고, 켰는데 정책이 없으면 시작을 거부한다. **정책 함수는 활성 모드 전체에서 최대 하나**이고 둘이면 로드 오류다. 교체는 `override=True`로 명시한다(Def 교체 S1과 같은 규칙).

**이유:** 멀티인지 아는 쪽(호스트)이 안전장치를 건다. 없으면 거부(B)는 싱글·테스트마다 빈 정책을 강요하고, 여럿을 AND로 합치기(C)는 교체가 안 되고 거부 사유 순서를 따로 정해야 한다.

**상태:** 바뀜(G237)

**바뀜:** 입구 정책 함수가 없어져 "없으면 모두 허용", "정책 필수"(`requireSubmitPolicy`), "최대 하나"가 모두 할 일이 없다 → G237.

## G127

**위치:** S10 UI의 “나”(이전 `^Self`의 다섯째 역할)

**무엇이 비어 있었나:** UI는 “내 OP”, 버튼 활성(전제 조건에 `party` 필요), 커맨드 인자 채우기에 “나”가 필요한데 S10은 UI 경로가 어디서 시작하는지 말하지 않았다. 핫시트에서는 같은 연결의 “나”가 차례마다 바뀐다.

**어떻게 정했나:** **UI의 “나”는 그 클라이언트가 지금 보고 있는 엔티티이고 시뮬레이션 상태가 아니다**(UI 로컬, 저장·네트워크 대상 아님). 호스트(게임 C#)나 UI가 설정하고 바꾼다(시작 시 배정, 핫시트 전환, 관전자는 `None`). 고를 수 있는 후보는 정책 함수로 구한다(내 꼬리표로 `may_act`가 참인 엔티티). UI가 커맨드를 낼 때 `party`·응답 엔티티의 기본값으로 쓰지만 커맨드 기록에는 명시된 값이 남는다(G126). 커널이 할 일은 없고 표기는 UI 모듈 몫이다. 공유 상태에 기계 기준 값(“로컬 플레이어”)을 두지 않는다.

**이유:** 이전 ENG·TR·WG·QU 모두 클라이언트 세션 별칭 `"Player"`(`SessionLifecycleLinker.RegisterAlias`, 저장 안 함)를 게임 C#이 설정했다. OpenTTD는 UI용 `_local_company`와 커맨드 실행용 `_current_company`를 따로 둔다(소스 확인). Factorio 스크립트에는 암묵적 “나”가 없다(`game.player`는 콘솔 명령에서만, 공식 문서). Civ VI UI 스크립트는 기계마다 LocalPlayer용이고 상태 변경은 게임 API로 한다(포럼). TR `Comp_PartyController.Type = LocalPlayer`는 보는 기계마다 달라야 할 값을 공유 상태에 넣은 반례다.

**상태:** 일부 바뀜(G237)

**바뀜:** "나"의 후보는 정책 함수가 아니라 커널 배정 표에서 그 연결이 앉은 엔티티로 구한다. "나"가 UI 로컬이라는 것은 그대로 → G236·G237.

## G130

**위치:** G122의 표기: `acts_for` 람다가 인자를 받는 방식, 정책 데코레이터 이름

**무엇이 비어 있었나:** G122 예시 `acts_for=lambda party, unit, dest: party`는 커맨드의 모든 인자를 순서대로 받는 모양이라, 매개변수가 하나 늘거나 순서가 바뀌면 모든 `acts_for`를 고쳐야 하고 순서가 바뀌면 조용히 틀린다. 매개변수 이름 문자열(`acts_for="party"`)은 G120의 `unit.owner` 같은 끌어낸 값을 못 쓴다.

**어떻게 정했나:** **`acts_for` 람다는 커맨드 매개변수를 이름으로 골라 받는다**: `@command(free=True, acts_for=lambda unit: unit.owner)`. 람다의 매개변수는 커맨드에 있는 이름이어야 하고(없으면 `CMD001`과 “혹시 …?”), 필요한 것만 적는다. 값은 람다나 `None`만 받는다. `acts_for`는 자유 커맨드에만 적는다(응답 커맨드는 응답한 엔티티로서 행동, G123·G126). 람다는 순수 자리라 쓰기 함수를 부를 수 없다(G117). **정책 함수는 `@submit_policy`(교체는 `@submit_policy(override=True)`)**이고 함수 이름은 모더 마음이다. 기본값 없는 매개변수 둘(`issuer, target`)을 받고 어노테이션은 강제하지 않으며, 쓰기 함수면 로드 오류(`CMD004`), 모양·개수·교체 오류는 `CMD005`. 교체 판정(자기 정책 교체 금지, 의존해야 교체 가능, 순서 없는 두 교체는 충돌)은 Def 교체(S1)와 같다. 정책 함수는 커맨드가 아니라 로직에서 불러도 된다.

**이유:** 커맨드 시그니처가 바뀌어도 깨지지 않고 이름 오타는 로드 때 잡힌다. 끌어낸 값까지 덮는다. OpenTTD는 커맨드 패킷에 회사 필드가 따로 있어 이 표기 문제가 없다(같은 사례는 확인하지 못함, 일반 설계 판단).

**상태:** 일부 바뀜(G237)

**바뀜:** `@submit_policy`와 그 오류(`CMD004`·`CMD005`의 입구 정책 부분)는 없어진다. `acts_for` 람다 표기는 그대로 → G237.

## G131

**위치:** S6 제출 API(`Submit`)가 돌려주는 결과의 모양

**무엇이 비어 있었나:** 제출은 자유 커맨드 확인, 인자 검사(G115), 입구(G122), 전제 조건(G110), 본문을 차례로 거치고 어디서 멈췄는지에 따라 호스트가 할 일이 다르다(사유 표시 또는 모드 버그 기록). 기존 `CheckPreconditions`는 거절은 값으로, 스크립트 오류는 예외로 냈다.

**어떻게 정했나:** **제출의 결과는 모두 값 하나(`SubmitResult`)다.** `Outcome`은 성공, Request 필요(자유 커맨드가 아님), 인자 거절, 입구 거부, 전제 조건 실패, 스크립트 오류 중 하나이고, 세부(인자 거절 목록, `acts_for`가 고른 대상, `PreconditionReport`, 오류 진단)를 함께 담는다. 스크립트 오류(`acts_for`·정책·전제 조건·본문의 실행 오류, `acts_for`가 엔티티나 None이 아님, 정책이 bool이 아님)도 결과이고 효과를 남기지 않는다(C8). 예외는 호스트의 프로그래밍 실수(없는 커맨드 id, G115)뿐이다. 결과에는 기본값까지 채운 전체 인자를 담아 호스트가 커맨드 로그에 쓴다(G116). 순서는 자유 커맨드 확인, 인자, 입구, 전제 조건이다(`acts_for` 람다가 인자를 읽으므로 인자가 먼저). Request가 아직 없으므로 `free=True`가 아닌 커맨드는 “Request 필요”로 거절한다(S6 기본 거부). 호스트는 `World`를 만들 때 `requireSubmitPolicy`를 켤 수 있고 정책이 없으면 생성이 실패한다(`RUN016`, G124).

**이유:** OpenTTD 커맨드는 실패도 메시지와 함께 결과 객체(`CommandCost`)로 돌려준다. RimWorld는 틱 중 예외를 잡아 기록하고 게임을 계속한다(일반 지식). 오류가 난 제출도 로그에 “효과 없음”으로 남아야 리플레이가 같아지므로 값이 옮기기 쉽다. 예외 방식(B)은 호스트마다 `try/catch`가 필요하고, 결과마다 다른 타입(C)은 내용은 같고 모양만 다르다.

**상태:** 일부 바뀜(G237)

**바뀜:** 입구 거부는 정책이 아니라 배정 표로 판정하고, 정책 실행 오류와 `requireSubmitPolicy`(`RUN016`)는 없어진다. 결과 모양과 순서는 그대로 → G237.

## G132

**위치:** S6 커맨드 본문 실행: 쓰기가 닿는 곳과 실행 모양 (G117 2단계)

**무엇이 비어 있었나:** G117은 쓰기를 “엔티티 상태 경로의 속성 대입”으로 정했지만 실행기는 모든 함수를 순수로 돌려 `u.Moves.left -= 1`을 거부했다. 키 줄 쓰기와 리스트 칼럼의 `+=`가 열려 있었다.

**어떻게 정했나:** **본문의 속성 대입은 `World.Set`과 같은 검사(G92)를 거친 상태 쓰기다.** 컴포넌트의 `field`·Ref에 쓰고(`const`·`derived`는 거부), **키 컴포넌트는 있는 줄에만 쓴다**(`h.Skill[k].level += 1`). 줄이 없으면 읽기가 None이라 “None에 쓸 수 없음”이고, 줄을 붙이는 길은 스크립트의 엔티티·컴포넌트 생성과 함께 미룬다. 복합 대입은 파이썬처럼 대상 객체를 한 번만 평가한다. 사전 조건과 본문은 한 실행으로 돈다: 모든 `require`가 통과하면 블록의 지역 변수를 이어 받아 본문을 실행하고(예산은 커맨드 하나에 하나), 실패가 있으면 본문은 돌지 않는다. 쓰기는 본문(과 본문이 문장으로 부른 쓰기 함수) 실행 중에만 열리고, 본문이 읽는 `derived`는 따로 도는 순수 실행이라 앞의 쓰기를 본다. 리스트 칼럼의 `+=`는 생기지 않는다: 상태 칸은 리스트·맵을 담지 못하고(SCH004, G129) 리스트 칸은 `const`라 쓰기 거부다.

**이유:** 줄 쓰기는 줄 뷰가 이미 있어 추가 개념이 없다. 사전 조건을 두 번 평가하지 않아 블록의 지역 변수가 그대로 이어진다.

**상태:** 확인

## G133

**위치:** C8 커맨드 단위 롤백의 방식

**무엇이 비어 있었나:** C8은 스크립트 오류가 난 커맨드가 어떤 효과도 남기지 않을 것을 요구하는데, 본문이 몇 칸을 쓴 뒤 오류가 나면 앞의 쓰기가 남았다. 바뀌는 곳은 엔티티 값·줄 기록과 전역 색인(Ref 역방향)이고, 스크립트의 엔티티 생성·삭제·기여 행이 열리면 더 는다.

**어떻게 정했나:** **되돌리기 기록(undo 로그).** 커맨드 실행 중(사전 조건 + 본문)에 상태를 바꾸는 기본 연산은 바뀌기 전 상태로 돌리는 동작을 기록하고, 실행이 어떤 예외로 끝나든 거꾸로 되감은 뒤 결과를 스크립트 오류로 돌려준다. 성공하면 기록을 버린다. 기록하는 기본 연산은 값 칸 쓰기, `keys="all"` 줄 기록 생성, 역방향 색인 추가·삭제다. 커맨드 밖(호스트 API)에서는 기록하지 않는다. 스크립트에서 생성·삭제·부착을 열 때 그 연산도 기록에 넣는다.

**이유:** 비용이 쓴 횟수에 비례해 틱 게임(시나리오 ③④)에서도 부담이 작다. 통째 스냅샷(B)은 월드 크기에 비례하고, 처음 건드린 엔티티만 복사(C)는 전역 색인 때문에 결국 A의 일부가 필요하다. 데이터베이스 undo 로그와 같은 방식(일반 지식). OpenTTD는 롤백 대신 시험 실행 뒤 실제 실행을 하지만 모더 스크립트는 중간 오류를 막을 수 없어 맞지 않는다.

**상태:** 확인

## G235

**위치:** S10 4항 "칼럼 버전"의 단위와 API (콘솔 호스트에서 드러남)

**무엇이 비어 있었나:** S10 4항은 "바인딩의 읽기 집합과 칼럼 버전 카운터로 바뀐 것만 다시 읽는다"는 방향만 정했고, 버전을 무엇마다 세는지와 호스트 API는 없었다. 커널에는 바뀐 것을 세는 장치가 하나도 없어 콘솔 호스트는 입력마다 모든 엔티티의 모든 컴포넌트를 다시 읽었다.

**어떻게 정했나:** **바뀜 도장.** 쓰기마다 전역 시계를 하나 올리고 그 값을 (엔티티, 칸 이름)에 적는다. 칸 이름은 컴포넌트 이름이거나 그 타입의 역방향 컬렉션(`inverse`) 이름이다. 호스트 API는 `Version()`(전역 시계, 그대로면 어느 엔티티도 안 바뀜), `Version(id)`(그 엔티티의 어느 칸이든), `Version(id, 이름)`(그 칸)이다.
- 찍는 것: 값 쓰기(줄 포함), 컴포넌트 붙이기·떼기, 줄 붙이기·떼기(키 엔티티가 죽어 지워지는 줄 포함), 그 칸을 겨냥한 기여 행, Ref 쓰기가 바꾼 대상의 역방향 컬렉션, 엔티티 생성(그때가 모든 칸의 첫 도장)·삭제(시계만 오르고 도장은 사라짐).
- 죽었거나 없는 엔티티는 0. 컴포넌트도 역방향 컬렉션도 아닌 이름은 오류.
- 실패한 커맨드는 도장과 시계도 되감는다(C8). 커맨드 안에서 칸마다 처음 찍을 때만 옛 도장을 기록한다.
- 도장은 저장하지 않는다. 불러온 월드는 모든 엔티티를 새로 찍는다(호스트는 새 월드로 다시 그린다).
- 아직 안 담는 것: 거른 읽기(`ViewAs`)의 도장(못 보는 칸의 바뀜이 새지 않게 해야 한다), 남의 엔티티를 읽는 `derived` 값(읽기 집합이 필요하다), 열린 질문·틱(호스트가 따로 견준다).
- 콘솔 호스트는 엔티티 도장이 그대로면 그 줄을 다시 읽지 않는다.

**이유:** 고른 것은 가(지금 넣음), 나(실제 호스트가 정해질 때까지 미룸) 중 가, 단위는 컴포넌트 단위·엔티티와 컴포넌트 단위·바뀐 목록 커서 중 엔티티와 컴포넌트 단위. 값이 바뀌는 순간 구독자를 부르는 방식(이전 엔진의 R3 `ReactiveProperty`, WPF, Godot 시그널)은 커맨드 한가운데서 실패할 중간값을 알리고, 구독자가 시뮬레이션 안에서 돌아 결정론을 해치고, 콜백이 경계를 넘는다(P1a). 도장은 묻는 쪽이 정한 때(커맨드가 확정된 뒤)에 숫자 하나만 견준다. Bevy의 `Changed<T>`(칸마다 바뀐 틱), Unity ECS의 청크 버전, Unity UI Toolkit 런타임 바인딩의 버전 숫자, Salsa의 리비전이 같은 생각이다(일반 지식). 이전 엔진의 `binding-path`(UXML이 경로만 적고 참조가 바뀌면 다시 붙음)는 잘한 점이라 경로 컴파일과 읽기 집합으로 잇는다(handoff의 다음 구멍 후보). 지금 넣는 것은 쓰기 경로가 늘기 전에 되감기와 함께 묶어 두기 위해서다.

**상태:** 일부 바뀜(G251)

**바뀜:** "아직 안 담는 것" 가운데 거른 읽기와 남의 엔티티를 읽는 `derived`는 앞으로도 도장에 담지 않는다. 화면 값은 `Call`·`ViewAs(…).Call`의 영수증이 맡는다(G244~G248). 콘솔 덤프는 `derived` 칸이 있는 엔티티의 줄을 매번 다시 읽는다 → G251.

## G236

**위치:** S6 입구(②)의 담당 정보: G121·G122를 다시 엶 (콘솔 호스트 구멍 5번, 모드가 연결 이름 `"red"`를 박아 넣음)

**무엇이 비어 있었나:** G121은 "연결 A가 엔티티 P를 맡는다"를 모드 데이터로, G122는 그 검사를 모드가 쓰는 `may_act`로 정했다. 그래서 예시 게임은 `Seat.conn` 칸과 `may_act`를 손으로 짜고 `Start`가 `Seat(conn="red")`를 박아 넣었다. 로비에서 정한 배정이 게임 안으로 들어가는 길이 없고, 호스트는 모드 안의 이름을 미리 알아야 했으며, S6의 "호스트가 상태에 직접 쓰는 하나뿐인 경로"는 모양이 없었다.

**어떻게 정했나:** **커널이 "엔티티 → 앉은 연결" 배정 표를 게임 상태 안에 든다.** 저장되고, 커맨드처럼 기록·되감기의 대상이며, 바꾸는 길은 호스트 API 하나다(S6의 직접 쓰기 경로). 입구는 `acts_for`가 고른 엔티티(응답이면 답하는 엔티티)로 이 표를 본다. 앉을 수 있는 엔티티의 종류는 따로 선언하지 않는다(어떤 엔티티든 됨, 진영이든 캐릭터든 게임이 고름). 정하지 않은 것(이어서 정함): `may_act` 정책 함수를 남길지와 G124, API 이름과 모양, 로비가 고를 수 있는 엔티티 목록을 얻는 길, 스크립트가 배정을 읽을 수 있는지, 한 엔티티에 연결 여럿·한 연결이 엔티티 여럿.

**이유:** 고른 것은 가(게임 상태에 둠), 나(커널이 들되 시뮬레이션 밖, 저장 안 함), 다(G121 유지, 표준 모드로 메움) 중 가. 레퍼런스는 모두 배정과 입구 검사를 엔진이 한다(소스 확인): Wesnoth는 시나리오가 `[side]`를 선언하고 엔진 C++(`connect_engine.cpp`)이 사람을 앉혀 그 자리의 `player_id`·`current_player`가 게임 데이터에 남는다, 0 A.D.는 로비 화면만 모드 JS이고 배정 표(`m_PlayerAssignments`)와 "배정과 다른 플레이어로 낸 커맨드는 버림"은 엔진 서버 C++이다, OpenTTD는 `client_playas`와 다르면 강퇴한다. 저장은 갈린다: Wesnoth와 EU4(세이브의 `players_countries`, 나라마다 `was_player`, pdx-tools 소스)는 남기고 OpenTTD·0 A.D.는 시뮬레이션 밖에 둔다. 가는 G121의 이유(저장·리플레이에 남고 게임 규칙이 담당을 바꿀 수 있음)를 지키면서 검사를 엔진이 일률적으로 한다. 나는 사람이 빠진 자리를 AI가 넘겨받는 규칙을 게임이 쓸 수 없다. 이전 엔진은 G121의 근거와 달리 빈자리였다: `INetworkService.OnCommandReceived`는 보낸 연결을 모르고 `EngineCommandRouter`는 클라이언트가 봉투에 적은 진영 id를 그대로 믿어서, TR·WG가 `SessionCommandRouter`를 새로 짜 메웠다.

**상태:** 확인

## G237

**위치:** G236 이후 입구(②)의 정책 함수 `may_act`(G122·G123·G124)

**무엇이 비어 있었나:** G236으로 커널이 배정 표를 들게 되자 입구가 표로 직접 검사할 수 있게 됐다. 모드가 쓰는 `may_act(issuer, 대상)`가 할 일이 남는지, `acts_for=None` 커맨드는 누가 낼 수 있는지, G124의 "정책이 없으면 모두 허용"과 호스트의 "정책 필수"가 어떻게 되는지가 열렸다.

**어떻게 정했나:** **`may_act`를 없애고 배정 표가 유일한 입구 검사다.** `acts_for`가 엔티티를 고르면(응답이면 답하는 엔티티) 보낸 연결이 그 엔티티에 앉아 있어야 통과한다. `acts_for=None`은 어느 연결이든 통과한다(관전자 포함). `@submit_policy`와 G124의 규칙, 호스트의 `requireSubmitPolicy`는 없어진다. G123(자유 커맨드는 `acts_for`를 반드시 적음)은 그대로이고, `None`이 "아무 엔티티로서도 아님 = 누구나"를 뜻하는 명시 표시가 된다.

**이유:** 고른 것은 ㄱ(없앰), ㄴ(조이기만 하는 덧검사로 남김), ㄷ(갈아 끼울 수 있게 남김) 중 ㄱ. OpenTTD(`client_playas`와 커맨드의 회사 비교, 회사 없이 낼 수 있는 커맨드는 커맨드 정의에 표시), 0 A.D.(배정 번호와 커맨드의 플레이어 비교, 예외는 게임 설정 `CheatsEnabled`), Wesnoth 모두 게임이 바꿀 수 없는 고정 검사 하나다(소스 확인). 모드가 정책을 잘못 짜서 뚫릴 길이 없어진다. 공동 조종은 표에 연결을 여럿 앉히는 쪽으로 풀 수 있다(G236에서 이어서 정함). 관전자 채팅 금지 같은 규칙은 채팅이 시뮬레이션 커맨드여야 하는지부터 따질 일이라 이것 때문에 정책 자리를 남기지 않는다.

**상태:** 확인

## G239

**위치:** G236에서 이어서 정할 것: 로비가 고를 수 있는 엔티티 목록을 얻는 길

**무엇이 비어 있었나:** 배정 표는 어떤 엔티티든 앉힐 수 있다(G236). 어느 엔티티가 사람이 고를 자리인지(예시 게임의 진영 Red·Blue는 후보, 판 Battle·병사 Soldier는 아님)를 알 길이 없어 콘솔 호스트는 `--seat red=Red`처럼 모드의 Def 이름을 미리 알아야 했다.

**어떻게 정했나:** **엔진이 기본 제공하는 표시 컴포넌트 `Seatable`이 앉을 후보를 나타낸다.** 붙은 살아 있는 엔티티가 후보이고, 호스트 API `World.SeatChoices()`가 id 순으로 돌려준다. 처음부터 끝까지 후보면 Def의 `components`에 적고, 상태에 따라 바뀌면 규칙이 붙이고 뗀다(`attach(e, Seatable())`·`detach(e.Seatable)`, 호스트는 `World.Add`·`Remove`). Def에 적은 컴포넌트는 뗄 수 없으므로(spec S4) 후보에서 빠질 수 있는 엔티티는 Def에 적지 않고 붙인다. 지금은 엔진 필드가 없다. 남의 컴포넌트에 칼럼을 더하는 길은 없으므로(S1 `extend`는 타입에 컴포넌트·`const`를 더할 뿐) 게임 데이터는 모드가 자기 컴포넌트를 같은 엔티티에 붙인다. 목록은 로비에 보일 후보일 뿐 `Seat`를 막지 않는다(AI 연결을 목록 밖 엔티티에 앉히는 경우). 엔진이 읽을 필드 후보(로비 순서, 사람만·AI 가능, 표시 이름)는 사례가 생기면 정한다. 이름은 `Tick`처럼 엔진이 먼저 자리를 잡아 모든 모드에 보이고(의존 선언 없이), 모드가 같은 이름의 Def 타입·컴포넌트·신호를 선언하면 그 모드의 오류(SCH001)이며 다른 이름을 쓰라는 안내가 붙는다(G154와 같은 규칙). 엔진 제공 컴포넌트의 일반 기준은 G240.

**이유:** 고른 것은 가(모드의 순수 함수 하나 `@seat_choices`), 나(`deftype(..., seatable=True)`에 조건 함수), 다(엔진은 안 하고 로비 화면이 정함), 그리고 사용자가 낸 라(기본 제공 컴포넌트) 중 라. 가는 진영을 더하는 모드마다 함수 전체를 `override`해야 해 모드끼리 합쳐지지 않는다(패러독스의 파일 통째 덮어쓰기 충돌과 같은 모양, 일반 지식). 나는 합쳐지지만 타입 단위라 같은 타입의 중립 진영을 뺄 수 없고, 조건 함수는 계산값이라 저장·도장에 남지 않는다. 라는 엔티티 단위이고 상태라서 저장·덤프·바뀜 도장(G235)에 보이며, 정적(Def에 적음)과 동적(붙이고 뗌)을 한 장치로 덮는다. 대가는 떼기를 잊으면 틀린 후보가 남는다는 것(덤프로 보인다). 다는 UI 모듈이 생길 때까지 호스트가 모드 이름을 아는 우회가 남는다. 레퍼런스: Wesnoth `[side]`의 `allow_player`(자리마다 표시), 0 A.D.는 플레이어가 `IID_Player`를 가진 엔티티(`simulation/helpers/Player.js`, 소스 확인), CK3는 상태에 따른 플레이 가능 조건(일반 지식).

**상태:** 확인

## G240

**위치:** G239로 생기는 첫 엔진 제공 컴포넌트: 어떤 컴포넌트를 엔진이 제공하나

**무엇이 비어 있었나:** 지금까지 엔진이 스키마 이름 공간에 미리 둔 것은 `Tick` 신호 하나였다(G154). X3 경계 규칙은 커널에 "엔진 지원이 꼭 필요한 것"만 두고 나머지는 모드라고만 한다. 이전 엔진(`unity-kesa-engine`)은 Core에 `Comp_Renderer`·`Comp_StatTracker`·`Comp_CommandContainer` 등 12개 C# 컴포넌트를 두어 Core가 Unity와 특정 기능에 묶였다.

**어떻게 정했나:** **엔진 제공 컴포넌트는 커널(또는 호스트 API)이 그 이름을 알아야 할 때만 둔다. 엔진이 정하는 필드는 커널·호스트 API가 뜻을 정해 읽는 것만 둔다. 게임마다 뜻이 다른 데이터(팀, 색, 문명, 시작 자원)는 모드가 자기 컴포넌트로 같은 엔티티에 붙인다(남의 컴포넌트에 칼럼을 더하는 길은 없다, S1).** "필드 없음"은 기준이 아니다(필드를 엔진이 읽어야 하는 경우가 있다). 그래픽·UI 쪽 컴포넌트는 이 기준으로 커널에 오지 않고, 그 이름을 아는 공식 그래픽·UI 모듈의 몫이다(P1·P5, 6절, S10에서 정함).

**이유:** 사용자가 "필드 없음"을 기준으로 두는 것을 바로잡았다. 이름을 누가 아느냐가 커널과 다른 층을 가르는 선이다(`Tick`도 커널이 내는 신호라 커널에 있다). 게임마다 다른 항목을 엔진이 고정하면 이전 TR의 고정 질문 클래스(G137의 `PendingChoiceData`)와 같은 벽이 된다. Wesnoth `[side]`(`team_name`·`color`·`gold`·`faction`)와 0 A.D. `PlayerData`(`Civ`·`Color`·`Team`·`AI`)도 자리에 붙는 항목이 서로 다르다(소스 확인).

## G241

**위치:** G236에서 이어서 정할 것: 스크립트가 배정 표를 읽는 길

**무엇이 비어 있었나:** 배정 표는 엔티티마다 연결 꼬리표를 담지만 스크립트는 전혀 읽지 못했다(G236). AI는 커널 밖에서 호스트가 앉힌 연결이라(spec 사례 ③) 규칙은 그 자리가 사람인지 AI인지 비었는지 알 수 없었다. 빈자리 차례 건너뛰기, AI 진영 보너스, 사람만 업적 같은 규칙을 모드가 쓸 수 없었다.

**어떻게 정했나:** **호스트가 앉힐 때 연결의 종류(사람·AI)를 함께 주고, 스크립트는 종류만 읽는다.** 호스트 API는 `World.Seat(e, issuer, kind)`(`SeatKind.Human`·`Ai`, 주지 않으면 사람)와 `SeatKindOf(e)`. 스크립트 내장 `controller(e)`는 `"human"`·`"ai"`를, 빈자리나 죽은 엔티티면 `None`을 준다. 엔티티가 아닌 값을 주면 실행 오류. 연결 꼬리표는 계속 스크립트에 보이지 않는다. 종류는 배정 표와 함께 저장되고(`"kind"`), 앉히기·비우기는 그 엔티티를 읽은 `@when` 조건을 다음 정착에서 다시 보게 한다.

**이유:** 고른 것은 가(읽지 않음), 나(`seated(e)`로 앉았나만), 다(종류) 중 다. 꼬리표 글자는 판마다 달라 규칙이 기대면 깨지므로 셋 다 꼬리표는 주지 않는다. 규칙이 실제로 묻는 것은 "사람·AI·빈자리"이고, 나는 AI도 앉은 연결이라 사람과 AI를 가르지 못한다. 레퍼런스: Wesnoth는 자리마다 `controller`가 `human`·`ai`·`none`(`connect_engine.cpp`의 `side_controller`, 시나리오의 `controller=human`, 소스 확인), EU4는 세이브의 나라마다 `human` 표시가 있고 업적 검사가 그것을 본다(`eu4game/src/achievements.rs`, 소스 확인), CK3·Stellaris의 `is_ai` 조건(일반 지식). 호스트의 `Seat` 호출은 커맨드처럼 기록되므로 리플레이에서도 같게 읽힌다.

**상태:** 확인

## G242

**무엇이 비어 있었나:** G236·G239·G241의 이름(`Seat`·`Unseat`·`SeatOf`·`SeatsOf`·`SeatKindOf`·`SeatChoices`·`SeatKind`, 스크립트 `controller(e)`)은 구현하며 붙인 것이고 사용자가 고른 적이 없었다. 한 개념에 호스트는 "자리", 스크립트는 "조종자"라는 두 낱말을 쓴다.

## G244

**위치:** S3·S10 4항 UI가 보여 줄 값을 읽는 길 (콘솔 호스트 구멍 3의 "호스트용 경로 읽기"에서 이어짐)

**무엇이 비어 있었나:** S3은 UI도 문자열 경로(`unit.Location.city`)로 상태를 참조하고 로드 때 스키마로 검사한다고 했고, S10 4항은 바인딩한 경로를 컴파일해 읽기 집합을 얻는다고 했다. 호스트에는 경로 API가 없어 핸들(`Member`·`Get`)로 한 단계씩 따라가야 했고, 다른 엔티티로 건너가는 경로(`Owner.party.Order.next`)는 어느 도장을 봐야 하는지도 호스트가 챙겨야 했다. 이전 엔진(`unity-kesa-engine`의 `DataPathResolver`)은 UXML 경로를 그릴 때 풀어 오타가 조용히 묻혔고, 시작점(`Self`·`Target`·`Root`·`App`)의 `Self`가 자리마다 인스턴스이기도 플레이어이기도 했으며, 계산이 필요해지자 경로 문법에 집계 함수(`Sum(…)`·`Count()`)가 붙었다.

**어떻게 정했나:** **호스트용 문자열 경로를 두지 않는다. UI가 보여 줄 값은 모드 스크립트의 순수 함수가 만든다.** 호스트 연결부는 UI 정의가 가리키는 함수를 (엔티티 인자와 함께) 불러 값과 그 값을 만들며 읽은 곳(영수증: 엔티티와 컴포넌트, `query` 목록, 틱)을 받고, 영수증의 도장이 바뀐 칸만 다시 부른다. 경로는 스크립트의 속성 접근(`u.Owner.party.Order.next`)이고 오타는 기존 로드 검사(G228·G231)가 잡는다. "체력이 낮으면 경고" 같은 판단은 함수 안에 있고, 호스트 연결부는 함수 이름을 UI 정의에서 읽어 부르고 결과를 생긴 대로 그릴 뿐 게임 단어를 모른다(호스트 엔진마다 한 번 짬). 이어서 정할 것: 부르는 API의 모양과 부를 수 있는 함수의 범위, 영수증의 내용과 `query` 목록의 도장, `ViewAs` 아래에서 부르기. UI 정의(배치) 파일 형식, 함수가 위젯 트리까지 돌려줄지, `@ui_action`은 S10의 몫으로 따로 정한다.

**이유:** 문자열 경로(호스트가 `world.Path(…)`로 컴파일)는 검사기와 읽기 집합 수집을 새로 만들어야 하고, 곧 계산이 필요해져 UI 쪽에 두 번째 식 언어가 생긴다. 스크립트 함수는 로드 검사, 쓰기 금지(순수 함수, S2), 읽은 곳 기록(`@when` 조건의 기록 장치), 숨긴 정보 거름(`ViewAs`)을 이미 갖고 있다. 모드가 콘텐츠에 경로를 선언하는 안은 UI 정의 형식보다 앞서 UI 이름표를 커널에 박는다. 근거(일반 지식): Factorio는 모드 UI를 로직과 같은 Lua로 짜고, WoW 애드온은 배치 XML이 Lua 함수를 가리킨다. 패러독스 GUI는 데이터 바인딩 식(`[GetPlayer.GetName]`)이라는 별도 언어를 둬 `scripted_gui`로 스크립트를 다시 끌어오고, RimWorld는 UI가 C#이라 모더가 UI를 고치려면 C# 패치가 필요하다.

**상태:** 확인

## G245

**위치:** G244에서 이어서: 호스트가 부를 수 있는 함수의 범위

**무엇이 비어 있었나:** G244는 UI가 보여 줄 값을 모드 스크립트의 순수 함수가 만들고 호스트가 그것을 부른다고 정했다. 호스트가 아무 순수 함수나 부를 수 있는지, UI용으로 표시한 함수만 부를 수 있는지는 없었다.

**어떻게 정했나:** **모드의 아무 순수 함수나 부른다.** 이름은 `모드.함수`(`skirmish.unit_row`)이고 표시 데코레이터는 두지 않는다. 쓰기 함수(G117)·커맨드·핸들러는 부르지 않고 이유를 알려 준다. 순수인지는 모드 로드 때 이미 판정되어 있으므로 부르는 순간 안다. UI 로더가 UI 정의를 읽을 때 그 이름이 부를 수 있는 함수인지 미리 확인할 길을 둔다. 스텁이나 UI 로더용 목록이 필요해지면 표시를 나중에 더할 수 있다.

**이유:** 순수 함수는 불러도 상태를 바꿀 수 없고 순수인지는 커널이 이미 알아서, 표시(`@view`)가 막아 줄 위험이 거의 없다. 표시를 두면 데코레이터가 하나 늘고 도우미 함수(`game()`)도 따로 표시해야 한다. 근거(일반 지식): WoW 애드온의 XML은 아무 전역 Lua 함수나 이름으로 가리키고 따로 표시하지 않는다. CK3 `scripted_gui`는 블록으로 따로 선언하지만 GUI가 효과(쓰기)까지 하기 때문이다.

**상태:** 확인

## G246

**위치:** G244에서 이어서: 영수증의 모양

**무엇이 비어 있었나:** G244는 호스트가 함수를 불러 값과 영수증(읽은 곳)을 받고 바뀐 칸만 다시 부른다고 했다. 영수증을 호스트에게 내용으로 보여 줄지, 그 단위가 엔티티인지 (엔티티, 컴포넌트)인지, `query` 목록이 바뀐 것을 무엇으로 알지는 없었다.

**어떻게 정했나:** **닫힌 영수증.** 호스트는 영수증에 "다시 불러야 하나"(지금 세계에서 읽은 곳이 바뀌었나)만 묻고 안의 내용은 보지 않는다. 안은 `@when` 조건의 기록과 같은 세 가지로 시작한다: 읽은 엔티티(함수 안의 함수 호출과 다른 엔티티를 읽는 `derived`까지), `query`로 읽은 목록 출처(그 타입의 엔티티가 생기거나 죽음, 그 컴포넌트가 붙거나 떨어짐), 틱을 읽었나. 목록 출처의 도장은 커널 안에 새로 둔다. 단위가 엔티티라 읽지 않은 컴포넌트가 바뀌어도 다시 부를 수 있지만, 나중에 (엔티티, 컴포넌트) 단위로 나눠도 호스트 코드는 바뀌지 않는다. 커널은 먼저 알리지 않는다(끌어오기, G235의 결정). 밀어주기가 필요한 호스트는 제출·답·시간 진행 호출이 끝난 뒤 칸들의 영수증을 훑어 바뀐 칸에만 이벤트를 낸다. 커맨드 가운데의 값은 새지 않고, 실패한 커맨드는 도장도 되감기므로 이벤트도 나가지 않는다.

**이유:** 열린 영수증(읽은 (엔티티, 컴포넌트) 목록을 호스트가 `Version(id, 이름)`으로 견줌)은 호스트의 일이 늘고 영수증 모양이 공개 API로 굳으며, 컴포넌트 단위 기록을 지금 새로 만들어야 한다. 엔티티 단위의 덜 정확함은 순수 함수를 한 번 더 부르는 정도다. 이전 엔진은 쓰는 순간 동기로 알려 커맨드 한가운데서 UI와 효과가 끼어들었다(G235). 근거(일반 지식): Unity ECS의 바뀜 확인은 청크 단위로 거칠고, React는 상태가 바뀌면 그 컴포넌트 함수를 통째로 다시 부른다. 둘 다 조금 더 자주 다시 부르되 확인을 싸게 한다.

**상태:** 확인

**바뀜:** 영수증의 단위가 (엔티티, 컴포넌트)로 좁아졌다. 호스트 코드는 이 항목의 말대로 그대로다(→ G290).

## G247

**위치:** G244에서 이어서: 부르는 API의 모양

**무엇이 비어 있었나:** G244~G246은 호스트가 모드의 순수 함수를 불러 값과 닫힌 영수증을 받는다고 했지만, C# 쪽에서 무엇을 어떻게 부르는지, 이름이 틀렸을 때와 함수가 실패했을 때 무엇을 돌려주는지는 없었다.

**어떻게 정했나:** `CallResult r = world.Call("skirmish.unit_row", new EntityValue(unit4));` 이름은 `모드.함수`이고 인자는 위치 순서의 `params Value[]`다. `r.Value`가 값, `r.Changed(world)`가 다시 불러야 하나(G246)다. `string? why = world.CheckCall("skirmish.unit_row", argumentCount: 1);`은 부르기 전에 이름과 인자 수를 확인해 괜찮으면 null, 아니면 이유 문장(없는 이름이면 "혹시 …?", 쓰기 함수·커맨드·핸들러면 G245의 거절 이유)을 준다. 연결부는 UI 파일을 읽을 때 칸마다 한 번 확인할 수 있다. 부르다 실패하면(없는 이름, 인자 수, 스크립트 오류, 걸음 예산 G224 초과) `Get`처럼 `WorldException`(코드, `파일:줄`, "혹시 …?")을 던진다. 연결부는 칸 하나를 `try`로 감싸 그 칸에 오류를 보이고 나머지 칸은 계속 그린다.

**이유:** 세계의 다른 읽기(`Get`)가 실패를 예외로 알리므로 같은 길을 쓴다. 결과에 오류 칸을 두면 호스트가 매번 확인을 잊기 쉽다. 미리 확인은 UI 파일을 고친 모더가 화면을 띄우자마자 틀린 이름을 알게 한다(G9의 "혹시 …?"와 같은 경험). 이름 문자열은 UI 파일에서 읽은 값이라 연결부에 게임 로직이 들어가지 않는다(G244).

**상태:** 확인

## G248

**위치:** G244에서 이어서: `ViewAs` 아래에서 부르기

**무엇이 비어 있었나:** G247의 `Call`은 실제 세계에서 돈다. 안개가 있는 게임에서 한 플레이어의 화면을 그릴 때 함수가 못 보는 값을 읽으면, 결과가 숫자 하나(예: 적 체력의 합)여도 숨긴 정보가 샌다. 보는 쪽 세계(`WorldView`, G196~G200)와 `Call`이 어떻게 이어지는지 없었다.

**어떻게 정했나:** `world.ViewAs("red").Call(이름, 값들…)`(과 `CheckCall`)을 둔다. 함수 안의 모든 읽기가 그 연결의 `WorldView`를 거친다: 못 보는 엔티티는 없는 것(`query`에서 빠지고 죽은 id와 같은 응답), 못 보는 컴포넌트는 붙지 않은 것(`u.Life is None`이 참, 그 안의 칸을 읽으면 붙지 않음 오류), 보이는 칸의 Ref가 못 보는 엔티티를 가리키면 `HiddenValue`, 보이는 `derived`는 G199대로 보인다. 함수는 그 플레이어가 아는 것만으로 계산하므로 결과를 따로 거르지 않는다. 모르는 경우(`-1 if u.Life is None else u.Life.hp`)는 모더가 다룬다. 보이는지 정하는 정책이 읽은 곳도 영수증(G246)에 넣어 시야가 바뀌면 `Changed`가 참이 된다. 관전자·리플레이처럼 다 보이는 연결은 `world.Call`을 쓴다.

**이유:** 실제 세계에서 계산하고 결과만 거르는 방식(`LegalMoves`, G201)은 결과가 Ref와 선택지일 때만 통하고, 숨긴 값으로 만든 숫자는 거를 수 없다. 모더에게 맡기면 한 번 잊을 때 멀티플레이에서 샌다. 근거(일반 지식): CK3은 비밀을 스크립트가 `is_known_by`로 직접 확인해 GUI로 새는 버그가 자주 고쳐졌고, Stellaris는 정보 수준에 따라 엔진이 UI에 "?"를 보인다. 이미 있는 `WorldView`를 쓰므로 새 규칙이 거의 없다.

**상태:** 확인

**고침(2026-10-20):** 처음에는 붙었는지를 없는 내장 `has(u, "Life")`로 적었다. 엔진의 표기 `u.Life is None`으로 고쳤고 뜻은 같다(모더 안내서를 쓰며 드러남).

## G249

**위치:** S10 2·4항 UI 정의 파일은 누구의 것인가 (G244에서 이어서)

**무엇이 비어 있었나:** G244는 "호스트가 UI 정의가 가리키는 함수를 부른다"고 했고 S10 2항은 UI 정의 형식을 ❓로 두었다. 그 파일을 엔진이 정하고 읽는지(모든 호스트 공통), 호스트마다 다른지가 없었다. 콘솔 호스트에서 스커미시 판을 보이려다(구멍 3의 4단계) 드러났다.

**어떻게 정했나:** UI 정의 파일은 호스트의 것이다. Unity는 UXML/USS, Godot은 장면과 Theme, 웹은 HTML/CSS, 콘솔은 콘솔 호스트가 정하는 형식이고, 그 안에 무엇을 보여 줄지(값 함수 이름)와 어떻게 생겼는지가 함께 있다. 엔진은 UI 파일을 읽지 않고 G247·G248의 `Call`·`CheckCall`·`ViewAs(…).Call`·`Changed`만 준다. 함수 이름이 틀렸는지는 호스트가 UI 파일을 읽을 때 `CheckCall`로 확인한다("혹시 …?"까지 엔진이 준다). 엔진이 검사하는 공통 패널 목록(무엇을 보여 줄지만 적은 층)은 두지 않는다. 범용 호스트가 여럿 생기면 그때 덧붙인다. 호스트 파일이 이미 함수 이름을 가리키므로 길은 막히지 않는다. S10 2항의 "같은 정의가 AI의 합법 수 열거에도 쓰인다"는 커맨드 정의가 맡는다(G184 `LegalMoves`, G232 `LegalResponses`). 그래서 UI 파일이 호스트 것이어도 AI는 그대로다.

**이유:** 모더는 대개 게임 하나와 그 게임이 고른 호스트 하나를 목표로 한다. RimWorld와 패러독스는 클라이언트가 하나다(일반 지식). 호스트가 몇 개(Godot·Unity·콘솔)뿐이면 공통 마크업과 호스트별 번역기를 만드는 값이 따로 쓰는 값보다 크다. Godot에는 마크업이 없어(노드 트리·컨테이너·Theme, 일반 지식) 번역기가 특히 크다. 이전 엔진은 UXML 안에 `binding-path`와 인라인 스타일을 두고 USS를 런타임에 직접 파싱했다(`Scripts/Test/Core/UIRepeaterTester.cs`, `Scripts/Core/Data/Base/UI/RuntimeStyleSheet.cs`). 그 바인딩이 문자열 경로라 Unity와 스키마에 묶였는데, 이제는 값이 모드의 순수 함수(G244)이므로 호스트 파일은 함수 이름만 가리킨다. 범용 콘솔 호스트도 호스트 하나라서 게임 모드가 콘솔용 UI 파일을 가지면 된다.

**상태:** 확인

## G250

**위치:** G249에서 이어서: 콘솔 호스트의 UI 파일

**무엇이 비어 있었나:** G249로 UI 파일은 호스트의 것이 됐다. 콘솔 호스트는 지금 스키마를 따라 모든 엔티티를 늘어놓아(`ConsoleGame.WriteState`) 게임을 몰라도 되지만 판이 읽히지 않는다. 콘솔이 모드에게서 무엇을 보여 줄지 받을 자리가 없었다.

**어떻게 정했나:** 모드 폴더의 `ui/console.txt`. 한 줄에 `모드.함수` 하나이고 `#` 뒤와 빈 줄은 무시한다. 여러 모드에 있으면 로드 순서대로 모은다. 화면을 그릴 때마다 자리(연결)마다, 그 연결이 앉은 엔티티마다 줄 순서대로 `world.ViewAs(연결).Call(함수, 앉은 엔티티)`를 부른다(앉은 엔티티가 UI의 "나", G127). 돌려준 값이 문자열이면 그대로, 목록이면 항목마다 한 줄, 그 밖은 콘솔의 값 글로 보인다. 지난 결과의 `Changed`가 거짓이면 다시 부르지 않고 지난 줄을 쓴다(G246). 시작할 때 줄마다 `CheckCall(함수, 1)`로 확인해 틀리면 `ui/console.txt:줄`과 이유("혹시 …?")를 보이고 멈춘다(로드 오류와 같다). 부르다 실패하면(G247) 그 칸에 오류 줄을 보이고 나머지는 계속 그린다. 파일이 없으면 지금의 덤프를 쓴다.

**이유:** 콘솔에 지금 필요한 것은 부를 함수 목록뿐이라 줄 단위 텍스트가 가장 직접 담는다. 파이썬 부분집합(`panel(...)`)은 커널 `Parser`로 읽을 수는 있지만 호출을 해석하는 평가기를 콘솔에 따로 짜야 하고, 명령줄 `--panel`은 무엇을 보여 줄지가 모드가 아니라 실행 명령에 남는다. 패널 제목이나 행동이 필요해지면 콘솔 혼자 형식을 바꾸면 된다(G249).

**상태:** 확인

## G251

**위치:** G235의 남은 몫: 남의 엔티티를 읽는 `derived`와 거른 읽기의 도장

**무엇이 비어 있었나:** G235의 바뀜 도장은 저장된 값을 쓸 때만 찍혀, 다른 엔티티를 읽는 `derived`(진영의 `Power.total` = 소속 유닛 hp의 합)는 유닛 hp가 바뀌어도 진영의 `Version(id)`·`Version(id, "Power")`가 그대로다(임시 테스트로 재현: 값은 4 → 9, 도장은 같음). 같은 값을 `world.Call`로 읽으면 영수증의 `Changed`는 참이었다(함수 안의 `derived`가 읽은 유닛도 기록됨). 도장만 보는 호스트(콘솔 덤프)는 옛 값을 보인다.

**어떻게 정했나:** 바뀜 도장은 **저장된 값의 도장**으로 확정한다. 남의 엔티티를 읽는 `derived`와 보는 쪽 세계(`ViewAs`)는 도장에 담지 않는다. 화면 값은 G244~G248대로 `Call`·`ViewAs(…).Call`로 읽고, 그 영수증이 함수 안의 `derived`가 읽은 남의 엔티티와 보기 정책이 읽은 곳까지 담는다. 도장은 저장·동기화·디버그용 바닥으로 남는다. 콘솔 덤프(UI 파일이 없을 때)는 `derived` 칸이 있는 엔티티의 줄을 매번 다시 읽는다.

**이유:** 도장이 `derived`까지 담으려면 계산마다 읽은 곳을 기억하고 `Version`이 그 최댓값을 구해야 한다. 그러면 숫자 하나 읽기가 아니게 되고, 계산한 적 없는 `derived`는 먼저 계산해야 하며, `Call` 영수증이 이미 하는 일을 한 번 더 만든다. Bevy의 `Changed<T>`와 Unity ECS의 바뀜 필터는 저장된 컴포넌트만 추적하고 계산값은 쓰는 쪽이 다시 계산할지 정한다. Salsa는 계산 결과마다 의존 그래프를 두지만 그것이 라이브러리의 핵심 기능이다(일반 지식).

**상태:** 확인

## G276

**위치:** S6 동작 종류·S10 3항 `@ui_action`: 화면만 바꾸는 동작을 누가 쓰나 (S6 열린 질문의 바탕)

**무엇이 비어 있었나:** spec은 버튼이 시뮬레이션 커맨드(`command=`)나 클라이언트 로컬 동작(`ui_action=`)을 가리킨다고만 정했다. UI 정의 파일은 호스트의 것(G249)이라, 화면만 바꾸는 동작(유닛 골라 두기, 창 펼치기, 렌즈)을 모드 스크립트가 쓰는지 호스트 언어(Unity C#, Godot 스크립트)가 쓰는지가 정해지지 않았다. 로컬 저장소의 모양과 본문의 범위는 이 답에 달려 있다.

**어떻게 정했나:** 모드 스크립트가 쓴다. 엔진이 `@ui_action`과 UI 로컬 저장소를 주고, 호스트의 UI 파일은 그 이름을 가리키기만 한다. 모양은 커맨드와 같게(이름, 타입 있는 매개변수, 로드 때 검사, 모드가 덮어쓰기·패치), 효과는 로컬로만(게임 상태는 읽기만, 로그·저장·네트워크·되감기·입구 검사 없음, 게임을 바꾸려면 커맨드를 제출). 첫 구현은 콘솔 호스트로 시험할 수 있는 작은 몫(스커미시의 "유닛 고르기 → 공격")부터. 로컬 저장소의 모양, 본문이 할 수 있는 것, 커맨드 이름·인자를 UI 파일에서 검사하는 API는 이어서 정한다.

**이유:** 사용자는 UI의 모양뿐 아니라 동작도 모드로 고칠 수 있기를 바란다(2026-10-19). 호스트 언어로 쓰면 모더가 동작을 고치려면 C#·GDScript를 써야 한다. CK3는 GUI 파일을 모드로 고칠 수 있고, 화면만 바꾸는 것은 저장되지 않는 UI 로컬 변수(`GetVariableSystem`)로, 게임을 바꾸는 버튼은 모더가 선언한 `scripted_gui`(`effect`·`is_shown`·`is_valid`, 멀티플레이 동기화)로 나눈다. RimWorld는 버튼(`Command_Action`)이 델리게이트로 상태를 바로 고쳐 멀티플레이 모드가 버튼마다 동기화 패치를 단다(둘 다 일반 지식, 세부 미확인). 이전 엔진의 QU는 초안을 시뮬레이션 상태에 적어 세이브·네트워크로 샜다(use-cases U12).

**상태:** 확인

## G277

**위치:** S6 열린 질문 "`@ui_action`의 로컬 저장소 모양" (G276에서 이어서)

**무엇이 비어 있었나:** G276으로 화면만 바꾸는 동작은 모드 스크립트의 `@ui_action`이 쓰고 그 상태는 UI 로컬 저장소에 두기로 했다. 저장소가 어떤 모양인지(선언하나, 아무 키나 쓰나, 엔티티에 붙나), 누구 것인지가 없었다.

**어떻게 정했나:** 스키마에 타입을 선언한다(예: `ui_state("Selection", unit=Optional[Ref[Unit]])`). 선언마다 **연결 하나에 기록 하나**이고(보는 쪽마다 따로, G127의 UI의 "나"와 같은 까닭), `@ui_action`이 쓰고 화면 함수가 읽는다(스크립트 표기는 예시로 `ui.Selection.unit`). 칸 이름·타입은 컴포넌트·커맨드처럼 로드 때 검사해 `파일:줄`과 "혹시 …?"를 낸다. 칸에 넣을 수 있는 값은 커맨드 인자와 같다(수·문자열·참거짓·Ref·리스트·사전). 엔티티마다의 표시는 `dict[Ref[Unit], bool]` 같은 칸으로 담는다. 이어서 정할 것: 선언의 정확한 표기와 기본값, 가리키던 엔티티가 없어질 때, 화면 함수가 읽을 때의 영수증, 저장소의 수명(언제 비우나).

**이유:** 타입 없는 사전(`ui["selected"]`)은 가장 간단하지만 오타가 조용히 빈 값이 된다(spec S9 "조용히 잘못 동작할 수 있으면 오류"에 어긋남). CK3의 UI 변수(`GetVariableSystem.Set("이름", 값)`)가 그런 문자열 키 방식이다(일반 지식). 엔티티에 로컬 칸을 붙이는 방식은 "어느 창이 열렸나"처럼 엔티티와 무관한 상태를 담지 못한다. 선언 방식은 엔진의 나머지(컴포넌트·커맨드)와 같은 검사를 받는다.

**상태:** 확인

## G278

**위치:** S6 동작 종류·S10 3항: `@ui_action` 본문이 할 수 있는 것 (G276·G277에서 이어서)

**무엇이 비어 있었나:** spec은 UI 동작이 "시뮬레이션 상태를 읽을 수 있고 쓸 수 없으며 커맨드를 제출할 수 있다"고만 했다. 어느 세계를 읽는지, 무엇이 금지인지, 실패하면 어떻게 되는지, 제출의 결과를 본문이 아는지가 없었다.

**어떻게 정했나:**
- 매개변수는 커맨드처럼 타입을 적는다. 보고 있는 엔티티(UI의 "나", G127)는 화면 함수(G250)처럼 호스트가 인자로 넘긴다(예: `def click(me: Ref[Party], u: Ref[Unit])`).
- 읽기: 게임 상태는 그 연결이 보는 세계(`ViewAs`, G248과 같은 길)로만 읽는다.
- 쓰기: UI 로컬 저장소(G277)만. 엔티티 쓰기·`spawn`·`destroy`·`emit` 등 게임을 바꾸는 내장은 로드 오류.
- 금지: 난수(게임의 시드 난수를 소모하면 판이 갈라짐), 멈추는 호출(`ask`·`wait`·`advance`).
- 오류: 본문이 도중에 실패하면 그 동작이 바꾼 로컬 값과 적어 둔 `submit`이 모두 없던 일이 된다(커맨드의 되감기와 같음).
- `submit("커맨드", 인자=…)`는 내 달라고 적어 두기만 한다. 동작이 끝나면 호스트가 적힌 순서대로 내고, 거절 이유는 호스트가 보인다. 본문은 결과를 모른다. 결과에 따른 화면은 다음 화면 함수가 게임 상태를 보고 그린다.

**이유:** 바로 내고 결과를 받으면(`r = submit(...)`) 네트워크 게임에서 클릭 동작이 서버 왕복 동안 멈춰야 하고, 동작 한가운데서 게임 상태가 바뀌어 앞뒤 읽기가 어긋난다. spec S6은 네트워크 방식을 정하지 않고 커맨드가 호스트의 큐를 거친다고 했으므로, 적어 두기만 하는 쪽이 락스텝·서버 권위 모두에 맞는다. 커맨드 하나를 돌려주는 방식은 단순하지만 여럿을 내거나 조건에 따라 내기가 어색하다. CK3의 GUI 버튼도 효과를 보내기만 하고 결과를 그 자리에서 받지 않는다(일반 지식, 세부 미확인). 보는 세계로만 읽는 것은 클릭 동작으로 숨긴 정보를 엿보지 못하게 하려는 것이다(G196~G206).

**상태:** 확인

## G279

**위치:** G277의 남은 몫: UI 로컬 저장소의 표기·기본값·없어진 엔티티·영수증·누가 드나

**무엇이 비어 있었나:** G277은 저장소를 스키마에 선언하고 연결마다 기록 하나를 둔다고만 했다. 선언의 표기, 처음 값, 가리키던 엔티티가 없어질 때, 화면 함수가 읽을 때의 영수증, 저장소를 월드와 호스트 중 누가 드는지가 없었다.

**어떻게 정했나:**
- 표기는 컴포넌트와 같다: `ui_state("Selection", unit=ref("Unit", optional=True), panel=field(bool, default=False))`. 칸은 모두 기본값이 있어야 하고(없으면 로드 오류) Ref는 `optional=True`여야 하며 처음은 `None`이다.
- 가리키던 엔티티가 없어지면 그 칸은 `None`으로 읽힌다(Ref의 id+세대, S8). 숨긴 엔티티는 그 연결의 세계 규칙을 따른다.
- 화면 함수가 UI 로컬 칸을 읽으면 영수증에 들어 그 칸이 바뀌면 `Changed`가 참이다(G246).
- **저장소는 호스트가 든다.** 엔진이 `UiState` 객체를 만들어 주고 호스트가 연결마다 하나씩 들며, `@ui_action`과 화면 함수를 부를 때 넘긴다. 엔진은 저장하지 않고, 언제 비울지(새 판·불러오기·재접속)는 호스트가 정한다. 콘솔은 자리마다 하나.

**이유:** 표기와 기본값은 컴포넌트를 따르되, UI 상태에는 `spawn`처럼 처음 값을 줄 때가 없어 기본값을 강제한다. 없어진 엔티티를 `None`으로 읽으려면 Ref가 늘 선택적이어야 한다. 저장소를 월드에 두면 서버 권위 게임에서 "내가 고른 유닛"이 서버의 월드에 들어가 이전 엔진 QU의 초안이 샌 모양이 된다(use-cases U12). 호스트가 들면 플레이어의 컴퓨터에 남고, 불러오기 뒤에도 창을 열어 둘지 같은 선택을 호스트가 할 수 있다.

**상태:** 확인

## G280

**위치:** S10 2항·G276~G279에서 이어서: 호스트가 `@ui_action`을 확인하고 부르는 법

**무엇이 비어 있었나:** 호스트는 UI 파일을 불러올 때 버튼의 이름을 확인하고, 누를 수 있는지(회색 버튼과 이유)를 보고, 눌러서 적힌 `submit`을 받아 내야 한다. 콘솔은 마우스가 없어 누를 수 있는 것을 나열해야 한다. 값 함수에는 `CheckCall`·`Call`이 있지만 UI 동작과 커맨드 버튼에는 짝이 없었다.

**어떻게 정했나:**
- `@ui_action`도 커맨드처럼 `with preconditions:` 안에 `require`·`choose`를 쓸 수 있다(입구 검사와 `cost`는 없음).
- 호스트 API는 커맨드의 것을 따른다: 이름 확인, `Candidates`·`LegalMoves`·`CheckPreconditions`에 해당하는 것, 부르기 `Act(ui, 이름, 인자)`. `Act`는 거절(이유)이나 적힌 `submit` 목록을 돌려준다. 모두 `ViewAs(연결)`의 세계에서 돈다(G278).
- 커맨드를 바로 가리키는 버튼(`command=`)을 위해 커맨드 이름과 매개변수 이름을 확인하는 `CheckCommand`를 `CheckCall` 옆에 둔다.
- 화면 함수도 `UiState`를 받아 부르는 꼴(`ViewAs(연결).Call(이름, ui, 인자…)`)을 더한다(G279).

**이유:** 사전 조건이 없으면 엔진 일은 작지만 회색 버튼을 그릴 수 없고 콘솔이 누를 수 있는 것을 나열할 수 없다. 커맨드의 사전 조건 실행기를 그대로 쓰면 같은 정의가 회색 버튼·나열·제출 검사에 함께 쓰인다(spec S6 `choose`의 "제출 검사와 나열 양쪽", G276의 "모양은 커맨드와 같게"). CK3 `scripted_gui`의 `is_shown`·`is_valid`가 이 자리다(일반 지식).

**상태:** 확인

## G281

**위치:** G277에서 이어서: `ui_state` 이름의 이름 공간 (구현하며 드러남)

**무엇이 비어 있었나:** 같은 모드에 `component("Selection", …)`와 `ui_state("Selection", …)`가 함께 있을 때 어떻게 되는지 정하지 않았다. UI 기록은 `ui.Selection`으로만 쓰이지만 스텁(`.pyi`)에서는 둘 다 `class Selection`이 된다.

**어떻게 정했나:** UI 기록 이름은 Def 타입·컴포넌트·신호와 한 이름 공간이다. 겹치면 `SCH` 이름 중복 오류(한 모드면 "declared more than once", 여러 모드면 충돌 오류)다. Def 타입·컴포넌트 자리에 UI 기록 이름을 쓰면 "is a UI state, not a …"로 알린다.

**이유:** 따로 두면 스텁 클래스 이름을 `UiSelection`처럼 바꿔 내야 하고 읽는 사람도 헷갈린다. 신호도 이미 같은 이름 공간이다(G145).

**상태:** 확인

## G282

**위치:** G278·G279에서 이어서: `ui.…`와 `submit`을 쓸 수 있는 함수 (구현하며 드러남)

**무엇이 비어 있었나:** G278은 `@ui_action` 본문이 UI 기록에 쓰고 `submit`한다고만 했다. 여러 동작이 함께 쓰는 보통 함수(`remember(u)`처럼 기록을 고치는 도우미)가 `ui`를 써도 되는지, 게임 쪽 코드(커맨드·핸들러·반응·정책·`derived`)가 그런 함수를 부르면 어떻게 되는지 정하지 않았다.

**어떻게 정했나:**
- 보통 함수도 `ui.기록.칸`에 대입하거나 `submit`할 수 있다. 그런 함수는 "UI를 쓰는 함수"이고 `@ui_action`이나 다른 UI를 쓰는 함수 안에서 문장으로만 부른다(쓰기 함수의 G117과 같은 규칙). `submit` 자체도 문장으로만 부른다.
- "UI를 건드린다"(읽기든 쓰기든 `submit`이든)는 표시는 문장 호출·식 호출 모두를 따라 퍼진다. 게임 쪽 입구(`@command`·`@on`·`@when`과 그 조건·`acts_for`·정책 함수)와 순수 자리(`derived` 등)는 그런 함수를 쓸 수 없다(`CMD007`, 증거는 처음 건드린 곳).
- 거꾸로 `@ui_action`은 게임을 바꾸거나 난수를 쓸 수 없다(`CMD007`). `ui.기록.칸.x = …`처럼 기록이 가리키는 엔티티에 쓰는 것도 게임 쓰기다.
- `ui`는 늘 `ui.기록.칸` 꼴로 적는다. `s = ui.Selection`처럼 기록을 값으로 들 수 없다. 그러면 뒤의 `s.unit = …`가 UI 쓰기인지 엔티티 쓰기인지 알 수 없다. 기록·칸 이름이 틀리면 `EVL001`("혹시 …?"), 의존하지 않는 모드의 기록이면 `SCH003`이다.
- `submit("이름", 인자=…)`에 리터럴로 적은 커맨드는 링크 단계에서 본다(`CMD008`): 있는지, `@ui_action`이 아닌지, 보이는지(`LNK003`), 넘긴 이름이 매개변수인지, 기본값 없는 매개변수를 넘겼는지. 인자는 이름으로만 넘긴다. 이름을 계산한 `submit`은 실행 때 본다.
- 호스트의 `Call`은 UI를 쓰는 함수를 거절한다. UI를 읽는 화면 함수는 G280의 `Call(이름, ui, …)`가 들어올 때까지 거절한다.
- Def 값이나 패치로 `Cond[...]`·`Action[...]` 자리에 넣은 함수도 같다(2026-10-21 구현). UI를 건드리는 함수는 로드 오류이고, 패치로 넣었으면 그 패치 모드의 오류다(G64). 처음에는 쓰기·난수 함수만 이 자리에서 막아 `ui`를 읽는 함수가 로드를 통과하고 실행 때 터졌다.

**이유:** UI 기록은 연결마다 다르고 저장되지 않으므로, 게임 쪽 코드가 한 번이라도 읽으면 컴퓨터마다 판이 갈라진다(spec P2). 도우미를 막으면 동작마다 같은 줄을 복사해야 한다. 커맨드 쪽 쓰기 규칙(G117)을 그대로 따르면 엔진 일이 적고 모더가 익힐 규칙도 하나다. RimWorld의 `Find.Selector`는 게임 코드가 선택을 읽을 수 있어서, 선택에 기댄 동작이 멀티플레이 모드에서 어긋나는 원인이 된다(일반 지식).

**상태:** 확인

## G283

**위치:** G278·G280에서 이어서: `submit`한 커맨드가 응답 커맨드일 때

**무엇이 비어 있었나:** `free=True`가 아닌 커맨드(스커미시의 `Attack`)는 열린 질문의 답(`Respond(요청, 커맨드, 인자)`)으로만 들어간다. `@ui_action`의 `submit("Attack", …)`에는 요청 번호가 없어서, 어느 질문의 답인지 누가 알아내는지 정하지 않았다.

**어떻게 정했나:**
- 엔진이 짝을 찾는다. 호스트는 `Act`가 돌려준 `submit`을 엔진의 전달 함수에 넘긴다.
- 자유 커맨드면 `Submit`이다.
- 아니면 그 연결(issuer)이 답할 수 있는 열린 질문 가운데 그 커맨드를 받는 것을 찾는다. 하나면 거기에 `Respond`하고, 없거나 둘 이상이면 이유를 붙여 거절한다.
- 모더는 요청 번호를 다루지 않는다. 둘 이상이 흔한 사례(동시 차례에서 한 연결이 여러 진영을 맡는 등)가 나오면 `submit(..., request=…)`를 더한다.

**이유:**
- 요청을 모더가 적게 하면(B) UI 동작이 열린 질문을 읽는 길이 따로 있어야 하고 모든 모더가 번호를 다뤄야 한다.
- 자유 커맨드만 받게 하면(C) "유닛 고르기 → 공격"처럼 고른 것을 인자로 넘기는 흐름을 응답 커맨드로 만들 수 없다.
- CK3·Stellaris의 UI 버튼도 질문 번호 없이 커맨드를 보내고 받을지는 게임 쪽 조건이 정한다(일반 지식).

**상태:** 확인

## G284

**위치:** G279에서 이어서: UI 기록의 리스트·사전 안에 든 엔티티가 없어졌을 때

**무엇이 비어 있었나:** G279는 한 칸짜리 Ref가 가리키는 엔티티가 없어지면 `None`으로 읽는다고 했다. `ui_state`만 담을 수 있는 리스트·사전(`group=field(list[Ref[Unit]], default=[])`) 안의 엔티티가 죽으면 어떻게 읽는지는 정하지 않았다.

**어떻게 정했나:**
- 읽을 때 죽은 엔티티를 뺀 새 값을 준다. 리스트는 산 것만 원래 순서대로 남은 보통 리스트다(인덱스·`len` 그대로).
- 사전은 키나 값이 죽은 항목을 뺀다. 값 타입이 `None`을 못 받을 수 있으므로 `None`으로 바꾸지 않는다.
- 리스트·사전 안에 든 리스트·사전도 같다.
- 저장된 값은 그대로 두고 읽을 때만 거른다. 보는 사람에게 숨긴 엔티티도 같은 자리에서 빠진다(G198, `@ui_action`은 `ViewAs`로 읽음).

**이유:**
- 죽은 자리를 `None`으로 두면 `list[Ref[Unit]]`에 `None`이 섞여 모더가 매번 걸러야 하고, 그대로 `submit`하면 커맨드 쪽에서 타입 거절이 난다.
- G194의 약한 묶음처럼 인덱스를 막으면, 모더가 직접 만들고 순서를 쓰는 UI 리스트가 불편해진다.
- RimWorld의 선택 목록도 없어진 것을 빼 버린다(일반 지식).

**상태:** 확인

## G285

**위치:** G250·G280에서 이어서: 콘솔 호스트가 `@ui_action`을 보이고 부르는 법

**무엇이 비어 있었나:** 콘솔의 UI 파일 `ui/console.txt`(G250)에는 화면 함수 이름만 적는다. 마우스가 없는 콘솔이 UI 동작(유닛 고르기 등)을 어디에 어떻게 보일지, 메뉴에 띄울 동작을 모더가 적는지 정하지 않았다.

**어떻게 정했나:**
- `ui/console.txt`의 표기는 늘리지 않는다.
- 콘솔이 자리(연결)마다 `UiState`를 하나 든다(G279).
- UI 동작의 합법 수(`LegalMoves(ui, …)`)를 커맨드의 합법 수와 같은 번호 메뉴에 `[화면]`을 붙여 섞어 보인다.
- 고르면 `Act`를 돌리고, 적힌 `submit`을 차례로 `Deliver`해(G283) 결과를 한 줄씩 보인다.
- `ui/console.txt`의 화면 함수는 늘 그 자리의 기록과 함께 부른다(`Call(ui, …)`). 그래서 `ui`를 읽는 함수도 한 줄로 적는다.

**이유:** 콘솔은 엔진을 시험하는 호스트라 낼 수 있는 것을 모두 보이면 된다. 표기를 늘리면(`action 모드.이름` 줄) 모더가 고를 수 있지만 잊으면 동작이 보이지 않는다. 어떤 버튼을 어디에 둘지는 실제 호스트(Unity·Godot)의 UI 파일이 맡는다(G249). RimWorld도 버튼(gizmo)을 UI 파일에 적지 않고 고른 대상이 내놓는 것을 모아 보인다(일반 지식).

**상태:** 확인

## G286

**위치:** G278·G285에서 이어서: 콘솔이 UI 동작에 '나'(앉은 엔티티)를 넘기는 자리

**무엇이 비어 있었나:** G278은 보고 있는 엔티티(UI의 "나")를 호스트가 인자로 넘긴다고만 했다. 화면 함수는 콘솔이 첫 인자로 넘기지만(G250), 이름 붙은 매개변수를 갖는 `@ui_action`에서 어느 매개변수에 넣을지는 정하지 않았다.

**어떻게 정했나:** 콘솔 호스트의 약속이다(엔진 커널은 이 이름을 모른다). 이름이 `me`인 매개변수가 있으면 그 자리가 앉은 엔티티를 넣고, 남은 매개변수만 합법 수로 나열한다. 한 연결이 여럿에 앉았으면 앉은 엔티티마다 따로 나열한다. `me`가 없는 동작은 넣지 않고 자리마다 한 번 나열한다. 다른 호스트는 제 UI 파일에서 따로 정한다.

**이유:** 첫 매개변수에 넣으면 `def select(unit)`처럼 '나'가 필요 없는 동작에서 유닛 자리에 진영이 들어가 거절된다. `@ui_action`에 `acts_for`를 두면 엔진 일이 늘고 "호스트가 넘긴다"(G278)와 어긋난다. 샘플 화면 함수가 이미 `me`라고 쓴다.

**상태:** 확인

## G290

**위치:** G246에서 이어서: 영수증을 (엔티티, 컴포넌트) 단위로

**무엇이 비어 있었나:** G246의 영수증은 엔티티 단위였다. `u.Life.hp`만 읽은 화면 칸도 같은 유닛의 `Owner`가 바뀌면 다시 불러야 한다고 답했다(임시 테스트로 재현). G246은 나중에 (엔티티, 컴포넌트)로 나눠도 호스트 코드는 그대로라고만 했고, 무엇을 읽으면 어느 칸을 읽은 것으로 치는지는 정하지 않았다.

**어떻게 정했나:** 영수증은 읽은 것마다 칸 하나를 기록하고, 그 칸의 바뀜 도장(G235)을 본다.

- **컴포넌트 이름:** 멤버 읽기(`u.Life.hp`, 줄의 멤버), `u.Mark is None`(붙이기·떼기가 그 이름에 도장을 찍는다), 키 컴포넌트의 줄 읽기·`in`·반복, `contribs()`.
- **역방향 컬렉션 이름:** `p.units`.
- **죽었는지만:** Def와 그 `const`, Ref가 가리키는 대상(죽으면 `None`으로 읽힘), `c.entity`.
- **배정:** `controller(e)`는 배정이 바뀔 때만이다(안에서만 쓰는 칸 이름에 도장).
- 나머지 읽기는 엔티티 전체로 남는다(전보다 넓지 않다).
- `derived`는 값을 담아 두지 않고 읽을 때마다 계산하므로, 계산이 읽은 칸이 그대로 영수증에 든다(다른 엔티티의 칸 포함).
- 칸 하나 안의 멤버까지 나누지는 않는다. 같은 컴포넌트의 다른 멤버가 바뀌어도 참이다.
- `@when` 조건의 기록도 같은 단위다(2026-10-21 구현). 읽은 것은 영수증과 같은 (엔티티, 칸 이름) 모음 하나로 모으고, 쓰기 표시 `Touch(id, 이름)`가 그 칸을 읽은 조건과 엔티티 전체를 읽은 조건을 깨운다. 이름 없는 쓰기(생성·삭제)는 그 엔티티를 읽은 모든 조건을 깨운다. 빠뜨림은 `WhenTrackingTests`의 전체 훑기 견주기가, 덜 평가하는지는 `WhenNarrowingTests`가 본다.

**이유:** 도장이 이미 (엔티티, 칸) 단위라 새 상태 없이 읽는 쪽만 이름을 넘기면 된다(G246이 예상한 대로). 멤버 단위는 쓰기마다 도장이 늘고, 한 컴포넌트는 대개 한 화면 칸이 함께 보여 얻는 것이 적다. 빠뜨림을 막으려고 테스트가 쓰기 열일곱 가지를 하나씩 하며 "바뀌지 않았다"고 답한 영수증은 다시 불러도 값이 같은지 본다. 근거(일반 지식): React의 `useSelector`와 MobX는 컴포넌트가 실제로 읽은 값에만 구독하고, Unity ECS의 바뀜 확인도 컴포넌트 타입마다 따로 둔다.

**상태:** 확인 (사용자 동의 2026-10-21: Ref 대상·Def는 죽었는지만, 컴포넌트 안 멤버는 나누지 않음)

## G323

**위치:** S10 첫 실제 호스트 엔진 (2026-10-19 "호스트 엔진은 미정"에서 이어짐)

**무엇이 비어 있었나:** 호스트 엔진이 정해지지 않아 텍스트 콘솔 호스트로 커널 API를 시험해 왔다. S10의 UI 정의 파일 형식(G249는 "호스트마다 제 형식")과 바인딩·입력 연결은 실제 엔진이 있어야 정할 수 있었다.

**어떻게 정했나:** **첫 실제 호스트는 Unity다**(사용자 결정 2026-10-25). 사용자의 게임들(Quarantined·TurbulentRepublic·Wargame·DiveUp)과 같은 6000.3 줄을 쓴다.

- 커널을 Unity에 묶는 방법, UI 시스템, 첫 화면은 이어서 정한다.

**이유:** 사용자의 기존 게임과 이전 엔진(`uk.kesa.engine`, 로컬 UPM 패키지)이 Unity라 쓸 사람과 쓸 게임이 이미 있다. 커널이 `netstandard2.1`·C# 9로 Unity의 컴파일 조건에 맞춰져 있다.

**상태:** 확인

## G324

**위치:** G323에서 이어서: 호스트가 커널을 부르는 모양 (Unreal은 C#을 바로 부를 수 없어 "별도 프로세스 다리"를 논의하다 드러남)

**무엇이 비어 있었나:** 콘솔 호스트는 `World`를 바로 부른다. Unity 연결부도 그렇게 짜면 `World`·`Value`·`CallResult` 같은 커널 객체가 연결부 곳곳에 퍼지고, 나중에 다른 엔진(Unreal은 C++)이나 별도 프로세스·서버 권위 멀티플레이로 붙일 때 그 자리를 모두 고쳐야 한다. 그런데 연결부가 하는 일(값 함수 부르기와 영수증, 바뀌었나 묻기, 커맨드·응답 내기, 합법 수, 보는 사람마다 거른 읽기)은 같은 프로세스든 다리든 같다.

**어떻게 정했나:** **엔진 무관한 좁은 "호스트 세션" 경계를 둔다.**

- 경계는 호스트가 하는 일만 담고, 주고받는 것은 모두 데이터다: 엔티티 id는 수, 값은 직렬화되는 모양, 영수증은 객체가 아니라 핸들("이 핸들들 중 바뀐 것은?"). 커널 객체가 경계 밖으로 새지 않는다.
- 지금은 같은 프로세스 구현(경계 뒤에서 `World`를 바로 부름)만 만든다.
- Unity 연결부와 콘솔 호스트는 이 경계만 쓴다. 콘솔 호스트를 옮겨 경계가 충분한지 시험한다.
- 별도 프로세스·다른 엔진·네트워크는 같은 경계의 다른 구현(같은 메시지를 소켓·파이프에 싣기)으로 하고, 필요해질 때 만든다.
- 경계의 모양(무엇이 들고 무엇을 돌려주나)은 이어서 정한다.

**이유:** 셋 중 고른 것: `World`를 바로 부름(지금 가장 간단하나 다리를 놓을 때 연결부를 다 고침), 경계 + 같은 프로세스 구현(이것, 지금 비용은 거의 같고 다리가 구현 하나로 줄어듦), 처음부터 별도 프로세스(아직 필요 없는 직렬화 비용과 두 프로세스 디버깅). G244·G249가 "호스트에는 게임 로직이 없다"로 정해 경계가 좁다. 커널을 C++로 다시 짜는 길(실제 코드 약 3만 줄과 테스트)보다 다리가 훨씬 싸다. 근거: 언어 서버 프로토콜(LSP)은 에디터마다 얇은 쪽을 두고 약속은 하나다(일반 지식).

**상태:** 확인
