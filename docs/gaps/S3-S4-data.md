# spec 빈틈 상세: S3·S4 데이터

색인과 상태 규칙은 `docs/spec-gaps.md`. 이 파일은 G 번호마다 무엇이 비어 있었고 어떻게, 왜 정했는지의 전문이다.

## G23

**위치:** S4·schema-design 4.2 이름 충돌

**무엇이 비어 있었나:** Def 타입과 컴포넌트의 이름 공간, 충돌 시 어느 모드를 끌지.

**어떻게 정했나:** Def 타입과 컴포넌트는 **한 이름 공간**(둘 다 Def 파일에서 생성자 이름이 됨). 여러 모드가 같은 이름을 선언하면 선언한 모드 모두 `SCH001`. `extend`가 타입 자체의 이름과 겹치면 확장한 모드만, 두 확장끼리 겹치면 둘 다 `SCH005`. Def 타입 안에서 const·컴포넌트·`inverse` 이름도 한 이름 공간이다.

**이유:** "두 모드 이름을 담은 로드 오류"를 따랐다. 결과가 모드 id(로드 순서의 동률 규칙)에 달리면 안 된다(G10과 같은 해석).

**상태:** 잠정

## G27

**위치:** S3·S4 같은 컴포넌트 참조

**무엇이 비어 있었나:** `order_by="pos"`와 `default_from="max"`가 가리키는 범위.

**어떻게 정했나:** 둘 다 **같은 컴포넌트**의 다른 값. `order_by`는 `field`여야 한다.

**이유:** 예시가 모두 같은 컴포넌트였다. 원소의 다른 컴포넌트를 가리킬 필요가 생기면 넓힌다.

**상태:** 잠정

## G31

**위치:** S4 키 컴포넌트의 키

**무엇이 비어 있었나:** spec은 키로 "Def 타입이나 엔티티 Ref"를 허용하지만 표기는 `key="X"` 하나였다. X가 컴포넌트를 가진 타입이면 Def마다 한 줄인지 엔티티마다 한 줄인지 알 수 없다.

**어떻게 정했나:** 표기로 가른다. `key="SkillDef"`는 Def 키, `key=Ref["Faction"]`은 엔티티 키. 엔티티 키는 항상 `listed`(생략하면 자동, `keys="all"`은 `SCH004`)이고, 대상은 보이는 범위에서 컴포넌트를 가진 타입이어야 하며(`extend` 적용 뒤, 의존하는 모드가 붙인 컴포넌트만 셈. 아니면 `SCH004`), Def 리터럴에 줄을 적을 수 없다(`DEF003`, 로드 시점에는 엔티티가 없음).

**이유:** `Ref["X"]`는 엔티티를 가리키는 표기다(G32). 타입에 컴포넌트가 있는지로 판정하면 다른 모드가 `extend`로 컴포넌트를 붙이는 순간 Def 키가 엔티티 키로 뜻이 바뀐다.

**상태:** 확인

## G86

**위치:** S4 런타임 첫 슬라이스의 범위와 입구

**무엇이 비어 있었나:** 상태 변경의 입구는 커맨드(S6)인데 커맨드·Flow·트랜잭션이 아직 없어서, 런타임 모델을 어디서부터 만들지 없었다.

**어떻게 정했나:** 호스트용 C# API `World`부터 만든다. 동결된 `DefSet`으로 만들고, Def id로 엔티티 생성·삭제, 컴포넌트·멤버 핸들로 읽기·쓰기, `all(Type)` 순회, 키 컴포넌트 줄, Ref·`inverse`를 다룬다. 스크립트는 이번에 `derived` 계산에만 쓰고, 스크립트가 쓰는 길(커맨드 본문)은 S6에서 이 API 위에 얹는다. 경계는 핸들과 닫힌 값 타입뿐(P1a)이고 정적 기본 월드는 없다(P3). DOTS의 World에서 시스템을 빼고 컴포넌트를 스키마 칼럼으로 바꾸고 Def 기본값 읽기를 더한 것이다. 저장소 벤치(spec 9절)는 이 API가 생긴 뒤 같은 API로 잰다.

**이유:** 로딩처럼 아래층부터 쌓으면 S4의 규칙을 커맨드 없이 테스트로 확인할 수 있다. 커맨드·저장·“왜?” 도구가 모두 이 API를 부르므로 나중에 바뀌지 않는 경계다. 커맨드·Flow까지 한 번에 하면 트랜잭션·롤백·`ask`·난수열이 엮여 너무 크고, 벤치만 먼저 하면 실제 읽기 규칙이 빠져 결론이 약하다.

**상태:** 확인

## G87

**위치:** S3·S4·S8 엔티티 id 할당과 세대

**무엇이 비어 있었나:** spec은 엔티티를 “ID(+세대)”, 오래된 Ref를 세대 카운터로 감지한다고 했지만 id를 재사용하는지 없었다. 세대는 재사용할 때만 의미가 있고, 재사용 여부에 따라 “id 순”의 뜻이 달라진다.

**어떻게 정했나:** id는 **재사용하지 않는다**: 월드마다 1부터 올라가는 64비트 카운터이고 다음 id는 세이브의 카운터(S8 메타)에 저장한다. 그래서 id 순 = 생성 순이다. 오래된 Ref는 “그 id가 살아 있는가”로 감지하고 세대 칸은 두지 않는다(재사용이 없어 세대가 하던 일을 생존 여부가 한다). 내부 저장소가 빈 칸을 재활용하는 것은 자유다(밖으로 보이는 id만 재사용하지 않음, S4 저장 방식 비공개).

**이유:** `all(Type)`과 `inverse` 기본 순서가 생성 순이라 직관적이고 저장·로드 후에도 같다. 재사용(DOTS·Flecs)은 새 엔티티가 옛것보다 앞에 정렬되어 순서가 직관과 어긋나고 세이브에 빈 칸 목록까지 남겨야 한다. 64비트는 소~중규모(P6)에서 고갈되지 않는다. 늘 0인 세대 칸은 핸들·세이브·스텁에 쓸모없이 퍼진다.

**상태:** 확인

## G88

**위치:** S4 구조 변경의 반영 시점 (S4 ✅ “지연(command buffer)”을 바꿈)

**무엇이 비어 있었나:** S4는 구조 변경(생성·삭제·부착)을 지연한다고 했고, 그 결과 “같은 Flow에서 붙인 직후 읽으면 `None`일 수 있다”가 🟡로 남았다. 지연된 변경을 언제 반영하는지도 없었다.

**어떻게 정했나:** **즉시 반영한다.** 생성·삭제·컴포넌트 부착과 분리·키 줄 부착과 분리가 바로 읽기와 쿼리에 보인다. 순회(`all(Type)`, `inverse` 컬렉션, 키 줄 순회)는 시작 시점의 목록을 돌고, 순회 중에 죽은 엔티티와 뗀 줄은 건너뛰며, 순회 중에 생긴 것은 그 순회에 나오지 않는다. 내부에서 일괄 처리하더라도 이 의미는 유지한다. 병렬 서브시스템(P4)이 생기면 그 안에서만 지연 버퍼를 쓴다. spec S4의 해당 문장과 🟡, schema-design 3.3.2의 🟡를 고쳤다.

**이유:** 다른 ECS(DOTS·Flecs·Bevy)의 지연은 병렬 실행과 아키타입 청크 이동 때문이고, 독점·단일 스레드 문맥에서는 모두 즉시 반영한다. 모드 로직이 월드를 바꾸는 경로는 단일 스레드이고 순차적이다(S2 평가 모델, S6 순차 실행, S5 트랜잭션 = Flow 한 번). 남는 이유인 순회 안전은 시작 시점 목록과 죽은 것 건너뛰기로 같게 얻는다. “붙였는데 안 보임”이라는 덫이 사라진다. 롤백(C8)은 트랜잭션의 쓰기 기록이 맡으므로 반영 시점과 무관하다.

**상태:** 확인

## G89

**위치:** S4 `field` 초기값을 저장하는 시점 (schema-design 3.3.1 9항 보강)

**무엇이 비어 있었나:** Flyweight(쓰지 않은 칸은 Def를 읽고 Def 패치가 기존 엔티티에 닿음)와 “`default_from`·`default=함수`는 생성 시 초기값일 뿐, 그 뒤로 원천 값과 별개”를 함께 만족시키는 방법이 없었다. `keys="all"` 줄은 생성 순간이 없다(G77).

**어떻게 정했나:** **생성 순간**(엔티티 생성, 런타임 컴포넌트 부착, `keys="listed"` 줄 부착)에, Def가 값을 주지 않았고 스키마가 `default_from`이나 `default=함수`를 선언한 `field`만 계산해 엔티티 값으로 저장한다(오버라이드). Def가 값을 준 칸과 고정값 `default`는 저장하지 않고 Def·스키마를 읽는다. `keys="all"` 키 컴포넌트의 `field`에 `default_from`·`default=함수`를 쓰면 스키마 오류다(생성 순간이 없음; `keys="listed"`를 쓰라는 안내). 기존 세이브에 새로 더해진 이런 칸의 처리는 저장 슬라이스(S8 “칼럼 추가”)에서 정한다.

**이유:** 두 규칙을 모두 지키는 유일한 방법이다. 모든 `field`를 생성 때 저장하면 Def 패치가 기존 엔티티에 닿지 않고(S4 “의도”와 어긋남), 저장하지 않으면 `current`가 `max`를 계속 따라간다. `keys="all"` 줄(기술·자원·스탯)은 보통 고정 기본값이라 금지로 잃는 것이 적고 G77과 같은 성격의 규칙이다.

**상태:** 확인

## G91

**위치:** S3·S4 Ref 칼럼의 처음 값과 죽은 대상

**무엇이 비어 있었나:** 엔티티 Ref는 Def가 줄 수 없어(로드 시점에 엔티티가 없음, G32) 생성 순간 필수 Ref가 비어 있다. 대상이 죽은 Ref를 런타임에 읽을 때의 동작도 없었다.

**어떻게 정했나:** 생성 API가 `field`와 Ref의 처음 값을 받고, **필수(`optional` 아님) Ref는 생성 때 반드시 준다**(없으면 생성 실패). 그래서 “비어 있는 필수 Ref”는 생기지 않는다. 엔티티를 삭제해도 남의 Ref 칸은 그대로 두고, 읽을 때 대상이 죽었으면 `optional`은 `None`, 필수는 런타임 오류다(S8 로드 규칙과 같은 모양). 역방향 컬렉션은 살아 있는 출처만 담고, 엔티티 키 줄은 키 엔티티가 죽으면 지운다(S4). 죽은 엔티티를 Ref에 쓰는 것은 오류다. 서로를 필수로 가리키는 두 엔티티는 만들 수 없으므로 한쪽을 `optional`로 선언한다. 대상 삭제 시 함께 삭제·칸 비우기 같은 정책은 필요해지면 더한다. **구현 한계:** 키 컴포넌트 줄 안의 Ref는 역방향 컬렉션을 아직 만들지 않는다(`Inverse`가 “not supported yet” 오류).

**이유:** 오류가 먼 읽기가 아니라 원인 지점(생성)에서 난다(S9). 죽은 대상 규칙이 세이브 로드 규칙과 하나로 통일된다. 생성 시 초기값은 커맨드가 위치·소유자를 함께 주는 흔한 경우에 어차피 필요하다.

**상태:** 확인

## G92

**위치:** S4·P2 런타임 쓰기와 `min`·`max`

**무엇이 비어 있었나:** `field(int, min=0, max=20)`의 범위는 로드 때 Def 값과 스키마 기본값에만 검사했고(G68·G73), 런타임에 범위 밖의 값을 쓸 때의 동작이 없었다.

**어떻게 정했나:** **오류다.** 범위 밖의 값을 쓰면 쓰기가 실패한다(커맨드 안이면 커맨드 전체가 롤백, C8). 자르려면 `clamp()`로 명시한다. 생성 시 초기값(G91)과 `default_from`으로 계산한 초기값(G89)도 같은 검사를 받는다. 타입이 맞지 않는 값(예: `int` 칸에 `fixed`)도 오류다. 불러온 저장의 값도 같은 검사를 받는다: 모드가 범위를 좁혀 저장된 값이 벗어나면 `SAV002`로 거부하고 자르지 않는다(고치는 길은 S8의 `migrate`, G140 구현 때 보강).

**이유:** P2 “상한은 명시적 `clamp()`”와 S9 “조용히 잘못 동작할 수 있으면 오류”를 따른다. 조용히 자르면 “+1이 무시됨” 같은 버그가 숨는다. 범위는 선언된 불변식이라 로드 검사와 같은 모양으로 누가 쓰든 지킨다.

**상태:** 확인

## G93

**위치:** S4 기본값이 없는 칸의 런타임 값 (G67·G69·G91 보강)

**무엇이 비어 있었나:** G67은 `field`를 필수로 보지 않아 `field(fixed)`(기본값 없음)를 Def가 안 적으면 엔티티에 읽을 값이 없었다. Def에 없던 컴포넌트를 런타임에 붙이면 기본값 없는 `const`도 구멍이 된다(G67 검사는 Def가 가진 컴포넌트만 본다).

**어떻게 정했나:** **생성 순간에 구멍이 없어야 한다.** `Create`·`Add`(컴포넌트 부착)·`AddRow`(줄 부착)는 엔티티 값·Def 값·스키마 기본값 어느 것으로도 값이 정해지지 않는 칸이 남으면 실패한다. 기본값 없는 `field`는 생성 시 초기값(G91)으로 준다. 런타임에 붙이는 컴포넌트(줄)의 `const`는 기본값이 있어야 한다(엔티티는 `const`를 줄 수 없음). `keys="all"` 키 컴포넌트의 `field`는 기본값이 있어야 하고 없으면 스키마 오류다(생성 순간이 없음, G77·G89와 같은 성격). 같은 이유로 `keys="all"` 줄의 Ref는 `optional`이어야 한다(필수 Ref는 생성 때 줘야 하는데 줄을 만드는 순간이 없음, G91). 그래서 런타임에 “읽을 값이 없음”은 생기지 않는다.

**이유:** G91(필수 Ref는 생성 때)과 같은 원칙: 오류가 원인 지점에서 나고 상태에 구멍이 없다. 로드 쪽 G69 “동결본에 구멍 없음”을 런타임까지 잇는다. 타입의 0값은 `DefId`에 없고 깜빡 안 준 값이 조용히 0이 된다(S9). 읽을 때 오류는 원인과 먼 곳에서 난다.

**상태:** 확인

## G98

**위치:** S4 기여 행의 모양·수명과 `contribs` (G90 보강)

**무엇이 비어 있었나:** S4는 기여 행을 `(owner, 대상 값, 연산, 값, 출처)`와 수명 넷(영구, N틱, 이벤트, 출처 제거)으로만 적고 “넣는 쪽의 모양은 S4 기여 행 설계에서 정한다”로 미뤘다. `value`가 `int`인지 `fixed`인지, 행이 어디에 사는지, 커널이 책임질 수명이 무엇인지 정한 적이 없었다.

**어떻게 정했나:** **기여 행은 커널 전용 저장이다.** 열: `target`(엔티티, 컴포넌트, 키 줄이면 키, 값 이름), `op`(`str`, 커널에 불투명), `value`(`fixed`), `source`(엔티티 Ref, 선택). `int` 값을 넣으면 `fixed`로 올려 저장한다(G95). `World` API는 `AddContribution`·`RemoveContribution`·`RemoveBySource`다. **커널이 책임지는 수명은 출처 제거뿐이다:** `source`나 `target` 엔티티가 죽으면 엔진이 행을 지운다(엔티티 키 줄과 같은 규칙). N틱과 이벤트는 시간(X2)과 반응(S5)의 일이라 표준 모드가 만료 칼럼과 `when` 반응으로 행을 지운다. **대상이 될 수 있는 값은 `derived`뿐**이고 그 밖의 이름은 로드 오류다. 식에서 `r.value`는 늘 `fixed`이므로 `derived(int, ...)`는 `floor()` 등으로 명시한다.

**이유:** 스탯 시스템이 있는 게임은 대부분 숫자 하나로 통일한다(RimWorld `float`, Paradox 고정소수점). 통일하면 다른 모드의 소수 기여 때문에 `derived(int)`가 멀리서 터지는 일이 없고, 저장·trace·`.pyi`가 한 타입이다. `floor()` 소음은 `std.stats`가 감싼다. `field`·`const`를 대상으로 하면 저장값과 합산 값이 헷갈린다. 정수 스탯에 소수 기여가 조용히 잘리는 점은 나중에 “대상이 `int`면 `fixed` 기여 거부” 검사로 좁힐 수 있다.

**상태:** 확인

## G99

**위치:** S4 `field`가 `derived` 상한을 넘는 경우 (schema-design 3.3.1 🟡)

**무엇이 비어 있었나:** 버프가 풀려 `max`가 15에서 13이 되면 저장된 `current`는 15로 남는다. `derived`는 쓸 수 없어 스스로 고치지 못한다. 후보는 읽을 때 `min`으로 보이기(A), settle 반응으로 잘라내기(B), 게임이 고르기(C)였다.

**어떻게 정했나:** **C로 정한다: 커널은 자동 규칙을 두지 않는다.** `field`의 `min`/`max`는 계속 숫자 리터럴만 받고(현재 동작) 다른 값을 따라가는 상한은 지원하지 않으며, 그렇게 쓰면 오류 `EVL` 타입 오류에 안내를 더했다. `current`가 `max`보다 큰 상태는 읽힐 수 있는 알려진 한계다. 모드가 쓸 표준 패턴: (D) `damage`를 `field`로 저장하고 `current`를 `derived`(max 빼기 damage, 0 아래는 clamp)로 둔다. 불변식이 필요 없고 버프가 다시 붙으면 복원된다. (B) S5가 생긴 뒤 `std.stats`가 settle 반응으로 저장값을 자르는 패턴을 제공한다.

**이유:** 선언으로 동적 상한을 거는 엔진은 조사에서 찾지 못했다(Unreal GAS는 게임 코드의 훅에서 클램프하고 RimWorld는 현재값 대신 피해량을 저장한다고 기억한다). A는 저장값과 읽는 값이 다르다는 규칙을 커널이 영구히 지게 되고 세이브가 달라져 B로 못 바꾼다. 지금 약속하지 않으면 나중에 열 수 있다. B는 반응 엔진(S5)이 필요하다.

**상태:** 확인

## G100

**위치:** S4·S2 `derived` 순환 검사 (schema-design 3.3.1 5항)

**무엇이 비어 있었나:** spec은 순환을 로드 시점에 타입으로 속성 경로를 보수적으로 추적해 막고 빠져나간 것은 실행 중 재진입 감지로 막는다고 했다. 정적 추적이 어디까지 보는지, 재진입 오류가 무엇을 보여 주는지 정한 적이 없었다.

**어떻게 정했나:** **이번 슬라이스는 실행 중 재진입 감지만 한다.** `derived` 계산 중 호출 스택에 같은 (엔티티, 컴포넌트 줄, 값 이름)이 이미 있으면 실행 오류이고, 메시지에 호출 체인(예: max, cap, max)을 보여 준다. 로드 시점 정적 추적은 로직용 `.pyi`(G207)와 같은 타입 정보를 쓰도록 그때 한다(G229로 함: 같은 엔티티 안의 순환만 로드 오류).

**이유:** 재진입 감지는 정적 검사가 놓친 경우의 안전망이라 어차피 필요하고 `World` 읽기와 바로 연결된다. 정적 추적은 식에 타입 추적기가 필요해 따로 만들면 `.pyi`와 중복된다. 그전까지 `check`는 순환을 잡지 못하고 읽을 때 오류가 난다는 한계가 있다.

**상태:** 확인

## G103

**위치:** S4·schema-design 3.3.1 2항 `derived` 함수 안에서 형제 컴포넌트와 엔티티에 닿는 길

**무엇이 비어 있었나:** 3.3.1은 함수 인자를 컴포넌트 하나로 정하고 “소유 엔티티를 거친 다른 컴포넌트”를 읽는다고 했지만, 컴포넌트에서 엔티티나 형제 컴포넌트로 가는 표기를 정한 적이 없다. 예시의 `h.owner`가 무엇인지 불분명했고, 형제를 읽을 때마다 엔티티로 올라갔다 내려와야 했다.

**어떻게 정했나:** **컴포넌트 인자는 유지하고 형제를 바로 읽는다.** `h.base_max`(내 값), `h.Location.city`(같은 엔티티의 형제 컴포넌트, 컴포넌트 이름으로), `h.Owner.faction.Tech.level`(형제, Ref, 다른 엔티티의 컴포넌트), `h.entity`(엔티티 자신, 함수에 넘기거나 비교할 때만). Def가 가진 컴포넌트는 항상 있고 런타임에만 붙는 컴포넌트는 스텁에서 None일 수 있는 타입이라 없는 형제의 멤버를 읽으면 실행 오류다. 키 컴포넌트 줄은 `s.key`(키)와 `s.entity`를 갖고 형제는 같은 방식이다. **예약 이름은 `entity`와 `key`**: 컴포넌트 멤버 이름으로 쓰면 스키마 오류이고, 컴포넌트 이름과 그 컴포넌트의 멤버 이름이 같아도 스키마 오류다. read-set에는 읽은 (엔티티, 컴포넌트 줄, 멤버)를 기록하며 형제를 읽는 것도 같다.

**이유:** 타입이 정확한 컴포넌트 인자(컴포넌트는 여러 Def 타입에 붙을 수 있어 엔티티 인자는 타입을 정할 길이 없음)를 지키면서 올라가는 단계를 없앤다. “소유”라는 말은 엔티티가 컴포넌트를 소유한다는 뜻으로 오해되어 쓰지 않는다.

**상태:** 확인

## G105

**위치:** S4 `derived`의 월드 연결과 읽은 값 근거(trace) (G90·G100·G103 보강)

**무엇이 비어 있었나:** 실행기를 월드에 어떻게 물릴지, 읽은 값(read-set)을 어떤 모양으로 내보낼지, 캐시를 둘지가 비어 있었다.

**어떻게 정했나:** **월드는 로드 결과의 모드 이름 공간을 받아** 함수 본문이 같은 모드의 함수·상수를 부를 수 있게 한다. `derived`는 읽을 때마다 새로 계산하고 캐시하지 않는다. **근거는 `World.Explain(엔티티, 멤버)`로만 낸다:** 계산 중 실제로 읽은 값의 트리(`ExplainNode`)이며, 종류는 저장값 읽기, 다른 `derived` 읽기(안쪽에 그 계산의 근거가 중첩), 기여 행 하나다. 읽은 순서대로 나열하고 같은 값을 두 번 읽으면 두 번 나온다. 기록은 `Explain` 중에만 켜지므로 평소 읽기에는 비용이 없다. 함수가 돌려주는 값은 선언한 타입과 맞아야 하고 `int`는 `fixed`로 올려 주지만 `fixed`를 `int` 칸에 돌려주면 `floor()` 등을 쓰라는 안내와 함께 거부한다. `derived`가 다른 `derived`를 읽는 연쇄의 깊이 상한은 64다. 실행 오류는 위치와 호출 흔적이 붙은 `WorldException`이 되고 코드는 그대로다. 다른 `derived`를 읽다가 난 오류의 흔적은 끊기지 않는다: 안쪽 함수들, 경계 줄 `reading 컴포넌트.값 of #id`, 바깥 함수들 순이고 바깥 쪽 가장 안 함수에는 그 값을 읽은 위치가 `at 파일:줄`로 붙는다(처음 구현은 안쪽 흔적만 남았고 실행기 검토에서 고쳤다). 캐시와 변경 추적은 필요가 생길 때 read-set을 이 기록기 위에 더한다.

**이유:** 사용자가 “읽은 값 기록을 근거로 노출하고 캐시는 나중에”(A)를 골랐다. 근거를 항상 모으면 모든 읽기가 느려지고, 캐시는 무효화 규칙이 필요해 아직 근거 자료가 없다. 트리 모양은 사용자와 세부를 논의하지 않은 잠정 모양이다.

**상태:** 확인

## G106

**위치:** S4 생성 순간에 계산하는 기본값의 순서와 실패 (G89·G90 보강)

**무엇이 비어 있었나:** 함수 기본값과 `derived`를 원천으로 하는 `default_from`은 엔티티가 있어야 계산되는데, 한 컴포넌트에 이런 칸이 여럿이면 서로 읽는 순서와 계산이 실패했을 때의 상태가 비어 있었다.

**어떻게 정했나:** 엔티티(컴포넌트, 줄)를 먼저 만든 뒤 이런 칸을 **선언 순서대로 하나씩 계산해 저장**한다. 앞 칸은 뒤 칸이 읽을 수 있고, 아직 계산되지 않은 뒤 칸을 읽으면 “아직 값이 없다”(`RUN007`)로 생성이 실패한다. **계산이 하나라도 실패하면 호출 전체를 되돌린다:** `Create`는 엔티티, 색인, id 증가분까지, `Add`는 붙인 컴포넌트, `AddRow`는 붙인 줄을 지운다. 오류에는 어느 칸의 기본값인지와 생성 맥락이 붙는다. 의존 순서 자동 정렬은 하지 않는다.

**이유:** 규칙이 한 줄이고 오류가 분명하다. 읽는 칸이 실행 중에 정해지므로 자동 정렬은 순환과 비용 문제를 만들고 지금 필요한 근거가 없다. 실패한 호출은 월드를 바꾸지 않는다는 기존 규칙(G91·G93)과 같다.

**상태:** 확인

## G129

**위치:** S4 상태에 담는 “이름 없는 값의 순서 있는 목록” (G128에서 이어짐)

**무엇이 비어 있었나:** 주사위 눈 `[5, 2, 6]`처럼 정체성 없는 값의 목록을 공유 상태에 둘 자리가 없었다: 런타임 필드에 리스트 금지, 키 컴포넌트의 키는 Def·엔티티만(schema-design 3.3.2 “런타임 int·str 키 금지, 오타 검사 불가”), 행 값의 맵 ❓. int 키 금지는 str 키와 묶인 것이고 이 경우(이전 게임에서 컴포넌트가 아니라 컨텍스트 바구니에 있었음)는 사례 표 P1~P5에 없었다.

**어떻게 정했나:** **키 컴포넌트의 키로 `int`를 허용한다(항상 `listed`).** `component("Die", key=int, value=field(int))` → `node.Die[0].value`. `keys="all"`은 오류(끝없는 키), 정적 접근 표기는 없고 `[i]`만, 없는 칸은 `None`. 줄 칼럼에 Ref를 둘 수 있다(일반 Ref 칼럼 규칙). **리스트처럼 쓰는 커널 내장 헬퍼 둘:** `replace_rows(node.Die, [...])`(모든 줄을 지우고 0부터 다시 만듦), `append_row(node.Die, ...)`(최대 키 + 1). 읽기는 키 순 순회, 칸 하나는 속성 대입. 번호를 다시 매기는 것은 **지우고 새로 만들기**라서 지워진 줄을 대상으로 하던 기여 행은 함께 지워진다(줄에 붙은 것을 유지해야 하면 원소에 정체성이 있다는 뜻이므로 원소 엔티티를 쓴다). `str` 키 금지는 그대로다. 스칼라 리스트 칼럼(`field(list[int])`)과 상태 안의 자유 리스트·맵은 열지 않는다(S2 리스트·맵 표의 “키 컴포넌트 줄의 맵 ❓”도 열지 않음으로 닫는다). `insert`·`remove_at` 같은 헬퍼는 실제로 자주 필요해지면 더한다. 구현은 스크립트에서 줄을 붙이고 떼는 길(handoff 미룸)과 함께 한다.

**이유:** ECS를 관계형 DB로 보면 S4 규칙은 정규화(제1정규형, 외래 키 = Ref, 키 컴포넌트 = 복합 키 테이블)이고, int 키 줄은 `order_lines(order_id, line_no)` 같은 약한 엔티티다. JPA `@OrderColumn`(순번 칼럼으로 리스트를 매핑하고 중간 삭제 시 순번을 고쳐 씀)이 같은 모양이다(일반 지식). 자유 리스트·맵(JSONB 같은 비정규화)은 숨은 참조 정리, 키 오타 로드 검사(TR `PaidExtraOP` 사례), 스키마 마이그레이션 추적, 단일 쓰기 경로(G117)를 깨뜨린다. 스칼라 리스트 칼럼과 함께 열면 순서 있는 목록을 만드는 방법이 셋이 된다. 헬퍼가 커널 내장인 것은 남의 컴포넌트 칼럼을 스크립트가 일반적으로 복사할 수 없어서다(이름 문자열이면 로드 검사가 사라짐).

**상태:** 확인

## G134

**위치:** S4·S6 스크립트에서 엔티티 생성·삭제, 런타임 컴포넌트 부착·분리, 키 줄 붙이기·떼기의 표기

**무엇이 비어 있었나:** spec은 구조 변경이 즉시 보인다는 것(G88)만 정하고 스크립트 표기가 없었다. 호스트 C# API(`Create`·`Destroy`·`Add`·`Remove`·`AddRow`·`RemoveRow`)만 있었다. 타입 이름 호출 `Unit("x", ...)`은 S2 표에서 로드 시점의 Def 생성이고, `add`·`remove`는 `patch.add`·`patch.remove`와 겹친다. 컴포넌트 값 생성자 `Health(...)`는 로드 시점 이름이었다.

**어떻게 정했나:** **이름 붙은 커널 내장 함수 여섯과, 처음 값은 Def 리터럴과 같은 컴포넌트 값 모양.** `u = spawn("core.Warrior", Health=Health(current=3))`(Ref를 돌려줌), `destroy(u)`, `attach(u, Wounded(turns=3))`, `detach(u.Wounded)`, `add_row(u.Skill, "core.Medicine", Skill(level=3))`, `remove_row(u.Skill, "core.Medicine")`. 줄 함수는 G129의 `append_row(node.Die, ...)`처럼 첫 인자가 줄 묶음이다. 컴포넌트 값 생성자는 런타임 이름으로도 연다(그 모드에 보이는 컴포넌트만, G112의 덮어쓸 수 있는 내장). `spawn`의 Def id가 리터럴이면 로드 때 존재·타입·보이는 범위를 검사하고(G116 기본값과 같은 방식), 값이면 실행 때 검사한다. 키 컴포넌트의 줄은 `spawn`에 넣지 않고 `add_row`로 붙인다. Def에서 온 컴포넌트·줄은 뗄 수 없다(S4). 검사는 호스트 API와 같다(G89·G91~G93).

**이유:** 처음 값의 모양이 Def 리터럴과 같아 새로 배울 것이 없다. `=`의 뜻이 값 쓰기(G132) 하나로 남는다(`u.Wounded = ...`·`del` 문을 쓰면 같은 `=`가 구조 변경도 되고, 이미 있는 줄에 대입할 때 덮어쓰기인지 애매하다). 평평한 키워드(`spawn("x", current=3)`)는 `extend`로 같은 멤버 이름이 두 컴포넌트에 생기면 모호하다. 사례: 이전 엔진 `InstanceFactory.CreateInstance(def)`(C# 쪽만), RimWorld `GenSpawn.Spawn`·`Thing.Destroy`·`AddHediff`/`RemoveHediff`, 패러독스 `create_character`·`add_modifier`/`remove_modifier`(동작 이름이 곧 효과, 일반 지식).

**상태:** 확인

## G190

**위치:** S3 전역 순회 `all(Type)`과 파이썬 `all(xs)`의 이름 충돌 (G189에서 이어짐)

**무엇이 비어 있었나:** spec S3는 엔티티 전역 순회를 "명시적 `all(Type)`"으로 적었는데 G189가 파이썬 뜻의 `all(xs)`를 내장으로 더해 같은 이름이 두 뜻이 된다.

**어떻게 정했나:** **`all`은 파이썬 뜻으로 둔다. 엔티티 전역 순회는 만들 때 다른 이름으로 정한다.** spec S3의 `all(Type)`은 이름이 아니라 "전역 순회는 명시적 호출로만"이라는 규칙으로 읽는다.

**이유:** 인자 종류로 나누는 안(`all(Unit)`은 목록, `all([...])`는 참/거짓)은 한 이름이 두 뜻이라 헷갈린다. 파이썬 `all`을 빼는 안은 파이썬을 아는 모더의 기대와 어긋난다.

**상태:** 확인

## G192

**위치:** S3 스크립트의 전역 순회 (G190에서 이어짐)

**무엇이 비어 있었나:** 스크립트가 엔티티에 닿는 길은 인자·Ref·`inverse`·`choose` 후보뿐이라 "타입 X 전부"를 꺼낼 수 없었다. G175는 "어느 정착지든"을 쓸 수 없다고 적었고, 턴 수입(진영 전부)과 승리 판정(도시 전부)도 가짜 싱글턴 엔티티로 돌아가야 했다.

**어떻게 정했나:** **`query(이름, ...)`: 출처는 Def 타입 하나 그리고/또는 컴포넌트들이고 모두 만족하는 엔티티를 id 순으로 준다.** (처음에는 리스트였고 G194가 엔티티 묶음으로 바꿨다.) `query("Unit")`, `query("Wounded")`(타입을 가로지름), `query("Unit", "Wounded")`. 컴포넌트는 Def에서 왔든 런타임에 붙였든 붙어 있으면 맞는다. 값으로 거르기는 컴프리헨션이 한다(`[s for s in query("Settlement") if s.Mood.value < 20]`). 이름은 문자열이고 Def 타입·컴포넌트는 한 이름 공간이라(SCH001) 겹치지 않는다. 리터럴이면 ⑤가 본다: 없는 이름·신호(`LNK001`, "혹시 …?"), 데이터 전용 Def 타입·한 호출에 Def 타입 둘(`LNK002`, 둘이면 늘 빈 목록이라 실수로 본다), 보이지 않는 모드(`LNK003`). 인자 없음·키워드 인자는 `EVL003`. 실행 중에 만든 이름은 실행할 때 같은 검사(`spawn`과 같음). 없는 컴포넌트 쪽(Without)은 사례가 나오면 `without=`으로 더한다. 호스트 API는 `World.Query(...)`.

**이유:** ECS 쿼리(Bevy `Query<_, With/Without>`, DOTS `EntityQuery`, Flecs)는 컴포넌트로 출처를 고르고 값 조건은 루프 본문에 둔다. 패러독스(`every_country`)와 RimWorld(`ThingsOfDef`)는 타입별 목록이다. 이 엔진은 Def 타입이 실제 개념(`Ref[Unit]`, `when` 주어)이라 둘 다 받는다. 값 거르기·정렬은 이미 컴프리헨션(spec S3 "쿼리 = 컴프리헨션")이 맡는다. 이전 엔진은 경로 `Root.All`·`Root.<DefId>`와 필터 목록이었다. 타입만(A)은 타입을 굵게 쓰는 모드에서 불편하고, 컴포넌트만(B)은 "유닛 전부"를 흉내 내야 한다.

**상태:** 확인

## G193

**위치:** S3·S5 `query`를 쓸 수 있는 자리와 반응이 목록 변화를 아는 법 (G192에서 이어짐)

**무엇이 비어 있었나:** `query`는 엔티티의 칸이 아니라 목록 자체를 읽는다. `when`의 재평가(읽은 엔티티의 칸이 바뀔 때만)로는 새 정착지가 기분 10으로 생겨도 "어느 정착지든 20 미만" 조건을 다시 보지 않는다.

**어떻게 정했나:** **어디서나(`derived`·`when` 조건·사전 조건·본문) 쓸 수 있고, 읽으면 그 출처의 목록을 읽은 것으로 기록한다.** 그 타입의 엔티티가 생기거나 죽을 때, 그 컴포넌트를 가진 엔티티가 생기거나 죽을 때, 그 컴포넌트를 붙이거나 뗄 때 그것을 읽은 `when` 조건을 다시 본다. `derived`를 거쳐 읽어도 같다. `Explain`에는 `query("Settlement") = [#2, #3]`으로 나온다.

**이유:** G155(`now()`는 어디서나 읽고 "틱" 칸을 읽은 것으로 기록)와 같은 규칙이다. `derived`·조건에서 막으면(B) G175의 빈자리가 남고, 추적하지 않으면(C) 결과가 조용히 틀린다. 패러독스도 전역 `any_county`를 조건 어디서나 쓰고 비용은 모더 몫이다.

**상태:** 확인

## G194

**위치:** S4 스크립트 순회에서 G88의 "죽은 것은 건너뛴다" (G88 구현 누락, 재현함)

**무엇이 비어 있었나:** G88은 순회가 시작 시점의 목록을 돌며 순회 중에 죽은 엔티티와 뗀 줄을 건너뛴다고 정했지만 호스트 API에만 있었다. 스크립트의 `c.units`·`query()`는 평범한 리스트라 `for` 안에서 다음 원소를 `destroy`하면 그 원소에서 실행 오류가 났고, `for k in u.Skill:` 안에서 다음 줄을 `remove_row`해도 그 줄을 읽다 실패했다(임시 테스트로 둘 다 재현).

**어떻게 정했나:** **엔진이 준 묶음만 건너뛴다(파이썬 `weakref.WeakSet`처럼).** 역방향 컬렉션과 `query()`는 리스트가 아니라 엔티티 묶음 값이다: 받을 때의 목록(id 순)을 들고 엔티티를 살려 두지 않는다. `for`는 시작 시점의 목록을 돌며 한 바퀴마다 물어 그사이 죽은 것은 건너뛰고, `len`·`in`·참/거짓은 지금 살아 있는 것만 본다. 인덱스는 오류이고 리스트가 필요하면 컴프리헨션으로 그 순간의 사본을 만든다(`[u for u in c.units]`, 사본은 파이썬 리스트라 건너뛰지 않는다). 리스트만 받는 자리(`+`, `min`·`max`, `random.choice` 등, `ask(choices=)`)는 오류이고 사본을 만들라고 안내한다. 묶음끼리는 살아 있는 원소가 같으면 같고 리스트와는 다르다. 묶음은 받을 때의 목록이라 죽은 것은 빠지지만 다른 곳으로 옮긴 것은 남는다(다시 읽으면 바뀐 목록). 키 줄 묶음도 같은 규칙으로 뗀 줄과 키 엔티티가 죽은 줄을 건너뛴다. 지금 도는 원소가 죽으면 그 바퀴에서 읽을 때 오류다(건너뛰기는 다음 차례부터). `ask`·`wait`로 멈춘 반복은 그 묶음을 저장해 불러온 뒤에도 건너뛴다. 컴프리헨션·`any`·`all`은 안에서 월드를 바꿀 수 없어 도중에 죽는 일이 없다.

**이유:** 파이썬에는 참조가 있는 한 객체가 죽지 않아 이 문제가 없다. 우리 Ref는 엔티티를 살려 두지 않는 약한 참조이고, 파이썬도 약한 참조의 평범한 리스트는 확인을 쓰는 사람에게 맡기고(C) 전용 묶음 `WeakSet`은 알아서 뺀다(B). 모든 `for`가 죽은 Ref를 건너뛰는 안(A)은 스크립트 리스트까지 파이썬과 달라지고 `len`은 죽은 것도 센다. 건너뛰지 않는 안(C)은 반복 중에 죽는 드문 경우에만 터져 테스트에서 놓치기 쉽다(RimWorld 모드의 흔한 실수). 삭제를 미루는 안(Unity·Godot·Bevy)은 "지웠는데 아직 있음"이 오류 없이 결과를 틀리게 해서 G88의 즉시 반영을 유지했다. 묶음이 리스트 연산을 받으면 평범한 리스트가 되며 건너뛰기가 조용히 사라지므로 받지 않는다.

**상태:** 확인

## G229

**위치:** S4·S2 `derived` 순환의 로드 시점 검사 (G100 보강, schema-design 3.3.1 5항 고침)

**무엇이 비어 있었나:** G100은 로드 시점 정적 추적을 타입 정보가 생기면 하기로 미뤘다. schema-design 3.3.1 5항은 "속성 경로를 보수적으로 추적해 순환 가능성이 있으면 로드 오류, 실제로는 순환이 아닌데 거부되면 식을 둘로 쪼갠다"고 했다. 그런데 로드 때는 어느 컴포넌트인지만 알고 어느 엔티티인지는 모른다. 하위 지역의 합(`total`이 자식들의 `total`을 읽음)처럼 다른 엔티티의 같은 값을 읽는 정상 식이 `Region.total → Region.total`로 보여 거부되고, 깊이가 정해져 있지 않아 쪼갤 수도 없다. 재현(2026-10-19): `a=derived(int, lambda h: h.b + 1), b=derived(int, lambda h: h.a)`를 로드가 오류 없이 통과시키고 읽을 때에야 `RUN014`가 난다.

**어떻게 정했나:** **같은 엔티티 안의 순환만 로드 오류(`SCH009`)다.** G228의 검사기로 `derived` 함수마다 자기 엔티티에서 읽는 `derived`를 모은다. 자기 엔티티는 인자(`h`, 키 컴포넌트면 그 줄), 그 형제 컴포넌트(`h.Life`), `h.entity`와 그 컴포넌트다. 모든 갈래를 읽는다고 보고, 자기 엔티티의 값을 넘겨받은 모드 함수(`helper(h)`) 안도 따라간다(오류 자리는 `derived` 함수 안의 그 호출). Ref·역방향 컬렉션·`query`로 간 다른 엔티티와 키 컴포넌트의 다른 줄(`h.entity.Skill.Cooking`)은 보지 않는다. 그쪽 순환은 데이터(누가 누구를 가리키나)에 달려 있어 로드 때 알 수 없으므로 실행 중 재진입 감지(G100)가 맡는다. 오류는 순환 하나에 하나이고 글은 `derived 'Loop.a' reads itself on the same entity: Loop.a -> Loop.b -> Loop.a`, 나머지 읽기 자리는 관련 위치다. 책임은 순환의 읽기 중 가장 늦게 로드되는 모드다(그 모드가 오기 전에는 순환이 없었다, G64와 같은 생각). 타입을 모르는 값은 넘어간다(G228). 함수 기본값(`default=함수`)은 생성 때 선언 순서로 한 번 계산되므로(G106) 여기서 보지 않는다.

**이유:** 같은 엔티티 안의 순환은 어떤 데이터에서든 읽는 순간 실패하므로 로드 때 막는 것이 맞다. 다른 엔티티를 거친 순환은 정상 식(계층 합산)과 코드만으로 구별되지 않아, spec처럼 넉넉하게 막으면 피할 길 없는 가짜 오류가 생긴다. 놓친 순환도 실행 중 감지가 호출 사슬과 함께 오류로 내므로 값이 틀린 채 굴러가지 않는다. 그래서 5항은 너무 엄격했다고 보고 고쳤다. Ref 관계에 "순환하지 않음"을 선언하게 해 엔티티를 넘는 순환까지 로드 때 보는 안(`acyclic=True`, 쓸 때 엔진이 지킴. 패러독스의 주군·속국 계층처럼, 일반 지식)도 논의했으나 사용자가 넣지 않기로 했다.

**상태:** 확인

## G288

**위치:** G134에서 이어서: 생성자로 만든 컴포넌트 값을 엔티티에 붙이기 전에 읽기 (handoff "남은 일"의 정할 일, 2026-10-19 재현)

**무엇이 비어 있었나:** `m = Moves(left=3)`으로 만든 값은 `spawn`·`attach`·`add_row`에 넘길 수만 있었다. `m.left`는 힌트 없는 실행 오류(`'Moves(...)' has no attribute 'left'`)였고, 의도인지 정한 적이 없었다.

**어떻게 정했나:** 붙기 전의 컴포넌트 값은 **준 칸만 든 값**이다.
- 준 칸은 읽힌다(`Moves(left=3).left`는 3).
- 안 준 칸을 읽으면 실행 오류다. 그 칸의 처음 값은 붙는 순간 그 Def의 값, 없으면 스키마 기본값으로 정해져 상자만으로는 알 수 없다.
- 없는 칸 이름은 "혹시 …?"를 붙인 오류, `derived` 칸은 엔티티에서 계산된다는 오류다.
- 칸에 쓰기(`m.left = 4`)는 오류이고 새 값(`Moves(left=4)`)을 만들라고 알린다. 값은 정체성이 없고 내용으로 비교한다(G142).
- 붙은 뒤의 `unit.Moves.max`는 지금처럼 엔티티의 진짜 값이다.

**이유:** 2026-10-21 임시 테스트: `Unit("Scout", Moves=Moves(max=8))`에 `spawn("Scout", Moves=Moves(left=3))`이면 생긴 엔티티는 left=3, max=8이다. 안 준 칸을 스키마 기본값(5)으로 읽게 하면 조용히 틀린 값을 준다(spec S9). 막아만 두면 상자를 받는 도우미 함수가 안을 볼 수 없다. ECS 엔진도 컴포넌트를 값(구조체)으로 만들어 생성할 때 넣는다(Bevy `commands.spawn((Health(3), …))`, Unity DOTS `AddComponent(e, new Health { … })`, 일반 지식). 우리 값은 정체성이 없고 붙일 때 복사되므로 백본의 ECS화(G226)와도 어긋나지 않는다(사용자 물음, 2026-10-21).

**상태:** 확인

## G293

**주제:** 엔티티가 자기 Def id를 읽는 속성 `defid` (사용자 제안 2026-10-21, Pandemic 예시를 만들다 드러남).

**결정:** 엔티티에서 `e.defid`는 그 엔티티를 만든 Def의 전체 이름(`pandemic:Atlanta`)이다. 값은 Def id 값(`DefId`)이라 `defid("Atlanta")`와 비교하고, 맨 리터럴과 비교하면 `LNK005` 경고다(G261). 컴포넌트·Def 타입 이름은 대문자로 시작하는 관례라 부딪히지 않고, 같은 이름의 컴포넌트가 있으면 컴포넌트가 먼저다(`entity`가 멤버 뒤인 것과 같은 순서). 스텁은 그 Def 타입의 구체 Def id 리터럴을 돌려주는 읽기 속성으로 적는다. 호스트의 `World.DefOf`와 같은 값이다.

**이유:** 지도 도시처럼 Def가 곧 정체성인 엔티티를 이름으로 찾으려면 엔티티에서 Def id를 읽어야 하는데 스크립트에는 방법이 없어, 같은 값을 필드에 따로 적어 두는 중복이 필요했다.

**상태:** 확인

## G294

**위치:** S4 스탯/모디파이어 세 부품(spine-spec 157줄)의 경계: 보너스를 손으로 넣을지, 있으면 붙을지 (G98 보강)

**무엇이 비어 있었나:** 기여 행은 호스트 API(`AddContribution` 등)로만 넣고 뺄 수 있고 스크립트는 `contribs()`로 읽기만 했다. 그래서 모더가 기여 행을 만들 수 없었고, G98의 "만료는 표준 모드가 반응으로 행을 지운다"도 할 수 없었다. 더 큰 빈칸은 장비·특성·건물처럼 **상태에 남아 있는 것이 주는 보너스**였다. `derived` 함수가 찾아 읽으면 찾을 곳을 미리 알아야 해서 닫혀 있고(새 모드의 보너스를 넣으려면 남의 함수를 고쳐야 함), 기여 행을 손으로 넣으면 "입었다"와 "+3 줄"을 두 곳에 적는 이중 기록이 된다. 이중 기록은 서로 모르는 모드가 섞이면 어긋난다(모드 B가 갑옷을 `detach`하면 모드 A의 줄이 남음, 커널은 출처 엔티티가 죽을 때만 지움). 또 값을 저장하는 줄은 넣은 순간의 값으로 굳어서, Def 패치가 옛 세이브에 반영되지 않는다(schema-design 268줄의 원칙과 어긋남).

**어떻게 정했나:** 두 층으로 나눈다.
- **커널(층 1): 선언 보너스.** 컴포넌트가 스키마에서 "붙어 있는 동안 이 대상에 이 기여"를 선언할 수 있고, 키 컴포넌트 줄은 그 키 Def에 적힌 선언도 준다. 커널은 이것을 저장하지 않고 `contribs()`를 읽는 순간 붙어 있는 것의 선언을 모아 저장된 기여 행과 함께 돌려준다(가상 기여 행). 그래서 떼면 저절로 빠지고, 값은 지금 Def에서 오므로 패치가 옛 세이브에도 반영되며, `Explain`에 출처가 나온다. `derived` 함수는 그대로 `contribs()`만 읽는다.
- **커널: 스크립트용 값 기여 행 입구.** 호스트 API와 같은 넣기·빼기·출처로 빼기를 스크립트 쓰기 내장으로 연다(쓰기 자리에서만). 값 기여 행(G98, 값 저장)은 Def에 적을 수 없는, 그 순간 계산된 숫자(예: 약탈로 잃은 만큼)에 쓴다.
- **표준 모드 `std.stats`(층 2): 이름 있는 효과.** 축제·질병·정책 같은 효과는 효과 Def를 키로 하는 키 컴포넌트 줄을 붙였다 떼고(값은 그 Def의 선언 보너스), 만료는 남은 턴 칸과 반응으로 줄을 지운다. 공개 스크립트 API만으로 짤 수 있으므로 `ext.*`가 아니라 `std.*`의 몫이다. 이 모양(컴포넌트 이름, 만료 칸, `stat()` 틀의 합치는 순서)은 커널이 정하지 않고 모드가 바꾸거나 갈아 끼울 수 있다.
- **아직 안 정한 것:** 선언 표기(`grants=`·`contrib(...)`는 논의 때의 예시일 뿐), 스크립트 내장의 이름과 돌려주는 값, 다른 엔티티(Ref로 들린 칼 등)에서 오는 선언을 어디까지 모을지, 조건부 선언(패러독스 triggered)을 받을지. G98의 값 기여 행은 그대로 값을 저장한다.

**이유:** 사례(2026-10-21 논의). RimWorld는 Hediff·특성·장비 Def의 `statOffsets`를 `StatWorker`가 모으고, 시간제 버프도 Hediff(상태)로 붙인다. 패러독스는 특성·건물·법의 modifier를 있으면 모으고, 이벤트 modifier는 이름으로 붙여 기간으로 떨어진다(이상 일반 지식). GAS는 손으로 넣기가 기본이라 장비를 "입을 때 적용, 벗을 때 핸들로 제거"로 처리하는데, 한 팀이 모든 코드를 쓰는 게임이라 짝을 지킬 수 있다(일반 지식). 이전 엔진(`uk.kesa.engine`, 코드 확인)은 `ModifierDef`·`Comp_ModifierStorage`(손으로 넣기, `Modifier`는 값이 아니라 Def를 가리켜 패치가 반영됨)·`Comp_ModifierProvider`(있으면 붙음, R3 구독으로 자동 Add/Remove)를 이미 다 가졌다. 개념은 그대로 잇되, 구독으로 자동 넣기는 커맨드 한가운데의 즉시 알림·구독 누수·불러오기 순서 의존을 부르므로 읽을 때 모으기로 바꾼다. Def를 가리키는 효과를 키 줄로 표현하면 G98 저장 형식을 바꾸지 않고도 이전 엔진처럼 패치가 반영된다. 커널의 새 개념은 선언 보너스 하나뿐이고, 효과의 모양은 표준 모드가 짜 보며 커널이 충분한지 시험한다(spine-spec 279줄 범용성 시험).

**상태:** 확인

## G295

**위치:** G294에서 이어서: 선언 보너스를 어디에 어떻게 적나

**무엇이 비어 있었나:** G294는 "컴포넌트와 키 줄의 키 Def가 보너스를 선언한다"만 정하고 표기를 미뤘다. 쓰일 곳은 셋이다. ① 특성·효과처럼 키 줄의 키 Def(`Trait("Tough")`), ② Def마다 다른 컴포넌트 값(`Unit("Knight", Armor=Armor(...))`), ③ 종류 자체가 보너스인 상태 표시(`Fortified`). 후보는 (1) 커널의 값 타입 목록을 `const`로 두기, (2) `component()`·`deftype()`의 전용 키워드(스키마에 박힘, Def마다 못 다르고 패치 안 됨), (3) 보너스 목록을 돌려주는 순수 함수(대상이 실행 중에 만들어져 로드 검사가 약함)였다.

**어떻게 정했나:** **(1)로 한다.** 커널이 보너스 하나를 나타내는 값 타입(이름 미정, 논의 때는 `Grant`)을 주고, 그 타입의 목록인 `const`(`const(list[Grant])`) 칸은 어디에 있든 커널이 모은다. 모으는 곳은 엔티티에 붙은 컴포넌트의 그 칸(값은 엔티티의 Def가 준 컴포넌트 값, 없으면 스키마 기본값)과, 키 컴포넌트 줄의 키 Def에 있는 그 칸이다.

```python
deftype("Trait", grants=const(list[Grant], default=[]))
Trait("Tough", grants=[Grant("Health.max", "add", 3)])
component("Armor", grants=const(list[Grant], default=[]))
Unit("Knight", Armor=Armor(grants=[Grant("Health.max", "add", 3)]))
```

값이 Def에 있으므로 다른 모드가 `patch.append`로 보너스를 더하거나 바꿀 수 있고 옛 세이브에도 반영된다(G294의 목표). 대상(`"Health.max"`)은 리터럴이라 로드 때 컴포넌트·멤버가 있는지와 `derived`인지(G98) 검사할 수 있다. 어느 컴포넌트에 그 칸이 있는지는 스키마에서 로드 때 뽑아 두어 읽을 때마다 훑지 않는다. **남은 작은 것:** 타입 이름, 키 줄 대상의 표기(`Skill[Medicine].level` 같은), 모인 줄의 `source`에 보이는 것. 조건부·계산된 값(후보 3의 장점)은 조건부 항목에서 따로 정한다.

**이유:** 규칙 하나("그 타입의 목록 `const`는 모인다")로 세 쓰임을 다 덮고, 값이 Def에 살아 패치와 로드 검사가 된다. RimWorld의 `statOffsets`(Def에 적는 목록)와 이전 엔진 `ModifierDef.StatChanges`가 같은 모양이다. ECS로 옮기면(flecs 기준, 일반 지식) Def는 프리팹, 키 컴포넌트 줄은 쌍(spine-spec 153줄), 이 칸은 프리팹의 데이터 컴포넌트이고, 모으기는 "붙은 컴포넌트와 쌍의 대상 프리팹의 그 컴포넌트" 쿼리라 나중의 ECS 백본(G226)에도 그대로 옮겨진다. 같은 눈으로 보면 다른 엔티티(Ref로 들린 칼)에서 오는 보너스는 "어떤 관계가 보너스를 전하나"의 물음이 되고, flecs가 관계에 성질을 붙이듯 Ref 선언에 표시하는 길이 첫 후보다(그 항목에서 정함, 결정 아님).

**상태:** 확인

## G296

**위치:** G295에서 이어서: 보너스 값 타입의 이름

**무엇이 비어 있었나:** G295는 커널의 보너스 값 타입을 정했지만 이름은 미뤘다(논의 때 `Grant`). 후보는 `Contrib`(`contribs()`·"기여 행"과 한 단어), `Grant`("준다"는 뜻이 드러나지만 `contribs()`와 이름이 다름), `Modifier`(익숙하지만 패러독스에서는 묶음을 뜻하고 spine-spec 157줄 "모디파이어는 엔진 내장이 아니다"와 부딪힘)였다.

**어떻게 정했나:** 만드는 함수는 `contrib(대상, op, 값)`, 칸에 적는 타입은 `Contrib`이다(`const(list[Contrib])`). 커널 값의 기존 관례(`option(...)` → `Option`, `text(...)` → `Text`: 만드는 함수는 소문자, 타입은 대문자)를 따른다. 대문자 생성자는 모드가 선언한 컴포넌트(`Moves(...)`)의 것이다.

```python
deftype("Trait", grants=const(list[Contrib], default=[]))
Trait("Tough", grants=[contrib("Health.max", "add", 3)])
```

**이유:** 선언한 보너스는 `contribs()`를 읽을 때 저장된 기여 행과 같은 모양(`op`·`value`·`source`)으로 섞여 나오므로, 한 개념에 한 단어를 쓴다. 칸 이름(`grants`)은 모더가 짓고 엔진이 정하지 않는다.

**상태:** 확인
