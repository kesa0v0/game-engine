# spec 빈틈 상세: X4 로컬라이제이션

색인과 상태 규칙은 `docs/spec-gaps.md`. 이 파일은 G 번호마다 무엇이 비어 있었고 어떻게, 왜 정했는지의 전문이다.

## G254

**위치:** X4 번역 파일 형식과 포매터 (spec X4 "방식 🟡, 번역 파일 형식 미정", 콘솔 호스트 구멍 4번)

**무엇이 비어 있었나:** 커널에는 키와 인자를 들고 다니는 `text("키", 이름=값)`(G113)와 `mod.py`의 `defaultLanguage`(G12)만 있고, 키를 글로 바꾸는 쪽(번역 파일, 자리 표시자·복수형 포매터, 폴백, `check`의 번역 검사)이 없었다. spec X4는 원칙(P1~P4)만 정하고 방식은 "ICU MessageFormat 부분집합, 파일 형식 미정"으로 남겼다. 콘솔에는 질문 제목과 `require` 메시지가 키 그대로 보였다.

**어떻게 정했나:** **번역 파일은 Project Fluent 형식(`.ftl`)이고, 읽고 채우는 일은 Linguini(Fluent의 C# 구현)에 맡긴다.**
- 번역은 커널 밖의 새 어셈블리가 맡는다. 호스트와 CLI(`check`)가 참조하고 커널은 지금처럼 `TextValue`(키와 인자)만 든다(X4 P2: 시뮬레이션은 번역문을 읽지 않는다). 그래서 이 어셈블리는 결정론 분석기(`Determinism.props`) 밖이다.
- Linguini는 버전을 고정하고(처음은 0.11.0) 우리 인터페이스 뒤에 둔다. 호스트·모드 코드는 Linguini 타입을 보지 않는다. 라이브러리가 멈추면 고정 버전 유지 → 포크(MIT 또는 Apache-2.0) → 쓰는 부분만 다시 만들기 순으로 물러서며, 어느 경우에도 모드의 `.ftl` 파일은 그대로다.
- 우리가 쓰는 것: 모드별로 번역 파일을 찾고 로드 순서대로 모으기, 덮어쓰기와 충돌 규칙, 보이는 범위, 오류의 책임(G64), 폴백(X4 P3), `check`의 번역 검사, 조사 같은 언어별 사용자 함수. Linguini가 하는 것: `.ftl` 파싱(위치 포함), 자리 표시자·`select`·복수형(CLDR) 채우기.
- 이어서 정할 것: 키 표기(Fluent 식별자에는 점이 없고 점은 속성이다, 지금 모드들은 `harbor.charter`처럼 점을 씀), 파일 위치, 덮어쓰기 규칙, 폴백과 `check`, 숫자 인자의 모양(`fixed`), 조사 함수, 엔진 API.

**시험(2026-10-20, 임시 프로젝트, 저장소에 남기지 않음):** Linguini 0.11.0으로 (1) 같은 키를 `AddResource`로 다시 넣으면 `OverrideFluentError`로 거부, `AddResourceOverriding`은 그 키만 덮어씀, (2) CLDR 복수형: 러시아어 1·2·5·21이 `one`·`few`·`many`·`one`, 한국어는 `other`뿐, (3) 사용자 함수 `JOSA($name, "을")`로 `슬루프를`·`갈매기가`, (4) 파서만 따로 써서 글마다 변수 목록(`gold`, `ship`)과 오류 줄 번호, 빠진 인자는 `금화 {$gold}`와 `Unknown variable` 오류, (5) 0.8.1→0.11의 깨지는 변경은 호스트 API 몇 곳이고 `.ftl` 문법은 같음. 0.12(미출시)는 `CultureInfo`를 자체 언어 id로 바꿈.

**이유:** 후보는 Fluent+Linguini, gettext `.po`+Karambolo.PO(번역 도구가 가장 넓지만 자리 표시자 채우기와 `select`를 직접 써야 함), MessageFormat(.NET, 파일 형식은 따로), 우리 콘텐츠 언어(로더는 공짜지만 번역 도구가 없음), ICU4N(alpha, MessageFormat·PluralRules 미포팅으로 탈락)이었다. Fluent는 형식과 문법을 한 번에 주고, 모드를 받는 게임 엔진 OpenRA와 RobustToolbox(Space Station 14)가 Linguini를 쓴다(두 저장소의 프로젝트 파일로 확인). Linguini는 별이 42개이고 기여가 거의 한 사람(Ygg01)이라는 위험이 있지만 NuGet 내려받기 약 535만, 2026-10 기준 활발한 커밋이고, 형식은 Mozilla 표준(문법 1.0)이라 라이브러리와 따로 살아남는다. 사례: RimWorld는 XML Keyed·DefInjected와 언어별 C# LanguageWorker, 패러독스는 YAML 비슷한 `l_english:`과 글 안의 월드 읽기 `[ROOT.GetName]`(X4가 막은 방식, U14), Godot은 `.po`를 협업용으로 권함(일반 지식과 Godot 문서).

**상태:** 확인

## G255

**위치:** G254 번역 키의 표기 (Fluent 식별자에는 점이 없음)

**무엇이 비어 있었나:** 스크립트는 `text("harbor.charter")`처럼 점으로 이은 키를 썼지만, Fluent의 글 이름은 `[a-zA-Z][a-zA-Z0-9_-]*`이고 점은 속성(`harbor-charter.tooltip`)을 뜻한다. 스크립트의 키와 번역 파일의 이름을 어떻게 잇는지 없었다.

**어떻게 정했나:** **스크립트에 적는 키는 Fluent 이름 그대로다.** 이어 붙이기는 하이픈(`text("harbor-charter", gold=5)`), 점은 Fluent처럼 속성만(`text("harbor-charter.tooltip")`, 글 이름 뒤에 하나). 엔진은 키 문자열을 바꾸거나 모드 접두사를 붙이지 않는다. 모드 id 접두사(`harbor-`)는 관례이고, 서로 순서 없는 모드끼리 같은 키를 정의하면 어떻게 하는지는 덮어쓰기 규칙에서 정한다. 이것은 키 문자열의 규칙일 뿐이고 스크립트의 데이터 경로(`house.Purse.gold`)와 무관하며, 번역 파일의 `{ $gold }`는 넘겨받은 인자만 읽는다(X4, U14). 예시 모드의 키도 바꿈(`harbor-charter`, `harbor-already-open`, `skirmish-already-started`).

**이유:** 스크립트의 문자열로 번역 파일을 그대로 찾을 수 있고 번역자와 모더가 같은 이름을 본다. 엔진이 점을 하이픈으로 바꾸면 한 키에 표기가 둘이 되고 속성을 가리킬 길이 없어진다. 접두사를 엔진이 붙이면 남의 모드를 번역하는 모드가 대상 모드를 따로 적어야 하고 파일에 보이는 이름과 실제 이름이 달라진다. Space Station 14는 Fluent 키를 하이픈으로 길게 잇는 관례(`comp-gas-pump-ui-pump-status`), RimWorld Keyed·패러독스 키는 전역 이름에 모더가 접두사를 붙이는 관례다(일반 지식). 점을 속성으로 남기면 spec X4의 "규칙으로 도출한 키(`Scout.label`)"를 Fluent의 글과 속성(`Scout = 정찰병` / `.desc = …`)으로 옮길 길이 열린다(따로 정함).

**알아 둘 것:** 커맨드(`banking.Ask`)·단계(`harbor.market`)·호스트 함수·`Call`의 함수 이름은 지금처럼 점으로 모드를 가른다. 번역 키만 하이픈이다(Fluent 문법 때문).

**상태:** 확인

## G256

**위치:** G254 번역 파일의 위치와 모드 사이의 같은 키 (번역 팩 모드 포함)

**무엇이 비어 있었나:** 번역 파일을 모드 안 어디에 두는지, 언어 이름을 어떻게 적는지, 두 모드가 같은 언어에서 같은 키를 정의하면(남의 모드를 번역하는 팩 포함) 어떻게 하는지 없었다. `mod.py`의 `defaultLanguage`(G12)는 아무 문자열이나 받았다.

**어떻게 정했나:**
- **위치:** 모드 폴더의 `locale/<언어 태그>/` 아래 `.ftl` 파일 전부(하위 폴더 포함). `use` 목록에 적지 않고 엔진이 찾으며, 읽는 순서는 `use_all`처럼 상대 경로의 서수 순(G18). 언어 이름은 BCP 47 태그(`en`, `ko`, `pt-BR`)이고 `defaultLanguage`도 같은 태그여야 한다(틀리면 로드 오류, G12의 이 칸을 확정).
- **한 모드 안:** 같은 언어에서 같은 키(글 이름)가 두 번 나오면 오류.
- **모드 사이:** 같은 언어에서 같은 키를 여러 모드가 정의하면 **언제나 로드 순서상 나중 모드가 이긴다.** 두 모드 사이에 의존 순서(어떤 의존 선언이든 전이 경로, G37과 같은 판정)가 있으면 조용히 덮고, 없으면 경고 하나(키, 두 모드, 이긴 모드). 덮어쓰기는 글 하나(속성 포함) 단위다. 번역 팩은 대상 모드를 `dependencies`·`optional`·`loadAfter` 중 하나로 적으면 경고가 없다.

**이유:** 로드 순서는 의존이 없어도 G1의 동률 규칙(모드 id 서수)으로 늘 하나로 정해진다. G19·G37이 순서 없는 겹침을 오류로 한 것은 그 동률 순서가 모드 이름에 달린 우연이라 게임 규칙이 이름 하나로 조용히 뒤바뀌기 때문인데, 번역은 시뮬레이션이 읽지 않아(X4 P2) 누가 이겨도 게임 결과·저장·리플레이·동기화가 같고, 틀리면 화면에서 바로 보인다(사용자 제안, 2026-10-20). 서로 모르는 모드가 우연히 같은 키를 쓰면 한 모드의 화면에 남의 글이 나오므로 경고는 남긴다. 언어 태그는 Fluent·Linguini가 복수형 규칙을 고르는 이름이고 Space Station 14의 `Locale/en-US/`도 같다. RimWorld의 언어 이름 폴더(`Korean`)는 변형 구분에 이름을 따로 지어야 하고, 패러독스의 고정 목록(`l_korean`)은 모드가 언어를 더하기 어렵다(일반 지식). 사용자가 정한 로드 순서로 나중 모드가 이기는 것은 RimWorld와 비슷하다(일반 지식, 세부 미확인).

**상태:** 확인

## G257

**위치:** X4 P3 폴백과 `check`의 번역 검사 (G254~G256에서 이어짐)

**무엇이 비어 있었나:** spec X4 P3은 "요청 언어 → 모드의 기본 언어 → 키 자체"라 했지만 키는 전역 이름(G255)이라 "모드"가 어느 모드인지 없었고, 플레이어가 읽을 수 있는 다른 언어를 엔진이 몰라 한국어 플레이어가 중국 모드를 켜면 그 모드에 영어 글이 있어도 중국어가 나왔다(사용자 지적). `check`가 무엇을 보고 번역 오류가 모드를 끄는지도 없었다.

**어떻게 정했나:**
- **폴백:** (1) 호스트가 넘기는 **플레이어의 언어 목록**(예: `["ko", "en"]`)을 앞에서부터, 언어마다 태그를 줄인 것까지(`ko-KR` → `ko`, `pt-BR` → `pt`), (2) 어느 것에도 없으면 **그 키의 주인 모드의 `defaultLanguage`**(주인 = 로드 순서상 그 키를 처음 정의한 모드, 나중에 로드된 번역 팩은 주인이 아님), (3) 키 자체. 엔진은 어떤 언어도 특별히 대하지 않고 목록은 호스트(게임 설정)가 정한다. `locale/`이 있는 모드는 `defaultLanguage`를 적고 그 언어 폴더를 가져야 한다.
- **`check`:** `.ftl` 구문 오류(`파일:줄`)와 한 모드 안의 같은 키(G256)는 오류, 스크립트의 `text("키", …)`에서 키가 리터럴인데 어느 언어에도 없으면 경고(`파일:줄`), 그 언어의 글이 쓰는 변수를 그 호출이 넘기지 않으면 경고, 주인의 기본 언어 글에 없는 변수를 다른 언어 글이 쓰면 경고, 언어마다 빠진 글은 모드·언어마다 정보 한 줄(목록은 덤프). 호출이 넘겼는데 글이 안 쓰는 인자는 정상(Fluent가 허용), 아무도 쓰지 않는 글은 보지 않음(호스트 UI 파일도 키를 쓰는데 엔진은 그 파일을 읽지 않음, G249), 키를 계산한 호출은 검사하지 못함.
- **번역 오류는 모드를 끄지 않는다.** 오류가 난 글(Fluent의 Junk, 겹친 키)만 빼고 알리며 모드의 규칙과 다른 글은 그대로 쓴다. spec S1의 오류 정책("실패한 모드는 통째로 비활성화")의 예외다.

**이유:** 플레이어 언어 목록은 브라우저·Steam의 선호 언어 목록과 Fluent의 언어 협상(Linguini 0.12의 `LanguageNegotiator`)과 같은 장치다(일반 지식). 주인 모드의 기본 언어는 읽지 못해도 키 문자열보다 단서가 된다. 번역은 시뮬레이션이 읽지 않으므로(X4 P2) 철자 하나 틀린 번역 때문에 모드를 끌 이유가 없다(사용자 동의, 2026-10-20). RimWorld도 깨진 번역 XML은 로그만 남기고 게임은 돈다고 알고 있다(일반 지식, 미확인).

**상태:** 확인

## G262

**위치:** X4 Def 이름의 번역 키 (G255에서 멈췄다가 Def id 이름 공간 G258~G261을 정한 뒤 이어짐)

**무엇이 비어 있었나:** Def의 화면 이름을 번역 파일에서 찾을 키가 없었다. Fluent 메시지 이름은 `[a-zA-Z][a-zA-Z0-9_-]*`만 받아 Def id의 `:`·`/`를 그대로 쓸 수 없고, id를 `-`로만 바꾸면 모더가 지은 일반 키와 겹칠 수 있었다(`harbor:already/open` → `harbor-already-open`이 예시 모드의 실제 키 `harbor-already-open`과 같음). 같은 키는 하나만 살아남으므로(G256) 조용히 엉뚱한 글이 나온다.

**어떻게 정했나:** **Def의 번역 키는 Def id의 `:`와 `/`를 `-`로 바꾸고 앞에 `def-`를 붙인 것이다**(`harbor:rigs/Brig` → `def-harbor-rigs-Brig`). `def-` 접두사는 엔진이 예약하고, 모더가 `def-`로 시작하는 일반 키를 쓰면 `check`가 오류를 낸다(엔진 글의 `kesa-`와 같은 방식). Def의 종류 이름은 키에 넣지 않는다. 한 Def에 붙는 여러 글(설명 등)을 나누는 법은 이어서 정한다.

**이유:** 조각에 `-`가 없고(G259) `:`는 첫 조각 뒤에 한 번뿐이라 바꾼 키가 겹치지 않고 id로 되돌릴 수 있으며, 모드 id가 소문자로 시작해(G2) Fluent 이름 규칙도 맞는다. `_`로 바꾸면 조각 안의 `_`와 겹친다. Def id는 종류와 상관없이 전역에서 하나라(G19) 종류 이름 없이도 겹치지 않고, 종류 이름을 넣으면 모더가 종류 이름을 바꿀 때 모든 키가 깨진다. 사례: RimWorld는 Def 번역을 `DefInjected/<Def 종류>/` 폴더에 두어 일반 번역(`Keyed`)과 키 공간을 나누는데 접두사가 같은 효과를 낸다. 패러독스는 키가 id 그대로라 모드끼리 키가 겹치는 일이 흔하다. Minecraft는 등록부가 종류별이라 `item.create.brass_ingot`처럼 종류를 붙인다(일반 지식).

**상태:** 확인

## G263

**위치:** X4 한 Def에 붙는 여러 글 (G262에서 이어짐)

**무엇이 비어 있었나:** G262로 Def마다 번역 키가 하나 생겼지만 Def에는 이름 말고도 설명·툴팁 같은 글이 붙는다. 키 하나에서 그 글들을 어떻게 나눌지 없었다.

**어떻게 정했나:** **메시지 값이 화면 이름이고, 나머지 글은 Fluent 속성이다.**

```
def-harbor-rigs-Brig = 브리그
    .desc = 빠른 쌍돛배
```

속성 이름(`.desc` 등)은 모더가 정하고 Fluent 이름 규칙을 따른다. 엔진은 값만 "화면 이름"으로 알고 속성의 뜻은 정하지 않는다. 스크립트에서 속성을 꺼내 쓰는 법은 엔진 API를 정할 때 함께 정한다. 없는 속성을 찾으면 G257의 없는 키와 같이 `check`가 알리고 실행 중에는 폴백을 따른다.

**이유:** 속성은 Fluent가 한 대상의 여러 글을 위해 둔 장치라 겹침이 없고 번역가가 한 Def의 글을 한곳에서 본다. 패러독스식으로 키 뒤에 붙이면(`def-harbor-rigs-Brig-desc`) Def `harbor:rigs/Brig/desc`의 이름 키와 같아져 G262가 막은 겹침이 다시 생긴다. 엔진이 속성 이름을 정해 두면 오타는 잡지만 어떤 글이 필요한지는 게임마다 달라 모더의 일이다. 사례: RimWorld는 `DefInjected/ThingDef/Steel.label`·`Steel.description`처럼 Def의 필드 이름으로 나누고, 패러독스는 `building_farm`·`building_farm_desc`처럼 접미사 관례를 쓴다.

**상태:** 확인

## G267

**위치:** X4 번역 인자 값 표 (G254 "숫자 인자의 모양"에서 이어짐)

**무엇이 비어 있었나:** `text("키", 이름=값)`(G113)의 값은 커널의 값(int, fixed, str, 엔티티, 숨김 값 등)인데, 번역 파일(Fluent)에 무엇으로 넘기는지 없었다. 실행 중의 Def id는 그냥 문자열이라(G261) `text("harbor-bought", ship=k)`의 `k`가 Def인지 보통 글자인지 값만으로는 모른다. 그대로 넘기면 화면에 "harbor:Sloop을 샀다"가 나온다.

**어떻게 정했나:**

| 값 | 번역 파일에 가는 것 |
|---|---|
| int, fixed | Fluent 수(fixed는 `Fixed.ToString()`의 십진 표기). 복수형 `select`가 된다. 언어별 숫자 모양과 `NUMBER()`는 나중에 정함 |
| str | 글자 그대로. **다만 불린 Def의 전체 이름과 똑같으면 그 Def의 이름 값**(아래) |
| 엔티티 | 그 엔티티의 Def의 이름 값. Def는 커널이 `text()`를 부를 때 적어 두므로 나중에 엔티티가 없어져도 이름이 나오고 번역기는 월드를 읽지 않는다 |
| 숨김 값(G198) | 엔진이 주는 메시지 `kesa-hidden`("알 수 없음")의 글. 모드가 덮어쓸 수 있다 |
| `text()` 값 | 그 글을 같은 언어로 먼저 번역해 넣는다 |
| bool, None | 문자열 `true`·`false`·`none`. 번역문이 `select`로 고른다 |
| list, dict, 함수 등 그 밖 | `text()`를 부를 때 커널의 실행 오류(정적 타입을 알면 로드 때) |

**Def의 이름 값:** 화면에는 그 Def의 번역된 이름(G262의 키 `def-…`의 메시지 값, 폴백은 G257)이 나오고, 번역 파일의 사용자 함수(조사 등)에는 Def id를 아는 값으로 간다. Linguini는 직접 만든 값 타입으로 `select`를 하지 않으므로 Def에 따라 고르는 일은 함수가 문자열을 돌려주는 식(`{ GENDER($ship) -> … }`, 속성 `.gender`를 읽음)이다. 그런 함수는 조사 함수와 함께 정한다.

**시험(2026-10-20, 임시 프로젝트, 저장소에 남기지 않음):** Linguini 0.11.0에서 `IFluentType`을 구현한 값의 `AsString()`이 자리 표시자에 그대로 나오고(`슬루프을 샀다`, `SetFormatterFunc`는 자리 표시자에 쓰이지 않음), 사용자 함수에는 그 타입 그대로 가서 id를 꺼낼 수 있었다. 그 값으로 `select`하면 `Matches`가 불리지 않고 늘 기본 가지였고, 함수가 돌려준 문자열로는 골라졌다. 수는 `1.5`·`-0.25`·`1234567`처럼 불변 문화권 표기로 나오고(독일어도 `1234.5`), `NUMBER()`는 기본으로 없다. 러시아어 복수형은 1.5 → `other`, 21 → `one`.

**이유:** 넘긴 문자열이 실제 Def의 전체 이름(`:` 포함)과 우연히 같으면서 글자 그대로 보여야 하는 경우는 사실상 없어서, 모더가 감싸거나(`defname(k)`) 번역자가 함수로 바꾸게(`{ DEF($ship) }`) 하는 것보다 잊을 일이 없다(사용자가 고름). RimWorld도 Def·Pawn 자체를 인자로 넘기고 번역문이 `{PAWN_label}`처럼 꺼내 쓴다. 엔티티의 Def를 `text()` 때 적어 두면 기록에 남은 글이 엔티티가 죽은 뒤에도 이름을 보이고, 처음 생각한 `kesa-gone`이 필요 없다. list·dict는 어떤 모양으로 보일지 언어마다 달라 모더가 풀어서 넘긴다.

**상태:** 확인

**바뀜:** 숨김 값의 메시지 키는 `engine-hidden`이다(엔진 예약 이름은 `engine`) → G273.

## G268

**위치:** X4 조사 함수와 Def 속성으로 고르기 (spec X4 "조사 등은 언어 팩의 확장 포매터", G267에서 이어짐)

**무엇이 비어 있었나:** `{ $ship }을 샀다`는 넣는 이름의 받침에 따라 "슬루프을"처럼 틀린다. 번역자는 `$ship`에 무엇이 올지 모른다. G267에서 Def 이름 값으로는 `select`가 안 되는 것을 확인해 성별처럼 Def에 따라 고르는 길도 따로 필요했다.

**어떻게 정했나:**
- **조사는 번역문의 함수다:** `{ JOSA($ship, "을") } 샀다` → "슬루프를 샀다"·"갈레온을 샀다". 이름(값의 글)에 고른 조사를 붙여 돌려준다.
- 조사는 짝 중 아무 쪽이나 적는다(`"을"`과 `"를"`은 같은 짝). 짝: 이/가, 을/를, 은/는, 과/와, 으로/로(ㄹ 받침이면 "로": 길로), 이나/나, 이랑/랑, 아/야, 이여/여, 이라/라. 모르는 조사는 `check` 오류(번역 오류라 모드를 끄지 않음, G257)이고 실행 중에는 이름 뒤에 적힌 조사를 그대로 붙인다.
- 마지막 글자가 한글이면 받침으로, 숫자면 읽는 소리로(3 삼 → 을, 2 이 → 를, 10 십 → 을) 고른다. 받침을 알 수 없는 글(라틴 글자 등)은 두 형태를 다 쓴다(`Sloop을(를)`).
- 엔진이 모든 언어의 번역에 넣는다. 이름이 대문자인 것은 Fluent 내장 함수(`NUMBER`)의 관례다.
- **Def 속성으로 고르기:** `{ DEFATTR($ship, "gender") -> [f] 그녀 *[other] 그것 }`. Def 이름 값의 Def에서 그 Fluent 속성(G263, `.gender = f`)의 글을 문자열로 돌려줘 `select`가 된다. 속성 이름과 값은 모더가 정한다. 속성이 없으면 빈 문자열이라 기본 가지로 간다.
- 글을 다 채운 뒤 `(을)를` 같은 표시를 고치는 뒤처리는 두지 않는다.

**이유:** Fluent 함수 문법 그대로라 `check`가 모르는 조사·잘못된 인자를 줄 번호와 함께 잡고, 함수가 G267의 Def 이름 값을 받아 이름 글을 직접 본다(G254 실험에서 `JOSA` 확인). 뒤처리 표시는 아무 자리 뒤에나 붙는 장점이 있지만 보통 글의 괄호와 헷갈리고 오타를 잡기 어려우며, 길을 둘 두면 문서와 검사가 두 배다(사용자가 함수 하나로 고름). 사례: 이전 게임 QU는 `{Target.Label | josa:을}`(U14), RimWorld 한국어는 `LanguageWorker_Korean`이 완성된 글의 `(을)를` 같은 표시를 고친다고 기억한다(소스로 확인하지 않음). `DEFATTR`는 G267 실험에서 함수가 돌려준 문자열로 `select`가 되는 것을 확인한 방식이다.

**상태:** 확인

## G269

**위치:** X4 호스트의 번역 API와 번역 다시 읽기 (G254 "엔진 API"에서 이어짐)

**무엇이 비어 있었나:** 번역 어셈블리(G254)를 호스트가 어떻게 부르는지 없었다. 호스트가 글로 바꿔야 하는 것은 셋이다: 스크립트가 만든 쪽지(`require` 메시지·`ask` 제목의 `TextValue`), 화면 값(`view.py`가 돌려주는 dict·list) 안의 맨 값(수·엔티티), 호스트 자신의 글(메뉴 등). 콘솔은 `ValueText.cs`가 키와 인자, `#3 harbor:Sloop`을 그대로 찍었다. 번역 파일을 고친 뒤 다시 읽을 수 있는지도 없었다.

**어떻게 정했나:**

```csharp
var texts = Translations.Load(loadResult, diagnostics);  // 불린 모드들의 locale/
Translator tr = texts.For(new[] { "ko", "en" });         // 플레이어마다, 언어를 바꾸면 새로
tr.Format(textValue);                                    // 쪽지
tr.Value(value, world);                                  // 화면 값 안의 맨 값 하나
tr.Text("kesa-console-moves");                           // 호스트가 키로 직접
tr.Text("harbor-gold", ("n", new IntValue(5)));
tr.DefName("harbor:Sloop");
```

- 결과는 늘 문자열이고 예외를 던지지 않는다. 폴백은 G257(언어 목록 → 주인 모드의 기본 언어 → 키). 번역 오류는 `out` 인자 같은 따로 받는 길로 본다.
- `Value`는 G267 표를 맨 값에도 쓴다. 화면 값 안의 엔티티는 지금 살아 있으니 `world`에서 그 Def를 찾고, 숨김 값은 `kesa-hidden`이다. dict·list를 어떻게 늘어놓을지는 호스트마다 달라 값 하나씩만 바꾼다(`Render(view)` 같은 통째 바꾸기는 두지 않음).
- 호스트는 제 `.ftl` 폴더를 넘길 수 있고 가장 먼저 읽혀 모드가 덮어쓸 수 있다(G256의 "나중이 이김"). 엔진의 `kesa-hidden`도 엔진이 넣는 같은 식의 기본 파일이다. 호스트 키는 `kesa-console-…`처럼 `kesa-` 아래에 호스트 이름을 붙이는 관례다.
- 모드의 화면 파일(`ui/console.txt`)에는 키 부르기를 더하지 않는다. 모드가 화면에 글을 넣으려면 화면 함수가 `text("…")`를 값으로 돌려준다.
- 호스트·모드 코드는 Linguini 타입을 보지 않는다(G254). 언어를 월드에 거는 방식(`world.Language`)은 플레이어마다 언어가 달라 쓰지 않는다.
- **다시 읽기:** `Translations`는 만든 뒤 바뀌지 않는다. 번역 파일을 고치면 호스트가 `Load`를 다시 불러 새 `Translations`로 갈아 끼운다. 그리는 도중에 반쯤 바뀐 글이 섞이지 않고, 새 오류는 진단으로만 받으며 게임은 계속된다(번역 오류는 모드를 끄지 않음, G257). 파일이 바뀌었는지 지켜보는 일은 호스트 몫이다(콘솔이라면 명령 하나). 새 Def는 콘텐츠를 다시 불러야 생기고, 있는 Def의 이름·설명은 번역만 다시 읽어도 바뀐다.

**이유:** 번역은 시뮬레이션 밖이라(X4 P2) 다시 읽어도 월드·저장·결정론에 닿지 않는다. 스크립트·Def의 핫 리로드는 spec대로 후순위다(spine-spec S8 호환성 검사로 길만 열어 둠). 불변 값을 갈아 끼우는 방식은 다시 읽기를 위해 API를 따로 둘 필요가 없다. 사례: 패러독스는 디버그 모드에서 현지화 파일을 게임 안에서 다시 읽는다고 기억하고, RimWorld는 번역을 바꾸면 보통 다시 시작해야 했다고 기억한다(둘 다 확인하지 않음).

**상태:** 확인

**바뀜:** 제목·선택지 자리의 문자열은 키라 `Value`가 아니라 `Label`로 바꾸고, `DefName`·`DefAttr`는 `Label`·`Attr`에 합친다 → G270.

**바뀜:** 엔진·호스트의 번역 키는 `engine-hidden`·`engine-console-…`이다(엔진 예약 이름은 `engine`) → G273.

## G270

**위치:** X4 제목·선택지 자리의 글과 Def의 다른 글 (G269의 API를 고침, G263 "스크립트에서 속성을 꺼내는 법"에서 이어짐)

**무엇이 비어 있었나:** G269의 `tr.Value`는 G267대로 문자열을 글자 그대로 냈다. 그런데 질문 제목과 선택지 자리의 문자열은 키다(G138, `Request.Title`의 주석도 "텍스트 키"). `choices=["accept", "decline"]`을 `Value`로 그리면 "accept"가 그대로 보인다. Def의 이름 말고 다른 글(`.desc`)을 화면에 띄우는 길도 없었다. 스크립트가 키 `def-harbor-Sloop.desc`를 만들 방법이 없다.

**어떻게 정했나:**

```csharp
tr.Label(value, world);          // 제목·선택지 자리
tr.Attr(value, "desc", world);   // 그 값의 Fluent 속성
tr.Value(value, world);          // 화면 값 안의 맨 값 (G269 그대로)
```

- `Label`: 문자열은 Def의 전체 이름이면 그 Def의 이름, 아니면 키로 번역한다(키에는 `:`가 들어갈 수 없어 둘은 헷갈리지 않음). 쪽지는 번역하고, 엔티티는 그 Def의 이름, 숨김 값은 `engine-hidden`(G273), 그 밖은 `Value`와 같다. 선택지가 `option`이고 `label`이 있으면 그것을 쓴다(G271).
- `Attr`: 키면 `키.속성`, Def id면 `def-….속성`, 엔티티면 그 Def의 속성, 쪽지면 그 키의 속성을 같은 인자로. `option`에 `desc`가 있고 속성이 `"desc"`면 그것을 쓴다. 없는 속성은 G257의 없는 키처럼 폴백한다.
- G269의 `DefName`·`DefAttr`는 따로 두지 않는다(`Label`·`Attr`가 Def id를 받는다).
- **스크립트 내장 `deftext`는 만들지 않는다.** 선택지·제목에 Def의 글을 보이는 일은 화면이 값에서 꺼낸다(G137, "어떻게 보일지는 UI가 정함"). 스크립트가 직접 문장을 만들 때는 번역문의 `{ DEFATTR($ship, "desc") }`(G268)로 된다. 자주 필요해지면 그때 더한다.

**이유:** 한 값을 어디에 그리느냐에 따라 문자열의 뜻이 다르다. `text()`의 인자 자리는 플레이어가 지은 이름처럼 글자 그대로여야 하고(G267), 제목·선택지 자리는 키다(G138). 그래서 함수를 나눴다. Def의 글을 화면이 꺼내는 것은 RimWorld UI가 C#에서 `def.label`·`def.description`을 읽고, 패러독스 GUI 파일이 `[Building.GetName]`·`[Building.GetDesc]`로 칸마다 고르는 것과 같은 방식이다(사용자 제안: "호스트에서 여기에 k.title, 여기에 k.desc").

**상태:** 확인
