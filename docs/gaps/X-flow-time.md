# spec 빈틈 상세: X1 질문·X2 시간·X3 스택

색인과 상태 규칙은 `docs/spec-gaps.md`. 이 파일은 G 번호마다 무엇이 비어 있었고 어떻게, 왜 정했는지의 전문이다.

## G125

**위치:** X1 Request `accepts`와 `ask`의 반환값: 누구에게 묻는가

**무엇이 비어 있었나:** X1은 응답마다 허용 issuer 목록을 질의가 열릴 때 굳히고 `ask`가 제출자를 돌려준다고 했다(S2 `ask(me, ...)`). G122로 스크립트에서 issuer를 읽는 곳은 정책 함수뿐이라 규칙이 issuer를 적을 수 없다.

**어떻게 정했나:** **질문은 엔티티에게 한다**(`ask(party, "Title_Key", [...])`). 질의에 굳어 저장되는 것은 응답 이름별 **엔티티 목록**이다. 응답이 오면 입구가 목록의 엔티티 중 하나에 대해 `may_act(issuer, 엔티티)`(G122의 같은 정책)가 참인지 본다. 담당 확인은 질의가 열릴 때가 아니라 **응답이 올 때** 한다. `ask`는 issuer가 아니라 답한 엔티티를 돌려준다. 시간 초과 주입값(X2)의 모양, 목록에 같은 issuer가 맡은 엔티티가 여럿일 때 어느 것으로 답했는지 정하는 방법은 이 항목이 정하지 않는다.

**이유:** 자유 커맨드(G122)와 같은 검사 하나로 된다. 기다리는 중에 담당이 바뀌어도(접속 끊김 → AI, U10·U13) 질의를 다시 열지 않고 새 담당이 답한다. 이전 TR도 `Effect_Choice choosingParty`로 정당 엔티티에게 물었다(U6). 열릴 때 issuer로 바꿔 굳히기(C)는 이 경우 답할 수 없게 된다.

**상태:** 확인

## G126

**위치:** G125의 남은 둘: 응답이 어느 엔티티로서인지, 시간 초과 주입값

**무엇이 비어 있었나:** 핫시트처럼 한 연결이 목록의 엔티티를 여럿 맡으면 `may_act`가 모두 참이라 어느 엔티티로 답했는지 알 수 없다. X2는 시간 초과 응답을 “제출자 값 공간의 가짜 이름이 아닌 구분 가능한 값”으로 넣으라고만 했다.

**어떻게 정했나:** **응답 커맨드는 어느 엔티티로서 답하는지를 늘 명시한다.** 입구는 그 엔티티가 그 응답의 목록에 있는지와 `may_act(issuer, 그 엔티티)`를 본다. `ask`는 그 엔티티를 돌려준다. 목록에 하나뿐이어도 생략은 커널 규칙이 아니다(채워 주는 것은 UI·호스트 몫). **시간 초과 주입은 엔티티가 `None`**이고 응답 이름은 `on_timeout`이 정한다. 반환값의 필드 이름은 표기를 정할 때 정한다.

**이유:** 커맨드 기록에 늘 명시돼 리플레이가 단순하다. 자유 커맨드의 `acts_for`(G122)와 같고, OpenTTD도 패킷에 회사를 명시한다(소스 확인). `None`은 엔티티 자리의 “아무도 아님”이라 가짜 이름이 필요 없다. 생략 시 목록 첫 번째로 치기(B)는 핫시트에서 의도와 다른 엔티티로 처리될 수 있다.

**상태:** 확인

## G128

**위치:** X3 `std.stack`: 대기 중인 행동(“나중에 해소할 것”)의 표현과 커널의 몫

**무엇이 비어 있었나:** 이전 TR 스택 노드는 효과 객체와 컨텍스트 바구니를 들고 저장했고(U5), 새 spec은 세이브에 함수 객체를 넣지 못한다(S7). 노드를 데이터(행동 Def id + 인자)로 둘지, 행동의 Flow가 멈춰 기다리게 할지가 비어 있었다.

**어떻게 정했나:** **표현은 `std.stack`(모드)의 몫이고 커널 결정이 아니다.** 방향은 데이터 방식(노드 엔티티에 행동 Def id와 인자를 두고, 해소할 때 그 Def의 `Action` 함수를 부름)이며 `std.stack`을 만들 때 확정한다. **커널의 몫은 이 방식을 커널 기능만으로 만들 수 있게 하는 것**이고, 막히는 곳은 상태에 담을 수 있는 값의 모양(행동마다 다른 인자, 주사위 눈 같은 목록)이다(이어서 정함). Flow가 다른 Flow의 신호를 기다리는 기능은 지금 추가하지 않는다(데이터 방식이면 필요 없음, 다른 사례가 요구할 때 다시 본다).

**이유:** X3 경계 규칙과 “표준 모드를 만들다가 커널이 부족하면 커널의 결함”. MTG 스택(카드 + 대상), RimWorld `Job`(JobDef + 대상 칸), CK3 지연 이벤트(`trigger_event` + `save_scope_as`)가 모두 데이터 방식이다(일반 지식). 데이터면 UI·AI가 스택 내용을 읽을 수 있고 모드 업데이트 뒤에도 새 본문으로 해소된다(멈춘 Flow는 본문 해시가 바뀌면 로드 거부, S8).

**상태:** 확인

## G137

**위치:** X1 질문의 선택 방법(창·지도 강조 클릭 등)을 누가 정하나, 질문에 실을 추가 정보

**무엇이 비어 있었나:** 이전 엔진 TR은 질문 모양이 C# 클래스로 고정되어(`PendingChoiceData`는 정당·제목·설명·문구 키 목록뿐, `PendingTargetSelectionData`는 후보 id뿐) 해소 중인 카드나 `Amount`처럼 UI가 보여 줄 정보를 더하려면 엔진을 고쳐야 했고, 종류마다 전역 자리가 하나라 새 종류나 동시 질문이 막혔다. 선택 방법은 게임마다 다르다: 효과 코드가 지정(RimWorld `Targeter`·창, Slay the Spire 선택 화면, HOI4 `on_map_mode`), UI가 후보 종류로 결정(MTG 계열 클라이언트), 스크립트는 종류 이름만 주고 모양은 UI 파일이 정함(패러독스 이벤트 `type`·`.gui`). (모두 일반 지식)

**어떻게 정했나:** **스크립트는 제안만, 결정은 UI.** `ask`는 선택 사항으로 `hint=` 문자열을 받아 Request에 싣고 커널은 해석하지 않는다. 해석과 등록이 없을 때의 기본 방식(후보 종류에 따라 강조 클릭 또는 목록 창)은 UI 모듈 몫이다. 질문에는 모드가 정하는 자유 데이터 `data=`(값·엔티티)도 실을 수 있고 UI는 그것과 시뮬레이션 상태(S10 path)를 읽는다. 선택 방법은 답의 의미를 바꾸지 않으므로 응답은 어떻게 골랐든 같은 데이터이고 AI·서버·테스트는 `hint`를 무시한다. 여러 단계 고르기(강조 후 확인, 필터)는 UI 로컬(`@ui_action`)이다. `hint` 이름 규칙과 UI 쪽 등록 방식은 UI 모듈을 만들 때 정한다.

**이유:** 커널이 표시 방식 목록을 검사하면(B) 새 방식마다 커널을 고쳐야 해 TR의 고정 클래스와 같은 벽이다. UI가 후보 종류로만 정하면(C) 예외 연출을 요청할 길이 없다.

**상태:** 확인

## G138

**위치:** X1 `ask`의 호출 모양과 돌려주는 값 (G126이 미룬 필드 이름)

**무엇이 비어 있었나:** 실제 질문은 세 모양이었다(TR): 문구 N개 중 하나(`Effect_Choice`), 후보 중 하나(`Effect_SelectTarget`), 인자가 있는 여러 행동 중 하나(우선권의 통과·대응). 앞의 둘은 원소 종류만 다르고 어떻게 보일지는 G137에 따라 UI가 정한다. 셋째는 조합(카드·대상·추가 지불)이 많아 목록으로 펼칠 수 없다.

**어떻게 정했나:** **`ask(who, title, choices=[...], responses=[...], hint=, data=)`.** `who`는 엔티티 하나 또는 목록(그중 누구든), `title`은 텍스트 키나 `text(...)`. `choices`는 고를 값의 목록(문구 키·`text(...)`·엔티티·Def id)이고 `responses`는 받을 응답 커맨드(자유 커맨드가 아닌 `@command`) 이름의 목록이며 하나만 써도 둘 다 써도 된다. 돌려받는 값 `r`은 한 모양이다: `r.response`(커맨드 이름, 고르기면 `None`), `r.index`·`r.choice`(고른 번호와 값, 응답 커맨드면 `None`), `r.by`(답한 엔티티, 시간 초과면 `None`). 고를 수 없는 선택지의 표시, 시간 관련 인자, 응답 커맨드 본문이 답한 엔티티를 읽는 법, 응답 커맨드 인자를 `r`로 받을지, 동시 고르기(시나리오 ②)는 이 항목이 정하지 않는다.

**이유:** 종류별 내장(`choose_option`·`choose_target`·`ask_response`)은 문구와 대상이 섞인 목록을 표현하기 어렵고 종류마다 커널 내장이 는다. 응답 커맨드만 두면 선택지 하나 묻는 데도 커맨드 선언이 필요하다.

**상태:** 확인

## G139

**위치:** X1·S6 응답 커맨드의 본문이 답한 엔티티를 아는 방법 (G126·G130에서 이어짐)

**무엇이 비어 있었나:** G126은 응답이 어느 엔티티로서인지 늘 명시한다고만 했고, G130은 `acts_for`를 자유 커맨드에만 적게 했다. 대응 커맨드의 본문은 그 정당의 카드를 내야 하므로 답한 엔티티가 필요하다. 행위자는 인자에서 나오고 숨은 `me`는 없다(G119·G120).

**어떻게 정했나:** **`acts_for`를 모든 커맨드에 쓴다.** 응답 커맨드도 `@command(acts_for=lambda party: party)`처럼 인자에서 행위자를 고르고, 제출자는 그 인자를 포함한 모든 인자를 낸다. 답하는 순서는 질문 확인 → 그 커맨드를 받는 질문인가 → 인자(G115) → `acts_for` → 질문의 목록에 있나 → `may_act` → 사전 조건 → 본문이고, 본문은 기다리던 Flow의 같은 트랜잭션에서 실행된 뒤 `ask`가 `r.response`(커맨드 이름)와 `r.by`(그 엔티티)를 돌려준다. 거절·사전 조건 실패·오류는 상태를 건드리지 않고 질문은 열린 채다. G130의 “`acts_for`는 자유 커맨드에만”은 “모든 커맨드에 필수”로 넓힌다. 응답 커맨드는 `acts_for=None`을 쓸 수 없다(답은 늘 어떤 엔티티로서). 빠지면 로드 오류(G123과 같은 규칙).

**이유:** 답할 엔티티를 받을 매개변수를 따로 지정하는 방식(`answers_as=`)은 자유 커맨드와 선언 방식이 갈리고 데코레이터 인자가 는다. 숨은 내장 `responder()`는 G119에서 없앤 `me`를 되살린다.

**상태:** 확인

## G154

**위치:** X2 엔진의 틱 신호와 지금 틱 읽기 (G145에서 미룸)

**무엇이 비어 있었나:** X2·S5는 옛 표기 `on("tick")`/`emit("tick")`으로 적었고, G145는 신호를 선언한 이름으로 바꾸며 엔진 신호는 엔진이 선언한다고만 했다. 스크립트가 지금 틱을 읽는 방법도 없었다.

**어떻게 정했나:** **엔진이 신호 `Tick`을 값 없이 미리 선언하고, 지금 틱은 내장 `now()`로 읽는다.** `@on(Tick, stage="core.economy")`. `Tick`은 모든 모드에 보이고 의존 선언이 필요 없다. 모드가 같은 이름을 선언하면 이름 충돌 오류다. 스크립트가 `Tick`을 `emit`할 수 있는지와 `now()`를 `derived`에서 쓸 수 있는지는 따로 정한다.

**이유:** 틱 번호를 신호 값으로 싣기(B)는 다른 곳에서도 `now()`가 필요해 같은 값을 얻는 길이 둘이 된다. 문자열 `"tick"` 특별 취급(C)은 G145 표기와 어긋난다. 근거: 패러독스 `on_monthly_pulse`는 날짜를 인자로 넘기지 않고 효과 안에서 현재 날짜를 읽는다(일반 지식).

**상태:** 확인

## G155

**위치:** G154 `now()`를 쓸 수 있는 자리

**무엇이 비어 있었나:** `derived`는 순수하고 읽을 때 계산한다(G103, 캐시 없음). `now()`를 `derived`·사전 조건에서 읽으면 값이 시간에 따라 바뀌고, 나중의 `when`(읽은 칸이 바뀔 때만 재평가, S5)과 `Explain`(G105)이 그 의존을 알아야 한다.

**어떻게 정했나:** **어디서나 읽을 수 있고, 읽으면 "틱" 칸을 읽은 것으로 기록한다.** `Explain`의 근거에 나오고 `when`의 읽은 목록에 들어간다(`when`은 반응 ②에서).

**이유:** `derived`·사전 조건에서 금지(B)는 도우미 함수를 거친 호출까지 막으려면 "시간을 읽는 함수" 등급이 새로 필요하고, 나이처럼 정상적인 쓰임도 막는다. 기록 없이 허용(C)은 `when`이 발동하지 않고 `Explain`이 근거를 빠뜨린다. 근거: RimWorld 폰 나이와 패러독스 캐릭터 나이는 태어난 시점과 현재 시점으로 계산한다(일반 지식).

**상태:** 확인

## G156

**위치:** G154 스크립트가 `Tick`을 내는 것

**무엇이 비어 있었나:** 신호 값 생성자는 선언한 신호면 누구나 쓸 수 있다(G145). 스크립트가 `emit(Tick())`하면 틱 카운터는 그대로인데 모든 틱 핸들러가 한 번 더 돌아(월급 두 번), 모드들이 믿는 "틱마다 한 번, 카운터가 오른 뒤"가 깨진다.

**어떻게 정했나:** **엔진 신호의 값은 스크립트가 만들 수 없다.** 함수 본문에 `Tick(...)`이 적혀 있으면 로드 오류이고, 그 밖의 경로(함수 값 등)는 실행 오류다. 메시지는 `Tick`은 `advance`가 낸다고 알린다. 엔진 신호가 더 생기면 같은 규칙이다. 시간을 흘리려면 `advance`를 부른다.

**이유:** 허용(B)은 위 문제가 그대로 남는다. 엔진 신호에 붙은 약속은 스크립트가 흉내 낼 수 없어야 지켜진다. 일반적인 설계 판단이다.

**상태:** 확인

## G157

**위치:** X2 `wait`에서 깨어난 Flow의 오류

**무엇이 비어 있었나:** 답(`Answer`)이 이어 간 구간이 실패하면 효과를 되감고 질문을 열어 둔다(제출자가 다시 답할 수 있다). 깨우기는 엔진이 하므로 같은 규칙이면 다음 틱에 다시 깨어나 매 틱 같은 오류가 난다.

**어떻게 정했나:** **그 구간을 되감고 Flow를 버린다.** 오류는 `Advance` 결과의 반응 목록(G148)에 깨어난 Flow 항목으로 남긴다(신호 자리 `wait`, 핸들러 자리에 Flow를 만든 커맨드·핸들러 id). `wait` 전에 끝난 트랜잭션의 효과는 그대로다.

**이유:** 되감고 다시 재움(B)은 매 틱 같은 오류가 쌓인다. 깨우지 않고 둠(C)은 살릴 방법 없는 Flow가 저장에 영원히 남는다. 반응 오류는 그 반응만 되돌리고 진단을 남긴다는 S5와 같은 방향이다. 일반적인 설계 판단이다.

**상태:** 확인

## G158

**위치:** X2 `wait`로 잠든 것을 호스트가 아는 방법

**무엇이 비어 있었나:** 제출·답의 결과에는 연 질문(`OpenedRequest`)만 있어 `wait`로 잠든 커맨드가 그냥 끝난 커맨드와 같아 보인다. 게임이 진행 표시를 띄울 근거가 없다.

**어떻게 정했나:** **결과에 깨울 틱 `SleepsUntil`을 둔다.** `SubmitResult`·`AnswerResult`(답과 응답)에, 같은 이유로 반응 항목 `Reaction`(핸들러가 잠들거나 깨어난 Flow가 다시 잠들 때)에도 둔다. 잠들지 않았으면 null. 결과 종류(`Succeeded`)는 그대로다.

**이유:** 결과 종류를 하나 더 둠(B)은 앞부분 효과가 남은 성공을 둘로 나눠 호스트가 성공을 두 곳에서 봐야 한다. 그대로 둠(C)은 깨어날 때까지 호스트가 모른다. CK3 지연 이벤트(`trigger_event = { days = n }`)는 부른 쪽에 아무것도 돌려주지 않아 기댈 사례가 아니다. 일반적인 설계 판단이다.

**상태:** 확인

## G159

**위치:** X2 `ask`가 시간을 막는지의 기본값

**무엇이 비어 있었나:** X2는 `blocks_time`인 질문이 열려 있으면 `advance`를 거부하고, 막는 질문에 마감을 두면 오류라고만 했다. 아무것도 적지 않은 `ask`가 막는지는 정하지 않았다.

**어떻게 정했나:** **마감 유무로 정한다.** `deadline=`이 없으면 막고 있으면 막지 않는다. `blocks_time=`을 적으면 그것을 따른다(`blocks_time=False`만 쓰면 마감 없이 시간이 흐르는 질문). 막는 질문에 마감을 두는 오류는 둘을 직접 함께 적었을 때만 난다.

**이유:** 기본 막음(A)은 마감을 쓸 때마다 `blocks_time=False`를 함께 적어야 하고 빠뜨리면 오류다. 기본 안 막음(B)은 턴제에서 막기를 깜빡하면 질문을 건너뛴 채 시간이 흐르는데 눈에 띄지 않는다. RimWorld 선택 편지와 패러독스 이벤트는 시간이 흐르며 마감이 있고, 이전 엔진의 `isMandatory`(U10)는 막는 쪽이다. C는 적은 것만 보고 둘을 나눈다.

**상태:** 확인

## G160

**위치:** X1·X2 `deadline=`의 표기

**무엇이 비어 있었나:** X1은 Request에 `deadline`(선택) 필드가 있다고만 했다. 몇 틱 뒤인지, 몇 틱째인지 정하지 않았다.

**어떻게 정했나:** **몇 틱 뒤인지 적는다: `deadline=n`(1 이상 int).** `wait(ticks=n)`과 같은 방식이다. 질문이 열릴 때 지금 틱 + n으로 바꿔 굳히고 저장하며 호스트는 `Request.Deadline`에서 그 틱을 본다. 정해진 틱까지라면 `deadline=그틱 - now()`로 쓴다.

**이유:** 몇 틱째(B)는 흔한 "n틱 안에"마다 `now()`를 더해야 하고 빠뜨리면 지난 틱이 된다. 둘 다(C)는 이름이 늘고 함께 쓴 경우의 오류가 필요하다. 패러독스 스크립트의 지연은 대개 "며칠 뒤"(`days = n`)이고 RimWorld 선택 편지의 제한도 지금부터의 틱이다(세부는 일반 지식 수준).

**상태:** 확인

## G161

**위치:** X2·G126 `on_timeout=`이 가리키는 것

**무엇이 비어 있었나:** X2는 마감이 지나면 엔진이 기본 응답을 넣고 G126은 그때 답한 엔티티가 `None`이며 응답 이름은 `on_timeout`이 정한다고만 했다. 선택지 질문에서 무엇을 가리키는지, 어떻게 적는지는 정하지 않았다.

**어떻게 정했나:** **선택지 값이나 응답 이름으로 가리킨다.** `on_timeout="hide"`는 `choices` 안의 값이어야 하고(같은 값이 여럿이면 앞의 것) 마감이 지나면 `ask`가 그 선택지(`r.choice`·`r.index`)와 `r.by = None`을 돌려준다. `responses=` 질문이면 `on_timeout="Pass"`처럼 응답 이름을 쓰고 `r.response`가 그 이름이며, 응답 커맨드의 본문은 돌지 않는다(인자를 낸 제출자가 없다). 선택지와 응답 이름에 모두 맞거나 어디에도 없으면 실행 오류다.

**이유:** 번호(B)는 선택지 순서를 바꾸면 기본 답이 조용히 바뀐다. 정하지 않고 스크립트가 처리(C)는 spec의 "기본 응답 주입"과 멀고 처리를 빠뜨리면 `None`으로 뒤에서 오류가 난다. 이전 엔진은 선택지에 `isDefault`를 붙였고(U10) EU4 이벤트도 정해진 선택지 하나가 골라진다(세부는 기억 수준).

**상태:** 확인

## G162

**위치:** X2 마감만 있고 `on_timeout=`이 없는 질문

**무엇이 비어 있었나:** G161은 `on_timeout=`이 마감을 요구한다고 했지만 반대(마감이 있는데 기본 답이 없음)는 정하지 않았다. 그대로 두면 마감이 지나도 아무 일도 없이 열려 있다.

**어떻게 정했나:** **실행 오류다: `deadline=`을 쓰면 `on_timeout=`도 적는다.** 마감이 지나면 무슨 일이 일어나는지가 늘 스크립트에 보인다. 그냥 넘기기를 원하면 그런 선택지를 두고 기본 답으로 지정한다.

**이유:** "아무도 답하지 않음" 값(B)은 처리를 빠뜨리면 `None`으로 뒤에서 오류가 난다. 질문을 닫고 Flow를 끝냄(C, RimWorld 선택 편지가 사라지는 것과 비슷)은 뒤의 코드가 왜 안 돌았는지 헷갈린다. 마감을 정보로만 둠은 X2의 "마감 시 기본 응답 주입"과 맞지 않는다. 막는 쪽이 나중에 B·C를 더해도 기존 모드가 깨지지 않는다. 일반적인 설계 판단이다.

**상태:** 확인

## G167

**위치:** X2 스크립트의 `advance(n)`

**무엇이 비어 있었나:** X2는 `advance`를 게임 C# 루프나 스크립트 Flow가 부를 수 있다고만 했다. Flow는 다음 멈춤까지 한 트랜잭션인데 틱 안의 깨우기·핸들러는 각자 트랜잭션이라(S5) Flow 한가운데서 시간을 흘리는 순서가 정해지지 않았다.

**어떻게 정했나:** **`advance(n)`은 `wait`처럼 멈추는 내장이다.** Flow가 거기서 멈춰 그때까지가 확정되고, 같은 호출 안에서(그 호출의 신호 처리가 끝난 뒤) 엔진이 n틱을 진행한 다음 Flow를 이어 간다. `advance()`는 실제로 간 틱 수를 돌려준다(막는 질문으로 멈추면 n보다 작다). 시간이 흐르는 중(깨어난 Flow·마감·틱 핸들러)이나 신호 핸들러 안에서 부르면 실행 오류다. 커맨드나 답으로 이어진 Flow에서 부른다. n은 1 이상.

**이유:** 예약만(B, `emit`처럼)은 `advance` 다음 줄이 시간이 흐르기 전에 돌아 헷갈린다. 두지 않음(C)은 표준 모드의 턴 루프를 스크립트로 쓸 수 없다. 이전 엔진 WG의 턴 스텝은 반복마다 `await AdvanceTickAsync(1)`을 불렀다(U3).

**상태:** 확인

## G168

**위치:** X2 스크립트 `advance`가 호출 하나를 붙잡는 양 (G167에서 이어짐)

**무엇이 비어 있었나:** `advance`마다 구간이 새로 시작되어 단계 예산에 걸리지 않고 신호 연쇄도 아니라 세대 상한과도 무관하다. `for i in range(1000000): advance(1)`이면 제출 한 번이 백만 틱을 돌 때까지 돌아오지 않는다(코드로 판단, 재현 안 함).

**어떻게 정했나:** **호출 하나당 상한을 둔다.** 제출·답·응답 한 번 안에서 스크립트 `advance`가 요청한 틱의 합이 호스트 값 `maxAdvancePerCall`(기본 10000, World 생성·불러오기 인자)을 넘게 되면 그 Flow를 진행하지 않고 실행 오류로 버린다(G157). 그때까지 간 틱과 효과는 남는다. 막혀서 덜 갔어도 요청한 만큼 센다(막힌 채 도는 루프도 끝나게).

**이유:** 상한 없음(A)은 정상 쓰임엔 문제없지만 실수하면 오류 없이 게임이 언다. 연달은 `advance` 횟수(C)는 `advance(1000000)` 한 번을 못 막는다. 이전 엔진 `TickManager.AdvanceTickAsync`는 상한이 없고 진행 중 재요청은 조용히 무시했다(코드 확인). 패러독스의 `while` 반복 상한, Unity 고정 간격 루프의 한 프레임 단계 상한(Maximum Allowed Timestep)은 엔진이 상한을 두고 넘으면 멈춘다(일반 지식).

**상태:** 확인
