# spec 빈틈 상세: S2 로직 언어·실행기 (P2·P6, 실행 예산·벤치 포함)

색인과 상태 규칙은 `docs/spec-gaps.md`. 이 파일은 G 번호마다 무엇이 비어 있었고 어떻게, 왜 정했는지의 전문이다.

## G4

**위치:** P2 `fixed` 리터럴

**무엇이 비어 있었나:** 소수 자리가 6을 넘는 리터럴의 처리.

**어떻게 정했나:** 오류(`LEX007`). 단, 넘는 자리가 모두 0이면(`1.5000000`) 허용.

**이유:** 조용히 반올림하면 모더가 쓴 값과 다른 값이 된다.

**상태:** 확인

## G13

**위치:** S2 언어

**무엇이 비어 있었나:** 파이썬 부분집합의 어휘 수준 제한.

**어떻게 정했나:** 들여쓰기의 탭은 오류. 16·8·2진수, 지수 표기, 허수 금지. 문자열 접두사는 `u`만(`r`·`b`·`f`는 미지원). 이스케이프는 `\\ \' \" \n \r \t \0 \xhh \uXXXX \UXXXXXXXX`와 줄 잇기만. 튜플·집합·슬라이스·언패킹·체인 비교·조건식·컴프리헨션은 이 단계에서 미지원(`PAR002`, 구문 오류와 구분). **②에서 바꿈:** 첨자 안의 쉼표(`dict[K, V]`)는 파싱한다(타입 표기용, 값 인덱싱은 평가기가 거부, G22). `def`는 머리부만 파싱한다(G17). 람다는 파싱한다(G33).

**이유:** spec S2는 문장 수준 허용 목록만 있었다. 컴프리헨션은 spec상 허용이므로 로직 단계에서 지원 예정. 데코레이터와 `match` 문도 같은 방식으로 미지원 보고(`match`는 소프트 키워드라 블록을 여는 줄에서만).

**상태:** 잠정

## G14

**위치:** S2 언어

**무엇이 비어 있었나:** 식별자에 쓸 수 있는 문자.

**어떻게 정했나:** **ASCII만**: `[A-Za-z_][A-Za-z0-9_]*`. 비 ASCII 글자가 섞인 이름은 `LEX011` + "표시 문자열은 문자열이나 텍스트 키에". 문자열·주석·Def id(문자열)에는 제한 없음. 나중에 파이썬 규칙(XID 표 + NFKC 정규화, 유니코드 버전 고정)으로 넓힐 수 있다. ASCII는 두 규칙에서 같으므로 기존 모드·세이브가 깨지지 않는다. 그러려면 렉서 밖(세이브 칼럼 이름, 해시, did-you-mean)은 이름을 ASCII로 가정하지 않는다.

**이유:** 파이썬은 식별자에 XID 표와 NFKC 정규화를 쓴다. 이를 그대로 따르려면 표를 엔진에 넣어야 하고, 따르지 않으면 파이썬과 뜻이 달라진다(한글 완성형/조합형 등). 식별자는 세이브에 남는 내부 이름이고 화면 문자열은 텍스트 키로 간다(S2, X4). 비 ASCII 문자를 이름 한 덩어리로 묶는 판정만 런타임 유니코드 표를 쓰는데, 이는 오류 메시지를 고르는 용도이고 허용 여부는 바꾸지 않는다.

**상태:** 확인

## G17

**위치:** S2 함수 정의

**무엇이 비어 있었나:** 스키마가 가리키는 함수(`derived(int, health_max)`)를 로딩 슬라이스에서 어디까지 다룰지.

**어떻게 정했나:** `def`는 머리부(이름, 매개변수 이름과 어노테이션, 반환 어노테이션)만 파싱하고 본문은 건너뛴 채 함수 값으로 묶는다. 로드 중에는 호출하지 않는다(호출하면 `EVL005`). 본문 파싱·순수성 판정은 식 언어 단계. 매개변수 기본값, `*args`/`/`는 계속 `PAR002`. 람다는 G33.

**이유:** ②는 함수를 값으로 등록하기만 하면 된다. 본문 평가기는 식 언어 단계의 일이다. 본문의 구문 오류는 그 단계까지 보고되지 않는다(어휘 오류는 지금도 보고됨).

**상태:** 확인

## G20

**위치:** S2 최상위 이름

**무엇이 비어 있었나:** 파일 사이에 최상위 이름(`def`, `x = ...`)이 공유되는지, 다시 묶을 수 있는지.

**어떻게 정했나:** **모드마다 이름 공간 하나**를 실행 순서(스키마 파일 → Def 파일)대로 쓴다. 쓰기 전에 정의되어 있어야 하고(파이썬과 같음), 한 이름은 한 번만 묶는다(`EVL004`). ~~내장 이름(`component`, Def 타입 이름 등)은 다시 묶을 수 없다.~~ (G112가 바꿈: 엔진이 주는 이름은 덮어쓸 수 있는 내장) 다른 모드의 함수를 이름으로 쓰는 방법은 아직 없다.

**이유:** `import` 대신 `use`라는 S2의 말은 같은 모드의 파일들이 한 덩어리라는 뜻으로 읽었다. 재바인딩 금지는 Starlark 규칙이며 "로드 후 정의는 동결"과 맞는다.

**상태:** 잠정

## G22

**위치:** S2 로드 시점 평가

**무엇이 비어 있었나:** 로드 중에 어떤 식을 평가하는지.

**어떻게 정했나:** 리터럴, 리스트, 맵, 이름, 호출, 타입 표기의 `[...]`, 수 앞의 `+`/`-`만. 그 밖의 연산자·속성 접근·값 인덱싱은 `EVL002`(식 언어 단계에서 추가). 맵 키는 `str`·`int`만이고 중복 키는 오류. 이에 맞춰 스키마의 `dict[K, V]`도 K를 `str`·`int`·`DefId[...]`로 제한한다(그 밖이면 ②a에서 `SCH004`. 채울 수 없는 맵을 선언 단계에서 막는다). 첨자 안의 쉼표(`dict[K, V]`)는 이제 파싱된다(G13의 "튜플 인덱스 미지원"을 바꿈). 값 인덱싱에서는 여전히 거부.

**이유:** Def와 스키마에 필요한 최소한. `fixed` 연산이 아직 없다. 파이썬은 `1 == 1.0 == True`라서 키 타입을 섞으면 뜻이 갈린다.

**상태:** 잠정

## G24

**위치:** S2 함수 자리 타입 이름

**무엇이 비어 있었나:** `Cond`·`Fn`·`Action`의 이름과 모양이 ❓였다.

**어떻게 정했나:** `Cond["T"]`, `Action["T"]`(T는 Def 타입 이름 문자열)만 구현. `Fn`은 반환 타입 표기가 정해지지 않아 넣지 않았다. 함수 타입은 const에만(`field`·`derived`에 쓰면 `SCH004`). 자리와 함수 효과의 일치 검사는 식 언어 단계.

**이유:** schema-design 3.3.3의 예시 표기를 그대로 썼다. `.pyi` 구현 때 확정.

**상태:** 잠정

## G32

**위치:** S2·S3 참조 타입

**무엇이 비어 있었나:** `Ref["X"]`가 자리에 따라 뜻이 달랐다. `const(dict[Ref["Need"], fixed])`에서는 Def, 커맨드 매개변수 `Ref[Unit]`에서는 엔티티였다. 그래서 런타임 칼럼과 커맨드 매개변수에서 Def를 가리킬 표기가 없었고(지금 만드는 레시피, `Build(recipe=...)`), 엔티티 칼럼은 `ref("X")`와 `field(Ref["X"])` 두 가지로 쓸 수 있었다.

**어떻게 정했나:** 참조 타입을 둘로 나눈다. `Ref["X"]`는 어디서나 **엔티티**, `DefId["X"]`는 어디서나 **Def**(id). `const`에는 `Ref`가 올 수 없다(`SCH004`). 엔티티 칼럼은 `ref(...)`로만 선언한다(`field(Ref[...])`는 `SCH004` + 안내). `ref("X")`·`Ref["X"]`의 대상은 보이는 범위에서 컴포넌트를 가진 타입이어야 한다(G31과 같은 판정, `SCH004`). spec S2·S6과 schema-design 2.3·3.2의 예시에서 Def를 가리키던 `Ref`를 `DefId`로 바꿨다.

**이유:** 편집기에서 둘은 이미 다른 타입이다(Def 참조는 id 문자열 `Literal`, 엔티티는 타입 클래스). 이름이 그 차이를 드러내야 자리마다 뜻을 외울 필요가 없다. 이름은 "Def 참조는 문자열 id"(S2)를 드러내는 `DefId`. `Def`는 Def 타입 이름과 헷갈린다.

**상태:** 확인 (예시만 반영: 옛 `const(Ref[...])` 예시가 로드되지 않게 되므로 spec·schema-design의 예시와 3.2 설명은 먼저 고쳤다. 규칙 자체를 spec에 옮기는 것은 남음)

## G33

**위치:** S2 람다

**무엇이 비어 있었나:** spec은 "제한된 람다"를 허용하지만 무엇을 제한하는지가 없었다. schema-design의 예시(3.3.1 `derived`·`default=`, 3.3.3 `succeeded=`)가 람다를 쓴다.

**어떻게 정했나:** 람다를 지금 지원한다. 매개변수는 이름만 받고(기본값·`*args`·`/`는 `PAR002`), 본문 식은 끝까지 파싱한다(본문 안의 조건식·컴프리헨션은 아직 `PAR002`). 평가하면 `def`와 같은 함수 값이 되고(이름 `<lambda>`) 호출하지 않는다. 그 밖의 제한(람다 안의 람다 등)은 식 언어 단계에서 순수성 판정과 함께 정한다.

**이유:** ②는 함수를 값으로 묶기만 하므로 평가기 없이 넣을 수 있다. 본문이 식 하나라 `def`와 달리 지금 파싱할 수 있고, 그래서 본문의 구문 오류도 지금 보고된다.

**상태:** 확인

## G40

**위치:** S2 효과 표의 `patch.*`

**무엇이 비어 있었나:** `patch.*`를 어디서 호출할 수 있는지(함수 몸체, `if`/`for` 안, 스키마 파일, 런타임)가 없었다.

**어떻게 정했나:** 효과 표에서 Def 생성과 같은 칸(로드 시점만). ②b의 Def 파일 어디서든 호출할 수 있다(최상위, `if`/`for` 안, 같은 모드의 보조 함수 안). 스키마 파일(②a)에서는 `SCH006`과 같은 오류, 런타임 Flow 본문에서는 로드 오류. 반환값은 없고 문장으로만 쓴다. 인자는 로드 시점에 평가 가능한 값(G22)이어야 한다. `if/elif/else` 문장은 **이번 슬라이스에 연다**(G46). `for`는 식 언어 단계에서 열린다.

**이유:** 반복 패치(같은 태그의 Def 전부에 +1 등)가 흔하다. 모든 호출이 기록되고 같은 단계 순서로 적용되므로 어디서 불러도 안전성은 최상위만 허용할 때와 같고, 정적 분석 규칙이 Def 생성과 한 칸으로 합쳐진다. 런타임 호출은 "로드 후 정의는 동결"(S2)과 부딪힌다.

**상태:** 확인

## G46

**위치:** S2 조건문 `if`와 `mod_loaded`

**무엇이 비어 있었나:** `optional` 모드가 없을 때 호환 패치를 어떻게 쓰는지, 그리고 로드 시점에 `if`가 되는지가 없었다(파서는 모든 복합문을 `ParUnsupported`로 건너뛰고, 들여쓴 블록을 문장 목록으로 읽는 함수가 없음).

**어떻게 정했나:** **`if/elif/else` 문장을 Def 파일에 연다**(`for`·`while`은 열지 않음). 블록은 문장 목록이며 이름 묶기는 모듈 범위(파이썬과 같음). **조건은 bool을 돌려주는 로드 시점 호출 하나**로 제한한다(G22에 `and`/`or`/`not`/비교가 없음. 부정은 `else`로, 연산자는 식 언어 단계에서). **`mod_loaded("m")`**: 내장 순수 함수, 현재 활성 모드 집합에서 평가한다. 인자는 문자열 리터럴이고 이 모드의 `dependencies` 또는 `optional`에 선언된 모드 id여야 한다(아니면 오류 + "혹시 …?"). G28이 실패한 모드를 빼고 ②를 다시 만들 때마다 가드가 새로 평가되어 자동으로 일관되며, 모드가 줄어드는 방향이라 반복은 끝난다. **스키마 파일(②a)에서는 `mod_loaded`를 쓸 수 없다**(`SCH` 오류): 스키마가 설치 모드에 따라 달라지면 모드별 `.pyi`(4.3)와 `check`의 일관성이 깨진다. 스키마 파일의 `if`는 계속 미지원. **`mod_loaded` 가드의 참/거짓 가지 안에는 `patch.*` 호출과 중첩된 `if`만 쓸 수 있다**: Def 생성, 이름 묶기(대입), `def`는 오류("가드 안에서는 패치만 쓸 수 있습니다"). 설치 상태에 따라 Def id나 이름이 있기도 없기도 하면 모드별 `.pyi`의 `Literal[...]` id 목록과 `check`가 설치 상태마다 달라지고, 다른 파일의 참조가 깨지기 때문이다. 호환 패치라는 실제 용도를 모두 덮고, 나중에 조건부 Def가 필요해지면 `.pyi`·`check` 설계(조건부 id)를 정한 뒤 넓힌다(넓히는 방향이라 기존 모드는 깨지지 않음). 실행 중 "이 가지에서 참으로 가정된 모드"를 스택으로 들고, 기록하는 패치 호출에 함께 저장한다(G38의 가드 검사에 쓴다). 거짓 가지의 `patch.*` 호출 수는 구문을 훑어 센다. 구현 순서: ③에 들어가기 전에 `if`와 `mod_loaded`를 작은 독립 커밋으로 먼저 넣는다.

**이유:** 호환 패치는 조건 블록이 보통이고 여러 패치를 한 번에 묶는다. 블록 읽기는 `def` 본문·`@command` 때도 필요한 기반이다. 호출 하나로 제한하면 이번 슬라이스에 연산자 평가를 끌어오지 않는다.

**상태:** 확인

## G48

**위치:** S2·S1 데이터 값의 `int` → `fixed`

**무엇이 비어 있었나:** Def 리터럴 값의 타입 검사는 ⑥(G25)이라 `fixed` 필드에 정수 리터럴(`cost = 5`)을 쓸 수 있는지가 정해지지 않았다. G39는 패치에 대해서만 허용했다. S2의 "변환은 명시적"은 로직 식 안의 변환을 말하는 것으로 읽힌다.

**어떻게 정했나:** **데이터 값(Def 리터럴과 패치)에서는 `int` → `fixed`를 암묵적으로 허용**한다(정수는 정확히 10⁶ 스케일 `fixed`로 손실 없이 바뀜). `fixed` → `int`는 소수가 잘릴 수 있으므로 오류 + "정수를 쓰세요". 검사는 ⑥의 값 타입 검사이며 패치의 모양 검사(G39)는 ③에서 같은 규칙을 쓴다. 로직 식의 `int`/`fixed` 혼합 연산은 이 결정과 무관하게 S2대로 따로 정한다(식 언어 단계).

**이유:** 모더가 `cost = 5`와 `cost = 5.0`을 구별해 쓰게 하면 실수가 잦고 이득이 작다. 위험(소수 손실)은 반대 방향에만 있어 그쪽만 막으면 된다. S2의 "명시적" 원칙은 로직 식에 그대로 남는다.

**상태:** 확인

## G90

**위치:** S2·S4 `derived` 계산과 첫 런타임 슬라이스 (G86 보강)

**무엇이 비어 있었나:** 함수 본문을 실행할 장치가 없었다(코드 확인): 파서는 `def` 본문을 건너뛰고(`SkipBlock`), 인터프리터는 이항 연산자와 사용자 함수 호출을 지원하지 않으며 `return`·`for`·조건식도 없다. 로딩에는 Def 리터럴만 필요했기 때문이다.

**어떻게 정했나:** 첫 런타임 슬라이스(`World`)에서 `derived` 계산을 뺀다. `derived` 값을 읽으면 “아직 계산할 수 없음” 내부 오류로 명시적으로 실패한다. `default_from`은 원천이 `const`·`field`면 지원하고, 원천이 `derived`이거나 `default=함수`면 같은 오류다. 바로 다음 슬라이스가 **순수 함수 실행기**(본문 파싱, `int`·`fixed` 산술(P2), 비교, `if`·`for`·`return`, `floor`·`clamp`·`min`·`max`, `contribs`, read-set, 재진입 감지)이고 그때 `derived`·`default=함수`를 켠다. 기여 행(`contribs`)의 모양·수명과 `field`가 `derived` 상한을 넘는 경우(S4 🟡)도 `derived`가 있어야 의미가 있으므로 그 슬라이스에서 정한다.

**이유:** 저장소 설계와 언어 실행기 설계가 한 슬라이스에 섞이면 두 영역의 빈틈이 동시에 나온다. `World`가 먼저 있으면 실행기를 실제 엔티티 읽기로 바로 검증할 수 있다.

**상태:** 확인

## G95

**위치:** P2·S2 `/` 연산자와 `int`·`fixed` 혼합 (순수 함수 실행기)

**무엇이 비어 있었나:** P2는 `fixed`의 곱셈·나눗셈과 `//`·`%`의 규칙을 정하지만 `int / int`가 무엇인지는 없었다. schema-design 3.3.1의 대표 예제 `(base_max + flat) * (1 + pct / 100)`가 정확히 이 경우다. 파이썬이면 `float`이라 P2에 어긋나고, 정수 나눗셈이면 `pct=10`에서 0이 되어 조용히 틀린다.

**어떻게 정했나:** **`/`는 항상 `fixed`를 낸다.** `int / int`도 `fixed`(10 / 100 → 0.1)다. 정수 몫은 `//`(floor)다. `int`와 `fixed`를 섞으면 `int`가 `fixed`로 올라간다. `fixed` 결과를 `int` 자리에 쓰려면 `floor()` 등으로 명시한다. 0으로 나누기와 오버플로는 실행 오류다.

**이유:** 예제가 그대로 맞고, 파이썬의 “`/`는 실수” 직관과 같으며, 조용한 정밀도 손실이 없다. 변환은 명시적이라는 P2·S2 원칙과 일치한다.

**상태:** 확인

## G96

**위치:** P2·S2 로직에서 허용하는 연산자 집합 (G95 보강)

**무엇이 비어 있었나:** P2는 `/`·`//`·`%`만 정했고 `**`, 비트 연산(and, or, xor, not, 시프트), `@`는 말이 없었다. 파서는 모두 읽는다.

**어떻게 정했나:** **허용: `+ - * / // %`, 단항 `-`·`+`, 비교, `and or not`, `in`·`not in`.** `**`, 비트 연산, `@`는 로드 오류로 거부한다(“아직 지원하지 않음”, `EVL002`와 같은 모양). 나중에 허용을 넓히는 후보: `int ** 음이 아닌 int`(오버플로는 오류, 복리·레벨 곡선), `int` 비트 연산(플래그), `fixed ** int`. `@`는 값 타입이 없어 후보가 아니다.

**이유:** 사용 사례가 아직 없다. 허용을 넓히는 쪽은 기존 모드가 깨지지 않지만 좁히는 쪽은 깨진다. 결정적 구현 규칙(오버플로, 음수 지수, 시프트량)이 필요한 연산자는 쓰임이 생길 때 정한다.

**상태:** 확인

## G97

**위치:** S2 로직에서 쓰는 내장 함수 (순수 함수 실행기)

**무엇이 비어 있었나:** G90은 `floor`·`clamp`·`min`·`max`·`contribs`만 꼽았고, S2는 목록 연산 세트를 열린 점으로 남겼다. 반올림 함수와 `len`·`sum`·`abs`·`range`는 정한 적이 없었다.

**어떻게 정했나:** **수치:** `floor(fixed)`는 int, `ceil`, `round`(0에서 먼 쪽 반올림, P2의 규칙이며 파이썬 `round()`와 다름), `abs`, `min`, `max`, `clamp(x, lo, hi)`. `int`와 `fixed` 혼합은 G95 승격을 따르고 인자가 모두 `int`면 결과도 `int`다. **컬렉션:** `len`, `range(n)`(유한한 `int`, 상한 가드), 리스트를 받는 `sum`·`min`·`max`. `sum`은 파이썬과 같은 `sum(리스트나 range, 시작값=0)`이고 시작값은 수다(`sum(xs, 0.0)`로 빈 리스트의 합을 `fixed`로 고정). `min`·`max`처럼 여러 인자를 받던 처음 구현(`sum(1, 2)`는 3, `sum([1, 2], 10)`은 오류)은 실행기 검토에서 고쳤다. 제너레이터 식은 받지 않는다(G189가 바꿔 받고 `any`·`all`을 더함). **기여 행:** `contribs(컴포넌트, "값 이름")`은 `op`·`value`·`source`를 가진 행들의 리스트다. 변환 함수(`str`·`int`·`bool`)는 쓸 자리가 생길 때 추가한다.

**이유:** 퍼센트 계산에 `round`·`ceil`이 곧 필요하고 구현 비용이 거의 없다. 리스트만 받으면 제너레이터 식 미결(schema-design 3.3.1)과 부딪치지 않는다.

**상태:** 확인

## G101

**위치:** S2 실행 단계 상한 가드 (순수 함수 실행기)

**무엇이 비어 있었나:** S2는 “로드 시점 단계 예산과 실행 단계 상한 가드”를 요구하지만 단위와 한도를 정한 적이 없다. 코드에는 아직 예산 장치가 없다(로드 시점에는 사용자 함수를 호출하지 않아 필요 없었다). `derived`는 읽을 때마다 계산되어 중첩 `for`나 큰 `range`로 게임이 멈출 수 있다.

**어떻게 정했나:** **평가 노드 수 예산 하나.** 식·문장 하나를 평가할 때마다 1단계를 쓰고, 함수 호출 하나(최상위 `derived` 계산 하나)마다 예산을 새로 준다. 최상위는 `World`가 바깥에서 하는 `derived` 읽기 하나, 생성 순간의 기본값 계산 하나다. 그 안에서 읽힌 다른 `derived`는 새 예산을 받지 않고 남은 단계를 이어서 쓴다(`StepMeter`). 처음 구현은 중첩 읽기마다 예산을 새로 줘 비용이 곱해졌고(예산 100에 200단계 넘게 돎), 실행기 검토에서 고쳤다. 넘으면 실행 오류이며 함수 이름과 넘친 지점의 `파일:줄`을 보여 준다. 단계는 평가 순서로 세므로 같은 입력이면 같은 곳에서 멈춘다(결정론). 한도 값은 `World` 생성 옵션이고 모드는 바꿀 수 없다. 기본값은 넉넉하게 두고 테스트로 조정한다.

**이유:** 반복 수만 세면 반복 없는 긴 식과 중첩 루프의 곱을 못 막는다. 모드가 한도를 풀면 게임이 멈출 수 있다. 한도를 정할 근거 자료가 아직 없어 처음엔 넉넉하게 둔다.

**상태:** 확인

## G102

**위치:** S2 순수 함수 본문에서 허용할 문장과 식 (순수 함수 실행기)

**무엇이 비어 있었나:** S2의 허용 목록은 Flow 전체를 위한 것이고 `derived` 같은 순수 함수에서 무엇을 여는지는 따로 없었다. 파서는 `if`·`elif`·`else`만 문장으로 읽고 나머지는 `UnsupportedStmt`이며, 컴프리헨션은 `PAR002`로 거부한다.

**어떻게 정했나:** **이번 슬라이스에서 연다.** 문장: 지역 변수 대입, 복합 대입, `if`·`elif`·`else`, `for`(리스트, `range`, 맵의 키), `return`, `pass`, `break`·`continue`. 식: 리터럴, 산술·비교·논리, 조건식(a if c else b), 속성·인덱스 접근, 호출(G97 내장 함수와 사용자 함수), 리스트·맵 리터럴, 람다. **미룬다:** `while`과 `limit`, `match`·`case`, 함수 안의 `def`, 컴프리헨션, 제너레이터 식, f-string. 미룬 문법은 파서가 **로드 시점에** “아직 지원하지 않음”(`PAR002`)으로 거부하고 `파일:줄`을 낸다(`check`에서 보이며, 실행기까지 미루지 않는다). 함수 본문을 읽게 되므로 G17(본문 건너뜀)은 이 항목이 대체한다. 최상위 콘텐츠 파일에서는 `for`와 조건식이 계속 로드 오류(`EVL002`)이고, 함수 밖의 `return`과 반복 밖의 `break`·`continue`는 구문 오류다. 사용자 함수 호출은 허용하되 재귀는 금지한다(S2): 호출 체인에 같은 함수가 있으면 실행 오류이고 직접 재귀는 로드 시점에 안다.

**이유:** 3.3.1의 대표 예제는 대입, `for`, `if`·`elif`, `return`만 쓴다. 컴프리헨션과 제너레이터 식은 3.3.1의 제너레이터 미결과 함께 정해야 해 따로 뺐다. `while`은 `limit` 문법이 따로 필요하고 순수 함수에서 쓸 일이 적다. f-string은 `derived` 안에서 쓸 곳이 거의 없다.

**상태:** 확인

## G104

**위치:** S2 순수 함수 실행기의 구현 세부 (G95~G103 보강)

**무엇이 비어 있었나:** 실행기를 만들며 spec이 정하지 않은 작은 규칙들을 정해야 했다.

**어떻게 정했나:** **참/거짓 판정은 파이썬과 같다:** `None`, `False`, 0, 0.0, 빈 문자열·리스트·맵·`range`는 거짓이고 그 밖(엔티티 Ref와 호스트 값 포함)은 참이다. `if`·`elif`·조건식의 조건과 `not`에 쓰이고, `and`·`or`는 파이썬처럼 결정한 쪽의 피연산자 값을 그대로 돌려준다(`x or 5`). 처음에는 bool만 받게 했으나(`if r.source:` 같은 optional Ref 검사와 빈 컬렉션 검사가 막혀 모더가 아는 파이썬과 달라짐) 사용자 의견으로 바꿨다. 로드 시점 `if` 가드의 조건(`mod_loaded(...)`, `EVL006`)은 별개 규칙이라 그대로다. **`bool`은 수가 아니다:** `True + 1`은 오류이고 `True == 1`은 거짓이다. **`fixed // fixed`는 몫을 floor한 정수 값을 `fixed`로** 돌려준다(7.5 // 2 = 3.0). **`is`·`is not`은 `None`과의 비교만** 된다(로드 시점 검사). **`len`은 리스트·맵·`range`만** 받는다(문자열 길이는 정하지 않음). **`sum`·`min`·`max`는 원소 10만 개를 넘는 `range`를 거부**하고 반복문을 쓰라고 안내한다. **람다는 파이썬처럼 늦게 묶인다:** 만든 함수의 지역 변수를 부를 때 읽는다. **지역 변수는 파이썬 규칙이다:** 함수 안 어디서든 대입하거나 `for`로 묶는 이름은 함수 전체에서 지역 변수이고(람다는 만든 함수의 지역 변수도 포함), 값이 아직 없을 때 읽으면 같은 이름의 전역·내장으로 넘어가지 않고 실행 오류다(`RUN015`). 처음 구현은 넘어가서 파이썬이라면 오류인 코드가 조용히 전역 값을 냈고, 실행기 검토에서 사용자와 고쳤다. 이름 집합은 G108의 로드 시점 검사와 같은 규칙(`FunctionLocals`)이다. **순수 함수 안의 값은 모두 불변이다(불변식):** 파이썬에서 값을 그 자리에서 고치는 연산은 전부 오류다. 항목·속성 대입은 로드 오류, 리스트·맵 메서드는 없음, `*=`는 리스트를 받지 않음, 맵 합치기 대입(비트 or 대입)은 G96으로 거부, 리스트 `+=`는 실행 오류(`a = a + [...]`로 쓰라는 안내)다. 그래서 별칭·얕은 복사·깊은 복사의 차이가 결과에 드러나지 않는다. 리스트 `+=`는 처음엔 새 리스트를 만들어 별칭이 있을 때 파이썬과 결과가 달랐고 검토에서 막았다. 나중에 메서드나 연산자를 열 때 이 불변식을 기준으로 한다. **키 컴포넌트의 줄 묶음(`h.Skill`)은 파이썬 `dict`처럼 다룬다:** `len`은 줄 수, `k in h.Skill`은 그 키의 줄이 있는가(키는 Def id 문자열이나 엔티티), 비면 거짓이다. `keys="all"`이면 키 타입의 모든 Def가 줄이다. 없는 Def id는 조용한 `False`가 아니라 `h.Skill[k]`와 같은 “혹시 …?” 오류다. 컴포넌트가 붙어 있는지는 `h.Skill is not None`으로 따로 묻는다(ECS의 “부착”과 “비어 있지 않음”을 `if`가 합치는 것을 사용자와 논의하고 받아들였다: `len`을 열면 파이썬 규칙상 비면 거짓이어야 하고, 게임 로직의 질문은 대개 “하나라도 있나”다). 처음 구현은 `for`만 되고 `len`·`in`은 오류, 빈 묶음도 참이었다. 새 코드는 `RUN012`(산술: 오버플로·0 나눗셈), `RUN013`(단계 예산), `RUN014`(재귀·재진입), `RUN015`(타입·이름·속성 등 식 오류)다. 로드 시점 정적 검사(`FunctionChecker`)는 `**`·비트 연산·`@`·`~`, 속성·항목 대입, 직접 재귀, `None`이 아닌 것과의 `is`를 `EVL002`로 막는다.

**이유:** S2의 전제는 “유효한 파이썬 부분집합”이고 모더는 파이썬을 안다. 실행되는 코드는 파이썬과 같은 결과를 내야 하므로 참/거짓과 `and`·`or`도 파이썬대로 한다(안 맞는 쪽을 오류로 막는 것은 부분집합이라 허용되지만 불편하다). 나머지는 P2(결정론)·G95~G97을 지키는 가장 작은 선택이며 사용자와 논의하지 않은 잠정 결정이다.

**상태:** 확인

## G107

**위치:** S2·S4 스크립트가 Def 타입 바로 아래의 `const`를 읽는 길 (G103 보강, schema-design 3.3.3)

**무엇이 비어 있었나:** schema-design은 `g.def.succeeded(g)`로 Def 값의 함수를 부른다고 적었지만 `def`는 파이썬 예약어라 `g.def`는 문법 오류이고(S2는 유효한 파이썬 부분집합), G103에는 Def 타입의 `const`를 읽는 길이 없었다.

**어떻게 정했나:** **엔티티의 Def 타입 이름을 속성으로 쓴다:** `g.ConflictGoal.succeeded(g)`, `h.entity.Unit.cost`. 컴포넌트를 이름으로 읽는 것과 같은 규칙이고 컴포넌트 뷰에서도 `h.Unit.cost`로 바로 쓸 수 있다. 엔티티의 타입과 다른 Def 타입 이름은 `None`이다(형제 컴포넌트가 없을 때와 같다). 없는 `const` 이름은 “혹시 …?”가 붙은 오류다. 읽은 값은 `Explain` 트리에 저장값 읽기로 남는다. Def 타입과 컴포넌트는 한 이름 공간이라 이름이 겹치지 않는다. 함수 값의 `const`는 그대로 부를 수 있다. schema-design의 `g.def.succeeded`는 이 표기로 바꾼다.

**이유:** 새 예약어 없이 G103의 “이름이 곧 이름 공간” 규칙을 따르고 `.pyi`에서 Def 타입이 클래스, `const`가 그 속성이 된다. `def` 같은 고정 속성은 예약어를 늘리고 타입 이름이 코드에서 안 보인다.

**상태:** 확인

## G108

**위치:** S2·S9 함수 본문의 이름 오타 검사 (G102·G105 보강)

**무엇이 비어 있었나:** 함수 본문의 이름은 실행 중에 지역 변수, 같은 모드의 최상위 이름, 런타임 내장 순으로 찾는다. 로드 시점에는 이름을 보지 않아, 드물게 타는 분기의 오타가 `check`를 통과하고 게임 중에 처음 터졌다. spec은 오타를 로드 시점에 “혹시 …?”로 잡는다고 하지만 함수 본문은 다룬 적이 없다.

**어떻게 정했나:** **`def`와 람다 본문의 이름이 어디에도 없으면 로드 오류다(`EVL001`, “혹시 …?”).** 허용 이름은 매개변수, 지역 변수, 그 모드의 최상위 이름, 런타임 내장(G97의 이름과 `contribs`, 커널의 한 목록을 실행기와 함께 쓴다)이다. 지역 변수는 파이썬처럼 함수 안 어디서든 대입하거나 `for`로 묶은 이름이고, 대입 전에 읽는지는 보지 않는다(실행 오류로 남는다). 람다는 바깥 함수의 지역 변수를 본다. 속성 이름(`h.Armor`, G103·G107)은 이름이 아니라 보지 않는다. 최상위 이름은 파일 뒤쪽이나 다른 파일에서 정의될 수 있으므로(스키마 파일의 함수가 Def 파일의 상수를 씀) 모드의 ②b가 끝난 뒤에 본다. **로드 시점에만 있는 이름**(`field`, `patch`, `inherit`, Def 생성자, 컴포넌트 값 생성자, `int` 같은 타입 이름)은 “콘텐츠 파일을 읽는 동안에만 있고 로직 함수 안에서는 쓸 수 없다”로 따로 안내한다. 최상위 대입이 오류로 실패해 이름이 묶이지 않았어도 그 이름은 정의된 것으로 보아 오류가 번지지 않게 한다.

**이유:** 실행 중에 이름이 생길 길이 없으므로 정의되지 않은 이름은 반드시 언젠가 터지는 코드라 경고가 아니라 오류다. 지역 변수 규칙은 흐름 분석 없이 파이썬과 같은 결과를 낸다. 로드 시점 이름은 로드할 때는 보이므로 일반 메시지로는 원인을 알기 어렵다.

**상태:** 확인

## G111

**위치:** S2 `with preconditions:`의 위치와 안에 올 수 있는 문장 (S2 문구를 넓힘)

**무엇이 비어 있었나:** S2는 영역 안에 `require`/`cost`/`choose`만 허용하고 커맨드당 최대 하나라고 했지만, 본문의 어디에 올 수 있는지는 없었다. 블록 앞에 문장이 있으면 본문 없이 하는 사전 검사가 그 문장을 실행할지(쓰기가 섞이면 검사만으로 상태가 바뀜) 정할 수 없다. 긴 경로를 `require`마다 다시 적어야 했다.

**어떻게 정했나:** **`with preconditions:`는 커맨드 본문의 첫 문장이다.** 없으면 조건 없는 커맨드다. 다른 곳(두 번째 이후 문장, `if` 안, 커맨드가 아닌 함수, 콘텐츠 파일 최상위)은 로드 오류. **블록 안에는 `require`/`cost`/`choose` 호출과 지역 변수 대입 `이름 = 식`만 온다**(복합 대입, 속성·항목 대입, `if`/`for`는 로드 오류). 블록은 순수 함수 규칙(G104)을 따른다. 대입의 실행 오류는 G110처럼 다룬다: 앞에 실패한 `require`가 있으면 그 대입은 평가 안 됨이고 그 변수를 읽는 뒤 `require`도 평가 안 됨, 앞에 실패가 없으면 스크립트 오류. 파이썬 `with`처럼 블록의 변수는 본문에서도 보인다.

**이유:** 조사한 사례(Paradox decision·interaction, Civ VI `CanStartOperation`, Wesnoth `[set_menu_item]`, Unreal GAS, 이전 엔진)는 모두 조건을 효과와 따로 두거나(RimWorld JobDriver의 `FailOn`처럼) 맨 위에 둔다. 함수 하나로 쓰는 이 엔진은 그 분리를 위치 규칙으로 지킨다. 대입을 블록 안에만 두면 사전 검사가 실행하는 코드가 모두 블록 안에 보이고 대입 오류도 G110 규칙 하나로 처리된다. S2의 “`require`/`cost`/`choose`만”은 부작용 금지가 이유였고 지역 변수 대입은 부작용이 아니다.

**상태:** 확인

## G112

**위치:** S2 엔진이 주는 이름과 모드 이름의 충돌 (G20의 “내장 이름은 다시 묶을 수 없다”를 바꿈)

**무엇이 비어 있었나:** 런타임 내장(`len`, `floor`, `contribs` 등)은 이미 모드 이름이 이겼지만, 로드 시점 함수(`field`, `patch`, `mod_loaded`, `inherit` 등)·타입 이름(`int`, `list` 등)·Def 타입과 컴포넌트 이름은 예약이라 모드가 묶으면 `EVL004`였다. 그 결과 (1) 모드 도우미 `def cost(x)`가 새 `cost` 검사에 걸렸고 (2) **서로 의존하지 않는 모드가 선언한 컴포넌트 이름**(`Score`)이 다른 모드의 `Score = 1`을 막아, 결과가 무관한 모드의 설치 여부에 달렸다(둘 다 재현).

**어떻게 정했나:** **엔진이 주는 이름은 모두 덮어쓸 수 있는 내장이다**(파이썬 builtins와 같음). 모드가 그 이름을 묶으면 그 뒤로 그 모드 안에서는 모드의 값이다. 묶기 오류는 같은 모드 안에서 두 번 묶는 것뿐이다. 이름의 모양으로 엔진의 뜻을 알아보는 자리(`@command`, `with preconditions:` 안의 `require`, `inherit`, `mod_loaded` 가드, `patch.*`)는 그 이름이 내장일 때만 그 뜻이다. `@command`와 블록 안의 `require`는 덮어쓴 이름이면 “이 모드가 덮어써서 내장을 쓸 수 없음, 이름을 바꾸라”는 로드 오류(`CMD001`·`CMD002`)이고, 나머지는 평범한 값으로 평가된다. 함수 본문의 `require` 등의 검사는 모드의 이름이 다 정해진 뒤(G108과 같은 시점)에 한다. 덮어쓰기 경고는 아직 없다(모든 내장에 한꺼번에 정할 일).

**이유:** 엔진에 새 내장(`stage`, `on`, `emit`, `ask`, `wait`, `rand`, `text`, `log` 등)이 늘어도, 의존 대상이 새 컴포넌트를 추가해도 기존 모드가 깨지지 않는다. 무관한 모드의 설치 여부가 결과를 바꾸지 않는다(G46과 같은 원칙). 런타임 내장이 이미 이렇게 동작해 규칙이 하나가 된다. 예약 이름(앞의 안)은 이 둘을 막지 못했다.

**상태:** 확인

## G113

**위치:** S2·S6 `require`의 모양과 메시지 평가 시점

**무엇이 비어 있었나:** S2 예제는 `require(조건, "msg.key")`뿐이고 메시지 인자를 어떻게 넘기는지, 언제 평가하는지가 없었다. `log("msg", name=...)`처럼 키워드로 받으면 `require` 자신의 옵션이 생길 때 모더의 메시지 인자 이름과 부딪힌다.

**어떻게 정했나:** **`require(조건, text("키", 이름=값, ...))`.** `text`는 메시지 값(키 + 이름 있는 인자, 번역하지 않음)을 만드는 런타임 내장이고 G112를 따른다. `require`는 위치 인자 둘만 받고 키워드 인자는 로드 오류, 둘째 인자가 문자열 리터럴이면 “`text(...)`로 쓰라”는 로드 오류, 실행 중 `text` 값이 아니면 `RUN005`. **메시지는 조건이 거짓일 때만 평가한다**(파이썬 `assert`의 메시지와 같음). 그래서 통과한 `require`에는 인자가 없고, 키는 `text("키", ...)`로 적혀 있을 때만 있다(평가 안 됨도 같다). `log`를 같은 모양으로 할지는 `log`를 만들 때 정한다.

**이유:** 메시지를 값 하나로 넘기면 `require`의 옵션과 메시지 인자가 섞이지 않고 같은 메시지를 툴팁·로그에 다시 쓸 수 있다(Django `ValidationError`, RimWorld `AcceptanceReport`). 늦은 평가는 UI가 자주 묻는 사전 검사에서 통과한 조건의 메시지 계산을 아끼고, `c is None or c.walls < 5`처럼 `or`로 지킨 조건의 메시지가 오류를 내지 않게 한다. 조건이 지키려던 값을 메시지에 쓰는 것(`c is not None`의 메시지에 `c.name`)은 어느 쪽이든 오류다. 대가: 메시지의 버그는 그 조건이 실패할 때 드러난다. Paradox식 자동 설명(키 생략)은 S2의 열린 점이라 나중에 이 모양 위에 더한다.

**상태:** 확인

## G117

**위치:** S2 함수 효과 표의 “엔티티 쓰기” 판정과 G104 불변식의 경계

**무엇이 비어 있었나:** S2는 커맨드 본문의 필드 대입을 기록되는 쓰기로 허용하고 함수의 효과를 엔진이 정적으로 자동 판정한다고 했지만, 무엇을 쓰기로 보는지, 판정이 어디까지 퍼지는지, 이름으로 알 수 없는 호출을 어떻게 막는지 없었다. G104는 모든 함수의 속성 대입을 막았다.

**어떻게 정했나:** **쓰기는 엔티티 상태 경로에 대한 속성 대입뿐이다**(`u.Health.current -= 3`, `u.Location.city = dest`, 연산자는 G96의 대입 연산자). 지역 값(리스트·맵)의 불변식과 항목 대입 금지는 G104 그대로다. **쓰기 함수:** 본문에 속성 대입이 있거나 같은 모드의 쓰기 함수를 이름으로 문장 호출하는 함수(전이적으로 퍼짐). 모드 사이에는 함수를 가져오는 길이 없어 판정은 모드의 ②b 끝에서 모드 안에서 한다. 오류 위치는 그 함수를 쓰기 함수로 만든 첫 대입이나 호출이다. **쓰기 함수는 문장으로만 부른다:** 식 안의 호출(대입의 값, 조건, `require` 인자, 람다 본문 등)은 로드 오류. **순수 자리에는 쓰기 함수를 둘 수 없다:** `derived` 함수, `field`의 함수 기본값, `Cond[...]` 자리의 값(Def 값과 패치 포함, ⑥에서 검사). `Action[...]` 자리는 된다. `with preconditions:` 안의 대입은 G111대로 이름 대입만이다. **이름으로 판정할 수 없는 호출**(속성 호출 `g.ConflictGoal.on_success(g)`, 매개변수·지역 변수에 든 함수 값)은 런타임 안전망이 막는다: 실행 프레임마다 순수/쓰기 모드가 있고, `derived` 읽기·사전 조건·`Cond` 호출·순수 함수에서 시작한 호출은 커맨드 실행 중이라도 순수 모드라 쓰기를 거부한다. 커맨드를 일반 함수처럼 부르는 문제는 따로 정한다(G118에서 정함). (구현 보강) 쓰기 모드는 커맨드 본문 프레임과, 쓰기 모드 프레임이 **문장으로** 부른 쓰기 함수(함수 값으로 불러도)뿐이다. 식 안에서 함수 값으로 부른 쓰기 함수도 순수 모드다. 순수 모드에서 상태 쓰기를 만나면 `RUN003`. 함수 값으로 커맨드를 부르면 실행 오류(G118의 마지막 방어선).

**이유:** spec의 “필드 대입”과 파이썬 직관을 지키면서 공용 효과 함수(`damage()`)를 쓸 수 있다. CK3도 trigger(읽기)와 effect(쓰기)를 문법적으로 나누고 `scripted_effect`는 effect 자리에서만 쓴다(일반 지식, 이 저장소에서 확인한 것은 아님). 여기서는 이름 대신 자동 판정이다. 정적 판정이 놓치는 경우가 구조적으로 있어 런타임 안전망은 어차피 필요하다.

**상태:** 확인

## G120

**위치:** S2 `me` ❓: 커맨드에서 행동하는 진영(행위자)은 어디서 오는가

**무엇이 비어 있었나:** G119로 issuer는 행위자가 아니게 됐다. 이전 엔진은 행위자를 엔진이 암묵적으로 넣었다(TR은 라우터가 연결을 정당으로 바꾼 `^Self`, WG는 issuer가 유닛일 수도 있고 소유 체인으로 진영을 찾음, U1·U2).

**어떻게 정했나:** **엔진은 커맨드에 행위자를 암묵적으로 넣지 않는다.** 행동하는 진영과 비용 지불자는 인자(`def Demonstrate(party: Ref[Party], ...)`, `cost(party.OP, 1)`)나 인자에서 끌어낸 값(`unit.owner`, `cost(unit.owner.Points, 1)`)이고, 어느 쪽을 쓸지는 모더가 정한다. 커맨드의 결과는 인자와 상태만으로 정해진다. 연결이 그 진영을 조종해도 되는지의 검사(입구 ②)와 그 자료의 위치는 이 항목이 정하지 않는다(이어서 정함).

**이유:** 커맨드 데이터만 보고 누가 비용을 내는지 알 수 있고, AI·핫시트는 다른 인자를 넣으면 된다. 호스트가 연결을 행위자로 바꿔 넣는 방식(옛 엔진)은 게임 중 조종 대상이 바뀌면(상속, 합병) 호스트의 표와 시뮬레이션 상태가 같은 사실을 따로 들게 된다.

**상태:** 확인

## G135

**위치:** G117의 “문장으로만 부른다”와 값을 돌려주는 쓰기 함수 (G134에서 이어짐)

**무엇이 비어 있었나:** G134의 `spawn`은 Ref를 돌려줘야 쓸모가 있는데, G117은 쓰기 함수를 문장으로만 부르게 해서 만들고 초기화해 돌려주는 도우미(`def make_scout(city): u = spawn(...); ...; return u`)의 결과를 받을 수 없었다. 로드 시점 판정은 속성 대입만 쓰기로 세어, 쓰는 내장만 부르는 함수가 순수로 판정되어 `derived`·`Cond` 자리에서 실행 중에야 걸렸다.

**어떻게 정했나:** **이름 대입의 오른쪽 전체도 문장이다:** 쓰기 함수(사용자 함수와 쓰는 내장 모두)는 `f(...)` 한 줄이나 `x = f(...)`로 부른다. `x += f()`, 조건, 다른 호출의 인자, 리스트·맵 안, `require` 인자, 람다 본문, `with preconditions:` 안은 지금처럼 식 안이라 로드 오류(CMD004). **쓰는 내장(G134의 여섯)을 부르는 것도 쓰기다:** 덮어쓰지 않은 내장을 부른 함수는 쓰기 함수로 판정되고(전이적으로 퍼짐, 오류 위치는 그 호출), 순수 자리 금지와 식 안 호출 금지가 로드 시점에 그대로 적용된다. bool을 돌려주는 `pay(...)`도 같은 규칙이라 `paid = pay(...)` 뒤에 `if paid:`로 쓴다.

**이유:** `x = f()` 한 줄은 쓰기가 하나이고 순서가 분명해 “쓰기를 식에 숨기지 않는다”는 G117의 목적을 지킨다. 결과를 변수로 받는 모양(`x = lst.pop()`)은 파이썬에서 흔하고, 조건 안에서 효과를 내는 모양은 명령·질의 분리(CQS, Bertrand Meyer) 관점에서 피하는 쪽이다(일반 지식). 파이썬에서 조건 안의 쓰기는 주로 “해 보고 됐는지 알려 주는” API(`if lock.acquire():`)인데, `pay`를 만들 때 두 줄 쓰기가 실제로 불편하면 `if` 조건 자리만 따로 다시 본다. 내장과 사용자 함수의 규칙이 같아진다.

**상태:** 확인

## G136

**위치:** S2 `ask`/`await`/`wait`를 일반 함수 안에 쓸 수 있는가

**무엇이 비어 있었나:** spec 표는 “`ask` 포함”을 쓰기와 같이 “Flow 본문의 문장 수준만”이라고만 적었다. 이전 엔진 TR의 `Effect_Choice`는 효과 트리 어디에나(주사위 효과 분기 안, U6) 들어갔고, 새 엔진에서는 카드 Def의 `Action` 함수 안에서 묻는 모양이 된다(G128 `std.stack`도 노드 해소 때 `Action`을 부른다).

**어떻게 정했나:** **쓰기 함수와 같은 규칙(G117·G135).** `ask`/`await`/`wait`를 포함하거나 그런 함수를 문장으로 부르는 함수는 멈추는 함수이고, 한 줄 전체나 이름 대입의 오른쪽 전체(`x = f()`)로만 부른다. 식 안에서 부르면 로드 오류, 순수 자리(`derived`·`Cond`·`acts_for`·정책 함수·`with preconditions:`)에서도 로드 오류다. 멈춤은 여러 호출 깊이에 걸릴 수 있으므로 프레임 스택은 함수 호출마다 프레임 하나이고(S2 평가 모델), 식 안의 호출은 끝까지 실행하며 그 안에서 멈추려 하면 실행 중 안전망 오류다.

**이유:** 커맨드 본문에서만 묻기(B)는 효과 함수 안의 선택(U6)과 `std.stack`의 `Action` 해소를 막는다. 어디서나 허용하고 실행 중에만 잡기(C)는 S9 “조용히 틀릴 수 있으면 오류”와 맞지 않는다. 규칙이 G135와 같아 모더가 외울 것이 늘지 않는다.

**상태:** 확인

## G141

**위치:** S2·S8 멈춘 Flow의 지역 변수에 든 런타임 값의 저장

**무엇이 비어 있었나:** 멈춘 프레임의 지역 변수에는 엔티티, 컴포넌트·줄 뷰(`m = u.Moves`), Def, 답 `r`, 붙이기 전의 컴포넌트 값, 함수 값, 람다가 들 수 있는데 S2 표는 리스트·맵만 적었다. 이전 엔진 TR은 값 종류마다 저장기(`ISavedContextValue`)를 두었고(`Issuer`가 null로 복원되는 구멍), Ren'Py는 람다를 저장하는 순간 오류가 나는 것이 알려진 불편이다(일반 지식).

**어떻게 정했나:** **전부 저장한다.** 엔티티·뷰·Def·답·컴포넌트 값은 가리키는 대상(id, 컴포넌트 이름, 키)으로 적고 불러올 때 다시 잇는다. 함수 값은 이름(`모드.함수`, 내장 이름), 람다는 (어느 함수의 몇 번째 람다, 잡은 지역 변수가 어느 프레임의 것인가)로 적고, 이미 끝난 함수의 지역 변수를 잡았으면 그 사전도 함께 적는다. 멈출 수 있으면 저장할 수 있다(C1). 함수 본문이 바뀌어 람다 번호가 어긋나는 것은 S8의 본문 해시 검사가 막는다.

**이유:** 람다만 멈출 때 오류(B)는 `key = lambda u: ...` 같은 흔한 코드를 막는다. 수·문자열·리스트·맵·엔티티만(C)은 `m = u.Moves`마저 막는다.

**상태:** 확인

## G142

**위치:** S2 `==`가 런타임 값을 비교하는 기준 (G104 보강)

**무엇이 비어 있었나:** `==`는 수·문자열·리스트·맵·엔티티만 내용으로 비교하고 컴포넌트 뷰(`u.Health`)·줄 묶음(`u.Skill`)·Def 뷰·답 `r`·`range`·컴포넌트 값(`Wounded(turns=3)`)은 객체가 같은지로 비교했다(정한 적 없음). 그래서 `u.Health == u.Health`와 `range(3) == range(3)`이 거짓이었고(임시 테스트로 재현), 멈춘 Flow를 저장하면 `x = u.Health; y = x`의 `x == y`가 불러온 뒤 거짓이 되어 C1이 깨진다.

**어떻게 정했나:** **가리키는 대상이나 내용으로 비교한다.** 뷰는 같은 엔티티의 같은 컴포넌트(같은 줄)·같은 Def 타입이면 같고, 답은 `response`·`index`·`choice`·`by`가, 컴포넌트 값은 컴포넌트와 준 값들이, `range`는 파이썬처럼 같은 원소 순서가, 기여 행은 같은 행이면 같다. `text(...)`는 키와 인자가 같으면 같다(저장 ③에서 빠진 것을 찾아 보강). 객체의 정체는 스크립트에 보이지 않으므로 저장은 값마다 따로 적으면 된다. 함수 값은 이름으로 불러오면 같은 객체라 그대로 두고 람다는 저장 ③에서 다룬다.

**이유:** 객체 비교를 두고 저장이 공유를 보존(B)하면 이상한 `u.Health == u.Health` 거짓이 남고 저장이 복잡해진다. `==`를 오류로(C)는 `h in [u.Health, ...]`를 막는다. 근거: G104 "값은 모두 불변", 엔티티 뷰는 이미 id로 비교, 파이썬 `range`는 내용 비교(일반 지식).

**상태:** 확인

## G143

**위치:** S2 람다 값의 `==`와 S8 람다 저장 (G141·G142 보강)

**무엇이 비어 있었나:** 람다끼리의 `==`는 객체 비교인데, 답을 받고 이어서 실행할 때 프레임 사본을 만들며 람다를 나오는 자리마다 새로 만들어 `f = lambda: 1; g = f; ask(...)` 뒤 `f == g`가 거짓이 됐다(저장과 무관하게 재현). 저장해 불러올 때도 같은 문제가 생긴다.

**어떻게 정했나:** **파이썬처럼 객체 비교를 지키고, 같은 객체임을 보존한다.** 이어서 실행할 때 원본 람다 하나에 사본 하나만 만든다. 저장은 Flow마다 람다 목록과 잡은 지역 변수 묶음 목록을 두고 번호로 가리킨다: 람다는 (그 람다가 든 함수의 모드·이름, 그 함수 본문에서 람다 식이 나오는 순서 번호, 잡은 묶음이 몇 번째 프레임의 것인지 또는 묶음 목록의 몇 번째인지). 이미 끝난 함수의 묶음은 이름 목록과 값을 함께 적는다. 람다는 월드 상태와 질문에 담길 수 없어 Flow 밖으로 나가지 않으므로 Flow마다의 목록으로 충분하다.

**이유:** 같은 람다 식·같은 묶음이면 같다(A)는 단순하지만 반복문에서 두 번 만든 람다가 같아져 파이썬과 다르다. 함수끼리 `==` 오류(C)는 지금 되는 `f == double`도 막는다. 근거: 파이썬은 `range`는 내용, 함수는 객체로 비교한다(일반 지식).

**상태:** 확인

## G178

**위치:** S2 난수를 부를 수 있는 곳

**무엇이 비어 있었나:** S2의 함수 효과 표에 난수가 없다. 난수는 엔티티를 쓰지 않지만 부를 때마다 값이 다르고 Flow의 카운터를 쓴다. `derived`(아무 때나 다시 계산), `when` 조건(바뀐 것만 다시 평가), 사전 조건(UI가 거듭 확인)에서 굴리면 읽기만 해도 값이 바뀐다.

**어떻게 정했나:** **난수는 따로 한 종류의 효과다.** 커맨드·반응·핸들러 본문(Flow)에서만 부르고 식 안에서도 쓴다(`if rand(1, 6) >= 5:`). 난수를 부르는 함수는 전이적으로 난수 함수가 되어 순수 자리(`derived`, 조건, 사전 조건, 함수 기본값)와 로드 시점에서 로드 오류다.

**이유:** 쓰기처럼 문장으로만(B)은 `if rand(...)` 같은 흔한 쓰임을 막는다. 어디서나(C)는 결정론(P2)을 깬다. 패러독스는 확률(`random`·`random_list`)이 효과 쪽에 있고 조건 검사에서는 굴리지 않는다고 기억한다. 이전 엔진도 `Effect_RollTable`(U9) 효과 안에서만 굴렸다. RimWorld는 C#에서 어디서나 `Rand`를 부르고 결정론이 필요한 곳만 `Rand.PushState`로 감싼다(일반 지식).

**상태:** 확인

## G179

**위치:** S2 난수 API의 모양

**무엇이 비어 있었나:** spec은 `rand()`라는 이름만 두었다. 무엇을 받고 돌려주는지, 확률·고르기·가중치·섞기를 어디서 주는지가 없었다. 스크립트는 파이썬의 부분집합인데 `import`와 `float`이 금지이고 리스트는 바뀌지 않는 값이다.

**어떻게 정했나:** **엔진이 `random` 이름 공간을 `import` 없이 주고, 파이썬과 이름·뜻이 같은 것만 넣는다:** `randint(a, b)`(양 끝 포함), `randrange(stop)`·`randrange(start, stop[, step])`(끝 제외), `choice(seq)`(비면 오류), `choices(seq, weights=None, k=1)`(가중치는 정수, 리스트를 돌려줌), `sample(seq, k)`(중복 없이), `random()`(파이썬과 달리 `fixed`, 0 이상 1 미만). 그 자리에서 섞는 `shuffle`과 `seed`는 두지 않는다(섞기는 `sample(seq, len(seq))`). 호출 한 번에 Flow의 n이 1 늘고 안에서 여러 번 뽑는 것은 하위 번호로 구분한다. `chance` 같은 파이썬에 없는 편의는 표준 모드가 준다.

**이유:** 커널에 `rand(lo, hi)` 하나(A)는 가장 작지만 모더가 새 이름을 배우고 고르기·섞기가 표준 모드 이름으로 흩어진다. `random.randint`만 커널에(B)는 표준 모드가 `random.`에 이름을 넣을 수 없어 같은 일이 두 이름 공간에 갈라진다. 패러독스 `random_list`는 `choices`에, RimWorld `Rand.Element`는 `choice`에 해당한다(일반 지식).

**상태:** 확인

## G180

**위치:** S2 월드 시드

**무엇이 비어 있었나:** 난수 값은 `H(월드 시드, 키, n)`인데 시드를 누가 정하고 어디에 남기며 도중에 바꿀 수 있는지가 없었다. C1은 불러와 이어도 난수까지 같기를 요구한다.

**어떻게 정했나:** **호스트가 월드를 만들 때 준다**(`seed`, `long`, 주지 않으면 0). 저장 최상위 `"seed"`에 남고 불러오면 그대로 잇는다. 스크립트는 읽거나 바꿀 수 없다. 새 게임마다 다른 시드는 호스트 C#이 정한다(커널 밖이라 P2와 무관). 도중에 바꾸는 API는 없다. 결과로 불러와서 같은 행동을 하면 같은 결과가 난다.

**이유:** 도중에 바꾸는 `Reseed`(B)는 요구한 사례가 없고 나중에 더해도 깨지는 것이 없다. 모드 내용에서 정하기(C)는 모든 게임이 같은 시드가 된다. 이전 엔진의 마스터 시드도 호스트가 정했다(U9). XCOM 2가 기본으로 불러와도 같은 결과를 낸다고 알고 있다(일반 지식).

**상태:** 확인

## G181

**위치:** S2 난수 해시 H의 구체 (spec은 후보로 SplitMix64)

**무엇이 비어 있었나:** spec은 H를 이름으로 고정하고 골든 값으로 묶으라고만 했다. 한번 정하면 바꿀 수 없다(바꾸면 예전 세이브가 다른 난수를 낸다).

**어떻게 정했나:** **ChaCha20(RFC 8439 그대로, 20라운드).** 키 = SHA-256(시드, 난수열 키의 정의 id, 실행 횟수)로 Flow마다 한 번, nonce = n, 블록 카운터 = 한 호출 안의 블록 번호. 호출 한 번에 블록 하나(64비트 값 8개)를 쓰고 더 필요하면 다음 블록으로 넘어간다. 범위로 줄일 때는 버리고 다시 뽑기로 쏠림을 없앤다. 골든 테스트는 RFC 8439의 테스트 값과 엔진 출력값으로 묶는다(C6).

**이유:** SplitMix64(A)는 통계 품질은 충분하지만 섞기가 역산되어 결과 몇 개로 시드를 구할 수 있고(서버만 시드를 갖는 비공개 카드·선택에서 문제), 여러 입력을 이어 섞는 쓰임은 보증된 사용법이 아니다. 매번 SHA-256(B)은 D보다 무겁고 이점이 겹친다. ChaCha는 (키, nonce, 카운터) 입력용으로 설계되어 리눅스 `/dev/urandom`, Rust `rand`(ChaCha12), Go `math/rand/v2`(ChaCha8)가 쓴다(일반 지식). 락스텝처럼 모두가 시드를 알면 어떤 H든 예측할 수 있다. 8라운드는 빠르지만 RFC 테스트 값으로 검증할 수 없다.

**상태:** 확인

## G182

**위치:** S2 난수열 키와 횟수 카운터의 세부

**무엇이 비어 있었나:** spec은 키를 (커맨드 정의 id, 실행 횟수)·(반응 정의 id, 발동 횟수)로만 정했다. 핸들러, 이어 가는 Flow, 실패한 입력, 저장이 비어 있었다.

**어떻게 정했나:** **Flow의 출처는 커맨드(자유·응답, 커맨드 id), 신호 핸들러(엔진 `Tick` 포함, 핸들러 id), `when` 반응(반응 id)이고 정의 id마다 카운터 하나.** 깨우기·마감·`advance` 뒤에 이어 가는 것은 새 Flow가 아니라 키와 n을 잇는다. 카운터는 Flow를 만들 때마다 1 늘고 본문이 난수를 쓰는지와 무관하다. 사전 조건 거절은 Flow가 없어 소비하지 않고, 본문 오류는 카운터와 n을 함께 되감는다(C10). 저장은 최상위 `"rand"`(정의 id → 횟수)와 멈춘 Flow마다 (횟수, n). 불러올 때 사라진 정의의 카운터는 버린다. 같은 커맨드를 두 참가자가 내면 먼저 들어온 쪽이 앞 번호(spec대로, 제출자는 키에 없음).

**이유:** 월드 전체 카운터 하나는 어떤 모드의 Flow 하나가 다른 모든 난수를 민다(spec이 피한 안). 이전 엔진의 (틱, 정의 id)는 같은 틱에 두 번 내면 같은 값이 났다(U9).

**상태:** 확인

## G183

**위치:** S2 `choose`가 하는 일

**무엇이 비어 있었나:** spec은 `choose(unit, where=...)`·`choose(dest, from_=...)`의 모양과 "UI 비활성 사유와 AI 합법 수 나열에 쓴다"만 두었다. 제출 때 검사하는지, 후보가 어디서 오는지가 없었다.

**어떻게 정했나:** **`choose`는 매개변수의 후보를 정하고 엔진은 그것을 검사와 나열 양쪽에 쓴다.** 후보: `where=조건`은 그 매개변수 타입(`Ref[T]`)의 살아 있는 엔티티 전체(id 순)를 조건으로 거르고, `from_=목록`은 그 목록(엔티티가 아닌 값도 됨). 제출(과 사전 검사)에서 인자가 후보에 없으면 `require` 실패와 같은 구조로 거절한다(사유에 "후보 아님"과 매개변수 이름, C7). 나열은 호스트 API로 준다(모양은 따로). `choose`가 없는 매개변수는 후보를 모르므로 나열할 때 호스트가 값을 준다.

**이유:** 나열에만 쓰기(B)는 검사를 `require`로 다시 적어야 하고 빠뜨리면 조작된 입력이 통과한다. `require`만(C)은 모든 조합을 시험해야 하고(유닛 200 × 도시 50 = 1만 번) UI가 클릭할 대상을 미리 모른다. 이전 엔진 WG의 `requiredSelections`의 `targetFilter`(U12), RimWorld `TargetingParameters`의 `validator`와 실행 때 재검사(일반 지식), CK3 상호작용의 `is_shown`·`is_valid`(기억)가 모두 후보 필터를 UI와 실행 검사에 같이 쓴다.

**상태:** 확인

## G184

**위치:** S2·S6 후보와 합법 수를 호스트에 주는 API, `choose` 후보가 큰 경우(S6 열린 질문)

**무엇이 비어 있었나:** UI는 앞에서 고른 값에 따라 다음 후보가 필요하고(`dest`는 `unit`에 따라), AI는 낼 수 있는 조합 전체가 필요하다. 후보 집합이 클 때의 처리는 열린 질문이었다.

**어떻게 정했나:** **호스트 API 둘.** (1) `Candidates(커맨드, 정한 인자들, 매개변수)`: 그 `choose`의 식과 식이 읽는 블록 안 변수의 대입만 따라가 필요한 매개변수를 알아내고, 빠졌으면 목록 대신 "먼저 정할 매개변수"를 돌려준다. `require`·`cost`는 보지 않는다(고른 뒤 막히는 이유는 사전 검사 보고서). (2) `LegalMoves(커맨드, 정한 인자들, 최대 개수)`: `choose`가 있는 매개변수를 블록 순서대로 펼쳐 조합마다 사전 검사(`require`·`cost`·`choose`)를 통과한 것만, `choose` 순서 → 후보 순서로. 최대 개수에 닿으면 멈추고 잘렸음을 알린다(큰 후보의 답). `choose`가 없는 매개변수는 호스트가 정해야 하고 빠지면 오류.

**이유:** `Candidates`만(B)은 조합을 펼치고 검사하는 반복을 AI마다 짜야 하고 시나리오 ③의 "엔진이 합법 수를 나열"과 맞지 않는다. `LegalMoves`만(C)은 UI가 유닛 하나를 고른 뒤 도시를 강조하려면 전체를 만든 뒤 걸러야 한다. 보드게임 AI 프레임워크(OpenSpiel `legal_actions()`)는 합법 수 전체 API를 기본으로 둔다(일반 지식). CK3 상호작용은 대상을 먼저 고르고 실패 사유는 툴팁에 뜬다(기억). 이전 엔진 WG `HeadlessBot`의 합법 수 계산은 확인하지 못했다(U13).

**상태:** 확인

## G185

**위치:** S2·S6 `cost`가 하는 일 (G120은 누가 내는지만 정함)

**무엇이 비어 있었나:** spec은 "비용(1급)"(S6)과 본문 중간의 `pay(...)`(S2)만 두었다. 확인만 하는지 빼는지, 실패를 어떻게 보이는지, 같은 칸에 여러 번이면 어떤지가 없었다.

**어떻게 정했나:** **확인하고, 본문이 시작될 때 엔진이 뺀다.** 사전 검사에서 값이 금액보다 작으면 실패이고 보고서에 `require`처럼 한 줄로 나온다(칸, 가진 양, 필요한 양을 구조로). 모든 사전 검사를 통과하면 본문 첫 줄 전에 블록에서 계산한 금액을 그대로 빼고, 같은 트랜잭션이라 본문이 실패하면 함께 되돌아간다(C8). 같은 칸의 `cost`는 합해서 확인한다. 금액이 음수면 오류다.

**이유:** 확인만(B)은 확인과 지불에 금액을 두 번 적어 어긋날 수 있다(EU4·CK2 결정의 `allow`와 효과 블록이 그렇다, 일반 지식). `require` + 본문(C)은 거기에 더해 보고서와 AI가 자원 때문에 막혔는지 구분하지 못한다. CK3 상호작용의 `cost = { gold = 50 }`은 확인과 차감을 함께 하고 부족분을 툴팁에 보인다(기억). spec의 "비용(1급)"과 "본문 중간의 동적 비용은 `pay`"는 머리부 `cost`가 본문 전에 내는 고정 비용이라는 읽기와 맞다.

**상태:** 확인

## G186

**위치:** S2 `cost`의 첫 인자 (G185에서 이어짐)

**무엇이 비어 있었나:** 파이썬에서 `cost(party.Treasury.gold, 1)`은 숫자를 넘길 뿐이라 함수가 그 칸을 바꿀 길이 없다. 뺄 칸을 어떻게 받는지가 없었다.

**어떻게 정했나:** **특수 동작으로 인정한다: `cost`의 첫 자리는 칸 자체다.** `엔티티.컴포넌트.멤버`(키 줄은 `party.Stock.Wood.amount`·`party.Stock[wood].amount`) 모양으로 적고, 엔진이 마지막 이름 앞까지만 계산해 그 칸을 확인하고 뺀다. 칸이 아닌 것(`cost(3, 1)`, `cost(max(...), 1)`, 지역 변수)은 로드 오류. 칸이 `int`·`fixed`인 `field`가 아니면(`derived`·`const`·문자열) 실행 중 오류(속성 이름은 로드 때 보지 않는다, G108). 보통 함수의 인자는 지금처럼 값으로 계산해 넘긴다(파이썬과 같다).

**이유:** 객체와 키워드(`cost(party.Treasury, gold=1)`)는 파이썬 의미를 지키지만 읽기 어색하다. 확인은 `require`, 빼기는 본문(파이썬 그대로)은 금액을 두 번 적고 G185와 어긋난다. 읽은 값에 출처 꼬리표를 다는 방식은 모든 값의 비교·저장·호스트 경계를 손봐야 한다. 사전 조건 블록은 이미 엔진이 따로 읽는 영역이고 `ask`·`require`도 엔진이 알아보는 이름이라 특수 동작이 블록 밖으로 새지 않는다. pytest가 `assert`를 고쳐 읽는 것도 비슷한 사례다(일반 지식).

**상태:** 확인

## G187

**위치:** S2 본문 중간의 `pay()`와 취소 때 돌려주기

**무엇이 비어 있었나:** spec은 "본문 중간의 동적 비용은 참/거짓을 돌려주는 `pay(...)` 문장"이라는 한 줄뿐이다. 첫 인자, 부르는 곳, 취소 때 돌려주기가 없었다.

**어떻게 정했나:** **`pay(칸, 금액)`: 첫 자리는 `cost`처럼 칸 자체(G186).** 값이 금액 이상이면 빼고 `True`, 모자라면 아무것도 바꾸지 않고 `False`. 금액이 음수면 오류. 상태를 바꾸므로 쓰기 규칙(G117·G135)을 따른다: 본문에서 한 줄 전체나 `ok = pay(...)`처럼 이름 대입의 오른쪽에만 쓰고 `if pay(...):`처럼 식 안에 넣으면 로드 오류. 사전 조건 블록에서는 쓸 수 없다(그 자리는 `cost`). **취소 때 돌려주기는 엔진이 하지 않는다.** 낸 양을 게임 상태(예: 스택 노드 엔티티)에 적어 두고 취소하는 쪽이 더해 준다.

**이유:** `pay` 없이 `if x.op >= 2: x.op -= 2`로 쓰게 하는 안은 파이썬 그대로지만 spec이 이미 `pay`를 약속했고 확인하고 빼기가 흔한 패턴이다. 엔진이 Flow마다 낸 비용을 기록해 돌려주는 안은 돌려줄 대상이 Flow가 아니라 스택 노드 같은 게임 개념이라 맞지 않다. 이전 엔진의 TR 끼어들기 스택은 노드마다 환불 OP·환불 모디파이어를 들고 있다가 취소 때 돌려줬다(U3). 전액인지 반만인지 등은 게임마다 다르다. G177(취소는 상태로 표현)과 같은 방향.

**상태:** 확인

## G188

**위치:** S2·S6 `choose` 후보 식이 다른 매개변수를 읽을 때 (G184에서 이어짐)

**무엇이 비어 있었나:** 나열은 `choose`를 블록 순서대로 푸는데 후보 식이 아래쪽 `choose`의 매개변수나 자기 매개변수를 읽으면 풀 수 없다. 제출 검사에서는 인자가 다 있어 드러나지 않는다.

**어떻게 정했나:** **로드 오류로 막는다: 블록에 적힌 순서가 고르는 순서다.** `choose(P)`의 식이 자기 매개변수 `P`나 아래쪽 `choose`가 정하는 매개변수를 읽으면 로드 오류. 식이 읽는 블록 변수(`here = ...`)의 대입도 따라가서 본다. 람다의 매개변수는 빼고 `x if c else y`처럼 안 읽힐 수 있는 이름도 읽는 것으로 친다(보수적). `choose`가 없는 매개변수(호스트가 주는 것)는 어디서나 읽어도 된다. 같은 분석이 `Candidates`의 "먼저 정할 매개변수"를 정한다.

**이유:** 엔진이 의존 순서로 다시 맞추는 안(B)은 적힌 순서와 고르는 순서가 달라져 헷갈린다. 검사하지 않는 안(C)은 잘못 적은 블록을 나열해 볼 때까지 모른다. CK3 상호작용은 대상을 정해진 순서로 고른다(기억, 세부는 불확실). 이전 엔진 WG의 `requiredSelections`도 목록 순서로 고르는 모양이었다(U12, 뒤 필터가 앞 선택을 읽는 규칙은 확인 못 함).

**상태:** 확인

## G189

**위치:** S2 컴프리헨션과 제너레이터 식 (G102가 미룸, schema-design 3.3.1의 🟡)

**무엇이 비어 있었나:** spec S2는 컴프리헨션을 허용하고 제너레이터를 금지한다고만 적었다. `sum(r.value for r in rows)` 같은 제너레이터 식이 금지에 드는지와 받을 모양이 없었다.

**어떻게 정했나:** **리스트·딕트 컴프리헨션과 제너레이터 식을 받는다.** `for`·`if` 절은 여러 개 이어도 된다. 제너레이터 식은 파이썬 문법대로 호출의 인자로만 쓰고 값으로 존재하지 않는다: `any`·`all`(G97 목록에 파이썬과 같은 뜻으로 더함)은 하나씩 당겨 파이썬처럼 일찍 멈추고, 그 밖의 내장(`sum`·`min`·`max` 등, 어차피 끝까지 읽음)과 사용자 함수에는 리스트로 펼쳐 넘긴다. 괄호로 감싼 제너레이터 식도 호출 인자 자리에서만 받는다. 반복 변수는 밖으로 새지 않고(파이썬 3) 한 바퀴마다 단계를 센다(G101). **금지는 `yield` 함수와 제너레이터 객체를 값으로 들고 다니는 것으로 읽는다.**

**이유:** spec은 금지 이유를 적지 않아 다른 규칙에서 추론했다: 제너레이터는 값 안에 멈춘 실행을 품어 (1) 식 한가운데서 멈추고 이어 가 "식은 중단 불가, 멈춤은 문장 수준 `ask`·`wait`뿐"(S2 평가 모델)을 깨고 (2) 지역 변수에 든 채 `ask`에서 멈추면 저장이 그 안의 프레임까지 적어야 해 "값은 직렬화 가능"과 어긋나고 (3) 한 번 돌면 소진되어 같은 값을 두 번 읽으면 결과가 달라 G104(지역 값은 불변)와 어긋난다. 그 자리에서 다 쓰는 제너레이터 식은 셋 다 해당하지 않는다. 사용자 함수에 리스트로 넘기는 것은 (2)를 막는 장치다. 금지 목록은 Starlark의 제한과 거의 같다(일반 지식, 불확실). 제너레이터 식을 거부하는 안(B)은 흔한 파이썬 표기를 막고, 리스트로 먼저 다 만드는 안(C)은 `any`·`all`이 일찍 멈추지 않아 예산·오류가 조용히 달라진다.

**상태:** 확인

## G195

**위치:** S2 `while`과 `limit` (G102가 미룸, 검증 시나리오 ①에서 드러남)

**무엇이 비어 있었나:** S2는 `while`을 "필수 `limit`과 함께만 허용"이라 적었지만 파이썬에는 `while`에 상한을 붙일 문법이 없고, G102가 미뤄 파서가 `PAR002`로 거부했다. 시나리오 ①의 우선권 고리("누군가 반응하는 동안 계속")를 `for i in range(100)`으로 대신 쓰면 횟수를 다 쓴 커맨드가 성공으로 끝나 스택에 효과가 남고 열린 질문이 없는 채 게임이 멈췄다(임시 테스트로 재현).

**어떻게 정했나:** **`while 조건:`을 파이썬 그대로 열고 따로 `limit`을 두지 않는다.** 상한은 이미 있는 단계 예산이 맡는다: 몸통의 문장은 바퀴마다 세고 조건 검사도 바퀴마다 한 단계를 쓴다. 예산은 제출·답·응답·반응 구간마다 새로 세므로, 묻지 않고 혼자 도는 반복은 예산을 넘어 실행 오류가 되고(되감김), 바퀴마다 `ask`하는 반복(우선권 고리)은 걸리지 않는다. `break`·`continue`는 `for`와 같다. `else` 절은 `for`처럼 미지원(`PAR002`). `ask`·`wait`로 멈춘 `while`도 저장·불러오기·재개된다(블록 위치만 저장, 조건은 이어서 실행할 때 다시 평가). 최상위 콘텐츠 파일에서는 `for`처럼 로드 오류(`EVL002`).

**이유:** 시나리오 ①처럼 끝이 플레이어에게 달린 반복은 횟수를 미리 정할 수 없고, 고정 상한은 넘치면 오류가 나도 정상 진행을 끊는다. 파이썬 문법이 그대로라 pyright와 `.pyi`가 바뀌지 않는다. CK3의 `while`에는 고정된 최대 반복 횟수가 있다고 알고 있다(일반 지식, 확인 안 함). 단계 예산이 그 역할을 이미 하므로 `limit`은 같은 일을 두 번 한다.

**상태:** 확인

## G223

**위치:** spec 9절 규모 벤치의 방식과 범위

**무엇이 비어 있었나:** spec 9절은 엔티티 1천·1만·10만에서 저장소·쿼리·순회·`derived` 추적·커맨드 롤백 비용을 재라고만 했다. 무엇을 어떤 도구로 재고 기준을 둘지, 테스트에 넣을지가 없었다. 엔진은 `derived` 캐시(G105), 컴포넌트 쿼리 색인, 보기 정책 캐시(G199)를 벤치로 필요가 보일 때 더한다고 미뤄 두었다.

**어떻게 정했나:** **`bench/` 아래 콘솔 프로그램으로 잰다**(예열 뒤 여러 번 재서 중앙값과 할당량, 새 패키지 없음). 장면은 다섯: C# API 직접 읽기·쓰기·쿼리·순회, 스크립트 `on(Tick)` 핸들러가 N개를 갱신하는 틱, `derived` 읽기(기여 행 없음과 있음), 커맨드 성공과 실패(롤백), 같은 갱신을 `Writes` 호스트 함수 한 번으로. **합격 기준은 두지 않고 결과를 handoff에 적는다.** `dotnet test`에는 넣지 않는다. 목적은 병목이 저장·인터프리터·추적 중 어디인지 숫자로 알아내 미뤄 둔 최적화의 순서를 정하는 것이다. 몇 퍼센트 차이를 비교해야 할 때 BenchmarkDotNet으로 옮긴다.

**이유:** 지금 필요한 것은 자릿수(틱 하나가 1ms인지 100ms인지)라 정밀한 통계 도구는 실행이 수십 분 걸리는 값을 못 한다. 기계마다 숫자가 달라 테스트의 합격 기준으로 쓰면 불안정하다. 일반 지식: BenchmarkDotNet은 .NET의 표준 마이크로 벤치 도구다.

**상태:** 확인

## G224

**위치:** 읽기와 행동의 단계 예산 (G101 보강, 규모 벤치에서 드러남)

**무엇이 비어 있었나:** G101은 실행 하나에 예산 하나(기본 10만 단계)를 줬다. 규모 벤치(G223)에서 모든 유닛을 도는 `@on(Tick)` 핸들러가 유닛 1만~2만 개 사이에서 예산을 넘어 틱 전체가 되감겼다(재현). 코드는 멀쩡한데 세계가 커지면 실패한다. 한 단계는 약 45ns라 10만 단계는 약 5ms로, 무한 반복을 막는다는 목적에 비해 낮다.

**어떻게 정했나:** **예산을 둘로 나눈다.** 읽기(`derived`, 입구·정책 함수, `choose` 후보)는 지금처럼 `stepBudget`(기본 10만). 행동(커맨드 본문, `@on`·`@when` 핸들러, 멈춘 Flow를 이어서 실행하는 구간)은 `actionStepBudget`(기본 1천만, 약 0.5초, 한 바퀴 7단계면 유닛 약 140만 개). 커맨드의 사전 조건은 제출 때 본문과 한 계량기라 사전 검사(`CheckPreconditions`)만 할 때도 행동 예산을 쓴다(검사는 넘치는데 제출은 되는 어긋남을 막는다). 행동 안에서 읽은 `derived`는 지금처럼 바깥 계량기의 남은 단계를 쓴다(G101). 둘 다 `World` 생성·`World.Load` 옵션이고 모드는 못 바꾼다. 넘으면 지금처럼 실행 오류이고 되감긴다. 함께 정한 경고 문턱(읽기 예산을 넘은 행동을 실패시키지 않고 알림)은 알리는 길을 정한 뒤 따로 적는다.

**이유:** 이전 엔진(ENG `Effect_ForEach`)은 컬렉션 순회에 상한이 없었다(`while`이 없어 영원히 멈출 길이 없었다). 일반 지식: RimWorld 모드는 C#이라 단계 상한이 없고 무거우면 느려질 뿐이며 일을 Tick·TickRare·TickLong으로 나눈다. 패러독스는 전체 순회에 상한이 없고 `while`에만 최대 반복이 있는 것으로 안다(확인 안 함). 셋 다 끝이 있는 일은 막지 않는다. 세계 크기에 비례한 예산은 계수의 근거가 없고 제곱으로 느는 일엔 다시 걸리며, 유한한 `for`를 세지 않는 방식은 `range(10**12)`와 무거운 `derived`를 못 잡는다. 엔티티마다 따로 부르는 핸들러(RimWorld의 물건별 Tick)는 실제 필요가 보일 때 따로 정한다.

**상태:** 확인

## G225

**위치:** 무거운 행동의 경고 (G224와 함께 고름)

**무엇이 비어 있었나:** G224로 행동의 오류 상한이 1천만 단계가 되어, 무거운 핸들러가 실패하기 전에 알 길이 없었다. 실행 중의 경고를 내보내는 통로도 없었다(오류는 결과 객체에, 경고는 불러오기에만 있었다).

**어떻게 정했나:** **행동 실행 하나(가장 바깥 계량기)가 읽기 예산(`stepBudget`)보다 많은 단계를 쓰면 실패시키지 않고 경고 `RUN021`을 그 실행의 결과에 붙인다.** 결과는 `SubmitResult.Warnings`(사전 조건과 본문), `AnswerResult.Warnings`(응답 커맨드와 이어서 실행한 구간), `Reaction.Warnings`(`@on`·`@when` 핸들러, 엔진이 이어 간 Flow)다. 문구는 무엇이(커맨드·핸들러 이름), 몇 단계를, 읽기 예산과 오류 상한이고 위치는 함수 정의(엔진이 이어 간 Flow는 위치 없음), 안내는 여러 틱에 나누거나 호스트 함수로 옮기라는 것이다. **넘을 때마다 매번 붙인다.** 한 번만 보여 줄지는 게임이 정한다. 결과가 없는 실행(사전 검사만, `choose` 나열)의 경고는 버린다. 연결마다 거른 결과(`WorldView.Show`)에는 오류 본문처럼 빠진다. 실패한 실행은 오류만 있다.

**이유:** 결과마다 붙이면 어느 실행이 무거웠는지 바로 보이고 오류가 담기는 방식과 같다. 월드에 목록 하나를 두면 출처는 문구로만 알고 호스트가 비우지 않으면 쌓인다. 처음 한 번만 알리면 "알렸음"이 저장 대상인지 같은 질문이 생긴다. 일반 지식: RimWorld·패러독스에서는 모더가 성능 분석 도구로 무거운 곳을 찾는데, 이것을 엔진이 기본으로 해 준다.

**상태:** 확인

## G226

**위치:** S2 실행기의 구조 (속도, G223 벤치에서 드러남)

**무엇이 비어 있었나:** 실행기는 식을 AST 위에서 재귀로 평가한다(노드마다 단계 세기와 `try/catch`, 연산자는 문자열, 지역 변수는 이름으로 찾음). 벤치 `--shapes`로 스크립트 비용의 70~100%가 실행기였다(부르기 260ns 대 C# 5ns, 수식 950 대 70, 계산 반복 9800 대 42). 시제품(엔진 밖)으로 세 방식을 쟀다: 로드 때 풀어 둔 실행 객체(A) 부르기 24·수식 238·반복 약 3300, 바이트코드 VM(B) 10·226·3560, B에 값 구조체를 더하면 9·약 190·1550(시제품은 오류 위치·보기 정책·멈춤이 없어 상한이다).

**어떻게 정했나:** **A로 하되 층을 나눈다.** ① 풀기: 로드 뒤 함수마다 한 번, 이름을 지역 칸 번호·전역·내장으로, 연산자를 번호로, 함수의 칸 배치를 정한다. 결과는 AST 옆의 표로 두고, 실행 객체와 나중의 명령 생성기(B)가 모두 AST와 이 표에서 만든다. ② 값 연산(`PureOps`)과 ③ 월드 다리(속성 자리 캐시, 내장·호스트 부르기)는 실행 방식을 모르는 모듈로 둔다. ④ 프레임의 지역 변수는 이름 표 대신 칸 배열이다. ⑤ 오류 위치는 노드마다 감싸지 않고 실패한 자리에서 붙인다. ⑥ 멈춘 실행의 저장 형식은 지금의 문장 경로(블록마다 다음 문장 번호, 갈래, 반복 상태, 지역 변수는 이름으로) 그대로이고 실행기 내부와 분리한다. ⑦ 실행: 식은 노드 객체가 스스로 계산하고 문장은 지금처럼 블록 자료로 한 문장씩 돈다(멈춤·저장이 그대로). 단계를 세는 단위(노드 하나에 1단계, G101)는 바꾸지 않는다. **값 구조체화는 백본 ECS화(열 저장)와 함께 맨 끝에 한다.** 구현에서 ①의 공유 층은 칸 배치(`FrameLayout`, 함수 정의에 하나)와 연산자 번호이고, 이름은 노드를 만들 때 배치에서 찾는다(따로 된 풀이 표는 두지 않았다). ⑤는 자기 연산이 실패할 수 없는 노드(상수, 지역 변수, 전역, 리스트, 람다)만 감싸지 않고 나머지 노드는 자기 몸체를 감싼다(오류 위치 표로 바꿀지는 열어 둠).

**이유:** 시제품에서 A와 B의 속도가 거의 같았다. 이득은 실행 모양이 아니라 노드마다의 덧비용과 부르기 준비를 없앤 데서 났다. 층을 나누면 나중에 B로 갈 때 ⑦만 새로 쓰고 ①~⑥은 그대로 쓴다. 값 구조체는 계산이 많은 모양에서만 2배이고, `Value`는 호스트 API 타입이며 저장소와 만나는 읽기 경계에서 함께 바꾸는 것이 한 번에 끝난다. 일반 지식: 풀기와 실행을 나누는 구조는 CPython(AST → 코드 객체)·Lua(파서가 바로 레지스터 배치)에서 흔하고, Truffle 같은 AST 실행기도 노드를 미리 특수화해 빠르게 한다. RimWorld는 C#이라 해당이 없고, 패러독스 스크립트는 로드 때 효과·조건 객체 트리로 바꿔 실행하는 것으로 알며(확인 안 함) A와 같은 방식이다.

**상태:** 확인

## G227

**위치:** P6 스크립트 경로의 바인딩 시점 (G226 뒤 spec 대조)

**무엇이 비어 있었나:** P6은 "스크립트 경로는 로드 시점에 슬롯 핸들로 바인딩한다"고 했다. 구현은 지역 변수를 함수를 처음 부를 때 칸 번호로 묶고(G226), 상태 경로(`u.Food.amount`)는 그 자리를 처음 실행할 때 푼 것을 자리마다 기억한다(속성 자리 캐시). `for u in query("Unit"):`의 `u`처럼 로드 때 타입을 알 수 없는 이름이 있어서 문자 그대로의 로드 시점 바인딩은 할 수 없었다.

**어떻게 정했나:** **P6 문구를 "실행 전에 한 번 슬롯 핸들로 묶는다"로 고친다.** 로드 때 알 수 있으면 로드 때, 타입을 로드 때 알 수 없으면 그 자리를 처음 실행할 때 한 번 풀어 기억하고, 쓸 때마다 스키마·컴포넌트 객체가 같은지만 확인한다(결과는 매번 이름으로 찾는 것과 같다). 로드 때 타입 추론으로 진짜 로드 바인딩을 하는 일은 목표로 두지 않는다.

**이유:** P6의 목적(읽을 때마다 이름 문자열로 찾지 않기)은 자리 캐시로 이미 이루었고, 로드 때 타입 추론은 `.pyi` 수준의 타입 정보가 필요한 큰 일감(G100 정적 검사와 같은 종류)인데 속도 이득은 자리 캐시와 거의 같을 것으로 추정한다. 일반 지식: CPython 3.11의 적응형 특수화와 JS 엔진의 속성 인라인 캐시가 같은 방식으로 실행 중 자리마다 한 번 푼다.

**상태:** 확인
