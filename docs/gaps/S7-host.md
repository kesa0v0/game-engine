# spec 빈틈 상세: S7 호스트 함수

색인과 상태 규칙은 `docs/spec-gaps.md`. 이 파일은 G 번호마다 무엇이 비어 있었고 어떻게, 왜 정했는지의 전문이다.

## G215

**위치:** S7 호스트 함수의 서명 선언 방식 (S7 열린 질문)

**무엇이 비어 있었나:** S7은 서명(입력·출력 타입)을 등록 때 선언하고 `.pyi`를 자동 생성한다고만 했다. C# 타입만으로는 `Ref[Tile]`·`DefId[T]`·`fixed` 같은 엔진 타입을 표현할 수 없다.

**어떻게 정했나:** **서명은 스크립트의 `def` 한 줄 문자열로, 구현은 타입 있는 C# 람다로 등록한다.** 예: `var core = host.For("core");` 다음 `core.Pure("def path.find(start: Ref[Tile], goal: Ref[Tile], max_steps: int = 50) -> list[Ref[Tile]]", "가장 짧은 길을 찾는다.", (EntityId start, EntityId goal, long maxSteps) => Pathing.Find(start, goal, maxSteps))`(C# 타입 대응은 G222). 소유 모드는 `host.For`로 한 번 밝히고 `def` 뒤 이름은 그 아래 경로다(G218). 효과 등급은 메서드 이름(`Pure`, 엔티티를 쓰면 `Writes`)이고 `Writes`의 람다는 첫 인자로 접근기를 받는다. 등록할 때 람다와 서명을 대조한다: 인자 개수, 타입 대응(`Ref[Tile]`은 `EntityId` 등, G222), 이름(`maxSteps`와 `max_steps`처럼 낙타 표기와 밑줄 표기를 같게 봄, 넘겨받은 람다 하나의 매개변수 이름을 읽는 것이라 S7이 금지한 리플렉션 스캔이 아니다), 반환 타입. 어긋나면 등록 오류다. 타입 있는 람다는 인자 수에 상한(예: 8)이 있고 넘으면 이름으로 꺼내는 형태(`call => ... call.Int("max_steps")`)로 받는다. 서명은 커맨드 매개변수와 같은 어노테이션 파서로 읽고, 모드가 정의한 타입을 쓰므로 스키마가 완성된 뒤 검사한다(틀리면 그 호스트 함수 이름을 단 로드 오류). 인자는 커맨드 인자와 같은 검사(G115)를 거친 엔진 값으로 구현에 들어가고 반환값도 서명대로 검사한다. 스텁은 서명과 독스트링을 옮긴다. **엔진 안의 기준 형태는 "소유 모드, 서명, 효과 등급, 독스트링, 구현"이고 위 등록 모양은 그 위의 첫 앞면이다.** 빌더 API, 특성과 C# 소스 생성기, 모드 쪽 선언 파일처럼 더 보기 좋은 등록 모양은 같은 기준 형태를 만드는 앞면으로 나중에 더할 수 있다(실제 호스트를 붙일 때, Godot·Unity 결정 뒤).

**이유:** 사용자가 처음 기준 형태(`Register(이름, 서명, 효과 등급, 독스트링, args => (Ref)args[0] ...)`)가 깔끔하지 않다고 해서 다시 비교했다. 번호로 꺼내기는 서명 순서를 바꾸면 조용히 틀어지고, 이름으로 꺼내기는 오타가 첫 호출 때야 잡힌다. C# 빌더 API는 길고 스크립트 모양과 다르며 타입 이름은 여전히 문자열이다. 메서드에 특성을 붙이는 방식은 `Ref[Tile]` 같은 엔진 타입을 결국 특성 문자열로 적어야 한다. 모드 파일에 서명을 두고 C#은 구현만 붙이는 방식(WebAssembly 가져오기와 같은 구조)은 CLI가 호스트 없이 검사할 수 있지만 같은 함수를 두 곳에 적고 G221을 바꿔야 한다. 일반 지식: Factorio·Godot·Roblox는 엔진 쪽에 한 번 적고 서명을 JSON으로 내보내며, sol2·Jint·wasmtime은 타입 있는 함수를 그대로 받는다. 서명 없이 받기는 로드 검사와 스텁을 잃는다. 일반 지식: 패러독스는 엔진이 고정한 효과·조건과 받는 범위를 문서로 덤프한다(`script_docs`). TypeScript `.d.ts`와 파이썬 C 확장의 `.pyi`가 선언 파일 안의 사례다. 이전 엔진은 `Effect_*` C# 클래스를 YAML로 직렬화해 세이브에 클래스 이름이 남았다.

**상태:** 확인

## G216

**위치:** S7 효과 등급과 부를 수 있는 곳

**무엇이 비어 있었나:** S7은 효과 등급(순수 / 엔티티 쓰기)을 등록 때 선언한다고만 했다. 등급마다 어디서 부를 수 있는지, 순수 등급이 월드를 읽을 수 있는지가 없었다.

**어떻게 정했나:** **두 등급을 스크립트 함수의 규칙(G117·G135)에 그대로 끼운다.** 순수(`Pure`)는 어디서나 부를 수 있고(`derived`, 사전 조건, 정책, `@when` 조건, `Cond`, 커맨드 본문) 월드는 접근기로 읽기만 하며 읽은 칸은 읽기 집합에 기록된다(`derived` 재계산, `when` 재평가, `Explain` 근거). 엔티티 쓰기(`Writes`)는 쓰기 자리(커맨드·핸들러·`@when` 본문)에서 문장이나 이름 대입의 오른쪽으로만 부를 수 있고 로드 때 `spawn`과 같게 판정한다. 난수는 쓰기 등급만 쓴다(접근기에서 정함). "월드를 전혀 읽지 않는 계산" 셋째 등급은 두지 않는다.

**이유:** 셋째 등급은 스크립트 함수에도 없는 구분이고, 아무것도 안 읽으면 읽기 집합이 빈 것으로 충분하다. 벤치에서 캐시 같은 필요가 보이면 기존 등록을 깨지 않고 더할 수 있다.

**상태:** 확인

## G217

**위치:** S7 호스트 함수에 건네는 접근기

**무엇이 비어 있었나:** S7은 "엔티티 접근은 엔진이 건네는 제한된 접근기로만(읽기 집합 추적 유지)"이라고만 했다. 무엇을 건네는지, 쓰기·난수·재진입을 어떻게 막는지가 없었다. 월드의 공개 읽기는 이미 읽기 집합(`when`)과 `Explain` 근거에 기록되고 공개 쓰기는 커맨드 안이면 되돌리기 기록에 들어간다.

**어떻게 정했나:** **호출마다 새로 만드는 창구 객체를 건넨다.** 순수 등급은 읽기만(`Get`, `GetRow`, `Has`, `IsAlive`, `DefOf`, Def 상수, `All`, `Query`, `Inverse`, 줄 목록, `now`), 쓰기 등급은 그에 더해 쓰기(`Set`, `SetRow`, 만들기, 파괴, 컴포넌트 붙이기·떼기, 줄 추가·제거, 기여 행)와 그 Flow의 난수 흐름(스크립트 `random`과 같은 이름, G178·G179)을 받는다. 창구는 월드의 공개 API를 그대로 부르므로 읽기 기록과 롤백이 스크립트와 같다. `Submit`·`Answer`·`Respond`·`Advance`·`Save`·`ViewAs`는 창구에 없다(재진입 금지). 호출이 끝나면 창구는 무효가 되어 붙잡아 두고 쓰면 예외다. 스크립트나 호스트 함수가 실행 중일 때 월드의 공개 쓰기·`Submit`·`Answer`·`Respond`·`Advance`를 직접 부르면 예외다(`Save`가 이미 그렇다). 호스트 함수가 스크립트 함수를 인자로 받아 부르는 것(예: 길찾기의 이동 비용 람다)은 함수 타입 서명·실행 예산·오류 처리가 필요해 미루고, 필요가 보이면 따로 정한다.

**이유:** `World`를 그대로 넘기고 문서로 약속하면 순수 함수가 `derived` 계산 중에 상태를 바꿔 읽을 때마다 값이 달라지는 비결정성이 조용히 생긴다. 접근 없이 인자만 받으면 길찾기처럼 맵 전체를 보는 함수를 쓸 수 없다.

**상태:** 확인

## G218

**위치:** S7 호스트 함수의 호출 모양과 이름 공간

**무엇이 비어 있었나:** S7은 "모드 id 접두사 네임스페이스(`core.find_path`), 충돌은 로드 오류"라고만 했다. 접두사가 로드된 모드여야 하는지, 어느 모드에서 보이는지, 무엇과 충돌하는지가 없었다. 스크립트 함수는 모드마다 따로인 이름 공간에 있어(G20·G105) `core.xxx` 모양은 다른 뜻으로 쓰이지 않고, `random.randint`처럼 "이름 공간.함수" 모양은 이미 있다(G179).

**어떻게 정했나:** **이름은 `소유모드id.자유로운.점.경로`다**(예: `core.path.find`, `core.economy.run_phase`). 커맨드(G109)·단계(G152)와 같은 "모드 id가 맨 앞" 규칙이다. 등록할 때 소유 모드를 밝히고, 게임 개발자가 등록하는 함수는 게임의 기본 모드가 소유한다(나중에 모드 DLL을 지원하면 그 모드가 소유자가 된다). **소유 모드 자신과 소유 모드를 필수 의존성으로 적은 모드에서만 보이고**, 그 밖에서 쓰면 로드 오류다(소유 모드가 빠지면 의존한 모드도 함께 비활성화되어 정리된다, S1). 스크립트는 `import` 없이 전체 경로로 부르고(`core.path.find(a, b)`), 함수 값으로 담을 수 있다(`find = core.path.find`). 경로 중간(`core`, `core.path`)은 값이 아니다. 같은 모드 안에서 같은 경로를 두 번 등록하면 등록 오류, 소유 모드가 로드되지 않았으면 그 등록은 쓰이지 않는다. 모드 스크립트가 최상위에 다른 모드 id와 같은 이름을 만들면 그 이름 공간을 가리므로 로드 오류다. 오타는 로드 때 "혹시 …?"로 잡는다(G108과 같은 검사). **다른 모드의 스크립트 함수를 `모드id.이름`으로 부르는 것은 이번에 열지 않는다**(G20 "아직 없다" 그대로, 공개 범위 등을 따로 정해야 함). 같은 이름 모양으로 나중에 열 수 있다.

**이유:** 처음 기록은 "모드 id 꼴이면 아무 접두사나, 로드된 모드일 필요 없음"이었는데, spec S7 원문("모드 id 접두사 네임스페이스")과 G152("자기 모드 접두사의 단계만 선언, S7 호스트 함수와 같은 규칙")와 어긋나 사용자가 짚었고 고쳤다. 모든 모드에서 보이게 하면 소유 모드가 없을 때 쓰는 쪽의 규칙이 따로 필요하다. 일반 지식: RimWorld에서 다른 모드의 C#을 쓰는 모드는 그 모드를 의존성으로 적는다.

**상태:** 확인

**바뀜:** 다른 모드의 스크립트 최상위 이름을 같은 모양 `모드id.이름`으로 연다. 같은 모드의 호스트 함수 경로 첫 조각과 스크립트 이름이 겹치면 로드 오류 → G309.

## G219

**위치:** S7 호스트 함수 경계의 오류와 실행 예산

**무엇이 비어 있었나:** 스크립트 오류는 `WorldException`이 되어 커맨드면 롤백된다(C8). 실행 예산(`RUN013`)은 스크립트의 끝나지 않는 반복을 막는다. 호스트 함수가 예외를 던지거나, 서명과 다른 값을 돌려주거나, 오래 돌 때의 규칙이 없었다.

**어떻게 정했나:** **구현이 던진 예외는 엔진이 잡아 스크립트 오류 `RUN019`("host function core.find_path failed: 예외 종류 메시지", 원래 예외는 `InnerException`)로 바꾼다.** 그다음은 스크립트 오류와 같다(커맨드면 롤백, 게임은 계속). **반환값이 서명과 다르면 호스트 코드의 버그이므로 따로 `RUN020`**("returned str, but its signature says list[Ref[Tile]]")으로 같은 길을 간다. 모더가 잘못 넘긴 인자는 지금의 인자 검사 오류이고 상수 인자는 로드 때 잡을 수 있는 만큼 잡는다. **실행 예산은 호출 한 번을 한 걸음으로 세고 접근기의 읽기·쓰기는 세지 않는다.** 호스트 코드의 무한 반복은 엔진이 막지 못한다(문서에 적음).

**이유:** 예외를 그대로 호스트까지 올리면 커맨드 하나의 실패가 게임 루프를 멈추고 롤백을 건너뛴다. 반환값 오류를 같은 코드로 내면 모더가 자기 탓으로 오해한다. 접근기 읽기까지 예산에 세면 큰 맵의 정상적인 길찾기가 실패할 수 있다. 예산은 모더 스크립트를 막는 장치이고 호스트 코드는 S7상 신뢰하는 쪽이다.

**상태:** 확인

## G220

**위치:** S7 결정론 위반 방어 (S7 열린 질문, S9)

**무엇이 비어 있었나:** 커널은 `BannedSymbols.txt`(부동소수점, 비시드 난수, 시스템 시계, 프로세스마다 다른 해시)와 `DeterminismAnalyzer`(`KE0001` 부동소수점 키워드, `KE0002` 순서 없는 순회)로 컴파일 때 막지만, 호스트 함수는 호스트의 코드라 닿지 않고 엔진은 실행 중에 기계마다 다른 결과를 알아챌 수 없다.

**어떻게 정했나:** **지금은 커널의 검사를 호스트도 켤 수 있게 내놓고 문서에 적는다.** 금지 목록과 분석기를 호스트 함수만 모은 어셈블리에 켜는 방법을 안내하고, 분석기 문구가 "커널"에 묶인 곳을 일반화한다. 켜는 것은 호스트의 선택이고 정적 변수에 숨긴 상태 같은 것은 못 잡는다. **상태 체크섬으로 어긋남을 감지하는 것은 리플레이·멀티플레이를 만들 때 그 기능의 일부로 한다**(정규 저장 C4와 내용 해시 G212가 재료). 순수 호스트 함수를 두 번 불러 비교하는 실행 중 검증은 하지 않는다.

**이유:** 두 번 불러 비교하기는 같은 기계 안이라 기계마다 다른 문제(부동소수점, 해시 순서)를 못 잡는데 실제로 위험한 쪽이 그쪽이다. 일반 지식: 패러독스 멀티플레이는 체크섬으로 동기 어긋남(OOS)을 감지한다.

**상태:** 확인

## G221

**위치:** S7 호스트 함수의 저장, 바뀜 알림, 게임 없이 도는 도구

**무엇이 비어 있었나:** 멈춘 Flow의 함수 값은 이름으로 저장된다(스크립트 함수 `{"function": [모드, 이름]}`, 내장 `{"builtin": 이름}`). 호스트 함수 값의 저장, 호스트 함수가 바뀐 것의 알림이 없었다. 또 `engine check`·`engine stubs`는 게임의 C# 코드 없이 모드 폴더만 읽으므로 등록된 호스트 함수를 몰라, 쓰는 순간 "모르는 이름" 오류가 나고 스텁에서 빠진다.

**어떻게 정했나:** **함수 값은 `{"host": "core.find_path"}`로 저장한다**(이름 문자열뿐, S7 "C# 이름 금지"). 불러올 때 없으면 `SAV002`이고 G214로 그 Flow만 취소할 수 있다. **세이브 메타에 등록된 호스트 함수 목록(이름, 서명, 효과 등급)을 싣고 불러올 때 다르면 `SAV003` 경고에 생김·없어짐·서명 바뀜을 적는다**(G212처럼 사실만, C# 구현이 바뀐 것은 엔진이 모르므로 호스트 책임). **호스트는 등록 목록을 선언만 담은 파일(이름, 서명, 효과 등급, 독스트링, JSON)로 내보내 게임과 함께 배포하고, CLI는 `--host <파일>`로 받아 구현 없이 검사하고 스텁을 만든다.** 원본은 C# 등록(G215)이고 파일은 그 결과라 둘이 어긋나지 않는다. 로드 중(스키마·Def 파일의 최상위)에는 호스트 함수를 부를 수 없고 값으로 참조만 한다(월드가 없어 접근기를 못 만들고 CLI에는 구현이 없다, 부르면 로드 오류). 스텁은 이름 경로를 따라 중첩한 클래스(`core.path.find`면 `core` 안의 `path` 안의 `find`, G218)에 서명과 독스트링을 넣고, 그 모드를 의존성으로 적은 모드의 스텁에만 넣으며, `Ref[Tile]`은 `Tile` 클래스로 바꾸며, 로직 스텁과 스키마 스텁 양쪽에 넣는다.

**이유:** 내장과 같은 `builtin` 태그를 쓰면 불러올 때 무엇이 없어졌는지 문구가 흐려진다. 내보내기 없이 두면 모더의 주 도구(`check`·스텁)가 호스트 함수를 쓰는 순간 깨진다. G215에서 미룬 선언 파일과 달리 내보낸 파일은 원본이 아니다. 일반 지식: 패러독스는 `script_docs`로 효과·조건 목록을 덤프하고 모더 도구(CWTools 등)가 그것을 읽는다.

**상태:** 확인

## G222

**위치:** S7 호스트 함수의 스크립트 타입과 C# 타입 대응

**무엇이 비어 있었나:** G215는 타입 있는 람다를 서명과 대조한다고 정하고 대응표는 구현 때로 미뤘다. 엔진 정수는 64비트(`IntValue`는 `long`)이고 엔티티는 `EntityId`이며, C#의 `Dictionary`는 순회 순서를 보장하지 않는다(`KE0002`가 막는 것).

**어떻게 정했나:** **`int`는 `long`만**(C# `int`는 넘침 규칙이 따로 필요해 받지 않으며 G215 예시의 `int maxSteps`는 `long maxSteps`다), `fixed`는 `Fixed`, `bool`은 `bool`, `str`은 `string`, **`Ref[X]`는 `EntityId`**(새 `Ref` 타입은 만들지 않음), `DefId[X]`는 `string`, `T 또는 None`은 null을 허용하는 타입(`long?`·`EntityId?`, 참조 타입은 그대로), `list[T]`는 인자로 `IReadOnlyList<T>`이고 반환은 그것으로 바꿀 수 있는 것(`List<T>`·배열)이다. 어느 자리든 엔진 값 `Value`로 받으면 바꾸지 않고 그대로 넘긴다. **`dict[K, V]`는 타입 있는 C#으로 바꾸지 않고 엔진 값(`Value`, 순서 있는 `DictValue`)으로만 주고받는다.** 반환이 `None`이면 람다는 값을 돌려주지 않는다(`Writes`만, 순수 함수가 None을 돌려주면 하는 일이 없어 등록 오류). 실제로 dict를 주고받는 호스트 함수가 생기면 그때 다시 정한다.

**이유:** C# `int`도 받으면 큰 값이 넘칠 때 오류인지 잘림인지를 정해야 한다. dict를 `IReadOnlyDictionary`로 주고 엔진이 키 순서로 정렬하는 안은 편하지만 호스트 코드 안에서 그 dict를 돌면 순서 문제가 남는다. 키·값 쌍 목록으로 주고받는 안은 순서는 안전하지만 쓰기 불편하고 지금 쓰는 사례가 없다.

**상태:** 확인

## G291

**위치:** G221에서 미룬 것: 콘텐츠 파일 최상위에서 호스트 함수를 값으로 쓰기

**무엇이 비어 있었나:** 호스트 함수는 함수 본문 안에서만 이름으로 풀렸다. Def 파일의 맨 위(`Goal("B", check=core.goals.reached)`)나 패치 값(`patch.set("core:B", "check", core.goals.reached)`)에 적으면 "이름 없음" 오류였다. 스크립트 함수는 `check=done`처럼 칸에 들어가므로, 호스트 함수만 한 줄짜리 스크립트 함수로 감싸야 했다.

**어떻게 정했나:**
- **읽기 등급 호스트 함수는 `Cond[...]` 칸의 값이 될 수 있다.** 이미 G216이 정한 "읽기 등급은 `Cond`에서도 부를 수 있다"를 파일 최상위의 값에도 적용한 것이다.
- **로드가 칸에 맞는지 본다** (값 검사, Def 값은 `VAL002`, 패치는 `PAT009`):
  - 쓰기 등급이면 거절한다. `Cond` 칸은 읽기만 받는다(G117과 같다).
  - 칸이 부르는 꼴로 부를 수 있어야 한다. 첫 매개변수가 그 칸의 Def 타입의 `Ref[X]`이고 나머지는 기본값이 있어야 한다.
  - 반환이 `bool`이어야 한다.
- **`Action[...]` 칸은 지금처럼 스크립트 함수만 받는다.** 호스트 함수는 한 번 부르고 끝나서 `ask`·`wait`로 멈출 수 없는데, 그 차이를 칸이 어떻게 다룰지는 쓰려는 사례가 생기면 정한다.
- 로드 때는 월드가 없으므로 값은 이름과 서명만 든 참조(`HostReference`)다. 게임이 그 칸을 읽을 때 그 월드의 호스트 함수 값으로 바뀐다. 참조를 로드 중에 부르면 오류다. 덤프는 `{"host": "core.goals.reached"}`로 적는다.
- 보이는 범위는 함수 본문과 같다(G218): 소유 모드가 자신이거나 필수 의존인 호스트 함수만 쓸 수 있다.
- 호스트 함수의 서명은 Def 파일을 실행하기 전에 푼다(전에는 실행 뒤).

**이유:** 호스트 함수의 읽기 등급은 엔진이 쓰기 창구를 건네지 않아 지킨다(G217). 그래서 믿고 말고 할 문제가 아니고, 감싸는 스크립트 줄을 모더가 쓰지 않게 하면 된다. 서명은 로드 때 보는 편이 칸을 평가하는 순간 인자 어긋남으로 터지는 것보다 모더에게 친절하다(스크립트 함수의 매개변수 타입 추론은 G228). 일반 지식: 패러독스는 효과·조건 목록을 엔진이 내보내 모더가 이름으로 부른다.

**상태:** 확인

**바뀜:** `Action` 칸은 G292에서 호스트 함수를 받게 되었다. 위 "`Action[...]` 칸은 지금처럼 스크립트 함수만 받는다"는 더 이상 맞지 않다.

## G292

**위치:** G291에서 미룬 것: `Action[...]` 칸에 호스트 함수

**무엇이 비어 있었나:** G291은 `Cond` 칸에만 호스트 함수를 허용하고 `Action` 칸은 스크립트 함수만 받게 두었다. 이유로 "호스트 함수는 한 번 부르고 끝나서 `ask`·`wait`로 멈출 수 없다"를 들었다. 다시 보니 이것은 걸림돌이 아니다. 멈추지 않는 스크립트 `Action`과 같게 다루면 되고, 쓰기 등급 호스트 함수를 쓰기 자리의 문장으로 부르는 규칙(G216), 커맨드 안의 되감기(G217), 멈춘 Flow 안 호스트 함수 값의 저장(G221)이 이미 있다.

**어떻게 정했나:**
- **`Action[...]` 칸(`list[Action[...]]` 포함)에도 호스트 함수를 값으로 쓸 수 있다.** 읽기 등급이든 쓰기 등급이든 되고 반환은 가리지 않는다. 스크립트 함수가 `Action` 칸에서 쓰기 여부나 반환을 가리지 않는 것과 같다.
- **로드가 칸이 부르는 꼴만 본다.** 첫 매개변수가 그 칸의 Def 타입의 `Ref[X]`이고 나머지는 기본값이 있어야 한다(`Cond`와 같다). 안 맞으면 로드 오류다(Def 값 `VAL002`, 패치 `PAT009`).
- `Cond` 칸의 규칙(읽기 등급, bool 반환)은 그대로다.
- 칸을 읽을 때 목록 안의 참조도 그 월드의 호스트 함수 값으로 바뀐다.

**이유:** 모더가 `def zero_it(g): core.goals.zero(g)`처럼 한 줄을 감싸지 않아도 된다. 규칙이 `Cond`와 닮아 외울 것이 늘지 않는다. 앞서 걸림돌로 본 "멈출 수 없음"은 멈추지 않는 스크립트 `Action`에도 똑같은 일이라 호스트 함수에 특별한 제약이 아니다. 아직 호스트 함수를 `Action` 칸에 쓰려다 막힌 사례는 없고, 이 결정은 규칙을 `Cond`와 맞추는 일이다.

**상태:** 확인 (사용자 동의 2026-10-21, 선택지 A)
