# spec 빈틈 상세: S9 진단·CLI

색인과 상태 규칙은 `docs/spec-gaps.md`. 이 파일은 G 번호마다 무엇이 비어 있었고 어떻게, 왜 정했는지의 전문이다.

## G5

**위치:** S9 진단

**무엇이 비어 있었나:** 위치 표기 규칙.

**어떻게 정했나:** 줄·열은 1부터, 열은 UTF-16 코드 단위. 줄 0·열 0은 파일 전체에 대한 진단(위치 없음, 예: 파일을 읽을 수 없음)이며 정렬에서 그 파일의 맨 앞에 온다. `check` JSON에서 어떻게 나타낼지는 출력 스키마 때 정한다. 파일 경로는 모드 루트 기준 상대 경로, 구분자 `/`. 줄바꿈은 `\r\n`·`\r`·`\n` 모두 한 줄. UTF-8 BOM은 무시. 진단 출력은 (파일, 줄, 열, 코드, 메시지) 순으로 정렬.

**이유:** VS Code·C# 문자열과 같은 단위. 절대 경로는 골든 출력을 기계마다 다르게 만든다.

**상태:** 잠정

## G6

**위치:** S9 진단 코드

**무엇이 비어 있었나:** 코드 체계가 열린 질문이었다.

**어떻게 정했나:** 영역 접두사 + 세 자리: `LEX`(렉서), `PAR`(파서), `MOD`(매니페스트·정렬). 영역은 단계가 늘 때 추가.

**이유:** 최소한의 체계로 시작. 이후 모든 단계의 진단이 이 체계를 따랐다(`CMD`·`RUN` 등).

**상태:** 확인 (2026-10-19, 사용자 동의)

## G75

**위치:** S9 `check` 출력 스키마

**무엇이 비어 있었나:** S9는 “`check` 출력 스키마”를 열린 질문으로 남겼다.

**어떻게 정했나:** `check` JSON은 한 객체다: `version`(1, 스키마가 바뀌면 올림), `ok`(오류 심각도가 하나도 없을 때만 true, 경고·정보는 영향 없음), `counts`(`error`·`warning`·`info`), `mods`(`loaded`는 로드 순서, `disabled`는 모드 id 순), `diagnostics`(결정적 정렬: 파일, 줄, 열, 코드, 메시지). 진단 하나는 `code`, `severity`(소문자 `error`/`warning`/`info`), `message`, `mod`, `file`, `line`, `col`, `hint`, `related`(위치 목록 `file`·`line`·`col`)이고 키는 항상 있으며 없는 값은 `null`이거나 빈 배열이다. 키 순서와 들여쓰기가 고정이라 같은 입력이면 같은 문자열이다. 직렬화는 라이브러리 없이 직접 쓴다(Unity 소스 패키지 P1a). 생성은 순수 함수 `CheckReport.ToJson`이고 파일 읽기·종료 코드·경고를 오류로 올리는 옵션은 CLI의 일이다.

**이유:** CI에서 diff할 수 있어야 하고, 키가 항상 있어야 소비하는 쪽이 존재 검사를 안 한다.

**상태:** 확인

## G76

**위치:** S9 최종 Def 덤프 (“왜?” 도구 1)

**무엇이 비어 있었나:** S9는 “최종 Def 덤프 + 필드별 출처”라고만 했고 형식·범위가 없었다.

**어떻게 정했나:** `check`와 같은 JSON(`version` 1)이다. **`abstract`를 포함한 모든 Def**를 등록 순서로, Def마다 `id`·`type`·`mod`·`abstract`·`parent`(id 또는 null)·`consts`·`components`를 낸다. 값마다 `value`, `origin`(`own`·`inherited`·`patched`·`default`), `source`(처음 적은 Def·모드·위치, `default`면 스키마 선언 위치만), `patches`(그 칸에 영향을 준 패치를 적용 순서로, 부모 쪽 패치 먼저: `mod`·`def`·`op`·`path`·`value`·`status`·`file`·`line`·`col`)를 둔다. 구체 Def는 기본값까지 채운 동결본을, `abstract`는 기본값 없이 상속을 펼친 값을 낸다. 컴포넌트는 `values`·`rows`·`attachedBy`로 낸다. 값 표현: 정수는 JSON 정수, `fixed`는 문자열(`"1.5"`, 정밀도 보존), 문자열·bool·`null`은 그대로, 리스트는 배열, 맵은 객체(정수 키도 문자열), 함수는 `{"function": 이름}`. **실패한 패치는 덤프에 넣지 않는다**: 실패한 모드는 비활성화되어 최종 값에 기여하지 않으므로 `check` 진단(`PAT0xx`)으로만 본다(G45). (구현 보강, 2026-10-19) "영향을 준 패치"는 값을 만들 때 따라 적는다(`ResolvedValue.Patches`): 물려받은 값은 부모의 것을 그대로, 자식이 직접 적은 값과 통째 `set`은 그 전 것을 지우고, `add`·`append`·`remove`·맵 항목 `set`은 그 전 것 뒤에 쌓고, `merge="append"` 리스트와 `inherit` 식은 읽은 부모 값의 것을 잇는다. 그래서 자식이 덮은 부모 패치는 나오지 않는다(전에는 부모 체인의 겹치는 경로를 모두 훑었다).

**이유:** 덤프의 목적은 최종 값이 어떻게 만들어졌는지 보이는 것이다. 실패 항목을 섞으면 비활성화된 모드가 기여한 것처럼 보이고, 남기려면 회차 사이로 이력을 보존해야 한다.

**상태:** 확인

## G78

**위치:** S9 `engine check`의 종료 코드

**무엇이 비어 있었나:** G75가 종료 코드를 CLI의 일로 미뤘고 체계가 없었다.

**어떻게 정했나:** **0** = 오류 없음(경고·정보만 있어도 0), **1** = 모드 콘텐츠에 오류가 있음, **2** = 사용법·환경 문제(잘못된 인자, 없는 모드 폴더 등 진단을 만들기 전에 막히는 것), **3** = 엔진 내부 예외(엔진 버그). 종료 코드 0과 JSON의 `ok`=true는 항상 같이 간다. 경고를 오류로 올리는 옵션이 생기면 올린 뒤의 심각도로 `ok`와 종료 코드를 정한다.

**이유:** 1은 모드를, 2는 명령을, 3은 엔진을 고치라는 뜻이라 CI와 모더의 대응이 다르다. pyright·ESLint처럼 작은 번호가 CI 설정에서 익숙하고, sysexits(64·65·70)는 정확하지만 낯설다.

**상태:** 확인

## G79

**위치:** S9 `engine check`의 출력 형식

**무엇이 비어 있었나:** S9는 “JSON 출력 포함”이라고만 했고 기본 출력과 JSON을 내보내는 곳이 없었다.

**어떻게 정했나:** 기본은 사람용 텍스트를 stdout으로 낸다. 진단 한 줄은 `파일:줄:열: 심각도 코드: 메시지`이고 힌트와 관련 위치는 들여쓴 줄로 붙는다. 순서는 JSON과 같은 정렬이며 끝에 개수 요약과 로드·비활성 모드를 한 줄로 낸다. 정보 진단도 기본으로 보인다(G38의 건너뜀 알림). 텍스트의 파일 경로는 사용자가 준 모드 폴더 경로를 앞에 붙여 현재 폴더 기준으로 낸다(터미널에서 클릭으로 열리게). JSON은 G75대로 모드 폴더 기준이다. `--json`이면 stdout에 G75 JSON 한 덩어리만 낸다. 사용법 오류(종료 코드 2)와 내부 예외(3)의 메시지는 형식과 무관하게 stderr로 낸다. 텍스트 생성도 순수 함수(`CheckReport.ToText`)다.

**이유:** 기본 사용자는 터미널의 모더이고 `파일:줄:열:`은 편집기 터미널에서 클릭된다. 기계는 `--json` 하나로 깨끗한 stdout을 받는다. 텍스트·JSON·종료 코드가 같은 진단 목록과 같은 `ok`(G78)에서 나와 어긋나지 않는다.

**상태:** 확인

## G80

**위치:** S9 최종 Def 덤프의 CLI 진입점 (G76 보강)

**무엇이 비어 있었나:** G76은 덤프의 모양만 정했고 CLI에서 어떻게 부르는지 없었다. G79로 `check --json`의 stdout은 JSON 한 덩어리뿐이라 같은 stdout에 덤프를 실을 수 없다.

**어떻게 정했나:** 별도 명령 `engine dump <mods-dir>`. stdout에는 G76 덤프 JSON만, 로드 진단은 G79의 사람용 텍스트(요약 줄 포함)로 stderr에 낸다. 종료 코드는 G78 그대로이고, 오류가 있어도 살아남은 모드로 덤프를 낸다. 특정 Def만 고르는 옵션은 뒤로 미룬다.

**이유:** 오류가 있을 때 원인을 보는 것이 덤프의 목적이다. S9의 다른 “왜?” 도구도 각자 명령이 될 자리이고, `check`는 짧고 결정적인 판정으로 남는다. 옵션 하나로 출력 종류가 바뀌는 방식(`check --dump`)은 혼란스럽고, 파일 출력은 실패 경우만 늘린다.

**상태:** 확인

## G84

**위치:** S9 경고를 오류로 올리는 옵션 (S9 열린 질문, G78 보강)

**무엇이 비어 있었나:** S9가 “경고를 오류로 승격하는 옵션(CLI)”을 열린 질문으로 남겼고, G78은 올린 뒤의 심각도로 판정한다는 것만 정했다.

**어떻게 정했나:** `engine check --warnings-as-errors` 하나. 모든 경고를 심각도 `error`로 바꾼 진단으로 출력하므로 텍스트, JSON의 `severity`·`counts`·`ok`, 종료 코드가 모두 올린 뒤의 값이다. 정보(`info`)는 올리지 않는다. 코드와 메시지·위치·힌트·관련 위치는 그대로이고 정렬 기준에 심각도가 없어 순서도 같다. `dump`와 `stubs`는 이 옵션을 받지 않는다(사용법 오류). 코드별로 고르는 옵션은 필요해지면 더한다.

**이유:** 컴파일러의 `-Werror`·`TreatWarningsAsErrors`와 같은 이름과 동작이라 익숙하다. 출력의 심각도 자체를 바꿔 G78의 “종료 코드 0 ⇔ `ok`”가 유지된다. 정보는 의심이 아니라 알림(G38의 건너뜀)이라 올리면 호환 패치를 가진 모드가 늘 실패한다. 판정 명령은 `check`뿐이다.

**상태:** 확인

## G85

**위치:** S9 `check`와 `optional` 모드 (G38의 열린 점)

**무엇이 비어 있었나:** G38이 `check`가 선택 모드를 모두 설치한 것으로 놓고 검사하는 방식을 열어 두었다.

**어떻게 정했나:** 옵션을 두지 않는다. `check`는 모드 폴더에 있는 모드 집합만 검사한다. 호환 패치(`if mod_loaded("x"):` 안)까지 검사하려면 그 선택 모드를 폴더에 함께 둔다. 없는 선택 모드의 가드는 G38의 정보 진단(“패치 N건 적용 안 함”)으로 출력에 보인다.

**이유:** “설치로 간주”는 할 수 없다: 폴더가 없으면 그 모드의 스키마·Def가 없어 가드 안을 검사할 재료가 없고, 폴더가 있으면 이미 설치되어 가드가 참이다. “없는 것으로 간주”(`--without`, 조합별 반복)는 새로 잡는 오류가 없다: G38이 호출의 유효성을 설치 상태와 무관하게 만들었다.

**상태:** 확인

## G252

**위치:** 모더용 문서의 형식

**무엇이 비어 있었나:** spec과 spec-gaps는 결정 기록이라 모더가 읽을 글이 아니다. 모드를 처음 쓰는 사람이 무엇을 어떤 순서로 쓰는지 설명한 문서가 없었다.

**어떻게 정했나:** 저장소 안의 마크다운 안내서 `docs/modding/`. 장은 시작하기, 데이터(스키마·Def·패치), 로직, 커맨드, 흐름(질문·시간), 반응, 자리와 숨긴 정보, 화면에 보일 값, 아직 없는 것이고 예시 게임 `samples/skirmish`를 따라간다. 빠짐없는 목록(레퍼런스)은 손으로 쓰지 않고 엔진이 만드는 `.pyi` 스텁(G207~G209)을 가리킨다. 안내서의 예시 코드는 테스트가 로드하는 모드(`samples/`)에서 가져와, 예시가 깨지면 테스트가 실패한다. 엔진이 만드는 레퍼런스 페이지(`kesa docs` 같은 것)와 문서 사이트는 미룬다. 마크다운으로 써 두면 사이트로 그대로 옮길 수 있다.

**이유:** 코드와 같은 커밋으로 고칠 수 있고 GitHub·VS Code에서 바로 읽힌다. 손으로 쓴 레퍼런스는 코드와 금방 어긋난다. Factorio는 엔진이 내보낸 JSON으로 Lua API 레퍼런스를 만들고 안내서는 위키에 두며, 패러독스는 `script_docs` 명령으로 트리거·효과 목록을 뽑아 주고, RimWorld는 공식 레퍼런스 없이 커뮤니티 위키가 메운다(일반 지식). 번역(X4)·UI 행동처럼 비어 있는 곳이 있어 지금 생성 레퍼런스를 만들면 금방 바뀐다.

**상태:** 확인

## G289

**위치:** S9 "왜?" 도구 (5) 단계 순서 덤프의 CLI 진입점 (G80에서 이어서, handoff "남은 일" 3번)

**무엇이 비어 있었나:** spec S9는 단계 순서 덤프에 담을 것(신호별 최종 단계 순서, 각 단계의 핸들러와 선언 모드, 순서를 정한 `after`/`before`와 동률 규칙)만 적었다. 어떻게 부르고 어떤 모양으로 내는지, `@when` 반응도 담는지가 없었다.

**어떻게 정했나:**
- 새 명령 `engine stages <mods-dir> [--host <file>]`. G80의 "왜? 도구는 각자 명령"을 따른다.
- stdout에 사람이 읽는 텍스트를 낸다.
  - 단계 순서와 동률 규칙(앞에 올 수 있는 단계가 여럿이면 id 서수순).
  - 각 단계 앞에 오게 한 `after`·`before`와 그것을 적은 위치.
  - 신호별로 단계마다의 핸들러와 그 위치. 순서 규칙(단계 → 로드 순서 → 정의 순서, `stage=` 없는 것은 맨 뒤)을 머리에 적는다.
  - `@when` 반응을 같은 모양의 한 절로.
- 진단은 stderr에 G79 텍스트로, 종료 코드는 G78. 오류가 있어도 살아남은 모드로 낸다(G80과 같다).
- JSON(`--json`)은 필요한 사례가 생기면 더한다.

**이유:** 순서 문제를 찾을 때 사람이 눈으로 보는 도구라 텍스트가 먼저다. `dump`의 JSON에 넣으면 한 명령의 출력이 여러 목적을 갖게 되고 읽기 어렵다(G80의 이유와 같다). `@when`도 같은 단계 규칙을 따르므로(S5) 빼면 순서가 궁금한 반응 하나가 도구 밖에 남는다.

**상태:** 확인
