# 엔진 개선 후보

Commander를 만들며 `uk.kesa.engine.core`(`17c71d1`)에서 만난 제약과 비용이다. 아직 어느 것도 엔진에 고치지 않았다.

## 측정 조건

- Ryzen 7 7800X3D, RTX 4070 Ti SUPER, Unity 6000.3.8f1 에디터(Mono), 플레이어 빌드는 재지 않음
- 별도 표기가 없으면 Release DLL + 에디터 Release 코드 최적화
- 판: 직진하고 튕기기만 하는 유닛, 초당 10틱, 모든 유닛이 매 틱 이동, `move="0.1"`
- 값은 200라운드의 중앙값(ms)이다. 같은 조건을 다시 재면 차이는 4% 안쪽이었다
- 다시 재기: Commander의 `Assets/Editor/CommanderMeasure.cs` (`-executeMethod CommanderMeasure.Run -releaseCodeOptimization`)

| 유닛 수 | 틱 | 틱 뒤 판 갱신 | 변화 없는 판 갱신(프레임마다) |
|---|---|---|---|
| 1000 | 13.95 | 11.27 | 0.78 |
| 2000 | 28.74 | 27.52 | 1.72 |
| 5000 | 76.98 | 108.56 | 6.60 |

참고로 DLL 빌드 설정의 영향은 작다. n=1000 틱이 에디터 Debug에서 Release DLL 43.22, Debug DLL 44.18이고, 에디터 Release에서 13.95, 14.37이다.

## 성능

### 1. 이동 재생 정리가 n²에 가깝다 (가장 먼저 볼 것)

`src/Kesa.Engine.Ui/LookStage.cs:156`의 `_playbacks.RemoveAll(p => !p.Live)`가 재생을 새로 시작하는 물체마다 불린다. 한 번에 N개가 움직이면 약 N개짜리 목록을 N번 훑는다.

| 유닛 수 | `RemoveAll`, 유닛당 µs (평균, 계측판) |
|---|---|
| 500 | 0.94 |
| 1000 | 1.81 |
| 2000 | 3.52 |
| 5000 | 9.52 |

- n=5000에서 `Stage.Apply` 59.7ms 가운데 47.6ms다.
- `move="0"`이면 n=5000 판 갱신이 108.56ms에서 61.60ms로 줄지만 보간이 없어진다.
- 후보: 물체마다 치우지 않고 한 번의 적용이 끝날 때 한 번 치운다. 377번 줄에 같은 정리가 있다. 156번 줄에서 그 시점에 치우는 이유는 확인하지 않았다.

### 2. 프레임마다 모든 물체를 확인한다

`LocalSession.WorldObjects`가 세계가 그대로여도 매 프레임 SortedSet을 만들고 모든 영수증을 확인한다. 유닛당 프레임마다 약 1.0~1.5µs다.

틱에 나눠 처리해도, 호스트 함수로 옮겨도 줄지 않는다. n=5000에서 틱 없는 프레임이 약 14ms라 60fps의 대부분을 쓴다. 이것이 유닛 수의 실질적인 벽이다.

### 3. 판 갱신의 나머지

n=1000 판 갱신의 구성(평균): `WorldObjects` 약 77%, `Stage.Apply` 약 23%. `WorldObjects` 안에서는 `where` 38%, 추적·영수증 26%, `ToBridge` 15%다.

`where`·`look` 칸에는 호스트 함수를 넣을 수 없어(안내서 3장) 유닛당 약 5µs가 스크립트에 남는다. 위치 칸을 읽어 바로 넘기는 흔한 경우를 스크립트 없이 선언할 길이 있으면 줄일 수 있다.

### 4. 호스트 접근의 할당 (재지 않음)

`HostAccess`의 Get/Set이 호출마다 `Use(() => ...)` 클로저를 만든다. 코드에서 읽은 내용이고 비용은 따로 재지 않았다. 호스트 함수로 옮긴 틱은 스크립트의 약 1/3이었다(n=1000 4.61ms).

## 기능

### 5. Unity 호스트에 호스트 함수 등록 경로가 없다

`hosts/unity/uk.kesa.engine.unity/Runtime/LoadedMods.cs:74-80`의 `LoadedMods.Load`가 `ContentLoader.Load`에 호스트 함수를 넘기지 않고 생성자는 private이다. 안내서 3장의 호스트 함수를 Unity 호스트에서 쓸 수 없다. 측정에서는 패키지 복사본에 매개변수를 하나 더해 돌렸고, 같은 시드의 스크립트 판과 값 108만 개가 일치했다.

Commander는 이웃 찾기와 이동 수학을 틱마다 한 번에 처리하는 배치 호스트 함수를 쓰려 한다. 이 경로가 그 선행 조건이다.

**해결:** `LoadedMods.Load`에 선택 매개변수 `HostFunctions? host = null`을 추가했다. 실제 호스트 함수를 등록해 돌려 보지는 않았다.

### 6. 틱 결과에 핸들러 오류와 경고가 실리지 않는다

`BridgeAdvance`에는 핸들러 실패와 `RUN021`이 없다. `LocalHost.Advance`가 이를 버리므로 Commander 호스트는 `World.Advance`를 직접 부른다. 경계 너머의 호스트는 이것을 볼 수 없다.

### 7. 게임 쪽 공간 종류가 설정 파서를 못 쓴다

`LookAttributes.FromText`, `UiSuggest.Hint`, `UiExprParser.ParseNumber`가 `internal`이다. 게임의 `SpaceKind`는 파싱을 직접 쓰고 "혹시 …?" 힌트를 못 낸다. 연속 공간 종류가 엔진의 표준이 되면 이 문제도 함께 사라진다(`10-updates-and-limits.md`의 "다른 공간 종류").

### 8. 내장 수학 함수가 적다

제곱근, 삼각함수, `**`가 없다. 연속 공간에서 이동 방향을 정규화하려면 축마다 잘라 움직이거나, 거절 표집이나 근사를 스크립트로 짜야 한다.

### 9. `engine check`가 그림과 공간 파일을 보지 않는다

`.space.xml`·`.look.xml`·`.view.xml`의 오류는 Unity에서 `mods.Looks.Problems`로만 나온다.

### 10. Unity 6.3과 이름이 겹친다

`UnityEngine.EntityId`와 `Kesa.Engine.Runtime.EntityId`가 부딪혀, 두 namespace를 함께 쓰는 파일은 별칭이나 전체 이름이 필요하다.

### 11. 읽기 한도 경고(`RUN021`)가 실제 시간과 멀다

경고 기준 10만 걸음은 에디터 Release에서 약 9ms다. 유닛 판단이 목표 이동과 벌어지기만으로 약 450~500걸음이라, 틱마다 200개를 판단하면 바로 닿는다. 시작할 때 한 번만 도는 판 깔기(약 29만 걸음)에도 같은 경고가 나서, Commander는 깔기를 여러 커맨드로 나누고 스크립트의 계산을 함수 없이 풀어 썼다. 핸들러의 경고 기준을 호스트나 모드가 정하는 길이 있으면 이런 꼴을 피할 수 있다.

### 12. 평가 걸음 수를 밖에서 읽을 수 없다

걸음 수는 `RUN021` 문구에만 나온다. 경고가 나지 않는 틱의 비용은 시간으로만 잴 수 있다.

### 13. 스크립트가 엔티티 id를 읽을 수 없다

위치가 같은 두 유닛을 결정적으로 가르는 데 id를 쓸 수 없어, Commander는 게임 난수를 쓴다.

### 14. 엔진 내장 배치 함수와 공간 색인 (구상)

스크립트는 엔티티를 하나씩 처리한다. 이웃 찾기처럼 많은 엔티티에 같은 계산을 하는 일을 엔진이 한 번에 처리하고 결과를 컴포넌트에 적어 주면, 스크립트는 판단만 하면 된다.

- 후보: 공간 색인과 `near` 같은 내장 함수.
- 값 구조체와 열 저장(G226)을 하더라도 스크립트가 하나씩 읽는 동안에는 이득이 작을 것으로 어림한다. 배치 함수를 먼저 두면 모드를 고치지 않고 내부만 나중에 열 저장으로 바꿀 수 있다.
- 호스트 함수가 스크립트 함수를 부를 수 없으므로(G217) 판단 자체는 배치 안에 넣을 수 없다.
- Commander에서 호스트 함수로 먼저 시험하고, 쓸모가 확인된 부분만 제안할 예정이다. 아직 효과를 재지 않았다.

### 15. 열 저장에 호스트용 묶음 읽기·쓰기를 함께 둔다 (요구)

값 구조체와 열 저장(G226)을 설계할 때 넣어 주었으면 하는 것이다. Commander는 이를 전제로 호스트 함수를 읽기, 계산, 쓰기 층으로 나눠 짤 계획이다.

- 묶음 읽기: 한 컴포넌트의 열을 통째로 읽는다. 호스트가 `Get(id, 멤버)`로 하나씩 읽으면 저장 구조의 이득이 대부분 사라진다.
- 묶음 쓰기: 여러 값을 한 번에 쓴다. 쓸 때마다 남기는 되감기 기록과 도장을 묶음 단위로 처리할 수 있어야 한다.
- Burst를 쓰려면 관리 객체 없이 struct 메모리를 넘길 수 있어야 한다. Burst 작업은 Unity 쪽에 두고, 코어(`netstandard2.1`)는 메모리만 내주면 된다.

어림(유닛 1000, 틱당 200판단, 인식과 이동만): 지금 저장소 + C# 배치 1~1.5ms, 열 저장 + C# 배치 0.1~0.3ms. 실측은 아니다. 열 저장은 조회와 호스트 경계에 듣고, 스크립트 실행 자체에는 효과가 작을 것으로 본다. G226과 엔진 `handoff.md`의 관련 부분에서 이 요구는 찾지 못했지만 계획 문서 전체를 확인하지는 않았다.
